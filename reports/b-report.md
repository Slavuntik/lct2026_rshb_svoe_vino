# Отчёт агента B — Backend API

Зона: `apps/api/`, `packages/llm/`. Контракты реализованы по v0.3 (`contracts/openapi.yaml`,
`contracts/schema.sql`, `contracts/llm-adapter.md`, `contracts/rag-interface.md`,
`contracts/events.md`). RAG — мок по `contracts/rag-interface.md` на 6 вымышленных винах для
основного прогона тестов; с волны 3 есть отдельный интеграционный smoke-тест на НАСТОЯЩЕМ
индексе агента A (`RAG_PROVIDER=real`, см. раздел про `test_integration_real_rag.py` ниже) —
«не жди его» по-прежнему соблюдено (мок остаётся дефолтом, интеграция — опциональная, скип по
умолчанию), но связка B+A теперь и реально проверена, не только теоретически готова.

Про Xcode-лицензию (упоминалось в предыдущей версии отчёта): починена оркестратором, `git`
снова работает без `DEVELOPER_DIR`-префикса — но pathspec на каждом коммите остаётся
обязательным правилом (гонка общего индекса, см. «Блокеры» ниже).

## Как поднять

Одноразовая установка (Python 3.12 через uv, зависимости из `uv.lock`):

```bash
cd packages/llm && ~/.local/bin/uv venv --python 3.12 && ~/.local/bin/uv pip install -e ".[dev]"
cd apps/api    && ~/.local/bin/uv venv --python 3.12 && ~/.local/bin/uv sync --frozen --extra dev
```

### Сервер — mock-LLM + mock-RAG (DoD: одна команда, без единого ключа)

```bash
cd apps/api
./.venv/bin/uvicorn app.main:app --reload
# GET  http://127.0.0.1:8000/v1/healthz      -> {"status":"ok","index_version":"mock-fixtures-0.2"}
# GET  http://127.0.0.1:8000/docs            -> Swagger UI
# GET  http://127.0.0.1:8000/openapi.json
```

Ничего дополнительно не требуется: `LLM_PROVIDER` и `RAG_PROVIDER` по умолчанию `mock`,
`DATABASE_URL` по умолчанию `sqlite:///./svoy_somelye.db` (создаётся сама). Проверено не
только через `TestClient`, но и вживую — `uvicorn` на реальном сокете, `curl` на `/v1/healthz`,
`/openapi.json` и `POST /v1/auth/guest` отвечали корректно.

Переключение на реальные провайдеры — только через env, без правок кода:

```bash
LLM_PROVIDER=anthropic LLM_API_KEY=... LLM_MODEL=claude-3-5-haiku-latest ./.venv/bin/uvicorn app.main:app
LLM_PROVIDER=deepseek  LLM_API_KEY=... LLM_BASE_URL=... LLM_MODEL=deepseek-chat ./.venv/bin/uvicorn app.main:app
LLM_PROVIDER=gigachat  GIGACHAT_AUTH_KEY=... ./.venv/bin/uvicorn app.main:app
DATABASE_URL=postgresql+psycopg://user:pass@host:5432/db ./.venv/bin/uvicorn app.main:app

# RAG_PROVIDER=real — теперь ДЕЙСТВИТЕЛЬНО работает против настоящего индекса
# агента A (проверено, см. раздел про интеграционный тест), не просто деградирует:
cd apps/api && ~/.local/bin/uv sync --extra dev --extra integration   # ставит packages/rag
RAG_PROVIDER=real RAG_MODE=embedded ./.venv/bin/uvicorn app.main:app
```

### Тесты

```bash
cd packages/llm && ./.venv/bin/python -m pytest -q     # 21 passed
cd apps/api     && ./.venv/bin/python -m pytest -q     # 114 passed, 3 skipped (integration)

# Интеграционный smoke-тест на реальном индексе агента A (не по умолчанию):
cd apps/api && ~/.local/bin/uv sync --extra dev --extra integration
RUN_RAG_INTEGRATION=1 ./.venv/bin/python -m pytest -q tests/test_integration_real_rag.py   # 3 passed
```

Основные прогоны зелёные, без сети (реальные LLM-драйверы тестируются офлайн через
`httpx.MockTransport`, RAG — мок на фикстурах). `sqlite:///:memory:` + `StaticPool` на процесс
теста — полная изоляция между тестами, без файлов на диске. Интеграционный прогон — единственное
место, где действительно грузятся локальные ML-модели (embedder + reranker, из уже тёплого
`packages/rag/.fastembed_cache/`, без повторного скачивания) — 3/3 за ~5 секунд.

### Как именно проверен «email не утекает в промпт»

`tests/test_chat.py::test_email_never_reaches_llm_prompt` — регистрирует пользователя с
характерным email, даёт ему вкусовой профиль (лайк вина), подменяет `app.state.llm` на
`RecordingLLM` (обёртка вокруг настоящего mock-драйвера, запоминающая все `messages`), дёргает
`/chat` и проверяет, что ни email, ни `user_id`, ни сам домен `@example.com` не встречаются ни в
одном сообщении, реально ушедшем в LLM. Плюс структурная гарантия: `build_messages()` в
`app/chat/prompt.py` физически не принимает email/id как параметры (тест
`test_build_messages_signature_has_no_identity_parameters` проверяет сигнатуру) — утечка
потребовала бы сначала осознанно изменить сигнатуру функции, а не просто дописать одну строку.

### Как проверен refusal на пустой выдаче

Два теста: юнит `test_stream_chat_events_refuses_on_empty_retrieval_without_calling_llm` —
`stream_chat_events()` на стабе `Retriever.search() -> []` напрямую (и проверка, что LLM в этом
случае вообще не вызывается); end-to-end `test_chat_endpoint_refuses_end_to_end_on_gibberish` —
настоящий HTTP-запрос с бессмысленным текстом даёт `{"type":"refusal","reason":...}` без единой
`citation`. Потребовалось добавить порог `_SEARCH_MIN_SCORE=0.08` в `MockRetriever.search()`
(иначе fuzzy-скоринг всегда возвращал «наименее плохие» top-k даже на полную бессмыслицу) —
это реальное улучшение мока, не костыль теста, задокументировано в `app/rag/mock.py`.

### v0.3: форма Candidate.meta зафиксирована буквально

Раньше `MockRetriever` использовал ДВЕ разные формы `meta` для `kind=wine`: полную
(`{"source","derived"}`) только в `get_by_id`, и усечённую плоскую (`name`/`winery_name`/...) во
всех остальных методах (`search`/`resolve_label`/`similar`/`analog_for_style`/
`candidates_for_taste`). Контракт v0.3 (ревью 02, блокер 1) зафиксировал ОДНУ форму на все
методы — `{"source": {...}, "derived": {...}}` целиком для вина, `{"article_id","title",
"heading","rubric"}` для чанка знаний, идентично независимой реализации агента A
(`packages/rag/rag/meta.py::public_meta`). `app/rag/mock.py::_wine_to_candidate` теперь один на
все случаи; роутеры (`scan.py`, `analogs.py`, `taste.py`) переведены с `meta.get("name")` на
`meta["source"].get("name")`. `tests/test_rag_mock.py` проверяет форму по каждому методу отдельно
— значимая находка ревью: без единой формы клиент API (сам B) не мог одинаково читать карточки
из разных ручек, а после смены поставщика (mock → real) сломался бы тихо, без исключения (просто
`.get("name")` на новом плоском/вложенном месте начал бы возвращать `None`).

### v0.3: настоящий SSE-стриминг — что изменилось и как это тестируется

До этой волны `run_chat()` делал `list(llm.chat_stream(messages))` ДО того, как SSE-генератор
роутера начинал отдавать хоть один `token`. Работало корректно по протоколу (клиент получал те
же события в том же порядке), но нарушало реальную задержку до первого байта — на живом LLM это
означало бы 5-10 секунд тишины на сцене демо. Контракт v0.3 прямо запрещает буферизацию.

Исправление: `run_chat()` заменён на `stream_chat_events()` — генератор, который прокидывает
каждый чанк `llm.chat_stream()` наружу немедленно, без промежуточного списка. Честная цена:
старый защитный приём «ответ без единого валидного `[n]` — тихо превратить в refusal» для уже
показанных токенов больше невозможен (нельзя отозвать то, что клиент уже отрисовал) — теперь это
доходит до `done` как обычный ответ, возможно вовсе без `citation`. Твёрдый барьер остаётся ровно
там, где его ещё можно применить: пустая выдача ретривера (до первого обращения к LLM) и системный
промпт. Задокументировано подробно в докстринге `app/chat/service.py`.

Тестирование этого свойства оказалось нетривиальным: `TestClient.stream()` в этой среде не
отражает реальную потоковую доставку по сети — диагностическим скриптом на голом
`StreamingResponse` с `time.sleep()` между `yield` подтверждено, что ВСЕ серверные `yield`
успевают отработать до того, как клиент получит первую строку, независимо от кода. Тайминг- и
even order-тесты через HTTP оказались бы теориями о транспорте теста, а не о моём коде. Решение:
`tests/test_chat.py::test_stream_chat_events_pulls_llm_chunks_one_at_a_time_not_eagerly` —
детерминированное, независимое от транспорта доказательство на уровне генератора (после первого
`next()` у LLM запрошен ровно один чанк, не пять) + отдельный HTTP-тест на корректность порядка
после сборки (`test_chat_sse_over_http_delivers_tokens_in_llm_yield_order`). Разница с тем, что
просил оркестратор («по таймингу или порядку событий») — по существу дела, не по букве: тайминг
через этот конкретный TestClient недостижим, а вот доказательство отсутствия
eager-материализации — да, и оно строже теста «дошло не позже X мс» (не зависит от машины/нагрузки).

### v0.3.2: непривязанные citation-события, когда LLM не расставила [n]

Малая доработка поверх v0.3 (контракт, коммит `693fb71`, по моему предложению №8): honest-цена
настоящего стриминга была в том, что ответ без единого `[n]` в тексте уходил клиенту вовсе без
`citation` — контракт признал это законным следствием, но потребовал восстановить гарантию
«каждый ответ несёт источники» другим способом. Решение: `stream_chat_events()` теперь при
отсутствии валидных `[n]` в `full_text` подставляет `citations` по ВСЕМ кандидатам, реально
попавшим в промпт, нумеруя их `n=1..len(candidates)` — без привязки к каким-либо маркерам в
тексте (контракт явно это разрешает: «нумерация n продолжается, соответствия маркерам в тексте
нет»). Клиент рендерит такой набор как блок «Источники» под ответом. Мёртвая с прошлой волны
константа `UNGROUNDED_ANSWER_REASON` удалена (не использовалась нигде после перехода на
`stream_chat_events()`, а с этой правкой и подавно не нужна — путь «ответ без источников» большe
не существует в принципе). Один тест по просьбе оркестратора:
`tests/test_chat.py::test_chat_falls_back_to_prompt_citations_when_llm_omits_markers` — LLM-стаб
без единого `[n]`, проверяет, что `citation`-события всё равно приходят до `done`, нумерация без
дыр, и что их количество совпадает с `trace.candidate_ids` (персистентность подтверждает то же,
что ушло в SSE).

### v0.3.3: collections не форсируется в /chat — единственный кодовый блокер заморозки (ревью 03)

Живым зондом ревьюера через реальный API обнаружено: сцена 2 демо цитировала 8/8 статей знаний
вместо 8/8 вин на wine-pick вопросы. Причина — `app/chat/service.py` звал
`retriever.search(..., collections=("wines", "knowledge"), ...)` явным tuple, что молча обходило
intent-роутинг настоящего ретривера агента A (pairing-приоритезация wines над knowledge,
`packages/rag` коммит `ee94ef3`). Контракт v0.3.3 закрепил `collections=None` как дефолт и норму
(явный tuple остаётся легальным, но только для принудительных спецвызовов — не для `/chat`).

Исправлено: `retriever.search(message, filters=filters, top_k=top_k)` — `collections` не
передаётся вовсе. `Retriever` (Protocol) и `MockRetriever.search()` приведены к сигнатуре
`collections: tuple[str, ...] | None = None`; мок при `None` по-прежнему ищет везде (у него нет
собственного intent-роутинга — не его задача реплицировать эвристики A на 6 фикстурах).

Проверено НАПРЯМУЮ на реальном индексе (не только юнит-тестом на моке) — сравнение одного и того
же запроса «Посоветуй красное вино к стейку» через настоящий `packages/rag.get_retriever()`:
- `search(q, top_k=8)` (новое поведение, `collections=None`) → `['wine']*8` — 8/8 вин;
- `search(q, collections=("wines","knowledge"), top_k=8)` (старое поведение агента B) →
  `['chunk']*8` — 8/8 статей, ТОЧНОЕ воспроизведение бага живого зонда.

Тесты: `tests/test_chat.py::test_stream_chat_events_calls_search_without_forcing_collections` —
шпион на аргументах `search()`, проверяет отсутствие ключа `collections` в вызове из
`stream_chat_events()`; `tests/test_rag_mock.py::test_search_default_collections_is_none_and_behaves_like_searching_everything`
— сигнатура и эквивалентность `None`/без аргумента/форсированного tuple на моке.

Второй пункт того же ревью (риск-митигация, не сам блокер): в `SYSTEM_PROMPT`
(`app/chat/prompt.py`) добавлена строка — если вопрос вообще не о вине/еде, модель обязана
вежливо отказаться, а не подгонять ответ под нерелевантные выдержки, которые всё же прошли порог
отсечки ретривера. Второй барьер поверх самой отсечки, не замена ей. Тест:
`test_system_prompt_refuses_off_topic_questions_not_just_insufficient_excerpts` (строковая
гарантия — не поведенческая, реальную дисциплину модели юнит-тестом не проверить, что и есть
смысл контракта иметь второй барьер, а не полагаться на один).

114 тестов зелёных (было 111), 3 skipped (integration, без изменений; прогнаны и они — 3/3 на
реальном индексе). Волна 3 (ревью 02 + ревью 03/prefreeze) для зоны B закрыта.

### v0.3: /consents — enum скоупов

`ConsentPostRequest.scopes` остался `list[str]` в pydantic (не `list[Literal[...]]`) сознательно:
контракт требует именно `400 validation_error` на неизвестном скоупе, а pydantic `Literal` дал бы
generic `422` через уже существующий `RequestValidationError`-обработчик. Валидация — вручную в
`routers/consents.py` по словарю `CONSENT_SCOPES` (тот же `get_args(ConsentScope)`, что использует
`/auth/register`); при хоть одном неизвестном скоупе в ledger не попадает НИЧЕГО из этого запроса
(не частичная запись валидных). `/auth/register`, для сравнения, как и раньше полагается на
pydantic `Literal` (контракт для него отдельного `400` не документирует) — асимметрия осознанная,
не оплошность, объяснена в коде.

### Гость с NULL-identity: апгрейд и атрибуция (v0.2.1)

`users.is_guest` — единственный источник истины про «кто это»; JWT несёт только `sub`, поэтому
апгрейд строки (гость → регистрация) применяется мгновенно ко всем уже выданным токенам этой
строки, без переиздания. `POST /auth/register` с гостевым `Authorization: Bearer` в заголовке
дозаполняет ТУ ЖЕ строку (`email`/`password_hash`/`birth_date`, `is_guest=false`,
`age_confirmed_at` сохраняет момент ПЕРВОГО подтверждения 18+, не перезаписывается) — id не
меняется, поэтому `scans`/`chat_messages` этого id остаются на месте. Без токена, с мусорным
токеном или с токеном уже полноценного пользователя — обычная новая строка, чужая не трогается
(последние два случая контрактом не описаны буквально, см. допущения ниже).

Раньше (v0.2) гость был просто голым uuid без строки в `users`, и FK у
`scans`/`chat_messages`/`events`/`feedback` приходилось обходить, записывая туда `NULL` вместо
гостевого id (`security.fk_user_id`, теперь удалена) — иначе `PRAGMA foreign_keys=ON` уронил бы
вставку. Теперь эта проблема не нужна: гость атрибутируется как обычный `user_id`.
`tests/test_guest_attribution.py` доказывает это напрямую (реальный `user_id` в каждой из четырёх
таблиц) и отдельно доказывает, что сама PRAGMA не декоративна: вставка `Scan`/`ChatMessage` с
заведомо несуществующим `user_id` через ORM в обход роутеров ловит `IntegrityError` — без этой
проверки расхождение с Postgres всплыло бы не на dev-машине, а на демо.

## Ключевые допущения (не специфицировано контрактом буквально)

- **Кто аутентифицирован на каких путях.** `openapi.yaml` не содержит `securitySchemes`/`security`
  вообще. Решение: `/healthz`, `/auth/*`, `/waitlist`, `/events` — без токена (события ДО
  аутентификации вроде `age_gate_failed` иначе невозможны); `/scan/resolve`, `/scan/ocr`,
  `/wines/{id}`, `/chat`, `/chat/feedback`, `/analogs`, `/consents` — нужен принципал (гость или
  юзер); `/taste/*` — принципал + активный scope `profiling` (гость отсекается всегда, до похода
  в ledger); `/profile/data-export`, `DELETE /profile` — только зарегистрированный. Мотив жёстко
  требовать принципала на scan/chat/wines/analogs: иначе 18+ гейт тривиально обходится прямым
  вызовом API мимо `/auth/guest|register` — см. докстринг `app/security.py`.
- **Гость и таблицы с FK на `users`** — решено в v0.2.1 (было допущением/предложением в первой
  версии этого отчёта): гость теперь полноценная строка `users` (NULL-identity), FK у
  `scans`/`chat_messages`/`events`/`feedback` работают на него без обходов. `consent_ledger`
  по-прежнему намеренно без FK — но уже не из-за гостя, а потому что обязан пережить `DELETE
  /profile` (см. `apps/api/app/models.py::ConsentLedger`).
- **`POST /auth/register` с токеном НЕ гостя** (уже полноценный юзер, или мусорный/просроченный
  токен) — контракт описывает только два случая («с гостевым Bearer» / «без токена»). Решение:
  любой токен, который не резолвится в живую гостевую строку, молча игнорируется — обычная новая
  регистрация, чужая строка не трогается и не возвращается ошибка о «уже вошли». Так эндпоинт
  остаётся полностью публичным (не требует валидного заголовка вообще).
- **Ответ `/consents` GET** — контракт не даёт схему («200: ok»). Отдаю список последних записей
  по каждому scope: `[{scope, consent_version, granted, at}]`.
- **`/profile/data-export`** — контракт не даёт схему («полный дамп»). Отдаю
  `{user, consents, swipes, taste_profile, scans, chat_messages, events, feedback}`;
  `password_hash` из `user` сознательно исключён (это секрет аутентификации, не персональные
  данные в смысле права на выгрузку).
- **`answer_id` в `/chat/feedback`** — контракт типизирует как `string`; это стрингифицированный
  `chat_messages.id` (int). Нечисловой/несуществующий `answer_id` → `404 not_found`, а не `422`.
- **Вектор вкусового паспорта** — ни один контракт не описывает алгоритм. Эвристика уровня MVP:
  среднее сенсорных векторов лайкнутых вин, топ-3 самых частых `reference_style_matches`; без
  лайков — нейтральный вектор `0.5`. `dislike`/`skip` не двигают вектор, но входят в
  `swipes_count`.
- **Регистрация** дополнительно требует `"base" in consent_scopes` (иначе `400 validation_error`)
  и уникальность email (иначе `400 validation_error`, кода `conflict` в словаре нет). Оба —
  легальные допущения по духу consent-ledger дизайна, не по букве контракта.
- **`/scan/ocr` → всегда `501 not_implemented`** — было решением ревью 01/заметкой
  оркестратора, с v0.3 формально в контракте (`openapi.yaml` больше не обещает 200/422). Форма
  запроса (`multipart`, `image`+`explicit_consent`) в контракте осталась для формы
  OpenAPI-схемы, тело не разбирается.
- **Сервер не пишет `events` сам за другие эндпоинты** — единственная точка записи в таблицу
  `events` это `POST /events`, вызываемый клиентом. Домены (`scans`, `chat_messages`, `feedback`,
  `swipes`) пишутся эндпоинтами напрямую, это разные таблицы с разным назначением. Если
  продукту важна аналитическая полнота при ненадёжном клиенте — стоит явно решить, каким
  событиям (`chat_answer_done`, `scan_resolved`) быть server-authoritative; см. предложение ниже.
- **SSE стримится по-настоящему с v0.3** (было буферизацией полного ответа до этой волны, см.
  раздел выше) — `token`-события уходят по мере генерации LLM, без промежуточного списка. Изначальная
  цена (v0.3): «ответ без единого валидного `[n]`» нельзя было тихо подменить на `refusal`, если
  хотя бы один токен уже ушёл клиенту. Закрыто в v0.3.2: в этом случае сервер перед `done`
  подставляет citation-события по всем выдержкам промпта (непривязанные к тексту, контракт это
  явно разрешает) — гарантия «каждый ответ несёт источники» снова жёсткая. См. докстринг
  `app/chat/service.py` и предложение №8 ниже.

## Расхождения SQLite vs `contracts/schema.sql` (Postgres)

Подробно в докстринге `apps/api/app/models.py`; коротко: `uuid`→`String(36)` (id генерирует
приложение), `bigserial`→`Integer autoincrement`, `jsonb`→`JSON` (сериализуется как TEXT),
`timestamptz`→naive `DateTime` (везде UTC без tzinfo), `ON DELETE CASCADE/SET NULL` работает
только при `PRAGMA foreign_keys=ON` (включено вручную на каждое соединение — **этот пункт был
явно проверен по запросу оркестратора**: `tests/test_guest_attribution.py` доказывает и что
constraint активен в dev, и что без него он был бы молча проигнорирован — см. раздел выше),
составные индексы без `DESC` (портируемости ради, функционально не важно на объёме MVP),
CHECK-констрейнт `users` (`is_guest OR identity NOT NULL`) воспроизведён как есть — SQLite его
поддерживает нативно. В проде (Postgres, `DATABASE_URL=postgresql+psycopg://...`) код тот же —
SQLAlchemy сам работает с настоящими типами; синхронный `create_engine` теперь имеет рабочий
драйвер (`psycopg[binary]`, добавлено по замечанию агента E, см. ниже).

   «Источники»). Гарантия «каждый ответ несёт источники» снова жёсткая, а не мягкая: теперь она
   не зависит от дисциплины модели вообще — обеспечена на уровне API по построению. Мёртвая
   константа `UNGROUNDED_ANSWER_REASON` (осталась от дореформенного `run_chat()`, нигде не
   использовалась) удалена. Тест:
   `test_chat_falls_back_to_prompt_citations_when_llm_omits_markers` — LLM-стаб без единого `[n]`
   в ответе, проверяет, что citation-события всё равно приходят до `done`, нумерация `n` идёт без
   дыр 1..N, и что число цитат совпадает с числом выдержек в `trace.candidate_ids` (не часть, не
   с потолка).

## Кейс: /scan/photo (contracts/image-scan.md v0.4)

Проект развёрнут под кейс ЛЦТ 2026 (`case.md`) — сканер вина по фото. Реализовано в зоне
`apps/api`/`packages/llm` без изменений (CV-ядро — зона агента G, `packages/cv`, на момент
написания пуст: датасет кейса ещё не приехал). Как и с RAG в первой волне — работаю через мок
`ImageIndex`/`LabelVerifier` по сигнатурам контракта, не дожидаясь готовности пакета.

### Что сделано

- **`app/cv/interface.py`** — `Match`, `ImageIndex` (Protocol), `LabelVerifier` (Protocol,
  сигнатура из задачи этой волны — контракт описывает роль верификатора в пайплайне, но не даёт
  класса), `get_image_index()` — фабрика `mock|real` symmetric к `rag.get_retriever()` (изначально
  заглушка на мок-провайдер; на что она выросла, когда агент G сдал пакет — см. отдельный
  подраздел «Финальный шов кейс-волны» ниже). **Не в `packages/llm`** — прямое указание
  оркестратора, лежит рядом с остальным зеркалом CV-контракта.
- **`app/cv/mock.py`** — `MockImageIndex`/`MockLabelVerifier` на фикстурах (`app/cv/fixtures.py`):
  6 "уверенных" слагов — те же слаги, что в `app/rag/fixtures.py`, поэтому `card` реально
  гидратируется через RAG-мок (одна вымышленная витрина на оба пути, текстовый и визуальный); + 1
  синтетическая near-dup группа (`mock-tainoe-vino-2022`/`-2023`, специально НЕ в RAG — пайплайн
  обязан красиво деградировать в `card=None`, если CV нашёл позицию, которой ещё нет в каталожном
  слое, — реалистичный сценарий рассинхрона индексов). Реальных фото нет — "фото" в тестах это
  bytes по условной конвенции `MOCKPHOTO:<slug>` (и вариантами `weak:`/`near-dup`/`unknown`),
  задокументировано в докстринге модуля; любые другие байты (настоящее фото, если кто-то уже
  шлёт до готовности G) не роняют пайплайн — детерминированная деградация по хэшу.
- **`app/cv/service.py::run_photo_scan()`** — весь пайплайн: `ImageIndex.search()` -> near-dup
  routing по `gap` -> `LabelVerifier.verify()` -> `card`/`similar`/`analogs` через RAG-ретривер ->
  `timing_ms`, измеренный `time.monotonic()` вокруг всего вызова (реально, не константа — см.
  тест ниже). Возвращает `PhotoScanResult` с ОБОИМИ срезами сразу: `best_guess_slug` (всегда
  лучший доступный — для flat) и `slug` (только если уверенно — для rich); роутер строит из
  одного результата оба формата ответа без повторного вызова пайплайна.
- **`POST /v1/scan/photo`** (`routers/scan.py`) — `?flat=1` даёт ровно `{"slug": "..."}`
  (`ScanPhotoFlatResponse`), без параметра — `ScanPhotoRichResponse` (`slug, card, confidence,
  ocr_verified, timing_ms, not_in_catalog, similar, analogs`). flat-ветка обёрнута так, что
  НИЧЕГО не даёт ей ответить ошибкой (пустой/битый/переполненный файл, сбой записи в БД) —
  всегда `{"slug": ""}` в худшем случае, что для скрипта оценки эквивалентно честному промаху, но
  не ломает его цикл `POST -> распарсить JSON -> сравнить`. rich-ветка отвечает честными
  `400 validation_error` на тех же случаях — там ошибка полезна UI.
- **`GET /v1/metrics/scan`** (`routers/metrics.py`) — `app/cv/eval_report.py::read_eval_report()`
  читает JSON по `CV_EVAL_REPORT_PATH` (дефолт `../../packages/cv/eval/report.json`, файла пока
  нет — `packages/cv/eval` не существует); используется И здесь, И в `confidence` rich-режима —
  один источник истины. Файла нет -> все F1/match_rate/eval_set/measured_at `null`,
  `confidence.eval_missing=true` (по прямому заданию оркестратора — честное поле вместо
  притворного нулевого F1), `index_version` — от живого `ImageIndex.index_version` как
  единственное, что реально известно без eval-прогона.
- **Оба эндпоинта БЕЗ обязательной авторизации** (`get_current_principal_optional`) — сознательное
  отступление от моего собственного правила "scan/chat/wines/analogs требуют принципала"
  (`app/security.py`, мотивированного 18+ гейтом): скрипт оценки кейса шлёт фото без токена
  (`case.md`: "bash шлёт фото по одному"), и жёсткая авторизация здесь сломала бы контрольный
  прогон на звонке. Токен, если есть (гость/юзер приложения), просто атрибутирует запись в
  `scans` — легальный компромисс, задокументирован в докстринге `routers/scan.py`.
- **Текстовый `/scan/resolve` и `/scan/ocr` (501) не тронуты** — по прямому указанию, проверено
  тестами (весь прежний набор остался зелёным без единой правки в их логике).

### Ключевые допущения

- **Near-dup routing по `gap`** — контракт не даёт явного порога, только "если топ-позиции из
  одной near-dup-группы (группировку отдаёт `search()` через `gap`/`view`)". Реализовано как:
  `top.gap < CV_NEAR_DUP_GAP_THRESHOLD` (дефолт `0.05`, env) -> собрать РАЗНЫЕ слаги среди топ-K и
  позвать `verifier.verify()`. `view` пока информационный (не участвует в решении) — контракт не
  даёт однозначного правила его использования, помечено как открытый вопрос на калибровку с
  агентом G. `CV_CONFIDENT_SCORE_THRESHOLD` (дефолт `0.55`) — тоже плейсхолдер, `case.md` даёт
  только качественное "отрыв 1-го от 2-го ощутимый и стабильный", не число. Оба порога —
  **пересчитать по приезду датасета кейса** вместе с реальной калибровкой ImageIndex (как уже
  сделал агент A для текстового refusal-порога).
- **`similar`/`analogs` в not_in_catalog** — `similar` строю из НИЗКОуверенных ANN-совпадений
  (визуально ближайшее, даже не будучи confident — честно показать "может, это?"), `analogs` —
  переиспользую уже существующий `retriever.analog_for_style()` (тот же механизм, что у
  текстового `/analogs`) по стилю лучшего слабого совпадения. Кейс явно ценит это высоко
  ("похожие/аналоги из других виноделен... оценивается особенно высоко", вес 20/100 в критериях)
  — решил не изобретать отдельный CV-механизм для аналогов, а протянуть готовый RAG-путь.
- **Формат `card`** — `{wine_id, source, derived, source_url}`, та же форма, что
  `GET /wines/{wine_id}`; `similar`/`analogs` — переиспользуют `AnalogsWineItem` из `schemas.py`
  (`wine_id, name, winery_name, region_name`) вместо новой модели.
- **`test_openapi_contract.py`** доработан читать ОБА контракта: `/scan/photo` и `/metrics/scan`
  описаны только в `contracts/image-scan.md` (прозой, `` `METHOD /v1/path` `` в backticks — не
  OpenAPI YAML), не влиты в `contracts/openapi.yaml`. Тест теперь парсит оба файла и мержит пути
  — иначе регресс-тест "нет путей мимо контракта" не сходился бы намеренно, что хуже, чем его
  доработать.

### Финальный шов кейс-волны: `IMAGE_PROVIDER=real` (packages/cv, агент G, коммит `4fdb445`)

Агент G сдала `packages/cv`: `ImageIndex` по контракту (`qdrant_embedded`, SigLIP2
`google/siglip2-base-patch16-224` через `transformers`/`torch`, self-match 93.9%, search p95
30.8 мс — см. `reports/g-report.md`). Задача волны — тот же паттерн, что RAG в волне 3: фабрика
`mock|real`, сверка своего Protocol с реальным кодом посимвольно, живой интеграционный smoke. Урок
ревью 02 «оба берега хороши, пока швы не примерены» подтвердился ещё раз, на этот раз дважды.

**Переименование `CV_PROVIDER` → `IMAGE_PROVIDER`.** Симметрично `RAG_PROVIDER`/`LLM_PROVIDER` —
по прямому указанию оркестратора при подключении реального пакета (`app/config.py::image_provider`,
везде далее по коду/тестам/докстрингам; старое имя `CV_PROVIDER` в этом отчёте ниже — тоже
поправлено, было упомянуто дважды в устаревшем виде).

**`get_image_index()` (`app/cv/factory.py`)** — на `IMAGE_PROVIDER=real` импортирует `cv.index`
(пакет ставится в venv api как editable path-зависимость: `[tool.uv.sources] cv = {path =
"../../packages/cv", editable = true}`, опциональная группа `integration` в `pyproject.toml` —
тяжёлые ML-зависимости не в основных, `uv sync --extra dev --extra integration` подтягивает 18
пакетов: `torch==2.14.0`, `transformers==5.17.0`, `opencv-python-headless`, `qdrant-client`, ...).
В реальном пакете нет фабричной функции (проверено эмпирически, пробуется на будущее — `try:
_cv_index.get_image_index()`) — берётся класс напрямую, `cv.index.ImageIndex()`, без обязательных
конструкторных аргументов.

**Сверка `Match` посимвольно** (`app/cv/interface.py` против `packages/cv/cv/index.py`): поля и
типы (`slug: str, score: float, gap: float | None, view: str`) совпали буквально. Расхождение —
только конвенция значения `view`: мой мок и черновая версия контракта использовали русское слово
`"реальный"`, реальный пакет (и исправленный текст v0.4.2) — ASCII `"real"`. Поправлено в
`app/cv/mock.py` (3 вхождения) и одном тесте (`test_cv_mock.py`); `packages/cv` не трогал.

**v0.4.1 (пробел нашёл агент C): `card` без `similar`.** Rich-режим требует `card` РОВНО тело
`GET /wines/{id}` (`{wine_id, source, derived, source_url, similar}`), а мой прежний
`_hydrate_card()` собирал усечённую форму без `similar`. Исправлено выносом общего билдера
**`app/rag/cards.py::build_wine_card()`**, которым теперь пользуются И `routers/wines.py`, И
`app/cv/service.py` — одна форма карточки на оба эндпоинта, а не две согласуемые вручную. Добавлен
тест буквального равенства JSON `card` из `/scan/photo` и ответа `GET /wines/{id}` для одного и
того же `wine_id` (`test_scan_photo.py::test_rich_mode_confident_match_full_schema`).

**Находка №1 — калибровка порога на реальных данных.** `CV_NEAR_DUP_GAP_THRESHOLD` был угадан по
шкале мок-скоров как `0.05`. На реальном индексе настоящая near-dup пара датасета
(`aligote-barrel-2024`/`aligote-barrel-2025`, одна этикетка, два урожая, см.
`packages/cv/cv/selfcheck.py::NEAR_DUP_GROUPS`) дала `gap=0.245` — порог `0.05` **никогда не
сработал бы** на реальных данных, near-dup routing тихо не вызывался бы вовсе. Пересчитан на `0.3`
(`app/config.py`) — всё ещё плейсхолдер (один пример — не калибровка на голд-сете), но хотя бы не
заведомо мёртвый.

**Находка №2 — семантика `gap`: настоящий баг в моём пайплайне, не в контракте.** Контракт
(`contracts/image-scan.md` v0.4.2) определяет `gap` буквально: «отрыв от следующего **НЕ-той-же-
группы** кандидата» — то есть `cv/index.py` сам пропускает соседей top1 из ЕГО ЖЕ near-dup группы
при вычислении gap. Мой `run_photo_scan()` этого не учитывал: войдя в near-dup ветку, он слал
верификатору **весь** срез `matches[:top_k]` целиком, а не только позиции той же группы, что и
top1. На полноразмерном каталоге это осталось бы незамеченным (top-K и так почти всегда = сама
группа плюс пара похожих), но интеграционный тест на намеренно КРОШЕЧНОМ 5-позиционном тестовом
индексе поймал это буквально: `search(..., top_k=5)` на 5-позиционном индексе отдаёт ВСЕ 5
позиций, из них реально в группе с top1 — только 2, остальные 3 — случайные чужие вина с более
низким score; `LabelVerifier.verify()` вызывался с 5 кандидатами вместо 2. Исправлено
(`app/cv/service.py`): кандидаты на OCR — не голый срез, а `[m.slug for m in matches if m.score >
top.score - top.gap]` — по построению контрактного определения gap это ровно позиции той же
группы, что и top1 (граничная НЕ-той-же-группы позиция и всё, что ниже неё по score, — исключены).
Мок (`app/cv/mock.py`) тоже перестроен: раньше он отдавал ровно 2 матча для near-dup сценария и
совмещал в одном числе два разных смысла (зазор между двумя членами группы и зазор до границы
группы) — теперь отдаёт 2 члена группы + одну «чужую» позицию ровно на границе, честно моделируя
то же самое, что нашлось на реальных данных
(`test_cv_mock.py::test_search_near_dup_returns_group_plus_boundary_match_with_small_gap`).

**Находка №3 — нестабильность ANN top-1 внутри near-dup пары (не баг, а причина, зачем вообще
нужен OCR).** Первая версия интеграционного near-dup теста жёстко ждала
`slug=="aligote-barrel-2024"` (топ-1 ANN на фото «2024» — якобы всегда сам запрошенный слаг).
Живой прогон это опроверг: на одной сборке индекса топ-1 оказался `aligote-barrel-2025` (сосед по
группе), на другой сборке (для цифр этого отчёта) — снова `aligote-barrel-2024`. Согласуется с
собственной цифрой агента G: self-match 93.9%, не 100% — ранжирование ANN ВНУТРИ пары
недостоверно само по себе в паре процентов случаев, и это ровно то, для чего нужен
OCR-верификатор. Тест переписан на поведенческую проверку (`_RecordingVerifier`-шпион вместо
`MockLabelVerifier`, который настоящих слагов датасета не узнаёт): проверяется не то, какой из
пары «победил» в ANN, а что `verify()` реально вызван с обоими членами группы и что итоговый
`slug` — РОВНО её ответ, а не молчаливый top-1.

**Транзитная сетевая проблема (не баг кода).** Один прогон поймал `ECONNRESET` от HF Hub
посреди ревалидации уже полностью валидного локального кэша SigLIP2 (веса на диске были целы —
`~/.cache/huggingface`, `model.safetensors` ~1.5 ГБ на месте, все ссылки снапшота целые). Смоуку
сеть до HF Hub не нужна вообще, если модель уже скачана — форсирован офлайн-режим
(`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` через `os.environ.setdefault(...)` в начале
`test_integration_real_cv.py`), что заодно делает тест воспроизводимее — не зависит от состояния
сети вообще, если кэш тёплый.

- `IMAGE_PROVIDER=real` теперь ПРОВЕРЕН вживую (в предыдущей версии этого отчёта это было открытым

  выше) — но это всё ещё НЕ калибровка на голд-сете, только один наблюдаемый пример (`gap=0.245`/

  качественное «отрыв ощутимый и стабильный»).
