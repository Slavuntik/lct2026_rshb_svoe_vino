# qa-auto: репетиция ночи проверки на Mac — hack-v15, максимальный конфиг (22.09)

**Вердикт: конфиг готов к ночи проверки.** `PORT=8081 infra/local-check/run-check-server.sh` (8081 свободен;
8080/8091/8092/8093 — чужие/служебные, не трогал, PID идентичны до/после). vlm_both+CROPS=8 — дефолты скрипта.

## Чек-лист ночи проверки
1. **Запуск**: `PORT=8081 infra/local-check/run-check-server.sh` (8081 занят → следующий свободный;
   8080/8091/8092/8093 НЕ трогать). Ждать `Application startup complete` и `GET /v1/healthz`→`warm:true`.
2. **Прогрев**: встроенный, в логе `cv_fusion warm-up: текстовая ветка … 3.33с` + `retriever warm-up …
   2.742 s`; ≈7-8с от старта процесса до `Application startup complete`. VLM-прогрев в лог не попадает
   при сбое шлюза — известная особенность (`reports/qa-auto-scan-budget.md`), не блокер.
3. **2-3 холостых скана**: `curl -F image=@<фото> http://127.0.0.1:$PORT/v1/eval/predict`. У меня: 6.49с
   (первый) / 3.25с / 3.33с — все HTTP 200, все три слага 1:1 со стендом hack-v15.
4. **Команда проверки**: `bash case-data/eval/participant_test.sh --images-dir case-data/real-photos
   --manifest <манифест> --endpoint http://127.0.0.1:$PORT/v1/eval/predict --output <served/новый.jsonl>`.
   Скрипт **сам принимает `--endpoint`** (проверено дважды, 100+15 фото) — 8080 освобождать НЕ нужно и
   НЕЛЬЗЯ (чужой процесс). Риск только человеческий: забыть флаг — уйдёт на дефолт :8080. Команду с портом
   держать под рукой у того, кто печатает её на созвоне.
5. **Сбой GPU-шлюза или локальной 4B**: ничего не делать руками — предохранитель (3 сбоя подряд → пауза
   60с, лог `cv_fusion: предохранитель модели <vlm|vlm_local> открыт/закрыт`), `/v1/eval/predict` всегда
   HTTP 200 даже при обеих недоступных.
6. **После**: `kill` свой процесс, порт свободен; `com.local-vlm.server` — `state=running`+`/v1/models` 200.

(18:18:53) — ровно по дизайну (`VISION_LLM_BREAKER_FAILS=3`). **15/15 HTTP 200 вовремя** (3017–6212мс),
**15/15 slug = чистому прогону** на тех же фото (9 из них — в размеченных 62, все верны). Два ответа
~6.2с — независимый одиночный джиттер GPU-шлюза (2×`vlm закрыт — успешный ответ`), не от локальной
модели. Служба восстановлена: `bootstrap` → `/v1/models` 200 после 3 проверок (~6с), `state=running` —
выполнено безусловно через `trap EXIT`, сработало бы и при сбое самого шага. Шум: Zed 0–2.5% CPU
(простаивал), лог 4B — 102 `/v1/chat/completions` с моего старта против ожидаемых ~103 (3 прогрева + 100
прогон) — постороннего использования не обнаружено. **После себя**: 8080/8091/8092 — чужие PID
(36134/1098/1096) не менялись; свой 8081 остановлен, порт свободен; 8093 — исходное `running`/200.

## Как воспроизвести
```
PORT=8081 infra/local-check/run-check-server.sh &
bash case-data/eval/participant_test.sh --images-dir case-data/real-photos \
  --manifest case-data/real-photos-labels/rehearsal_manifest.tsv \
  --endpoint http://127.0.0.1:8081/v1/eval/predict --output case-data/real-photos-labels/served/<new>.jsonl
```
Top-1/diff: `qa/real_photos_eval.py --served <photo/flat_slug/flat_ms JSONL> --only zzz` из `packages/cv`
(поля participant_test.sh конвертируются в served-схему разовым скриптом, не коммитил).

## Риски / предложения тимлиду
Только человеческий риск: забытый `--endpoint` тихо уводит на чужой :8080 — команда с портом зафиксирована
выше, копипастить на созвоне, не печатать по памяти. Diff 11/100 вне 62 — не регрессия, это два РАЗНЫХ
конфига (макс. Mac vs прод ams3), 1:1 не ожидается.
