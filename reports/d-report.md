+ новый `WineRoadsTeaser.tsx`) поверх каркаса C:

  доведён до финального тона (уверенный сомелье, без пафоса), добавлен заголовок секции

- **Тизер «Винных дорог»** (`WineRoadsTeaser.tsx`) — новый компонент, информационный блок
  (бейдж «Скоро» + заголовок + текст) про карту виноделен, чек-ины и штампы винного паспорта.
  Сознательно без кнопки/CTA и без новой аналитики: словарь `contracts/events.md` заморожен,
  события под этот блок в нём нет, а придумывать новое имя запрещено протоколом.
- **Waitlist**: чекбокс согласия + версия согласия уже были в каркасе C; добавил рядом с
  чекбоксом подпись-ссылку на политику ПД и тексты согласий (юридически такая ссылка обычно
  нужна прямо у места сбора согласия, не только в футере).
- **Юридические ссылки**: строка ссылок «Политика обработки данных · Тексты согласий ·
  Условия использования» в футере (`target="_blank" rel="noopener noreferrer"`, чтобы не терять
  состояние формы/гостевой сессии) — ведут на новые статические страницы.
- **18+ интерстициал** — логика уже была в каркасе C (`AgeInterstitial.tsx`, `lib/storage.ts`);
  не переделывал, только покрыл тестами (ниже) и проверил вручную в браузере.
- **SEO-минимум**: новый хук `useLandingSeo.ts` — задаёт landing-специфичные `document.title`,
  `meta[name=description]` и `og:title/og:description/og:type/og:locale/og:image` через прямые
  DOM-операции (без сторонних пакетов — `package.json` вне зоны агента D), с полным откатом на
  unmount, чтобы значения не «протекали» на `/app` при клиентской навигации. `index.html`
  (зона C) не трогал — он остаётся честным статическим дефолтом для не-JS краулеров и первого
  пейнта; favicon там уже был (`/icons/icon.svg`), новых иконок не потребовалось.
- Копирайт очищен от слова «купи»/«купить» (было в hero-подзаголовке — «без рекламы «купи
  именно это»» → «без рекламы «бери эту бутылку»»); цен на алкоголь нигде нет.

**Юридические черновики** (`apps/web/public/legal/`, все с баннером «ЧЕРНОВИК — документ не
проверен юристом и не является публичной офертой» и дисклеймером 18+/алкоголь внизу):

- `privacy.html` — политика обработки ПД, структура по 152-ФЗ (общие положения → термины →
  состав данных [таблица] → цели → правовые основания → локализация/хранение → права субъекта →
  меры безопасности → cookies/localStorage → изменение политики → контакты). Данные в таблице
  сверены с `contracts/schema.sql` (users/consent_ledger/swipes/taste_profiles/scans/events/
  waitlist) — не общий шаблон, а описание реальной модели данных проекта.
- `consent.html` — тексты согласий по всем четырём скоупам из `contracts/openapi.yaml` /
  `contracts/schema.sql` (`base` обязателен, `profiling` / `geo` / `marketing` — по желанию), плюс
  отдельный текст согласия для waitlist-формы (вне аккаунта). В каждом скоупе: формулировка для
  интерфейса, что именно обрабатывается, зачем, основание, как отозвать. Версия документа
  (`2026-08-v1`) синхронизирована со значением `CONSENT_VERSION` в `src/lib/consent.ts`.
- `terms.html` — условия использования: что сервис делает и (жирным, явно) чего не делает —
  не продаёт и не доставляет алкоголь, не является розничным продавцом, не рекламирует
  алкогольную продукцию; гостевой доступ vs аккаунт; права/обязанности сторон; ИС и источники;
  ограничение ответственности; изменение условий; применимое право.
- Общий стиль — `legal.css` (+ `tokens.css`, ручная синхронизированная копия
  `contracts/tokens.css`, см. «Предложения к контрактам»): те же переменные дизайн-системы,
  светлая/тёмная тема, баннер-черновик, `.todo`-плейсхолдеры для полей юриста (наименование
  юрлица, ИНН/ОГРН, контактный e-mail), таблица в `privacy.html` — в `.table-wrap` со
  `overflow-x: auto` (нашёл и починил горизонтальный оverflow на очень узких вьюпортах при
  визуальной проверке, см. ниже).
- `<meta name="robots" content="noindex, nofollow">` на всех трёх — черновики не должны попасть
  в поисковую выдачу до вычитки юристом.

## Lighthouse

`npm run build && npm run preview` (порт 4173) → `npx lighthouse` (headless Chrome, дефолтные
mobile-настройки CLI — `formFactor: mobile`, `throttlingMethod: devtools`, тот же метод, что
описан в `reports/c-report.md`), маршрут `/`, два прогона подряд:

| Прогон | Performance | Accessibility | Best Practices | SEO |
|---|---|---|---|---|
| 1 | 98 | 100 | 100 | 100 |
| 2 | 95 | 100 | 100 | 100 |

Было у C: 95–96 / 98 / 100 / 100. **Не уронил, местами лучше** (Accessibility 100 против 98 —
из-за замены сомнительного `aria-label` на секции фич на корректный `aria-labelledby`).
SEO остался 100, несмотря на добавление `og:*`-тегов через JS (Lighthouse не проверяет их
специально, но и не штрафует).

Бонус (не требовалось DoD, проверил из осторожности, т.к. это полностью новые страницы):
`privacy.html` отдельно — Accessibility 100, Best Practices 100, SEO 63. Единственная просевшая
позиция SEO — `is-crawlable` (страница блокирует индексацию): это **намеренно**, я сам поставил
`<meta name="robots" content="noindex, nofollow">` на черновик, который «не проверен юристом и
не является публичной офертой» и не должен попасть в поиск. Не блокер и не относится к DoD
«Lighthouse ≥ 90», который в брифе — про лендинг на `/`.

## Визуальная проверка (Browser pane)

Прогнал вручную поверх собранного `dist/` (`vite preview`): тёмная тема, hero, три карточки
фич, тизер «Винные дороги» (бейдж «Скоро»), waitlist с ссылками на юр-страницы, футер. 18+-флоу
проверен целиком: клик по CTA → диалог → «Да, мне есть 18» → `storage` пишет
`landing_age_ack=1` → повторный клик по CTA диалог **не** показывает. Гостевой вход в этом
Browser-пейне падает с честным `ctaTryError` («Не удалось войти») — это то же самое известное
ограничение песочницы, что задокументировал агент C («MSW Service Worker не регистрируется в
песочнице Browser-пейна этой сессии»), не регрессия моего кода: тот же путь зелёный в 43
vitest-тестах через `msw/node`, а флаг «показан один раз» пишется и переживается независимо от
исхода сетевого запроса — сам это проверил (localStorage хранит `1` даже после ошибки входа).

При визуальной проверке на очень узком вьюпорте (280 CSS px) нашёл и исправил реальный баг:
таблица в `privacy.html` вызывала горизонтальный overflow всей страницы. Обернул в
`.table-wrap { overflow-x: auto }` (`public/legal/legal.css`) — таблица теперь скроллится в
своём контейнере, страница — нет. Перепроверил все три юр-страницы и лендинг на той же ширине
после фикса — overflow нигде не осталось.

## Предложения к контрактам / для оркестратора

1. **Дублирование `tokens.css` — уже третья копия.** `contracts/tokens.css` (источник) →
   `apps/web/src/styles/tokens.css` (байт-в-байт копия C для React-бандла) →
   `apps/web/public/legal/tokens.css` (моя байт-в-байт копия для статических HTML-страниц,
   которые не проходят через Vite-сборку и не могут импортировать TS-модуль). Технически
   неизбежно при нынешней архитектуре (статические юр-страницы вне SPA), но риск рассинхрона
   при следующей правке токенов реален. Предложение: если токены снова поменяются — прогнать
   `diff` по всем трём копиям как чек-лист ревью, либо (более прочное решение) генерировать
   `public/legal/tokens.css` из `contracts/tokens.css` одним шагом в `vite build` — это правка
   `vite.config.ts`, вне моей зоны, оставляю решение оркестратору/агенту C.
2. **Риск 8 из `reviews/01-contracts.md` («версии текстов согласий нигде не архивируются»)
   остаётся не закрыт архитектурно.** Бриф прямо просит один `consent.html`, не
   `public/legal/consents/<version>.html` из предложения ревьюера — сделал по брифу (версия
   `2026-08-v1` явно указана в шапке документа и совпадает с `CONSENT_VERSION` в коде), но
   механизма архивации предыдущих редакций при будущей правке текста в репозитории всё ещё нет.
   Если юрист попросит правки текста согласий — предлагаю завести именно версионирование
   файлов (или git-тег на коммит) ДО публикации новой редакции, не после.
3. **Риск 7 из того же ревью («поведенческая аналитика не привязана к скоупу согласия»)
   зафиксирован как открытый вопрос прямо в `consent.html`** (раздел «Открытый вопрос юристу»):
   черновик относит обезличенные продуктовые события к базовому согласию как техническую
   необходимость — нужно подтверждение юриста, а не тихое решение агентом.
4. **`contracts/events.md` не содержит события под тизер «Винных дорог»** — сделал блок
   намеренно без интерактива и без трекинга, чтобы не изобретать имя события в обход
   заморозки словаря. Если тизер захотят сделать кликабельным (например, «узнать первым» —
   отдельная точка входа в тот же waitlist) — потребуется новое имя события, добавлять
   оркестратору.
