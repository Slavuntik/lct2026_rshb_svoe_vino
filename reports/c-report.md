## Что сделано

**apps/web** — Vite + React 19 + TypeScript + react-router 7, PWA, полностью рабочее в
мок-режиме (MSW) приложение:

- Маршрут `/` — лендинг: оффер, три фичи (скан→карточка / сомелье с цитатами / аналог
  импортного), 18+ интерстициал (разово, запоминается в localStorage), waitlist-форма
  (email + обязательное согласие, без согласия кнопка неактивна), кнопка «Попробовать в
  браузере» (гостевой вход, см. ниже), дисклеймер 18+/алкоголь в футере.
- Маршрут `/app/*` — шесть экранов и ни одним больше:
  1. `onboarding` — дата рождения (гейт 18+, honest блок без формы при отказе) + согласия
     по скоупам (base обязателен, profiling/geo/marketing — опционально);
  2. `scan` — фото и текст РАВНОПРАВНЫ; фото ветвится по платформе:
     iOS → нативный OCR-плагин (Vision, на устройстве) → распознанный текст →
     `POST /scan/resolve`, минуя сервер вообще; веб → `POST /scan/ocr` (контрактно
     всегда 501 — честная деградация «введите текст», без generic-ошибки, без чекбокса
     согласия на iOS, т.к. фото туда и не уходит). low_confidence → список выбора,
     пустой результат → честное «не нашли»;
  3. `wine/:wineId` — карточка вина (source/derived/source_url/similar), 7-осевой
     сенсорный профиль, переход «спросить сомелье про это вино»;
  4. `chat` — SSE-парсер (token/citation/done/refusal) поверх fetch (EventSource с Bearer
     невозможен — ревью 01, риск 11), режим-чип «Аналог импортного» → `POST /analogs`;
     цитаты `[n]` с `url` — кликабельные ссылки на первоисточник (`target=_blank
     rel=noopener`, «правило каталога №5» — ревью 02);
  5. `taste` — паспорт вкуса: колода — `GET /taste/candidates` (сервер сам исключает
     свайпнутое, без клиентских списков id), свайпы (кнопки + pointer-drag), 7-осевой
     вектор, топ-стили; честный гейт для гостей/без scope profiling — как до, так и по
     живому 403 от `/taste/candidates`;
  6. `profile` — «Мои данные»: согласия (переключатели), апгрейд гостя до полного
     аккаунта (email/пароль), выгрузка данных (скачивание JSON), удаление аккаунта
     (модалка подтверждения).
- i18n: свой хук (`src/i18n`), словарь `ru.ts` (полный) + `en.ts` (пустой, честный фолбэк
  на ru), ни одной строки интерфейса хардкодом в JSX — проверено grep-тестом.
- `tokens.css` скопирован **дословно** из `contracts/` (byte-for-byte, см. проверку ниже),
  хардкода цветов в компонентах нет. Шрифты — Google Fonts (Cormorant + IBM Plex
  Sans/Mono), загрузка асинхронная (см. «Lighthouse» ниже).
- API-клиент (`src/lib/apiClient.ts`) — вручную по `openapi.yaml`, типы в `apiTypes.ts`.
- MSW: 6 вымышленных вин (`src/mocks/fixtures/wines.ts`, форма полей — как в
  `catalog/wines/<slug>.json` у vines, но winery/name/регион полностью выдуманы),
  обработчики на все 21 путь контракта (v0.3), включая честную SSE-эмуляцию чата с
  `url` в цитатах, наивный `resolve_style` для `/analogs`, серверное исключение
  свайпнутых вин в `/taste/candidates` и безусловный 501 на `/scan/ocr`.
- Аналитика (`src/lib/analytics.ts`) — типобезопасно по словарю `events.md`, транспорт —
  `POST /events` (см. v0.2), пишет `props._v`.
- PWA: `manifest.webmanifest`, SVG-иконки (обычная + maskable), офлайн — баннер
  «нет сети» на `useOnlineStatus()` (без Service Worker — по прямому указанию
  оркестратора, риск двойной регистрации SW с MSW и «вчерашняя сборка в кэше» на демо).
- Capacitor (`apps/shell/`): `capacitor.config.ts` (appId-плейсхолдер
  `ru.svoysomelye.app`, webDir → `apps/web/dist`), iOS- и Android-проекты сгенерированы.
- **OCR-плагин** (`apps/shell/plugins/ocr-plugin/`) — TS-интерфейс + **полная** Swift-
  реализация на Vision (не заглушка — см. «Контракт v0.2 / смена объёма» ниже).

### Внеплановое: git был сломан фоновой установкой Xcode

Между волной 1 и этой волной на машине **сама** (без моего участия — не запускал
`xcode-select`, не трогал `sudo`) появилась полноценная установка Xcode 26.6
(`/Applications/Xcode.app`, `root:wheel`, время создания — во время моей предыдущей
сессии). Xcode-лицензия не принята — из-за этого **весь** `/usr/bin/git` на машине
падал с «You have not agreed to the Xcode license agreements» на любой команде, не
только на commit (задел бы и других агентов, если бы они коммитили в этот момент).

Sudo/`xcodebuild -license` не запускал — это решение пользователя, не моё. Оркестратор
подсказал корректный обход: `DEVELOPER_DIR=/Library/Developer/CommandLineTools` перед
git-командами — переменная окружения на ПРОЦЕСС, не системная замена `xcode-select`,
ничего постоянного не меняет и не требует sudo. Сработало сразу. Коммиты той волны —
с этим префиксом.

**Апдейт:** пользователь принял лицензию сам — голый `git` (и `xcodebuild`) снова
работают без префикса; коммит с этой сборкой под симулятор (раздел «Сборка под
симулятор» ниже) — уже обычным `git`, без `DEVELOPER_DIR`.

### Lighthouse — что реально было узким местом

Промежуточный вывод по ходу работы оказался неверным: я предположил, что мок-слой
(MSW-чанк, 162 КБ gzip) конкурирует за первый рендер, и вынес его старт из-под
`await` перед `createRoot().render()` (`src/lib/mockBootstrap.ts`, `apiClient` сам
дожидается готовности мока перед реальным запросом). Правка сама по себе корректна
и осталась в коде, но замер **показал ухудшение** (87→80/81) — дело было не в этом.

Настоящая причина: `<link rel="stylesheet" href="fonts.googleapis.com/...">` —
render-blocking запрос на сторонний домен, в трассировке занимал **~530 мс** сам по
себе (`network-requests` audit) и держал первую отрисовку. Три семейства шрифтов
(Cormorant + IBM Plex Sans + IBM Plex Mono) через один блокирующий `<link>` в `<head>`.

Фикс — классический loadCSS-приём в `index.html`: `media="print" onload="this.media=
'all'"` + `<noscript>`-фолбэк. Google Fonts остались (бриф прямо требует их, самостоятельно
на self-hosting не уходил), но перестали блокировать рендер. Результат: FCP 3.5с→1.9с,
LCP 3.9с→2.6с, Perf 80→95 (два прогона подряд — 95 и 96, стабильно).

Вывод для остальных агентов и на будущее: если лендинг снова просядет по Lighthouse —
сначала смотреть `network-requests`/`render-blocking-resources` на реальные тяжёлые
цепочки, а не гадать по интуиции (я потратил один лишний прогон именно на этом).

## OCR-плагин: что реально проверено, а что — нет

## Сборка под симулятор (дериск сцены 1)

Пользователь принял лицензию Xcode — на машине полный **Xcode 26.6** (build 17F113) с
**iPhoneSimulator SDK 26.5**. Оркестратор попросил довести дериск до конца: не
синтаксис, а полная компиляция `apps/shell/ios` под симулятор (без запуска, без
подписи). Сделано.

### Команда и результат

```bash
cd apps/shell
xcodebuild -project ios/App/App.xcodeproj -scheme App \
  -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' \
  -configuration Debug CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO \
  CODE_SIGN_IDENTITY="" clean build
```

**`** BUILD SUCCEEDED **`, 0 ошибок, 1 предупреждение** — и то не моё: `Metadata
extraction skipped. No AppIntents.framework dependency found.` (стандартный шум Xcode
для любого приложения без App Intents, к плагину и к коду C отношения не имеет).
Прогнано дважды — обычный build и `clean build` с нуля — результат одинаковый.

Проверил не только итоговый статус, но и что именно произошло с плагином:

1. **`OcrPlugin.swift` реально скомпилирован** — в логе есть `SwiftCompile normal
   arm64/x86_64 ... OcrPlugin.swift (in target 'SvoySomelyeOcrPlugin' ...)` для обеих
   архитектур симулятора (Apple Silicon и Intel — `generic/platform=iOS Simulator` не
   пинится к одной архитектуре).
2. **Слинкован в итоговый бинарник.** Финальный `Ld`/`clang` для таргета `App`
   подключает `SvoySomelyeOcrPlugin.swiftmodule` наравне с `Capacitor`/`Cordova`.
3. **Символы на месте.** `nm -g App.debug.dylib | grep OcrPlugin` отдаёт mangled-имена
   ровно тех методов, что в коде: `identifier`, `jsName`, `pluginMethods`,
   `recognizeText(_:)`, `isAvailable(_:)`, `bridge(pluginId:pluginName:)` (последнее —
   часть протокола `CAPBridgedPlugin`, то есть протокол реально удовлетворён компилятором
   против настоящего Capacitor SPM, не мока). Это и есть прямое доказательство: если бы
   `Vision`/`Capacitor` API были использованы неправильно, компиляция упала бы на этом
   же шаге с настоящей ошибкой типов — а не просто «не резолвится модуль», как раньше
   при `-parse`.
4. Собранный `App.app` физически лежит в
   `~/Library/Developer/Xcode/DerivedData/App-*/Build/Products/Debug-iphonesimulator/`
   (не в репозитории — это чужой для git путь, ничего коммитить не нужно).

### Один красный herring, честно зафиксирован

Отдельно пробовал собрать **автосгенерированную SPM-схему `SvoySomelyeOcrPlugin`** в
изоляции от `App` (`-scheme SvoySomelyeOcrPlugin`) — она упала: `could not build module
'Capacitor' ... module 'Cordova' not found`. Это НЕ ошибка в моём коде: эта схема — не
самостоятельная точка входа продукта, а служебный артефакт интеграции SPM-пакетов в
Xcode, и `capacitor-swift-pm` распространяет `Capacitor`/`Cordova` как **бинарные**
XCFramework-продукты, которые нормально резолвятся и подкладываются только в рамках
сборки зонтичного таргета `App` (там это происходит на шаге `Copy .../PackageFrameworks`
до всякой компиляции плагина). Собирать библиотечную SPM-схему отдельно от приложения,
которое её реально встраивает — искусственный сценарий, никто так не делает и Capacitor
так не тестируют. Реальный путь — сборка `App` — прошёл чисто дважды подряд, этого
достаточно.

### Итог

Полная компиляция подтверждена. Блокер «не могу гарантировать, что скомпилируется без
правок» из раздела выше — закрыт: скомпилировался БЕЗ единой правки кода, ровно как
был написан. Единственное, что осталось для publish-Mac — реальный запуск на симуляторе
(этот прогон намеренно не делал: оркестратор попросил только сборку) и подпись для
физического устройства/TestFlight (не нужна для симулятора, `CODE_SIGNING_ALLOWED=NO`
отключил её явно).

## Известные ограничения среды (не блокеры продукта)

- **MSW Service Worker не регистрируется в песочнице Browser-пейна этой сессии**
  (`navigator.serviceWorker.register()` падает с «unknown error fetching the script»
  даже для файла, который сам по себе отдаётся по HTTP 200, — проверено `curl`).

  та же логика проверена гораздо строже через `msw/node` в 30 vitest-тестах, а в
  обычном Chrome/Safari (открыто и проверено через реальный `open -a "Google Chrome"`)
  registration проходит штатно. Если ревьюер откроет `npm run dev` в обычном браузере —
  всё должно работать; если нет, первое, что проверить — не CSP/расширение ли блокирует
  Service Worker.
- Docker/CocoaPods на машине нет — не понадобились: Capacitor 8 по умолчанию ставит
  iOS-проект на SPM, `pod`/`Podfile` в этой конфигурации не участвуют вообще.
