## Что сделано

**apps/web** — Vite + React 19 + TypeScript + react-router 7, PWA, полностью рабочее в
мок-режиме (MSW) приложение:

- Маршрут `/` — лендинг: оффер, три фичи (скан→карточка / сомелье с цитатами / аналог
  импортного), 18+ интерстициал (разово, запоминается в localStorage), waitlist-форма
  (email + обязательное согласие, без согласия кнопка неактивна), кнопка «Попробовать в
  браузере» (гостевой вход, см. ниже), дисклеймер 18+/алкоголь в футере.
- Маршрут `/app/*` — шесть экранов и ни одним больше:
  1. `onboarding` — дата рождения (гейт 18+, honest блок без формы при отказе) + согласия
     по скоупам (base обязателен, profiling/geo/marketing — опционально);
  2. `scan` — фото и текст РАВНОПРАВНЫ; фото ветвится по платформе:
     iOS → нативный OCR-плагин (Vision, на устройстве) → распознанный текст →
     `POST /scan/resolve`, минуя сервер вообще; веб → `POST /scan/ocr` (контрактно
     всегда 501 — честная деградация «введите текст», без generic-ошибки, без чекбокса
     согласия на iOS, т.к. фото туда и не уходит). low_confidence → список выбора,
     пустой результат → честное «не нашли»;
  3. `wine/:wineId` — карточка вина (source/derived/source_url/similar), 7-осевой
     сенсорный профиль, переход «спросить сомелье про это вино»;
  4. `chat` — SSE-парсер (token/citation/done/refusal) поверх fetch (EventSource с Bearer
     невозможен — ревью 01, риск 11), режим-чип «Аналог импортного» → `POST /analogs`;
     цитаты `[n]` с `url` — кликабельные ссылки на первоисточник (`target=_blank
     rel=noopener`, «правило каталога №5» — ревью 02);
  5. `taste` — паспорт вкуса: колода — `GET /taste/candidates` (сервер сам исключает
     свайпнутое, без клиентских списков id), свайпы (кнопки + pointer-drag), 7-осевой
     вектор, топ-стили; честный гейт для гостей/без scope profiling — как до, так и по
     живому 403 от `/taste/candidates`;
  6. `profile` — «Мои данные»: согласия (переключатели), апгрейд гостя до полного
     аккаунта (email/пароль), выгрузка данных (скачивание JSON), удаление аккаунта
     (модалка подтверждения).
- i18n: свой хук (`src/i18n`), словарь `ru.ts` (полный) + `en.ts` (пустой, честный фолбэк
  на ru), ни одной строки интерфейса хардкодом в JSX — проверено grep-тестом.
- `tokens.css` скопирован **дословно** из `contracts/` (byte-for-byte, см. проверку ниже),
  хардкода цветов в компонентах нет. Шрифты — Google Fonts (Cormorant + IBM Plex
  Sans/Mono), загрузка асинхронная (см. «Lighthouse» ниже).
- API-клиент (`src/lib/apiClient.ts`) — вручную по `openapi.yaml`, типы в `apiTypes.ts`.
- MSW: 6 вымышленных вин (`src/mocks/fixtures/wines.ts`, форма полей — как в
  `catalog/wines/<slug>.json` у vines, но winery/name/регион полностью выдуманы),
  обработчики на все 21 путь контракта (v0.3), включая честную SSE-эмуляцию чата с
  `url` в цитатах, наивный `resolve_style` для `/analogs`, серверное исключение
  свайпнутых вин в `/taste/candidates` и безусловный 501 на `/scan/ocr`.
- Аналитика (`src/lib/analytics.ts`) — типобезопасно по словарю `events.md`, транспорт —
  `POST /events` (см. v0.2), пишет `props._v`.
- PWA: `manifest.webmanifest`, SVG-иконки (обычная + maskable), офлайн — баннер
  «нет сети» на `useOnlineStatus()` (без Service Worker — по прямому указанию
  оркестратора, риск двойной регистрации SW с MSW и «вчерашняя сборка в кэше» на демо).
- Capacitor (`apps/shell/`): `capacitor.config.ts` (appId-плейсхолдер
  `ru.svoysomelye.app`, webDir → `apps/web/dist`), iOS- и Android-проекты сгенерированы.
- **OCR-плагин** (`apps/shell/plugins/ocr-plugin/`) — TS-интерфейс + **полная** Swift-
  реализация на Vision (не заглушка — см. «Контракт v0.2 / смена объёма» ниже).

### Внеплановое: git был сломан фоновой установкой Xcode

Между волной 1 и этой волной на машине **сама** (без моего участия — не запускал
`xcode-select`, не трогал `sudo`) появилась полноценная установка Xcode 26.6
(`/Applications/Xcode.app`, `root:wheel`, время создания — во время моей предыдущей
сессии). Xcode-лицензия не принята — из-за этого **весь** `/usr/bin/git` на машине
падал с «You have not agreed to the Xcode license agreements» на любой команде, не
только на commit (задел бы и других агентов, если бы они коммитили в этот момент).

Sudo/`xcodebuild -license` не запускал — это решение пользователя, не моё. Оркестратор
подсказал корректный обход: `DEVELOPER_DIR=/Library/Developer/CommandLineTools` перед
git-командами — переменная окружения на ПРОЦЕСС, не системная замена `xcode-select`,
ничего постоянного не меняет и не требует sudo. Сработало сразу. Коммиты той волны —
с этим префиксом.

**Апдейт:** пользователь принял лицензию сам — голый `git` (и `xcodebuild`) снова
работают без префикса; коммит с этой сборкой под симулятор (раздел «Сборка под
симулятор» ниже) — уже обычным `git`, без `DEVELOPER_DIR`.

### Lighthouse — что реально было узким местом

Промежуточный вывод по ходу работы оказался неверным: я предположил, что мок-слой
(MSW-чанк, 162 КБ gzip) конкурирует за первый рендер, и вынес его старт из-под
`await` перед `createRoot().render()` (`src/lib/mockBootstrap.ts`, `apiClient` сам
дожидается готовности мока перед реальным запросом). Правка сама по себе корректна
и осталась в коде, но замер **показал ухудшение** (87→80/81) — дело было не в этом.

Настоящая причина: `<link rel="stylesheet" href="fonts.googleapis.com/...">` —
render-blocking запрос на сторонний домен, в трассировке занимал **~530 мс** сам по
себе (`network-requests` audit) и держал первую отрисовку. Три семейства шрифтов
(Cormorant + IBM Plex Sans + IBM Plex Mono) через один блокирующий `<link>` в `<head>`.

Фикс — классический loadCSS-приём в `index.html`: `media="print" onload="this.media=
'all'"` + `<noscript>`-фолбэк. Google Fonts остались (бриф прямо требует их, самостоятельно
на self-hosting не уходил), но перестали блокировать рендер. Результат: FCP 3.5с→1.9с,
LCP 3.9с→2.6с, Perf 80→95 (два прогона подряд — 95 и 96, стабильно).

Вывод для остальных агентов и на будущее: если лендинг снова просядет по Lighthouse —
сначала смотреть `network-requests`/`render-blocking-resources` на реальные тяжёлые
цепочки, а не гадать по интуиции (я потратил один лишний прогон именно на этом).

Прогнано дважды — обычный build и `clean build` с нуля — результат одинаковый.

Проверил не только итоговый статус, но и что именно произошло с плагином:

1. **`OcrPlugin.swift` реально скомпилирован** — в логе есть `SwiftCompile normal
   arm64/x86_64 ... OcrPlugin.swift (in target 'SvoySomelyeOcrPlugin' ...)` для обеих
   архитектур симулятора (Apple Silicon и Intel — `generic/platform=iOS Simulator` не
   пинится к одной архитектуре).
2. **Слинкован в итоговый бинарник.** Финальный `Ld`/`clang` для таргета `App`

3. **Символы на месте.** `nm -g App.debug.dylib | grep OcrPlugin` отдаёт mangled-имена
   ровно тех методов, что в коде: `identifier`, `jsName`, `pluginMethods`,
   `recognizeText(_:)`, `isAvailable(_:)`, `bridge(pluginId:pluginName:)` (последнее —
   часть протокола `CAPBridgedPlugin`, то есть протокол реально удовлетворён компилятором

   `Vision`/`Capacitor` API были использованы неправильно, компиляция упала бы на этом
   же шаге с настоящей ошибкой типов — а не просто «не резолвится модуль», как раньше

4. Собранный `App.app` физически лежит в
   `~/Library/Developer/Xcode/DerivedData/App-*/Build/Products/Debug-iphonesimulator/`

### Один красный herring, честно зафиксирован

Отдельно пробовал собрать **автосгенерированную SPM-схему `SvoySomelyeOcrPlugin`** в
изоляции от `App` (`-scheme SvoySomelyeOcrPlugin`) — она упала: `could not build module
'Capacitor' ... module 'Cordova' not found`. Это НЕ ошибка в моём коде: эта схема — не
самостоятельная точка входа продукта, а служебный артефакт интеграции SPM-пакетов в
Xcode, и `capacitor-swift-pm` распространяет `Capacitor`/`Cordova` как **бинарные**
XCFramework-продукты, которые нормально резолвятся и подкладываются только в рамках
сборки зонтичного таргета `App` (там это происходит на шаге `Copy .../PackageFrameworks`
до всякой компиляции плагина). Собирать библиотечную SPM-схему отдельно от приложения,
которое её реально встраивает — искусственный сценарий, никто так не делает и Capacitor
так не тестируют. Реальный путь — сборка `App` — прошёл чисто дважды подряд, этого
достаточно.

Полная компиляция подтверждена. Блокер «не могу гарантировать, что скомпилируется без

### Экран скана: фото вместо текста как первичный путь

`ScanScreen.tsx` переписан целиком. Раньше (ревью 02) фото и текст были
равноправны, а фото на iOS уходило через нативный OCR-плагин в текст, на вебе — в
`/scan/ocr` (контрактный 501). Кейс меняет саму механику: CV-поиск идёт по
изображению на сервере, одинаково для любой платформы, — эта ветка убрана целиком.
Теперь:

- Верхний блок экрана — дропзона (`data-testid="scan-dropzone"`): drag-and-drop,
  скрытый `<input type="file" accept="image/*" capture="environment">` за кнопкой
  «Выбрать фото» (`capture="environment"` — подсказка мобильным браузерам сразу
  открыть камеру, не галерею) и превью выбранного кадра.
- Выбор файла (диалогом или drop) **сразу** вызывает `apiClient.scanPhoto(file)` —
  без промежуточного «отправить»; статус «Ищем по фото… обычно до 3 секунд.» — SLA
  кейса `≤ 3 c` заявлен пользователю честно, не как гарантия, а как ожидание.
- Текстовый путь (`/scan/resolve`, как было) остался, но явно во вторую роль:
  отдельная карточка ниже разделителя «или», подпись «Не получилось
  сфотографировать?» — запасной вход, а не альтернатива с тем же весом.
- Аналитика: `scan_started{mode:"web_upload"}` на выбор фото, `scan_resolved{matched,
  confidence, wine_id}` на ответ (confidence уходит в аналитику/метрики — не в UI, см.
  ниже), `wine_card_viewed{wine_id, from:"scan"}` только для уверенного попадания.

### Одна карточка сразу, confidence не в UI

`ScanPhotoRichResponse` (новый тип в `apiTypes.ts`) несёт `confidence: {top1_score,
gap, f1_top1, f1_top5}` — контракт требует эти цифры «в API» (пункт 3 `case.md`:
«метрика уверенности (F1) … в API, в UI не обязательно»). В интерфейсе ScanScreen эта
цифра **нигде не рендерится**: при уверенном совпадении сразу показывается
`<WineCardContent wine={confidentCard} titleAs="h2" />` — та же карточка, что и на
`/app/wine/:id` (см. «Общий компонент карточки» ниже), без какого-либо экрана
кандидатов. Явно проверено тестом (`ScanScreen.test.tsx`, первый `it`): текст
результата не содержит `94%` (значение фикстуры `top1_score`), при этом ABV% вина
(легитимные данные карточки, например «13%») намеренно не забанены — проверка точечная
по конкретной строке confidence, не по любому проценту в разметке.

Старый текстовый путь резолвит `low_confidence`/пустой результат так же, как раньше
(список выбора / честное «не нашли») — эта логика кейсом не отменяется, только
перестаёт быть основной дверью в приложение.

### `not_in_catalog` — честная ветка, без выдумки карточки

Контракт: `not_in_catalog: bool` + `similar`/`analogs` в том же rich-ответе. Когда
`not_in_catalog: true`, `card` контрактно может быть `null` — экран это не
«подделывает» карточкой-заглушкой, а показывает отдельный блок
(`data-testid="scan-not-in-catalog"`): заголовок «Такого вина в каталоге нет»,
честный текст («не нашли точное совпадение… вот похожие варианты и аналоги»), и два
списка кликабельных карточек-чипов (`похожие вина` / `аналоги из других виноделен`),
каждый — переход на `/app/wine/:id` через уже существующий механизм (`from: "scan"`).
Пустые `similar`/`analogs` в ответе просто не рендерят свою секцию (те же условные
блоки, что и на карточке вина для «похожих»).

### Тихая подпись вместо чекбокса согласия

Прежний веб-путь фото (`/scan/ocr`, ревью 02) нёс `explicit_consent`
(чекбокс). `contracts/image-scan.md` v0.4 для `/scan/photo` **не содержит**
`explicit_consent` вообще — ни в multipart-полях, ни в ответе. Явно спросил себя:
подделывать чекбокс, которого не просит контракт, вредно (лишний клик перед
единственным способом решить задачу кейса) — заменил на некликабельную подпись под
кнопкой: «Фото используется только для поиска и не сохраняется.»
(`scan.quietPhotoCaption`). Тест фиксирует оба свойства сразу: подпись есть в DOM,
`role="checkbox"` в разметке нет вообще.

### Тема «портал»: как извлекались токены

Бриф прямо просил не выдумывать «винные» цвета, а взять реальные из
`pipeline/raw-archive/raw-snapshots.tar.xz` (архив HTML-снэпшотов портала,
sha256 сверен перед распаковкой). Методика:

1. Распаковал архив, нашёл в нём 3 страницы разных типов —
   `pipeline/raw/raw/{wines,wineries,articles}/*.html` (карточка вина, винодельня,
   статья) — сознательно не одна страница, чтобы не принять one-off инлайн-стиль
   за токен платформы.
2. Вытащил все инлайн `<style>`-блоки регэкспом, прогнал через частотный анализ
   (`sort | uniq -c | sort -rn`) по hex-цветам и `border-radius` — токен считается
   «настоящим», если он доминирует, а не встретился один раз.
3. Кросс-проверил акцентный цвет: `#8F3D42` — не просто самый частый акцентный hex во
   всех трёх снэпшотах, а буквально `background-color` реальной CTA-кнопки поиска
   сайта (`.core-header__mob-search-btn-container`) — то есть однозначно «фирменный»
   акцент, а не совпадение частот.
4. Шрифт `Playfair Display` — во всех трёх снэпшотах как `font-family` заголовков (с
   `serif`-фолбэком); для текста — системный sans (в снэпшотах — системный стек, не
   отдельный веб-шрифт).

Итоговые токены (`apps/web/src/themes/portal.css`, включается
`:root[data-theme="portal"]`, слоем поверх `tokens.css`/`global.css` — наша тема
остаётся дефолтом, портальная — опциональный флаг `VITE_THEME=portal` в
`src/lib/env.ts`/`main.tsx`):

| Токен | Значение | Источник |
|---|---|---|
| `--bg` | `#FDF9ED` | фон страниц во всех 3 снэпшотах |
| `--ink` | `#2C2A28` | самый частый hex вообще — основной текст |
| `--accent` | `#8F3D42` | CTA-кнопка поиска (см. п.3 выше) |
| `--font-display` | `"Playfair Display", Georgia, serif` | заголовки во всех 3 снэпшотах |
| `--radius` | `16px` | самое частое «круглое, не пилюля» значение (варианты 4/8/12/16/24/32) |
| `--radius-pill` | `999px` | пилюли/круглые кнопки шапки и поиска |

Честно НЕ переопределено (источник не даёт основания): `--ok`/`--warn` (в снэпшотах
нет заметных семантических цветов успеха/предупреждения — наследуются от дефолтной
темы), `--font-mono`, тёмный режим (портал светлый, в снэпшотах `prefers-color-scheme`
не встречается вообще). Из-за этого в `portal.css` умышленно нет
`@media (prefers-color-scheme: dark)`-блока — каскад устроен так, что
`:root[data-theme="portal"]` идёт в бандле ПОСЛЕ `tokens.css`, поэтому светлый
портальный набор выигрывает даже при системной тёмной теме (без этого при
`VITE_THEME=portal` на устройстве с тёмной темой получилась бы мешанина «портал
местами, наша тёмная тема местами» — проверил именно этот сценарий отдельно).

Визуально проверено (Browser-пейн, `localStorage` для обхода онбординга — тот же
приём, что и раньше в сессии, поскольку MSW Service Worker не регистрируется в этой
песочнице, см. «Известные ограничения среды»): `/app/scan` под дефолтной темой и с
`document.documentElement.dataset.theme = "portal"` — раскладка и структура экрана
идентичны, меняются только цвета/шрифт/радиусы (тёмная бумага/бордо → светлый
кремовый фон, засечки Playfair Display в заголовке, бордовая пилюля кнопки). Это же
доказано автоматически (см. «Тесты» ниже) — глазами лишь подтверждено дополнительно,
не единственное доказательство.

### Пробел в контракте: форма поля `card`

`contracts/image-scan.md` v0.4 описывает rich-ответ как `{slug, card, confidence: {…},

### OCR-плагин и `lib/nativeOcr.ts`: остались, но не используются

`apps/shell/plugins/ocr-plugin` (Swift/Vision, полностью рабочий и слинкованный —
см. «Сборка под симулятор» выше) и `src/lib/nativeOcr.ts` **не удалены** —
компилируются, тесты (`lib/nativeOcr.test.ts`) по-прежнему зелёные — но `ScanScreen`

клиентского OCR→текст на серверный CV-поиск по самому изображению, одинаковый для

внутренний усилитель точности, а не замена). Оставил код в дереве осознанно, а не
удалил: он честно рабочий, задел на случай, если понадобится клиентская
предобработка/подсказка текстом, и удаление сейчас — это удаление рабочего решения
без причины, кроме «сейчас не используется».

### Реальный баг, найденный по пути: имя файла в `apiClient.ts`

И `scanOcr`, и новый `scanPhoto` шлют `multipart/form-data`. При добавлении
`scanPhoto` обнаружилось, что `scanOcr` **всегда** отправлял третьим аргументом
`form.set(...)` жёсткую строку `"label.jpg"` — реальное имя файла, который выбрал
пользователь, никогда никуда не уходило. Не баг этой волны, но задет тем же кодом —
поправил сразу для обоих методов через общий хелпер:

```ts
function photoFileName(image: Blob): string {
  return "name" in image && typeof (image as File).name === "string" && (image as File).name
    ? (image as File).name
    : "label.jpg";
}
```

`"label.jpg"` остаётся честной заглушкой только для случая, когда на входе
буквально `Blob` без имени (нет `.name` вообще) — не потеря, а единственно
доступный дефолт. Регрессия закрыта отдельным тестом на реальном транспорте (см.
ниже) — эмуляция мока не поймала бы саму потерю имени, это баг сериализации, а не
бизнес-логики.

### Тесты

Новое/изменённое под эту волну (сверх исходных 56 — итог **64/64, 16 файлов**):

| Файл | Что проверяет |
|---|---|
| `app/scan/ScanScreen.test.tsx` | *переписан целиком*: уверенный матч → одна карточка, без экрана вариантов и без `94%` в разметке; аналоги из ответа кликабельны → карточка нужного вина; «Спросить сомелье об этом вине» → чат с префиллом; `not_in_catalog` → честное сообщение + похожие/аналоги, без выдуманной карточки; drag-and-drop = тот же путь, что и выбор файла; тихая подпись есть, чекбокса нет; + 3 теста текстового пути (не изменились по сути, но живут в этом же файле) |

**Архитектурная деталь, стоившая отдельного расследования:** jsdom-реализация
`File`/`FormData`, при настоящей сериализации через нативный `fetch()`, **молча
теряет имя файла** (на проводе всегда уходит `filename="blob"`, что бы ни было
передано третьим аргументом `form.set()`), а серверный multipart-парсер (`undici`,
внутри Node) на этом же теле падает внутренней ассерцией при `request.formData()` —
кросс-реализационная нестыковка jsdom-класса и нативного парсера, не баг ни в одном
из них по отдельности. Из-за этого `scanPhoto` тестируется в двух архитектурно
разных файлах: `ScanScreen.test.tsx` (jsdom, `vi.spyOn(apiClient, "scanPhoto")` —
проверяет UI-поведение, не транспорт) и `apiClient.scanPhoto.node.test.ts`
(`@vitest-environment node`, настоящие `File`/`fetch` — проверяет ровно транспорт,
которого jsdom не может проверить честно). Раздельные MSW-хендлеры в
node-тесте — намеренно: относительные пути в `mocks/handlers.ts` не резолвятся под
чистым Node без `window.location`, поэтому там свой абсолютный оверрайд-хендлер, а
не дублирование бизнес-логики мока.

Полный прогон после этой волны: **`npx tsc -b --noEmit` чист, `npx vitest run` —
64/64 (16 файлов), `npm run build` чист (296 модулей)**; отдельно проверено
`VITE_THEME=portal npm run build` — литерал `"portal"` компилируется прямо в бандл
(флаг резолвится статически на сборке, не в рантайме).
