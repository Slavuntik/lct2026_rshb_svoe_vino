## Как запустить

Одноразово ничего готовить не нужно — `make` сам поднимает `qa/.venv` (uv, Python 3.12):

```bash
cd /Users/vyacheslavfokin/ClaudeWorkspace/vines/svoy-somelye

make demo-pack WINERY=abrau-dyurso     # DoD: одна команда -> qa/packs/abrau-dyurso/{pack.md,pack.json}
make demo-pack WINERY=alma-valley      # второй пак, для проверки универсальности генератора
make demo-pack-all                     # оба разом

make qa-test                           # pytest demo_pack.py, без сети (быстрый, детерминированный)
make qa-test-network                   # то же + один тест с реальными HEAD на vino-svoe.ru
make qa-e2e                            # ставит chromium (~250 МБ, один раз) + playwright против apps/web mock
make qa-e2e-real                       # то же, но против настоящего apps/api (RAG_PROVIDER=real) — волна 3
make qa-test-all                       # все тесты агента F разом (mock)
make qa-clean                          # удалить сгенерированные паки (пересборка с нуля)
```

`UV` по умолчанию `~/.local/bin/uv` (как в ORCHESTRATION.md), переопределяется `UV=<путь>`.

### Накладка при первом прогоне e2e (исправлено, не блокер)

Фикстура `dev_server` поднимает `npm run dev` и ждёт готовности по `http://127.0.0.1:5199`.
На этой машине Vite слушает **только IPv6-loopback** (`[::1]`, подтверждено `lsof`) —
`127.0.0.1` отвечал `connection refused`, все 24 теста уходили в skip с honest-причиной
(таймаут 30 c), хотя сервер поднимался за 71 мс. Исправлено: хост — `localhost` (резолвится
через `getaddrinfo` в тот же `::1`), а не жёсткий `127.0.0.1`. После фикса — стабильно
зелёно на нескольких прогонах подряд. Раздел «Предложения» ниже — на будущее для других
агентов, если кто-то ещё будет поднимать dev-сервер программно на этой машине.

Отдельно: `qa/test_demo_pack.py` и `qa/e2e/*` изначально были двумя независимыми `conftest.py`
без `__init__.py` — при раздельном запуске (как в `Makefile`, единственный документированный
способ) всё работало, но комбинированный запуск (`pytest qa/e2e test_demo_pack.py` или просто
`pytest qa/`) падал `ImportError` из-за коллизии модуля `conftest` под одинаковым именем в двух
местах. Добавлен `qa/e2e/__init__.py` (пакет `e2e`), импорты в тестах `e2e/` переведены на
относительные (`from .helpers import …`) — теперь и раздельный, и комбинированный запуск
(`pytest qa/`, 60/60) зелёные из любой рабочей директории.

## Наблюдения по клиенту C (зафиксировано, НЕ чинил чужую зону)

1. **`ProfileScreen.tsx` — сообщение об успехе апгрейда гостя технически недостижимо.**
   `handleUpgrade()` одним и тем же React-рендером выставляет `accountKind="registered"` и
   `upgradeStatus="done"`. Параграф с текстом `profile.guestSuccess` («Аккаунт создан —
   свайпы и профиль теперь сохраняются.») лежит ВНУТРИ `{accountKind !== "registered" &&
   (<form>…)}` — форма (а с ней и это сообщение) размонтируется в тот же момент, когда
   должна была бы показать текст. Пользователь никогда не видит этой фразы — только
   исчезновение формы и смену бейджа «Гостевой доступ» → «Полный аккаунт». Не блокер (сам
   апгрейд работает, наблюдаемый сигнал успеха есть, просто не тот, что написан в словаре
   `ru.ts`) — e2e-тесты (`qa/e2e/test_taste_and_profile.py::test_guest_upgrade_changes_
   badge_and_unmounts_form`) сознательно проверяют реальное поведение, а не недостижимый
   текст, с комментарием на месте.
2. **`TastePassportScreen.tsx` гейтит свайпы только по `accountKind`, не по факту согласия
   `profiling`.** Гость, явно отметивший скоуп «Вкусовой профиль» на онбординге (чекбокс
   есть, `POST /consents {scopes:["profiling"]}` реально уходит и в моке реально
   принимается), всё равно упирается в честный, но безусловный экран-приглашение — гейт
   проверяет `storage.getAccountKind()==="guest"` при монтировании, без обращения к
   фактическому состоянию согласий. Единственный путь к настоящим свайпам — полный апгрейд
   до `registered` (который заодно молча проставляет `profiling: true` и в моке). По духу
   контракта («Гость может scan/chat/wines/analogs; swipes и профиль требуют полноценной
   регистрации») это не противоречие, но делает сам чекбокс «Вкусовой профиль» на
   онбординге функционально бесполезным для гостя — если продукту важно честно отражать
   состояние согласий на этом экране, стоит решить это явно в следующей волне C.

Оба пункта — наблюдения для отчёта, не блокеры demo-ready: обе сцены по брифу (скан → чат →
аналог) от них не зависят, паспорт вкуса в сценарии — бонус, а не одна из трёх сцен пака.
