## Что сделано

Полный CV-пайплайн «Своё Вино» до приезда датасета кейса — всё, что от него не зависит:

- **Аугментатор 3D-ракурсов** (`cv/augment.py`) — по мотивам arXiv:2404.08820: эталонное
  фото (после кропа к этикетке) наклеивается на цилиндр, виртуальная камера рендерит его
  под новым ракурсом через честный ray-casting (пересечение луча с цилиндром), не плоским
  `warpPerspective` — угловые искажения и light falloff по кривизне получаются из геометрии.
  Поверх — блики-полосы, расфокус/смаз, шум, композит с процедурным фоном (полка/рука/
  нейтральный), вариации экспозиции и "зума" (насколько близко сфотографировано). Детерминировано
  по seed, ≥ 20 ракурсов из одного эталона (по умолчанию 24).
- **Нормализация запроса** (`cv/normalize.py`): детект области этикетки (классический CV —
  силуэт бутылки по контрасту с фоном рамки кадра, этикетка = нижние ~2/3 силуэта; без
  обучаемого детектора, v1 по брифу) → кроп → приближённая обратная развёртка цилиндра
  (перспективное выравнивание + компенсация краевого сжатия) → фотометрия (мягкие CLAHE +
  серый мир). Флаг `enabled=False` для A/B — используется и `search()`, и eval.
- **Обвязка SigLIP 2** (`cv/encoder.py`): `transformers.AutoModel` + `AutoProcessor`,
  автовыбор устройства (mps > cuda > cpu), L2-нормированный эмбеддинг, дисковый кэш по
  sha256 пикселей. Чекпойнт и обоснование — раздел "Модель" ниже.
- **ImageIndex** (`cv/index.py`, `cv/store.py`) — контракт буквально: `embed/search/build/add`,
  `Match(slug, score, gap, view)`. Бэкенд `qdrant_embedded` (без Docker); мульти-ракурсная
  укладка (на позицию — эталон + N синтетических точек), схлопывание в позиции (лучший
  скор/ракурс на slug), `gap` — отрыв от первой позиции ВНЕ группы близких скоров (near-dup
  позиции естественно попадают в одну группу и не портят gap, см. "Предположения").
- **CLI** (`cv/cli.py`): `cv build-index --refs <dir|csv> --version`, `cv search <photo>`,
  `cv bench` (тайминги embed по устройствам + полный `search()`), `cv selfcheck` (self-match).
- **OCR-верификатор** (`cv/verify.py`, ревью 04 блокер 1) — `LabelVerifier.verify(image,
  candidates: list[VerifyCandidate]) -> str | None` по контракту v0.4.4: PaddleOCR (`lang=
  "ru"`, кириллица+латиница) на нормализованном регионе этикетки → токены года (19xx/20xx),
  объёма, категории (regex + словарь ключевых слов) → сопоставление с `name`/`vintage`
  кандидатов → slug при однозначном совпадении, иначе `None` (воздержание — норма). p95
  513 мс (бюджет ≤700 мс). Подробности — раздел "OCR-верификатор" ниже.
- **Полевой приём** (`cv/imageio.py`, ревью 04 блокер 2) — `ImageOps.exif_transpose()` при
  декодировании (телефонные JPEG почти всегда пишут поворот в EXIF, не в пикселях) и HEIC
  (`pillow-heif`, дефолт камеры iPhone) как обычный формат для `decode_image()`.
- **`ImageIndex.index_version`** (ревью 04 блокер 5) — property из манифеста, для
  `/v1/metrics/scan` у B.
- **Дев-фикстуры** (`packages/cv/devfix/`, гитигнорены): 56 фото бутылок, скачаны вежливо
  (1 rps, свой User-Agent, идемпотентно) скриптом `scripts/fetch_devfix.py` по `image_url`
  из `pipeline/catalog/wines/*.json` — включая ОБЕ near-dup позиции `aligote-barrel-2024` и
  `aligote-barrel-2025` (буквально один и тот же файл фото на сайте каталога, см.
  `devfix/manifest.json`). Не датасет кейса.
- **74 pytest-теста** (`packages/cv/tests/`) — все пункты брифа плюс контракт-level юниты.

## Как запустить

```bash
cd packages/cv
~/.local/bin/uv venv --python 3.12 .venv && source .venv/bin/activate
~/.local/bin/uv pip install -e ".[dev]"

# Дев-фикстуры (не входят в git) — один раз, ~1 минута (1 rps к api.vino-svoe.ru)
python3 scripts/fetch_devfix.py --n 56

# Модель SigLIP2 (~1.3 ГБ) скачивается при первом обращении к энкодеру — см. "Модель" ниже
# про скорость без HF_TOKEN. Кэш — стандартный HF (~/.cache/huggingface) или свой:
export HF_HOME="$(pwd)/.hf_cache"   # опционально, держит кэш модели внутри пакета

# PaddleOCR (LabelVerifier) качает модели детекции+распознавания (~150 МБ) при первом
# обращении, отдельно от HF_HOME — в ~/.paddlex/official_models/; офлайн после первой загрузки.

cv build-index --refs devfix --version dev-$(date +%Y%m%d)   # или: python3 -m cv.cli ...
cv selfcheck --fixtures devfix
cv bench --fixtures devfix --devices mps,cpu
cv search devfix/aligote-barrel-2024.webp
```

## Модель: выбор и обоснование

**Выбран `google/siglip2-base-patch16-224`** (env `CV_MODEL`, переопределяемо).

SigLIP2 официально выпускается в размерах base / large / so400m (giant) — крупнее base
модели в 3-10 раз по параметрам. HF без токена качает заметно медленно (наблюдалось
эмпирически: ~10 минут на ~1.3 ГБ base-чекпойнта на этой сети — см. `Warning: You are
sending unauthenticated requests to the HF Hub` в логе); скачивание large/so400m для
прямого сравнения не уложилось бы в разумный бюджет этой волны. Решение: взять МЕНЬШИЙ
официальный чекпойнт как более быстрый и практичный (следуя духу брифа "выбирай чекпойнт
по замеру" — замер сделан на нём, бюджет учтён), с запасом обосновать это самим замером:

```
устройство   p50      p95      max      (10 замеров, encode() без кэша, эталон 258×630)
mps          23.4 мс  24.2 мс  24.2 мс
cpu          45.1 мс  46.4 мс  46.4 мс
```

Оба — с большим запасом (>10×) от цели брифа "embed ≤ 300 мс/фото на MPS", и от CPU-бюджета
кейса (SLA всего пайплайна ≤ 3 c). Официальные полные цифры (100 замеров на 56 дев-фикстурах,
p50/p95/max/mean на MPS и CPU) — раздел "Метрики" ниже. При таком запасе апгрейд на `large`
имеет смысл рассматривать ТОЛЬКО если качество (self-match/F1) на реальном датасете кейса
окажется недостаточным — переключение чекпойнта: одна env-переменная, без изменений кода.

Технический нюанс (transformers 5.17.0): `Siglip2Model.get_image_features()` возвращает
не голый тензор (как в более старом CLIP-подобном API), а `BaseModelOutputWithPooling` —
нужный эмбеддинг лежит в `.pooler_output` (768-мерный для base). Обработано в
`cv/encoder.py` с fallback на голый тензор для другой версии/чекпойнта.

## OCR-верификатор: реализация и бюджет (ревью 04, блокер 1)

**Зачем отдельно от ImageIndex.** SigLIP2-эмбеддинг реагирует на общий облик этикетки
(цвет, композиция, иллюстрация) — у near-dup семьи (одна этикетка, разные год/категория/
объём) это визуально ОДНА И ТА ЖЕ картинка, ANN принципиально не может их развести (см.
"Предположения" п.5 — `aligote-barrel-2024/2025` даже эталонные фото буквально идентичны).
Год/объём/категория — мелкий печатный текст, эмбеддинг его не разрешает, OCR — да.

**Пайплайн `verify()`:** `decode_image()` (ValueError на битые байты, до всего остального)
→ `normalize_query()` (ТОТ ЖЕ детект+кроп+развёртка+фотометрия, что видит `ImageIndex.
search()` — OCR получает стабилизированный регион этикетки, не сырое фото целиком) →
даунскейл до 320px (см. "Бюджет" ниже) → `PaddleOCR(lang="ru").predict()` → токены из
`rec_texts`/`rec_scores` (только куски с confidence ≥ 0.5) → `match_candidates()`.

**Сопоставление (`match_candidates`, чистая функция — тестируется без OCR-движка):**
regex извлекает год (`(?:19|20)\d{2}` с границами не-цифра — не путает с объёмом в мл или
артикулом), объём (`0.75|750|0.5|500|1.5|1500` + опциональная единица) и категорию (словарь
ключевых слов рус+лат: брют/сухое/резерв/...). Скоринг кандидата: год из `vintage`
(структурное поле каталога, надёжнее текста) — вес 2, год из `name`-строки — тоже 2, объём/
категория — по 1. Побеждает кандидат со СТРОГО наибольшим скором; ничья или нулевой скор у
всех → `None`. Пустой список кандидатов → `None` без обращения к OCR вообще.

**Бюджет ≤700 мс p95 — замерено, выполнено с запасом:**

```
cv/verify.py::benchmark(), 30 замеров, читаемый синтетический ракурс (после прогрева —
загрузка модели ~3.2 с, один раз за время жизни процесса, не входит в p95 запроса)

p50 = 447 мс   p95 = 513 мс   max = 557 мс
```

Доминирующий рычаг бюджета — размер входа OCR-детектора: на полном 448px нормализованном
кадре p95 был ~800-950 мс (НАД бюджетом); даунскейл до 320px перед `predict()` держит тот
же текст читаемым (проверено: тот же распознанный текст, тот же результат сопоставления на
448/320/256/192px) и укладывается в бюджет с запасом. Деталь чекпойнта: авто-выбор PaddleOCR
для `lang="ru"` взял детектор `PP-OCRv5_server_det` (более тяжёлый вариант) — явная попытка
форсировать `PP-OCRv5_mobile_det` упёрлась в сетевой сбой при скачивании (тот же класс
проблем, что и с HF — см. "Модель"); даунскейл входа решил бюджет без необходимости
чекпойнта полегче, поэтому не форсировал — при повторной попытке в день датасета мобильный
детектор может дать дополнительный запас.

**Тесты (`tests/test_verify.py`, 21 штука):**
- юниты `match_candidates()`/регэкспов (14, без OCR — быстрые, много граничных случаев:
  неоднозначность, отсутствие сигнала, конфликт vintage/name, tie-break по категории);
- `verify()` на битых байтах → `ValueError` (до OCR, тот же контракт, что у `ImageIndex`);
- пустой список кандидатов → `None` без обращения к OCR;
- **DoD оркестратора**: пара `aligote-barrel-2024`/`2025` различается по году НА
  СИНТЕТИЧЕСКОМ РАКУРСЕ С ЧИТАЕМЫМ ГОДОМ, сгенерированном `cv.augment.render_synthetic_
  views()` — собственный эталон той же формы, что каталог (тёмное "стекло" + светлая
  этикетка в нижних 2/3, крупный текст с годом), т.к. настоящее фото `aligote-barrel-2024.
  webp` в devfix (258×630, студийное фото каталога) не несёт печатного года достаточно
  крупным планом для надёжного детерминированного теста на этом разрешении — см.
  "Предположения" п.8. `seed=0`, ракурс `[0]` — читаемый (год распознаётся), ракурс `[1]` —
  уже размыт/обрезан до нечитаемого (воздержание) — оба случая явным тестом;
- бюджет p95 ≤ 700 мс (тест выше).

## Предположения и решения, не зафиксированные контрактом

Контракт `image-scan.md` описывает интерфейс и намерение, но не каждую деталь реализации —
ниже то, что пришлось решить самостоятельно, с обоснованием.

1. **Конвенция порядка файлов в `build(refs, version)`.** Контракт: `slug -> список файлов
   (эталон + синтетические ракурсы)`, без указания, как отличить эталон от синтетики внутри
   списка. Решение: **первый элемент списка — эталон ("real"), остальные — "synth-N" по
   позиции** — именно так `cv.augment.save_synthetic_views()` пишет файлы на диск. Простая,
   не требует парсинга имён файлов.
2. **`add(slug, images)` — что такое `images`.** Контракт даёт только сигнатуру с комментарием
   "+50 позиций/день без ребилда", не уточняя, эталон это или уже готовые ракурсы. Решение:
   каждый элемент `images` — САМ ЭТАЛОН новой позиции (типично длина списка 1, в духе
   case.md "по одной эталонной фотографии на позицию") — `add()` сам прогоняет аугментатор
   и апсертит эталон+ракурсы в ту же коллекцию Qdrant (инкрементальный upsert не требует
   пересборки остального индекса — ровно то, что просит контракт).
3. **`Match.gap` — "отрыв от следующего НЕ-той-же-группы кандидата".** Контракт даёт
   докстринг-формулировку, не алгоритм. Решение: цепная кластеризация уже отсортированных
   по score позиций (сосед — той же группы, если разница с ПРЕДЫДУЩИМ ≤ `CV_GROUP_EPSILON`,
   0.03 по умолчанию для L2-нормированных векторов/косинуса) — `gap` для каждой позиции = её
   score минус score первой позиции вне её группы. Near-dup позиции (визуально почти
   идентичные — см. п.5) естественно попадают в одну группу, их взаимная близость не портит
   gap — именно этого просит контракт ("не убегает" из-за одной аномально близкой пары).
4. **Бэкенд `pgvector`.** Контракт называет его "прод-профилем в compose". На этой машине
   нет Docker/Postgres — не реализован. `cv/store.py::get_store()` бросает явный
   `NotImplementedError` с объяснением при `IMAGE_INDEX_MODE=pgvector`; интерфейс
   `ImageIndex`/`QdrantStore` спроектирован так, чтобы такая реализация добавлялась без
   изменений в остальном пакете (зеркалит `packages/rag/rag/store.py`, где та же развилка
   embedded/сетевой Qdrant уже решена для другого агента).
5. **Near-dup группы для self-match метрики (`cv/selfcheck.py::NEAR_DUP_GROUPS`).** Бриф
   прямо говорит: "near-dup: пара 2024/2025 попадает в одну группу кандидатов (различать
   будет OCR — не ты)". Т.е. CV СТРУКТУРНО не обязан и не должен различать
   `aligote-barrel-2024`/`aligote-barrel-2025` — их эталонные фото в каталоге буквально один
   и тот же файл (`devfix/manifest.json`: одинаковый `image_url`/sha256). Self-match top-1,
   попавший в СОСЕДНЮЮ near-dup позицию, засчитан как успех, а не провал — иначе метрика
   штрафовала бы за информацию, которой в кадре структурно нет (это не ослабление теста
   "чтобы прошёл" — наоборот, БЕЗ этой поправки тест наказывал бы корректное поведение).
   Список из одной известной пары; расширяется по мере появления новых known-групп (в
   датасете кейса такие группы, вероятно, будут в дампе БД явно или выводимы по
   winery+name без vintage — на усмотрение оркестратора/следующей волны).
6. **Синтетические фоны, не фото со стока.** "Полка"/"рука"/"нейтральный" фон аугментатора —
   процедурная генерация (numpy/cv2 примитивы: полосы, блюр, шум, эллипсы), не реальные
   фотографии — осознанно, чтобы не тащить в пайплайн лицензированный контент только ради
   фона аугментации.
7. **Реальный энкодер во всех pytest'ах, требующих self-match/near-dup/add.** Не мокирован —
   бриф явно требует ЧИСЕЛ (self-match rate, p95), которые без реальной модели не имеют
   смысла проверить. Это делает часть тестов медленнее (~секунды, не миллисекунды) и требует
   один раз скачанную модель — задокументировано в "Как запустить".
8. **Тестовый эталон для DoD OCR-верификатора — не настоящее фото devfix, а собственный
   синтетический "лейбл".** Задание оркестратора буквально просило проверить пару
   `aligote-barrel-2024/2025` — но их РЕАЛЬНОЕ фото в devfix (258×630, студийный кадр
   каталога) слишком мелкое, чтобы год на этикетке гарантированно читался OCR после кропа
   и даунскейла до 320px НЕЗАВИСИМО от конкретного ракурса; тест на нём был бы хрупким
   (иногда проходит, иногда нет, в зависимости от везения с конкретными пикселями). Решение:
   построил свой эталон той же СТРУКТУРЫ, что и настоящий каталог (тёмное "стекло" + светлая
   этикетка в нижних ~2/3 кадра — ровно то, что ожидает мой же детектор), с крупным читаемым
   текстом "ALIGOTE BARREL <год> SUHOE 0.75L", и прогнал его через настоящий
   `render_synthetic_views()` (не сырое изображение напрямую) — буквально выполняя "сгенерируй
   такой аугментатором" из задания. Slug'и в `VerifyCandidate` — настоящие
   (`aligote-barrel-2024`/`2025`), только пиксели эталона синтетические.
9. **Словарь категорий (`_CATEGORY_KEYWORDS`) — не полный `pipeline/ref/taxonomy.yaml`.**
   Минимальный набор ключевых слов (брют/сухое/полусухое/полусладкое/сладкое/резерв/
   крепленое, рус+лат), достаточный для tie-break внутри near-dup семьи по объявлению кейса
   ("год, категория, объём с этикетки" — contracts/image-scan.md, "Пайплайн /scan/photo").
   `taxonomy.yaml` — справочник пайплайна данных vines (read-only, не моя зона) — расширение
   словаря до него дешёвое, но не сделал превентивно без явного сигнала, что текущего набора
   не хватает на реальных near-dup семьях датасета кейса.
10. **PaddleOCR `lang="ru"` (не отдельные проходы ru+en).** Русские вина — контракт
    ("кириллица + латиница") видимо ожидает единый проход; `lang="ru"`
    (модель `eslav_PP-OCRv5_mobile_rec`) на практике читает И цифры, И латинские слова
    (проверено: "ALIGOTE BARREL", "SUHOE 0.75L" распознаны корректно на моём тестовом
    эталоне) — общий алфавит с кириллицей в этом движке. Отдельный проход латинской моделью
    удвоил бы бюджет (уже впритык к 700 мс) ради, вероятно, нулевого выигрыша на
    цифрах/коротких латинских словах — не стал делать превентивно.
11. **`ImageIndex._manifest_path` по умолчанию — из `self.store.path`, не из
    `config.MANIFEST_PATH`.** Найдено при интеграции B (коммит `f87768e`): модульные
    константы `cv/config.py` резолвятся ОДИН РАЗ при первом импорте пакета — если
    env/аргументы выставляются ПОСЛЕ этого (типично для изолированных тестов/инструментов,
    создающих несколько `ImageIndex` на разные `store` в одном процессе), второй индекс
    по умолчанию читал манифест ПЕРВОГО (общая глобальная константа). Фикс: дефолт
    `manifest_path = self.store.path / "manifest.json"` — резолвится лениво, в момент
    конструирования КОНКРЕТНОГО `QdrantStore`, так что у разных `store` разные манифесты
    сами по себе. Смена дефолтного расположения на диске (было `DATA_DIR/manifest.json`
    рядом с `qdrant/`, стало `DATA_DIR/qdrant/manifest.json` внутри) — не проблема для
    вызывающего кода, если он читает версию через property `index_version`, а не напрямую
    по пути (контракт и это задание оркестратора именно так и предполагают).

## Важная находка (решена): build-time/query-time рассинхрон нормализации

Диагностика self-match заняла существенную часть этой волны — итог положительный (DoD
выполнен, см. "Метрики" ниже), но путь стоит зафиксировать, потому что вскрыл реальный баг,
не просто "недостаточно оттюненный порог".

**Симптом.** Первая работающая версия пайплайна давала self-match (`normalize=True`,
контрактный дефолт) всего ~67-84% в разных промежуточных состояниях — ниже DoD (≥90%) — при
том, что `normalize=False` (без нормализации вовсе) стабильно давал ~95-96%. Это выглядело
так, будто нормализация РЕАЛЬНО ВРЕДИТ, что противоречило бы подсказке case.md
("нормализация заметно улучшает F1").

**Диагноз (ablation по компонентам).** Отключая геометрию/фотометрию по отдельности и
разглядывая конкретные проваленные примеры (сохранял и открывал промежуточные кадры на
каждом шаге пайплайна), нашёл ДВА независимых источника ошибки:

1. **Баг детектора этикетки** — первая версия `detect_label_region` (скоринг отдельных
   Canny-контуров) на кадрах, где содержимое занимает БОЛЬШУЮ часть кадра (типично для уже
   кадрированных синтетических ракурсов аугментатора), систематически проваливалась в
   мусорный под-контур: блик или блестящий капсюль набирали более высокий точечный
   "текстурный" скор, чем весь настоящий блок этикетки. Промежуточная версия на сглаженной
   saliency-карте не устранила проблему принципиально. **Фикс**: структурный подход —
   грубый силуэт бутылки по контрасту с фоном РАМКИ кадра (`_foreground_bbox`, медиана+MAD,
   устойчива к полосатым синтетическим фонам), затем "этикетка = нижние ~2/3 силуэта" —
   простой факт о бутылочной фотографии, не текстурная эвристика, которая раз за разом
   ломалась на глянцевых капсюлях/бликах.
2. **Настоящий баг рассинхрона доменов (главная причина оставшейся просадки после фикса
   детектора).** `ImageIndex.build()` прогонял `normalize_query()` только через "real"-ракурс
   (эталон), а "synth"-ракурсы заносил в индекс СЫРЫМИ — уже отрендеренными
   `cv.augment.render_synthetic_views()`, без повторного детект+кроп+фотометрия. При этом
   `search()` ВСЕГДА нормализует запрос (контракт). Результат: запрос (после нормализации) и
   его ближайшие соседи в индексе (synth-ракурсы ТОЙ ЖЕ позиции, БЕЗ нормализации) жили в
   разных "визуальных доменах" — как если бы модель обучалась на одних данных, а
   инферилась на распределении, чуть сдвинутом относительно него. **Фикс**: `build()`/`add()`
   теперь прогоняют `normalize_query()` через КАЖДЫЙ ракурс (и "real", и "synth") — тот же
   пайплайн, что видит `search()`, без исключений (см. `cv/index.py`).

Попутно смягчена фотометрия (`clipLimit` CLAHE 2.5→1.2, диапазон gain серого мира
0.8-1.25→0.92-1.08) — агрессивные учебниковые значения заметнее уводили эмбеддинг
SigLIP2-base от "естественного" распределения, чем помогали устранить блики; и добавлена
рандомизация "зума" аугментатора (`fill_frac`, 0.55-0.88 доли кадра) — фиксированный высокий
зум усугублял п.1 на близких ракурсах.

**Итог**: с обоими фиксами self-match `normalize=True` (контрактный дефолт) вырос до
**93.9%** — см. "Метрики" ниже, DoD выполнен с запасом.

## Метрики (официальный прогон: `cv build-index` + `cv selfcheck` + `cv bench`, дев-фикстуры — 56 позиций, эта машина, MPS=Apple M5)

### Self-match (DoD: ≥ 90%)

```
cv selfcheck --fixtures devfix --views 5   (56 позиций × 5 свежих holdout-ракурсов = 280)

top1_rate = 0.9393  (263/280)   normalize=True (контрактный дефолт search())
```

Near-dup пара (`aligote-barrel-2024`/`aligote-barrel-2025`) засчитана как взаимный успех
(см. "Предположения" п.5) — без этой поправки цифра ниже, но не потому, что CV ошибается:
эти два эталона в каталоге — буквально один и тот же файл фото, различить их по
изображению структурно невозможно (это работа OCR-верификатора).

### Латентность embed() — SiglipEncoder.benchmark(), 100 замеров, без кэша

```
устройство   p50      p95      max      mean
mps          23.5 мс  24.5 мс  138.2 мс  24.8 мс
cpu          45.9 мс  47.2 мс   64.8 мс  46.2 мс
```

Цель брифа "≤ 300 мс/фото на MPS" — выполнена с запасом ×12. MPS max=138мс — единичный
выброс (вероятно, thermal/scheduling джиттер на расшаренной с другими процессами машине),
не системный; p95 стабилен и близок к p50 на обоих устройствах.

### Латентность полного `search()` — 56 свежих синтетических ракурсов (не байты уже
проиндексированных фикстур — иначе кэш эмбеддингов тривиально "угадывает" ответ)

```
p50 = 29.6 мс   p95 = 30.8 мс   max = 26 799 мс
```

p50/p95 (нормализация + embed на MPS + ANN по ~1400 векторам + схлопывание в позиции) — с
огромным запасом от SLA кейса (≤ 3 с). **max — не баг, а холодный старт**: первый вызов
`search()` в бенчмарке создаёт СВЕЖИЙ `ImageIndex()` (свой `SiglipEncoder`, ещё не
загрузивший веса) — загрузка модели + первая MPS-компиляция кернелов действительно занимает
~27 с (совпадает с отдельно измеренным "first encode incl. model load" ~31 с). В реальном
сервисе это решается прогревом (`encoder.encode()` на dummy-картинке) при старте процесса,
не на первом запросе — за пределами `packages/cv` (зона агента B/API), но стоит явно учесть
при интеграции.

## Предложения к контрактам

1. **`build()`/`add()` порядок файлов и семантика `images`** (см. "Предположения" пп. 1-2) —
   предлагаю зафиксировать явно при следующей правке контракта, чтобы другой агент/будущая
   версия не переизобретали конвенцию иначе.
2. **`gap`-семантика ("не той же группы кандидата")** реализована через порог `CV_GROUP_EPSILON`
   на score, откалиброванный вручную (не на голд-сете — его нет). После приезда датасета
   кейса стоит перепроверить порог на реальных near-dup парах каталога (их может быть
   значительно больше одной).
3. **Фотометрия сейчас намеренно мягкая (`clipLimit=1.2`, gain 0.92-1.08)** — учебниковые
   агрессивные значения (2.5, 0.8-1.25) на дев-фикстурах измеримо ХУЖЕ (см. "Важная
   находка"), но дев-фикстуры — синтетические ракурсы моего же аугментатора, не настоящие
   "у полки" фото с реальными жёсткими бликами/тенями, для которых case.md обещает пользу от
   нормализации. Рекомендация: как только появится публичный датасет кейса, перепроверить
   `clipLimit`/gain-диапазон именно на нём — вполне возможно, что для РЕАЛЬНЫХ фото более
   сильная коррекция снова окажется полезной (синтетика хороша для инженерной проверки
   пайплайна и отладки рассинхронов, но не заменяет реальные условия для калибровки
   конкретно этого компромисса).
4. **Словарь категорий `LabelVerifier` — минимальный, не `taxonomy.yaml`** (см. "Предположения"
   п.9). Если в день датасета обнаружится, что near-dup семьи чаще различаются категорией,
   которой нет в словаре, — расширить список дешевле, чем эта строка предложения.
5. **PaddleOCR детектор — `PP-OCRv5_server_det` (не `mobile_det`)** — авто-выбор, попытка
   форсировать более лёгкий вариант упёрлась в сетевой сбой при скачивании (см. "OCR-
   верификатор"). Бюджет 700 мс выполнен и так (даунскейл входа), но при следующей волне
   стоит повторить попытку — доп. запас на случай, если реальные фото кейса потребуют более
   крупного `ocr_size` для мелкого шрифта, чем 320px дев-фикстур.
