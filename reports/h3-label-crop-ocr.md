# H3 · Третий проход OCR по кропу этикетки (1280 px) + бикубика для мелких входов

Третий, независимый масштаб RapidOCR — детектор+распознаватель на КРОПЕ ЭТИКЕТКИ
(боксы переиспользуются из уже сделанного прохода 960, без новой детекции), плюс
бикубическое увеличение кропа перед КАЖДЫМ проходом (640/960/1280), когда кроп меньше
целевой стороны. Основание — `reports/label-crop-study.md`, `reports/h2-rapidocr.md`.

## 1. `cv/label_crop.py` (новый) — `label_bbox()`

Перенос ДОСЛОВНО из `qa/real_photos_label_crops.py::label_bbox` (та же арифметика,
константы, порядок операций — кластеризация по вертикали от крупного бокса ближе к
центру, поля, минимальный размер с ростом ВНИЗ 0.3/0.7). Эквивалентность прототипу
проверена fuzz-сравнением на 500 случайных наборах боксов (разовый скрипт, не
коммичу) — 0 расхождений, включая случай пустых боксов (`None`).

Тесты `packages/cv/tests/test_label_crop.py` (13) на синтетических боксах (кадр
1000×2000): фильтры скора/центра/высоты → `None`; одиночный бокс без кластеризации
(только поля); рост ТОЛЬКО по ширине (минимум 45% кадра, симметрично, центр не
смещается) и ТОЛЬКО по высоте (минимум 32%, с явной проверкой асимметрии — вниз
СТРОГО больше, чем вверх, числами 51.0 против 119.0 при add=170); слияние двух
вертикально близких боксов в один прямоугольник; исключение далёкого бокса (gap
больше `6×med_h`) и горизонтально несовпадающего бокса; отсечение по границам кадра.

## 2. `cv/ocr_rapid.py` — третий масштаб `CV_OCR_LABEL_SIZE`

`RapidOcrReader.read()`: после цикла по `self.sizes` (боксы масштаба `max(self.sizes)`,
по умолчанию 960, запоминаются без дополнительного вызова движка) — если
`self.label_size > 0`: `label_bbox()` по этим боксам → область масштабируется ОБРАТНО
к разрешению кропа бутылки, ПЕРЕДАННОГО в `read()` (то есть до какого-либо
даунскейла — "оригинал, полное разрешение" в терминах брифа) → вырезается → ресайз до
`label_size` → отдельный, третий, закэшированный движок (`_engines[label_size]`) →
текст добавляется в объединение. Область не найдена → проход пропускается (не
заменяется чтением всего кропа бутылки — измерено отдельно, пользы не даёт).

`CV_OCR_LABEL_SIZE` (дефолт 1280, `0` — выключено) читается ЖИВЬЁМ в
`RapidOcrReader.__init__` — НЕ в `cv/verify.py` (зона записи брифа не включает этот
файл): `LabelVerifier._rapid_reader()` не изменена, третий масштаб настраивается
целиком изнутри `ocr_rapid.py`. Движок `label_size` конструируется/греется ВСЕГДА
(даже без найденной области — например, на 2×2-плейсхолдере прогрева), симметрично
остальным `self.sizes`, чтобы первый боевой запрос не платил холодный старт.

### Находка приёмки (не из офлайн-тестов) — numpy `ndarray` в булевом контексте

Первая версия использовала `if not boxes or not source_hw` / `scores or ()` — прошла
все юнит-тесты (там `boxes` — python-списки), но живой API падал 400 Bad Request на
**каждом** фото с `CV_OCR_LABEL_SIZE>0`: `RapidOCROutput.boxes` реального движка —
`numpy.ndarray` формы `(N,4,2)` (`.scores` — тюпл, это иначе), и `not <ndarray с >1
элементом>` бросает `ValueError: The truth value of an array with more than one
element is ambiguous` (пойман `apps/api/app/routers/scan.py` как `validation_error`
400). Исправлено на `boxes is None or len(boxes) == 0` (проверено: реальный движок на
пустом кадре отдаёт `None`, не пустой список/массив). Тесты усилены: `_box()`/`_boxes()`
теперь строят НАСТОЯЩИЙ `numpy.ndarray` (N,4,2), добавлены регресс-тесты на пустой
ndarray и на multi-box ndarray — без них баг остался бы незамеченным до живого прогона.

## 3. Бикубика для мелких входов — `_resize_to_longest_side()`

Новая функция (используется ПЕРЕД КАЖДЫМ проходом — 640/960/1280, не только третьим):
кроп БОЛЬШЕ/РАВЕН `target` → делегирует `_downscale_to_longest_side()` (H2, не
тронута, её тесты как были); кроп МЕНЬШЕ → `PIL.Image.resize(..., BICUBIC)`
(аспект сохранён). `_downscale_to_longest_side()` осталась НЕИЗМЕННОЙ (не переименована,
не тронута) — новая функция строго аддитивна.

Тесты (`test_ocr_rapid.py`): точное совпадение с `Image.resize(..., BICUBIC)` на
случайном изображении, сохранение аспекта, отсутствие нулевых сторон, делегирование
при кроп>=target. Плюс интеграционный тест `read_center()`: кроп 93×140 (< 640 по
обеим сторонам) реально доходит до движка увеличенным до 425×640, не в исходном
размере. Обновлён один существующий тест H1/H2 (`..._when_no_downscale_needed`,
переименован в `..._crop_exactly_at_target_is_unchanged`) — его фикстура (93×140,
target 640) — ровно тот случай, который теперь ДОЛЖЕН увеличиваться; добавлена новая
фикстура на границе (`W=915` → кроп ровно 640) для сохранения покрытия "без ресайза
вообще, побитово".

Эмпирическая проверка "читает не хуже" — не только юнит-тестом (мокнутый движок), но
и РЕАЛЬНЫМ движком на сжатых фото через живой API (раздел 5 ниже): +3.2 п.п. (88.7%
→ 91.9%, 55→57/62) от одной только бикубики — сильнее и честнее синтетического
юнит-теста на 700px без реального текста.

## 5. Приёмка живым API (Mac, `packages/cv/data-d1`, `CV_FUSION_TEXT_SOURCE=ocr`,
`CV_OCR_ENGINE=rapid`, `CV_OCR_RAPID_SIZES=640,960`, `CV_FUSION_CROPS=2`, без VLM)

Порт 8790 (не 8080/8091/8093 — чужие процессы, не трогала). Каждая конфигурация
прогнана дважды подряд — числа идентичны на обоих прогонах, ошибок HTTP 0/100 везде.

| Конфигурация | top-1 (flat) | top-5 (rich) | p50 / p95 `timing_ms` (run1 / run2) |
|---|---:|---:|---:|
| `CV_OCR_LABEL_SIZE=0` (третий проход выкл.) | **91.9%** (57/62) | 98.4% | 372/471 · 376/494 мс |
| `CV_OCR_LABEL_SIZE=1280` (третий проход вкл.) | **91.9%** (57/62) | 98.4% | 528/700 · 562/766 мс |

Цель "не хуже 91.9%" — **выполнена** (равенство, не регресс, на обоих прогонах).
Цель "+1 фото (93.5%)" — **не достигнута** через живой API на этом наборе из 62 фото
(поштучное сравнение: 0 фото поменяли ответ в любую сторону между двумя
конфигурациями). Третий проход стоит +150…190 мс к p50 и +230…270 мс к p95 (третий
движок на кропе, обычно крупнее 640/960).

### Почему офлайн +1 (91.9%→ здесь тоже 91.9%, но НЕ +1) не воспроизвёлся живым API — разобрано, не списано на шум

Офлайн (`qa/real_photos_cpu_path.py --union rapid_640+rapid_960+lab_rapid_1280`)
воспроизведён и подтверждён (56→57/62, 90.3→91.9%, W=0.3 α=0.5) — единственное
конкретное фото, которое офлайн-объединение чинит: **95.36\_...** (истина
`winemaker-selection`, фото — тот самый пример из брифа: "WINEMAKER'S SELECTION").
Живой API этот конкретный ответ **не переворачивает** ни в одной из конфигураций
(`flat_slug` = сосед по семье в обеих). Разбор:

1. **Область этикетки идентична** — мой кроп в координатах ПОЛНОГО фото
   `(453, 2294, 2570, 3494)` побитово совпадает с `label-crops/boxes.json` (эталон
   `qa/real_photos_label_crops.py`, `n=50`) — `label_bbox()` и координатная
   математика работают верно, это не баг.
2. **Причина расхождения — офлайн-кэш `ocr_lab_rapid_1280.jsonl` посчитан НЕ из
   оригинала.** Прочитан текст с ТРЁХ источников для одного и того же бокса:
   - мой код (кроп из оригинала, полное разрешение 2117×1200, ресайз до 1280):
     `"…WINEMAKERSELECH 2025 2025"`;
   - тот же самый кроп, прочитанный из **сохранённого файла**
     `case-data/real-photos-labels/label-crops/050.jpg` (это
     `qa/real_photos_label_crops.py::main` сохраняет `lab.thumbnail((1600,1600));
     lab.save(..., quality=92)` — то есть уменьшенный до 1600px и пережатый JPEG
     q92, РАЗМЕР ФАЙЛА 1600×907): `"…WINEMAKERS SELECI 2025 2025"` — **побитово
     совпадает с кэшем `ocr_lab_rapid_1280.jsonl`**.
   
   То есть исследовательский скрипт, которым офлайн посчитан "+1 фото", читал
   пережатый JPEG-артефакт своего же контакт-листа, а не оригинал в полном
   разрешении — ровно то, чего брифа явно требует избегать ("кроп этикетки ИЗ
   ОРИГИНАЛА, полное разрешение"). Мой код это требование выполняет буквально
   (проверено выше побитовым совпадением бокса) — и именно поэтому получает НА
   ЭТОМ КОНКРЕТНОМ, пограничном слове другой (не обязательно худший) OCR-текст.
   Тот же класс находки, что H2 задокументировала для PIL/cv2 (два технически
   валидных пути дают разный текст ровно на грани разрешимости мелкого слова).
3. **Живой сдвиг в правильную сторону, просто недостаточный.** У фото 95.36 gap
   между top1 (`inkermanskiy-...-12`) и верным `winemaker-selection` **сократился**
   с 0.00476 (`CV_OCR_LABEL_SIZE=0`) до 0.00112 (`=1280`) — третий проход реально
   пододвигает верный ответ (более чем в 4 раза меньший разрыв), просто не
   перепрыгивает его в живой формуле слияния `cv.text_fusion` (другие веса/токенизация,
   чем упрощённый `qa/text_v2.py`, которым считан офлайн-кэш).

Итог: реализация корректна и соответствует букве брифа; конкретное "+1 фото" из
офлайн-обоснования не воспроизводится живым API по независимой от этой волны причине
(артефакт способа генерации ИСТОРИЧЕСКОГО кэша-обоснования, не моей реализации) — не
регрессия, не баг, задокументировано численно.

## 6. Имитация «мессенджера» — 100 фото, сжатые до 1000px по длинной стороне

Временный каталог (вне git, scratchpad сессии), те же имена файлов: EXIF-transpose,
`thumbnail((1000,1000), BICUBIC)`, пересохранены `.webp` quality=85 (оригиналы —
4000–4624px по длинной стороне, медиана 4032). Тот же живой API,
`CV_OCR_LABEL_SIZE=1280` в обеих конфигурациях (сравнивается ТОЛЬКО бикубика) — "без
бикубики" получена временным monkeypatch `cv.ocr_rapid._resize_to_longest_side ->
_downscale_to_longest_side` (разовый скрипт для этого замера, не коммичу — не
постоянный переключатель продукта, в брифе такого env нет).

| Конфигурация (сжатые фото) | top-1 | top-5 | p50 / p95 `timing_ms` |
|---|---:|---:|---:|
| с бикубикой (как есть, boевой код) | **91.9%** (57/62) | 96.8% | 445 / 663 мс |
| без бикубики (`_downscale_to_longest_side`, поведение до задачи 3) | **88.7%** (55/62) | 96.8% | 324 / 503 мс |

Бикубика даёт **+3.2 п.п. (+2 фото)** именно там, где по брифу и должна — на мелких
входах: с бикубикой сжатые 1000px-фото читаются НЕ ХУЖЕ полноразмерных (91.9% в обоих
случаях). Поштучно: **95.36\_...** (winemaker-selection — тот же пример, что в п.5,
на СЖАТОМ фото кроп этикетки уже < 1280px, бикубика включается и в этот раз ПЕРЕВОРАЧИВАЕТ
ответ) и **95.49\_...** (near-dup пара `zhemchuzhnaya-9-pino-nuar-muskat-rozovyj-1/2`)
переходят из неверных в верные; ни одно фото не испортилось. Стоимость: +120 мс к p50,
+160 мс к p95 (больше пикселей в OCR на увеличенных кропах).

## 7. Как запустить

```bash
# юниты
cd packages/cv && .venv/bin/python -m pytest -q            # 354 passed

IMAGE_PROVIDER=real VERIFIER_PROVIDER=real \
CV_DATA_DIR=$(pwd)/../../packages/cv/data-d1 CV_MODEL=google/siglip2-base-patch16-384 \
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 LLM_PROVIDER=mock RAG_PROVIDER=mock \

./.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8790 &
cd .. && apps/api/.venv/bin/python qa/real_photos_serve.py --api http://127.0.0.1:8790 --out /tmp/served.jsonl
cd packages/cv && .venv/bin/python ../../qa/real_photos_eval.py --served /tmp/served.jsonl --only __none__
# CV_OCR_LABEL_SIZE=0 на отдельном порту — та же процедура, для сравнения
```

## 9. Предложения оркестратору

1. **"+1 фото" цели брифа не достигнуто живым API**, хотя реализация верна и
   соответствует букве брифа ("из оригинала, полное разрешение" — проверено побитовым
   совпадением бокса с эталоном `qa/real_photos_label_crops.py`). Причина —
   историческое обоснование (`ocr_lab_rapid_1280.jsonl`) посчитано из пережатого
   JPEG-артефакта контакт-листа (`label-crops/*.jpg`, thumbnail 1600px + quality 92),
   а не из настоящего оригинала: воспроизвела оба пути на фото 95.36 — из сохранённого
   файла текст побитово совпадает с кэшем, из оригинала — другой (не обязательно
   хуже, просто другой на грани разрешимости слова "WINEMAKER'S SELECTION"). Если
   орекстратор хочет именно этот +1 — рычаг НЕ в моей реализации, а в том, читать ли
   продакшн-путь из пережатого артефакта (что противоречит брифу) или пересчитывать
   офлайн-обоснование из оригиналов начисто (тогда, вероятно, тоже покажет 91.9%, не
   93.5%, и цель брифа стоит считать основанной на артефакте измерения, а не
   ошибкой реализации).
2. **Бикубика (задача 3) — чистый, самостоятельный выигрыш**, отдельно
   подтверждённый живым API на сжатых фото (+3.2 п.п., 2 фото из 62), в том числе
   решает РОВНО тот класс промаха, для которого её просили ("на фото < ~1000 px
   кроп бутылки меньше 960"). Рекомендую держать включённой независимо от решения
   по п.1.
3. **Найденный и исправленный баг** (numpy `ndarray` в булевом контексте на боксах
   реального `rapidocr`, 400 Bad Request на каждом фото при первом прогоне
   `CV_OCR_LABEL_SIZE>0`) — чистая находка этой волны: юнит-тесты (мокнутые python-
   списками, не ndarray) её не ловили; живой прогон поймал сразу. Тесты усилены,
