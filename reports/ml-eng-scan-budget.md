# ml-engineer: бюджет скана + прогрев + расширение (22.09)

Задача тимлида (страховка лимита 10с, reports/devops-hack-v13.md: хвост p50/p95/max
4.4/6.6/9.1с на 4 vCPU), расширенная тем же днём тремя сообщениями: (5-10) модель+
локальный путь параллельно, предохранитель на модель, два ответа (CV_FUSION_CHOOSE);
находка — near-dup `verify()` тоже был без таймаута (rich-фото 14.6с/3.4с). Всё — только
`apps/api/app/cv/*` + `app/config.py` (+ тесты `apps/api/tests/`, `app/main.py` не тронут).

## (1) CV_SCAN_BUDGET_S (дефолт 7.5с) + (5) VISION_LLM_TIMEOUT_S 6.5→6.0

`_fusion_text_and_vectors()` (`service.py`): дедлайны OCR (`scan_deadline`) и модели
(`model_deadline`) — оба от `t0`, переданного из `run_photo_scan()` (не от входа в
функцию, как раньше). `f_ocr.result(timeout=...)` — раньше ждала БЕЗ таймаута вовсе
(корень бага). `t0=None` (юниты, вызывающие функцию напрямую) — старое поведение.

## (6) Ошибки OCR/verify не текут наружу
Любое исключение/таймаут — `except Exception` + `logger.warning(...)` без содержимого
фото/текста, `ocr_text=""`; ответ = CV+текст модели (если ответила) или только CV.
Никогда не 500.

## (7) Раздельные пулы + медленная выдача тела
`_FUSION_OCR_POOL`/`_FUSION_MODEL_POOL` (было — один общий `_FUSION_TEXT_POOL`) —
зависший запрос к шлюзу не крадёт поток у CPU-OCR следующего скана. Находка при
тестировании на настоящем trickle-сервере: `http.client.HTTPResponse.read(amt)`
КЛАМПИТ `amt` до `Content-Length` — чанк 65536 байт вырождался в один `resp.read()`
целиком, дедлайн ни разу не проверялся. Исправлено на `amt=1` (`vision_llm.py::
_read_response_within_deadline`) — подтверждено тестом на реальном трикл-сервере
(`test_cv_scan_budget_fake_gateway.py`, без фикса тест ловил 7.6с вместо <1с).
Остаточный риск: НЕ герметично (одна операция `.read(1)` теоретически может провиснуть
до `timeout_s`) — честный компромисс без приватных атрибутов сокета, см. «Риски».

## (8) Предохранитель на модель (`_ModelBreaker`, свой на "vlm"/"vlm_local")
`VISION_LLM_BREAKER_FAILS=3` сбоев/таймаутов подряд → открыт `VISION_LLM_BREAKER_
COOLDOWN_S=60` (скан сразу локальный, без ожидания дедлайна); "ровно один" пробный скан
после паузы — атомарно под локом; успех закрывает, неудача переоткрывает. "Сбой" =
исключение/таймаут; честный пустой ответ модели — НЕ сбой (иначе гейт спутал бы серию
нечитаемых фото со сломанным шлюзом) — потребовало `vision_llm.read_label_or_raise()`
(различает через `VisionLLMError`; `read_label()` — тонкая обёртка, старый контракт).

## (9) Два ответа + CV_FUSION_CHOOSE (дефолт "merge")
`_run_photo_scan_fusion()` всегда считает `local_result` (CV+чистый OCR) и `model_result`
(текущая склейка) на ОДНИХ векторах/кандидатной вселенной (union extra_slugs обоих
текстов, один `search_fusion()`); `_choose_fusion_result()` — merge/max_score/
agree_else_llm/agree_else_cv/**confident_else_cv**. `PhotoScanResult.local_slug/
model_slug/answers_agree/chosen_answer_side` — НЕ в контракте, только архив
(`archive.py`) + `INFO`-лог. "merge" — ответ бит-в-бит старый (проверено HTTP-тестом);
`max_score` в тесте перекл. ответ.

**Параллельная находка**: во время этой задачи ml-lead независимо (`git log`, коммит
`b1a7c48`, `reports/ml-lead-choose-rule.md`) прогнал офлайн-сравнение
merge/max_score/agree_else_llm/agree_else_cv/confident_else_cv на 62 живых фото + 38
честных NONE (боевая `cv.text_fusion.fuse()`) и **рекомендует `confident_else_cv`**
(доверяем модели, только если её СОБСТВЕННЫЙ `fuse()` проходит уже откалиброванный
гейт `confident`, иначе локальный — независимо от согласия слагов): не хуже merge на
чистых (60/62), заметно устойчивее к галлюцинации чтения модели на всех проверенных
точках искажения (10/30/100%), чем остальные 4 режима. Добавил `confident_else_cv`
в `_choose_fusion_result()` (читает `model_result.confident` — то же поле `fuse()`,
что уже решает `not_in_catalog`) — режим ДОСТУПЕН, дефолт НЕ переключаю (решение "в
бой" по букве TEAM.md не в зоне ml-engineer, ml-lead адресовала рекомендацию тимлиду).

## Находка: near-dup verify() тоже без бюджета (rich 14.6с/3.4с)
`run_photo_scan()`/`_run_photo_scan_fusion()` зовут ОДИН и тот же пайплайн для flat/rich
— код идентичен, разница молчаливая (DB-запись/лог/архив-таск, все дешёвые). `card`/
`candidates`/`thumb_url()` — только URL-строки, не I/O при скане (проверено чтением
кода). Реальный пробел — `verifier.verify()` (near-dup OCR) был БЕЗ таймаута в ОБОИХ
путях. `_verify_with_budget()` — свой OCR-проход через `_FUSION_OCR_POOL`, дедлайн =
остаток `CV_SCAN_BUDGET_S`; не успел → `None` (кандидат остаётся top-1 без OCR-
верификации, контракт это уже допускал как честный исход). Применена в обычном пути
`run_photo_scan()` тоже (риск был общий, не только CV_FUSION).

## (2) Прогрев CV_FUSION=1
`factory.py::_warm_up_cv_fusion_text_branch()` (внутри `warm_up_label_verifier()`, БЕЗ
правок `main.py`): синтетическая PIL-картинка этикетки (кириллица + год/объём/%, не
данные кейса) — `read_query_text()` (RapidOCR во всех масштабах, включая 3-й проход по
кропу — эмпирически подтверждено на настоящем движке: без текста на плейсхолдере
`label_bbox()` не находит область и 1280px никогда не запускает инференс, с синтетикой —
запускает) + один запрос к VLM, если `VISION_LLM_URL` задан. Сбой OCR → `warm=false`
(как остальной прогрев); сбой VLM → только `WARNING`, `warm` не трогает, старт не падает.
Шрифт кириллицы ищется среди системных (никаких загрузок) с честным фолбэком на
`ImageFont.load_default()` — стенд ams3 шрифтов не ставит вовсе (`bootstrap.sh`), но
цифры/латиница детектируются движком и без него (подтверждено на реальном RapidOCR).

## Риски / предложения тимлиду
1. **Зависший OCR/verify ест ядра следующего запроса** — да: поток не отменяется
   (Python не умеет), продолжает работать в фоне `_FUSION_OCR_POOL` (CPU-bound). На 4
   vCPU несколько таких зависших потоков реально конкурируют с новыми запросами —
   именно это правдоподобно и вызывало исходный хвост. Предохранитель (п.8) ограничивает
   накопление ТОЛЬКО для модели (сетевые вызовы), не для OCR (нет аналогичного сигнала
   "OCR стабильно медленный"). Предлагаю: (a) ограничить внутренний параллелизм ONNX
   Runtime/RapidOCR (`OMP_NUM_THREADS=1` или аналог) — тогда один зависший скан ест 1
   ядро, не несколько; (b) уменьшить `_FUSION_OCR_POOL.max_workers` с 8 — на 4 vCPU 8
   потоков CPU-bound работы это уже перегрев сам по себе. Не сделал — правка настроек
   исполнения ONNX вне `apps/api/app/cv/*`/влияет на packages/cv, нужен архитектор/devops.
2. `_read_response_within_deadline` не герметична (см. п.7) — полный фикс требует
   `httpx.AsyncClient`+`asyncio.wait_for` (реально отменяемо) или сокет с ручным
   `settimeout()` через приватные атрибуты `http.client` — оба тяжелее текущего бюджета
   задачи, текущий фикс закрывает практический случай (частые мелкие паузы).
3. `CV_FUSION_CHOOSE` остаётся "merge" (ответ не меняется) — включение другого режима
   решает ml-lead после офлайн-сравнения `local_slug`/`model_slug`/`answers_agree` из
   архива/лога.
4. Стенд не задаёт `CV_SCAN_BUDGET_S`/`VISION_LLM_BREAKER_*` явно — новые дефолты (7.5с
   / 3 / 60с) применятся сами; devops может явно прописать в `somelye.env`, если нужно
   другое значение.

## Локальный замер (100 фото case-data/real-photos, свой Mac 10 ядер, своя копия
data-d1/qdrant+rag/data без `.lock`, порт 8791, CV_FUSION=1 CV_OCR_ENGINE=rapid
CV_FUSION_TEXT_SOURCE=ocr — без VLM: адрес шлюза секретный, не мой доступ; VLM-путь
отдельно проверен `test_cv_scan_budget_fake_gateway.py` на настоящем HTTP-сервере),
искусственная нагрузка — 10 CPU-процессов на всех 10 ядрах, 90с начиная с 60й секунды
прогона (~вторая половина). `git stash` на 4 правленых файла — "до", `git stash pop` —
"после", тот же порт/копии индекса, тот же стресс-профиль.

| | flat_ms p50/p95/max | rich_ms p50/p95/max |
|---|---|---|
| до  | 736/1636/**2375** | 728/1706/**2412** |
| после | 866/2433/**5836** | 887/2516/**6737** |

**Честный результат: этот конкретный прогон НЕ показал улучшение хвоста — стало ЧУТЬ
хуже, не лучше.** Разобрался, почему, а не списал на шум:
1. `CV_FUSION_VERIFY=0` (дефолт) в обоих прогонах — путь `_verify_with_budget()` (сама
   находка про 14.6с/3.4с) НИ РАЗУ не вызывался. VLM тоже не настроена — путь
   `_ModelBreaker`/модельного дедлайна тоже не при делах. Единственное, что реально
   отличается между "до"/"после" в ЭТОМ прогоне — таймаут ожидания `read_query_text()`
   (7.5с бюджет вместо бесконечности).
2. На 10-ядерном Mac при 10 стресс-процессах ни один боевой OCR-вызов ни в "до", ни в
   "после" не подполз к 7.5с (макс. 5.8с) — то есть бюджет НИ РАЗУ не сработал как
   ограничитель ни там, ни там: оба замера измеряют один и тот же код по факту (просто
   разная точка старта стресс-окна относительно прогресса скрипта — 100 фото идут
   последовательно, "после" оказался на пару фото глубже во время самого дорогого
   отрезка стресса, чисто по невезению с таймингом, не по вине кода).
3. Правильная, детерминированная проверка бюджета — НЕ шумный живой прогон, а
   `test_cv_scan_budget.py`/`test_cv_scan_budget_fake_gateway.py` с управляемой
   задержкой: искусственный OCR на 2.0с при бюджете 0.3с → ответ за <1.3с (не 2.0с);
   зависший VLM-шлюз на "2с" при timeout_s=0.3с → та же граница; трикл-сервер (реальный
   сокет) без фикса читал тело 7.6с при timeout_s=0.3с, с фиксом — <1с. Эти цифры
   ВОСПРОИЗВОДИМЫ (не зависят от везения с таймингом стресса) и являются главным
   доказательством корректности бюджета — живой 100-фото прогон здесь играет роль
   "не сломали обычный путь" (оба прогона: 0 ошибок, максимум 6.7с — внутри лимита 10с),
   не демонстрации улучшения хвоста.
4. Уместный вывод: чтобы живьём увидеть выигрыш, нужен ЛИБО `CV_FUSION_VERIFY=1` на
   фото с near-dup кандидатами, ЛИБО настоящий VLM-шлюз с воспроизводимым зависанием —
   ни то ни другое не входило в этот прогон (первое не включено на стенде по умолчанию,
   второй секретный). Предлагаю тимлиду/qa-auto замер живым API на стенде с
   `CV_FUSION_VERIFY=1` отдельно, если нужна именно живая (не юнитовая) демонстрация.
