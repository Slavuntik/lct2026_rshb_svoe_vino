# devops: проброс апстрима витрины Потапа — конфиг готов, включение ждёт адрес и root (26.09)

Задача тимлида 26.09. Адреса сервиса `apps/shelf-finder/server` (:8086) пока нет — Вячеслав уточняет.

## Сделано (в git)

- `infra/ams3/nginx-somelye.conf`: locations `/v1/shelf/` и `/shelf-ui/` читают `$shelf_upstream`;
  пустое значение → `return 404;` ДО `proxy_pass` (честно, не `try_files`-фолбэк на наш SPA).
  `/v1/shelf/` длиннее общего `/v1/` — nginx матчит самый длинный префикс НЕЗАВИСИМО от порядка
  блоков, общий `/v1/` → `apps/api` не задет гарантированно. `/shelf-ui/` — `rewrite ... break`
  отбрасывает префикс. Лимиты уже внутри: `client_max_body_size 20m` (лимит сервиса), таймауты 60с
  (сервис просит ≥60с при клиентских 45с).
- `infra/ams3/shelf-upstream.conf` (новый): `map $host $shelf_upstream { default ""; }` для
  `/etc/nginx/conf.d/`. `map`, не `set`: `conf.d` этой коробки подключается ВНУТРИ `http{}`
  (проверено `grep` на сервере) — `set` там не пройдёт `nginx -t`.
- `infra/ams3/bootstrap.sh`: ставит `shelf-upstream.conf`, только если файла ещё нет на сервере (тот
  же приём, что `somelye.env`) — повторный bootstrap не откатит уже включённый адрес.
- `docs/architecture/operations.md` §10 + `infra/ams3/README.md` («Проброс витрины Потапа»): данные,
  нужные от Михаила (хост/порт/схема/авторизация), команды включения/проверки/отката, разбор риска
  (после включения кто угодно шлёт фото на чужой GPU через наш домен) и минимальная защита — решение
  об усилении сверх лимита тела/таймаутов оставлено Вячеславу.

## Пробел прав — важно тимлиду

`sudo -n -l` на ams3 (26.09): пользователь `somelye`/ключ `ci_do_ams3` может ТОЛЬКО `systemctl
{restart,is-active,status} somelye-api`; `/etc/nginx/*` — `root:root`, ни записи, ни `nginx -t`, ни
`reload` в этот аккаунт не входят. **Включение (правка `shelf-upstream.conf` + `nginx -t` + reload)
требует root** — сам не применял и не пытался обойти (правка sudoers — вне мандата devops, это
изменение прав на боевом VPN-боксе). Нужно решение Вячеслава: либо он выполняет готовые 3 команды
сам (README §«Проброс витрины Потапа»/operations.md §10.3), либо расширяет sudoers на `nginx -t` +
`systemctl reload nginx` для самообслуживания devops в будущем.

## Дополнение 26.09 (вечер) — HTTP Basic-авторизация (коммит `10add97`, запушено в `main`)

Задача тимлида: закрыть проброс паролем — без него через наш домен можно бесплатно гонять чужой
GPU Михаила. В `infra/ams3/nginx-somelye.conf`: `auth_basic "Shelf access"` +
`auth_basic_user_file /etc/nginx/.htpasswd-shelf` на `/v1/shelf/` и `/shelf-ui/`. `/v1/shelf/health`
вынесен отдельным точным `location =` БЕЗ пароля — по `apps/shelf-finder/docs/server-api.md` отдаёт
только `{"ready": bool}`, каталог/скан не раскрывает, исключение оправдано. Поведение при
`$shelf_upstream = ""` не меняется: `if`/`return` — фаза rewrite, `auth_basic` — фаза access,
которая у nginx всегда следующая независимо от порядка директив в файле, — 404 гарантированно
раньше запроса пароля.

**Проверено на реальном nginx 1.28.3 с ams3** (изолированно — свой prefix/порт в `/tmp`, живой
экземпляр только на `127.0.0.1`, боевое не тронуто, всё убрано после): `nginx -t` на 2×2 (апстрим
пуст/задан × файл паролей есть/нет) — 4/4 успешно. Живой функциональный тест (мок-апстрим, разовый
тестовый пароль генерировался и использовался только внутри remote-скрипта, нигде не печатался):
health — 200/404 без пароля в обоих состояниях апстрима; `/v1/shelf/scan` и `/shelf-ui/` — 401 без
креденшелов и с неверным паролем, 200/passthrough с верным; апстрим OFF — честный 404 без запроса
пароля на всех трёх путях (п.2 задания). Проверены оба формата хэша — `apr1` (openssl) и bcrypt
(алгоритм `htpasswd -B`; сам пакет apache2-utils на коробке не стоит, сравнение сделано через
python `bcrypt`, который там уже есть) — оба корректно различают верный/неверный пароль.
Отсутствующий `auth_basic_user_file` (нынешнее боевое состояние) — НЕ 500: первый запрос честно
401, любой введённый пароль — 403; задокументировано отдельно, чтобы root не принял это за
поломку. `infra/scripts/validate.sh` — по-прежнему 33/2, оба FAIL старые, не мои.

**Документация** (README «Пароль для витрины», operations.md §10.3/§10.6/новый §10.7): команды
`htpasswd -Bc`/фолбэк `openssl passwd -apr1` от root, передача пароля Михаилу тем же каналом, что
остальные секреты, ожидаемое разовое окно логина в браузере за сессию (HTTP Basic кеш по
origin+realm — `/shelf-ui/` во фрейме и его же fetch к `/v1/shelf/scan` покрываются одним вводом),
отключение на время демо (2 строки в 2 locations + reload) независимо от вкл/выкл самого проброса.
Честно указана граница: стенд на голом `:80` без TLS — Basic-auth не защищает от сниффинга на
сетевом пути, только от случайных обращений на публичный URL (исходная угроза).

**Важно тимлиду:**

1. Файл сайта на сервере может быть ещё старым: обычный выкат nginx не трогает

   после прошлого коммита (`d1951dd`) никто руками не копировал `nginx-somelye.conf` на сервер —
   там до сих пор конфиг вообще без проброса витрины, не только без пароля. README/operations.md

   первым шагом.
2. Порядок root-шагов важен: файл паролей — ДО reload с новым конфигом (иначе 403 всем вместо
   честного запроса пароля до его появления).
