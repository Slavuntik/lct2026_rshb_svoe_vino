# H2 · RapidOCR в два масштаба + опция 8 кропов CV — CPU-путь без GPU

Пять накопительных изменений CPU-пути слияния (`CV_FUSION_TEXT_SOURCE=ocr`, без сети,
без VLM), поднятых на офлайн-исследовании оркестратора (`reports/cpu-path-study.md`) —
RapidOCR (ONNX Runtime, два масштаба) вместо PaddleOCR как источник текста, гомоглиф
`i→и`, опция 8 кропов CV:

1. **`packages/cv/cv/ocr_rapid.py`** (новый) — `RapidOcrReader`: центральный кроп
   кадра (`cv.verify.CENTER_CROP`/`_center_crop()`, те же доли, что H1), список
   масштабов `CV_OCR_RAPID_SIZES` (дефолт `640,960`), один экземпляр `RapidOCR` НА
   МАСШТАБ (проверено по исходнику `rapidocr==3.9.2`: `Det.limit_side_len` — параметр
   конструктора, не вызова), параметры движка дословно из прототипа
   (`qa/real_photos_rapidocr.py`: `Det.model_type=MOBILE`, `Det.ocr_version=PPOCRV5`,
   `Det.limit_type=max`, `Global.use_cls=False`, `Rec.lang_type=ESLAV`, порог 0.5).
   Тексты масштабов — через пробел. Сбой импорта/конструктора/вызова — warning +
   пустая строка для пострадавшего масштаба (деградация, не 500).

   **Находка приёмки (см. ниже)**: `Det.limit_side_len` управляет ТОЛЬКО внутренним
   ресайзом детектора — распознавание вырезает регионы из кадра, прошедшего лишь
   `Global.max_side_len` (дефолт 2000px), а не из входа детектора (проверено по
   исходнику `rapidocr.utils.process_img.resize_image_within_bounds()`). Без явного
   даунскейла ДО вызова движка `size` не управлял бы фактическим разрешением
   распознавателя — `_downscale_to_longest_side()` воспроизводит `PIL.Image.
   thumbnail()` (BICUBIC), КАК И ПРОТОТИП, а не `cv2.resize(..., INTER_AREA)` (тем
   `cv.verify.LabelVerifier.read_text()` даунскейлит для PaddleOCR) — два фильтра
   дают расхождение пикселей 18–27/255 и на границе разрешимости мелких слов теряют
   целые распознанные токены (подробности в разделе "Расхождение с офлайном" ниже).

2. **`packages/cv/cv/verify.py`** — `CV_OCR_ENGINE=paddle|rapid` (дефолт `paddle`,
   как в брифе — молчаливой смены дефолта нет). При `rapid` новый метод
   `read_query_text_rapid()` (центр через `cv.ocr_rapid.RapidOcrReader`, ленивый
   `_rapid_reader()`) вызывается из `read_query_text()`; `CV_OCR_QUERY_MODE` в этой
   ветке не читается вовсе. `verify()`'s собственный fallback (когда `ocr_text` не
   передан) НЕ тронут — всегда PaddleOCR, независимо от `CV_OCR_ENGINE` (брифа: "то
   же самое" для этого пути).

3. **`packages/cv/cv/text_fusion.py`** (+ синхронно `qa/text_v2.py`) — вторая пара
   гомоглифов без кириллического аналога: латинская строчная `i`→`и` (добавлена в
   `_LOW`). Найдена на тексте RapidOCR живого фото 96.96 (`Py6iH`=`Рубин`, читается
   ТОЛЬКО на масштабе 960px, на 640px тот же фрагмент читается как `Py6uH` — двойник
   `u`→`и` уже существовал). Та же дисциплина, что остальные пары: замена всего
   токена — только когда ВСЕ буквы токена являются двойниками (`Pinot` не трогается).

4. **`packages/cv/cv/index.py`** — `CV_FUSION_CROPS=2|8` (дефолт 2, живой резолв env
   в конструкторе `ImageIndex`, как `LabelVerifier.ocr_query_mode`). `embed_fusion_query()`
   возвращает кортеж из N векторов (2: кроп детектора + весь кадр, как раньше; 8: + три
   центральных кропа `cwide/cmid/ctight`, доли из `qa/real_photos_qemb.py::CROPS`, ×
   (как есть / через `normalize_query`) = 2+3×2=8), одним батчем через
   `SiglipEncoder.encode_batch()`. `search_fusion(vectors=...)` принимает любой N —
   per-slug максимум по всем векторам (обобщение существующей логики, не новая ветка).

5. **`apps/api/app/cv/factory.py`** — `warm_up_label_verifier()` греет ВЫБРАННЫЙ
   движок: `ocr_engine=="rapid"` → `read_query_text()` (RapidOCR, PaddleOCR не
   трогается вовсе); иначе (дефолт/двойники без атрибута) — старое поведение
   (`verify()`). `GET /healthz.warm` не меняется (AND обоих прогревов, как раньше).

6. **Зависимости**: `rapidocr>=3.9`, `onnxruntime>=1.18` — в основной набор
   `packages/cv/pyproject.toml` (как и `paddleocr`/`paddlepaddle`, не extra).
   `uv lock` в `apps/api` — чисто аддитивный диф (63 insertions, 0 deletions:
   rapidocr, opencv-python, omegaconf, antlr4-python3-runtime; onnxruntime уже был
   в локе транзитивно). `uv sync --frozen --no-dev --extra integration` в `apps/api`
   проходит (проверено).

7. **Инфра**: `infra/ams3/deploy.sh` — идемпотентный вызов `RapidOcrReader(...).read()`
   на плейсхолдере ДО рестарта (предзагрузка моделей под пользователем `somelye`, сеть
   на ams3 есть; сбой не роняет деплой). `somelye.env.example` — `CV_OCR_ENGINE=rapid`,
   `CV_OCR_RAPID_SIZES=640,960`, `CV_FUSION_CROPS=2` (не 8 — бюджет 4 vCPU). `infra/
   local-check/run-check-server.sh` — те же переменные, `CV_FUSION_CROPS=8` (бюджет
   Mac свободнее), обе с overridable env (`OCR_ENGINE`/`FUSION_CROPS` и т.п.).
   `infra/ams3/README.md` — новый раздел про RapidOCR.

### Расхождение с офлайном > 2 п.п. — разбор по фото, не списано на шум

Первый прогон (ДО находки п.1 выше, `cv2.INTER_AREA`): 2 кропа 87.1% при офлайне 90.3%
(7 расхождений офлайн/живой), 8 кропов 88.7% при 93.5% (4 расхождения). Сравнила
офлайн-предсказания (`qa/real_photos_cpu_path.py`-логика, вариант `rapid_640+rapid_960`,
`W=0.3, α=0.5` — боевые `CV_FUSION_W`/`CV_FUSION_OCR_UNCONFIRMED_W`) с живыми
`flat_slug` ПОФОТОЧНО (скрипт сравнения — не коммичу, разовый анализ, логика описана
здесь). На 4 из 7 фото (2 кропа) объединённый OCR-текст живого сервера ЗАМЕТНО отличался
от закэшированного офлайн-текста — не опечатки, а целые ПРОПАВШИЕ слова («РУБИН
ГОЛОДРИГИ», «Py6iH»). Прямая проверка причины: `cv2.resize(..., INTER_AREA)` и
`PIL.Image.thumbnail()` (BICUBIC) на ОДНОМ И ТОМ ЖЕ кропе дают расхождение пикселей
18–27/255 — воспроизвела ОБА пути на этих 4 фото: с `PIL.thumbnail` текст совпадает с
офлайн-кэшем ПОБИТОВО (проверено на всех 62 фото × 2 масштаба — 124/124 точных совпадений
после исправления, было 0 расхождений вместо прежних смешанных). Правка (`_downscale_to_
longest_side()` → PIL) внесена, `cv/ocr_rapid.py` обновлён.

**После правки** расхождения с офлайном упали с 7→3 (2 кропа) и остались 4 (8 кропов, те
же самые фото — правка про OCR-текст, эти случаи о другом), но ИТОГОВЫЙ top-1 не
изменился (87.1%/88.7% — те же самые 8/7 фото верны, просто по другой причине). Разобрала
оставшиеся: **91.43** (`merlo-litavshhuk`) — офлайн И живой оба неверны (тот же
неправильный ответ не выбран ни там, ни там — читаемый текст "Литавщуков" почему-то не
поднимает верный слаг вообще, вне зоны этой правки, текстовый скоринг). **92.6**
(`aratti-kaberne...`, только 8 кропов) — текст живого и офлайн ОДИНАКОВ («Apammu» —
собственный OCR-мусор на "Aratti", не двойник ни в одной таблице), решает CV-скор.
**96.79 и 96.83** (`oleg`, ОБЕ конфигурации) — офлайн-текст живого сервера побитово
совпадает с кэшем (проверено), но итоговый выбор всё равно расходится: офлайн верно
выбирает "oleg", живой — соседа по семье ("roze-2"/"bukovinka"). Это ТОТ ЖЕ пример,
что H1 уже разбирала в своём отчёте (`reports/h1-cpu-path.md`, "Табия"/"Олег" — гейт
неподтверждённой винодельни, узкий CV-зазор внутри near-dup семьи) — не новый дефект.

Для оставшихся 3 фото (2 кропа: 92.6 нет там, только 96.79/96.83 + нейтральный 91.43;
8 кропов: 92.6+96.79+96.83) текст ИДЕНТИЧЕН офлайну, значит источник — CV-скор:
`cv.encoder.SiglipEncoder` на этой машине считает эмбеддинги на **MPS** (проверено:
`pick_device()` → `"mps"`), а PyTorch/MPS matmul НЕ гарантирует бит-точную
воспроизводимость между запусками процесса (задокументированное ограничение,
аналогичное CUDA-недетерминизму) — для узкого CV-зазора near-dup пары ("oleg" против
соседей по одной этикетке "Табия") этого достаточно, чтобы перевернуть argmax. Кроме
того H1 уже указывала (не проверяла сама, ретранслирую): офлайн-снимок `sims384_*.npy`
мог быть посчитан на индексе СТАРШЕ боевого `index_vectors_base384_d1.npy` — тот же
класс расхождения "офлайн число не с того самого снимка индекса", не факт архитектуры
этой волны. `cv/encoder.py` вне зоны этой задачи — не трогала.

**Итог**: находка п.1 (PIL vs cv2) — реальный, воспроизводимый, исправленный дефект
(закрыл 4/7 и часть 8-кропового расхождения). Остаток (2–3 фото) — CV-скор на грани
near-dup решения, тот же класс хрупкости, что H1 уже задокументировала для того же
самого примера "Табия/Олег", не регрессия этой волны.

### RSS и время прогрева: rapid против paddle

| Движок (2 кропа, иначе идентичные настройки) | Время прогрева | RSS процесса после прогрева | p50 / p95 `timing_ms` |
|---|---:|---:|---:|
| `CV_OCR_ENGINE=rapid` | 9–12 с | **~1248 МБ** | 350–361 / 444–470 мс |
| `CV_OCR_ENGINE=paddle` (дефолт, `CV_OCR_QUERY_MODE=detector`) | ~9.3 с | **~1918 МБ** | 766 / 1064 мс |

RSS: **на ~670 МБ (35%) меньше** с rapid — PaddleOCR не грузится в процесс вовсе
(`CV_FUSION_VERIFY` не включён → `verify()` не вызывается). Время прогрева —
СОПОСТАВИМО в абсолютных цифрах (доминируют общие статьи: импорт torch/transformers,
SigLIP2, первый поиск в embedded Qdrant — тот же вклад что и раньше при любом движке
OCR); зато per-request `timing_ms` у rapid **более чем вдвое быстрее** (350–470 мс
против 766–1064 мс) — тут разница огромна и ожидаемо совпадает с офлайн-замером
оркестратора (0.34 с на кроп против 4.0 с). Оговорка: paddle-сравнение бралось при
`CV_OCR_QUERY_MODE=detector` (дефолт ДО принятия H1) — это НЕ повтор боевого 85.5%
H1 (тот использовал `center`+640), сравнение только для RSS/прогрева/тайминга при
прочих равных, не точность.

```bash

# приёмка (живой API, порт вне 8080/8091/8093 — чужие процессы на Mac)

CV_DATA_DIR=$(pwd)/../../packages/cv/data-d1 \

CV_FUSION=1 CV_FUSION_W=0.3 CV_FUSION_TEXT_SOURCE=ocr \

cd .. && apps/api/.venv/bin/python qa/real_photos_serve.py --api http://127.0.0.1:8770 --out /tmp/served.jsonl
cd packages/cv && .venv/bin/python ../../qa/real_photos_eval.py --served /tmp/served.jsonl --only __none__
# CV_FUSION_CROPS=8 на отдельном порту — та же процедура
```

## Предложения оркестратору

1. **Цели брифа (88%/91%) не достигнуты** (87.1%/88.7%) даже после исправления
   найденного дефекта даунскейла. Остаток — 2–3 фото на 62, все near-dup/CV-скоровые
   (не текстовые), один и тот же пример "Табия/Олег", что H1 уже фиксировала для
   PaddleOCR-пути (не новая проблема rapid). Возможные дальнейшие рычаги (вне мандата
   этой волны): пересчитать офлайн-снимок `qemb_base384.npz`/`index_vectors_base384_
   d1.npy` СВЕЖИМ прогоном (H1 уже подозревала рассинхрон снимков) и/или зафиксировать
   `torch.mps` детерминизм (если такой флаг вообще существует у PyTorch/MPS — не
   проверяла, вне времени задачи).
2. Найденный и исправленный даунскейл-баг (`cv2.INTER_AREA` вместо `PIL.thumbnail`)
   — чистая находка ЭТОЙ волны, не наследие: сама писала `cv/ocr_rapid.py` с нуля,
   первая версия скопировала паттерн `cv.verify.LabelVerifier.read_text()` (тот
   использует cv2) не проверив, что офлайн-прототип RapidOCR использует PIL. Урок:
   "параметры движка дословно" из брифа стоило явно распространить и на
   ПРЕДОБРАБОТКУ (ресайз) кадра, не только на `params={...}` словарь конструктора.
3. Порты 8770–8775 использовались последовательно на Mac (не 8080/8091/8093 — не
   трогала); процессы остановлены, `apps/api/svoy_somelye.db` (сгенерированный,
   гитигнорен) удалён.
