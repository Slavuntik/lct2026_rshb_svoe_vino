# Отчёт агента A · RAG-ядро

Зона: `packages/rag/`. Контракт: `contracts/rag-interface.md` (реализованы версии v0.1 → v0.2.3
включительно, по мере правок оркестратора в ходе работы).

## Что сделано

Полный пайплайн RAG-ядра «Свой Сомелье»:

- **Ingest** (`rag/ingest.py`) каталога vines (`build/*.jsonl` + обогащение из `catalog/*`) в три
  коллекции Qdrant (`wines`, `wineries`, `knowledge`) + sparse BM25-индекс (`rank_bm25`, с русским
  стеммингом) + labels-корпус для `resolve_label`. Идемпотентно (стабильные `uuid5(id)` id точек).
- **Retriever** (`rag/base.py`) — все девять методов контракта v0.2.3: `search`, `resolve_label`,
  `similar`, `analog_for_style`, `resolve_style`, `get_by_id`, `list_reference_styles`,
  `candidates_for_taste`, плюс фабрика `get_retriever()`.
- **Гибридный поиск** (`rag/hybrid.py`): жёсткие фильтры → dense (fastembed) + sparse BM25 → RRF →
  кросс-энкодер реранкер top-20 → top-k.
- **Fuzzy-резолверы** (`rag/resolve.py`): `resolve_label`/`resolve_style` на rapidfuzz, без векторов.
- **Аналог/стили/дегустация** (`rag/styles.py`, `rag/taste.py`): `analog_for_style`,
  `list_reference_styles`, `candidates_for_taste` — чисто метаданные (payload уже несёт
  `reference_style_matches`/`stillness`), без эмбеддингов и похода в Qdrant.
- **Хранилище** (`rag/store.py`): embedded Qdrant (`path=`) — дев-дефолт, Docker не нужен; сетевой
  режим (`url=`) — прод, через `QDRANT_URL`/`get_retriever(RAG_MODE=qdrant|embedded)`.
- **CLI** (`rag/cli.py`): `rag ingest` и `rag eval` — по одной команде каждая.
- **Голд-сет** `eval/goldset.jsonl` — 67 вопросов (pick 18, analog 14, pairing 12, fact 13,
  travel 10), сгенерированы из реальных данных, вручную проверены (детали ниже).
- **42+6=48 pytest-тестов** на синтетической мини-фикстуре (7 вин + 1 winery + 1 статья, НЕ
  настоящие данные vines) — быстрые (~5 c), детерминированные, изолированные.

## Модели: выбор и обоснование (важное расхождение с контрактом)

Контракт называет `bge-m3` (dense) и `bge-reranker-v2-m3` (реранкер). Обе модели **отсутствуют в
реестре установленной версии fastembed (0.8.0)** — `TextEmbedding.list_supported_models()` и
`TextCrossEncoder.list_supported_models()` их не содержат; добавить можно было бы только через
`add_custom_model` с ручным ONNX-экспортом, что не укладывается в разумный бюджет задачи. Бриф
прямо разрешает такую замену («возьми меньшую модель, задокументируй выбор») — этим и
воспользовался:

- **Dense**: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, 384-мерный, из реестра
  fastembed. ~240 текстов/сек на CPU этой машины. `RAG_DENSE_MODEL` — переопределяемо через env.
- **Реранкер**: `jinaai/jina-reranker-v2-base-multilingual` (1.1 ГБ, мультиязычный кросс-энкодер).
  Первая попытка скачивания упёрлась в таймаут (медленная сеть до HF, не блокировка); повторная
  фоновая попытка докачала модель успешно. `RAG_RERANKER_MODEL=""` полностью выключает стадию
  (падение на dense+BM25 RRF) — валидный режим по брифу.

**Находка про реранкер (важно для прод-пути, см. риск 1 ревью 01 — подтверждён на практике):**
латентность кросс-энкодера на CPU определяется в первую очередь **длиной документа**, не только
числом кандидатов. Полный текст статьи (до ~4000 символов) в top-50 давал 10–50 **секунд** на
запрос — не воспроизводимо для демо. Диагностировано и исправлено:
`RERANK_POOL=20` (реранкаем top-20 из уже отранжированных RRF top-50 — план Б, который сам
контракт разрешает) + `RERANK_TRUNCATE_CHARS=500` (обрезка текста перед реранком) +
`RAG_ONNX_THREADS=4` (машина используется параллельно другими агентами — без лимита onnxruntime
разбирал все 10 ядер под себя, на общей машине это давало гигантский system-time от
контекст-свитчей). После фикса: ~0.6–0.8 с/запрос. Все три параметра — env-переопределяемы
(`rag/config.py`).

## Ключевая находка по качеству (и как она была исправлена)

Первый прогон `rag eval` дал **hit@8 = 0.58** — заметно ниже 0.85. Диагностика по
`eval/report.json` (поле `details`) вскрыла две конкретные причины, обе исправлены:

1. **«Вытеснение» карточек вина статьями.** При дефолтном `collections=("wines","knowledge")`
   длинная просветительская статья про сорт («Сибирьковый: что за сорт…») стабильно обгоняла
   терпимую карточку самого вина из этого сорта — и по dense, и по BM25, и после реранка (статья
   длиннее и лексически «плотнее» по теме запроса). **Фикс**: `eval.py` роутит коллекции по типу
   вопроса (`pick`/`pairing` → `wines`, `fact` → `knowledge`, `travel` → `wineries`+`knowledge`) —
   ровно то, для чего в контракте есть параметр `collections` со свободным дефолтом; реальный
   продукт тоже сначала определяет намерение, потом решает где искать. hit@8: 0.58 → 0.78.
2. **Русская флексия ломает точное BM25-совпадение токенов.** «вино **из Дагестана**» /
   «**крымское** вино» не пересекались токенами с текстом карточки «... **Дагестан** ...» /
   «... **Крым** ...» — совпадение только по стеблю, не по словоформе. **Фикс**: русский стемминг
   токенов BM25 (`nltk.stem.snowball.SnowballStemmer`, `rag/textutil.py`) — без скачивания
   словарей/моделей. hit@8: 0.78 → 0.87.

**Что осталось (честно, не скрываю):** `pick` — самый слабый тип (0.722), несмотря на оба фикса.
Диагностика (`pick_with_filters_diagnostic`, не входит в пакет, воспроизводимо вручную): те же 11
вопросов, но с `Filters(color=…, region=…, grapes=[…])` вместо голого текста — **hit@8 = 1.000**.
Вывод: ядро retrieval (жёсткий фильтр + dense/BM25/RRF) работает безупречно, когда получает
структурные атрибуты; проблема **только** в извлечении региона/сорта из свободного разговорного
текста без единого стемминга (стемминг снимает падеж, но не прилагательное от существительного:
«**крымское**» не сводится к стеблю «крым»). Правильное место для полного решения — не RAG-ядро, а
слой NLU/LLM у B перед вызовом `search()`, который и должен наполнять `Filters` из реплики
пользователя (сцена 2 плана уже это подразумевает). Возможные дальнейшие шаги, если понадобится
поднять `pick` без переноса ответственности: полноценная лемматизация (`pymorphy3`) вместо
стемминга — не успел оценить в рамках этой задачи.

## Резолверы: пороги и скорер (rapidfuzz)

`resolve_label`/`resolve_style` используют `fuzz.token_set_ratio` с `processor=default_process`
(**не** `WRatio`, как было в первой версии). На реальном labels-корпусе (1978 вин) `WRatio` дал
ложное срабатывание **85.5** на семантически несвязанной фразе «погода в москве завтра» —
`partial_ratio` внутри `WRatio` совпадает по коротким символьным окнам почти со всем на кириллице.
`token_set_ratio` развело честное и мусорное намного чище (точное совпадение ~100, опечатка ~79-87,
шумный OCR-текст этикетки ~55-78, любой протестированный мусор ≤ 50). Пороги (`rag/config.py`,
env-переопределяемы): `LABEL_GARBAGE_CUTOFF=52`, `LABEL_CONFIDENT_CUTOFF=75`,
`STYLE_GARBAGE_CUTOFF=55`. Владелец порогов — агент A (бриф оставлял вопрос открытым, см. «придирки»
ревью 01); `low_confidence` отдаётся в `Candidate.meta`, так что B/C могут показывать
UI-подтверждение без изменений в RAG.

## Предложения к контрактам

1. **`resolve_label` «синонимы» — источник не был зафиксирован** (это уже отмечено как придирка в
   ревью 01). Решение: синонимы сорта винограда из `ref/grape_synonyms.yaml` (по `filters.grapes`
   вина) добавляются в search-текст лейбла. Названий винодельни/этикетки как таковых в vines-данных
   нет — если понадобится точнее, нужен отдельный источник алиасов производителей.
2. **Семантика `Candidate.score` не унифицирована между методами** — это ожидаемо для гибридной
   системы, но стоит явно закрепить одной строкой в контракте: скор **не сравним между вызовами и
   между методами** (RRF-доля без реранкера, сырой логит кросс-энкодера — может быть отрицательным
   — с реранкером, rapidfuzz/100 в `resolve_label`, `1/(1+sensory_distance)` в `analog_for_style`,
   `1.0` как признак «точное совпадение по id» в `get_by_id`). B уже, вероятно, использует score
   только для сортировки внутри одного ответа — но лучше зафиксировать явно, чтобы никто не сравнил
   его между двумя разными вызовами.
3. **`Filters.sugar` — одно значение, `reference_styles.yaml.sugar` — список.** Не противоречие (это
   две разные проверки: пользовательский фильтр против фактического сахара вина; допустимый список
   сахара для стиля — при матче стиля), но стоит явно упомянуть в контракте, чтобы не завели баг при
   рефакторинге.
4. **`knowledge`-payload не хранит `wine_slugs`/`winery_slugs`** из `build/articles.jsonl` (я их
   отбросил при ingest ради компактности payload). Если B/F захотят кросс-ссылки статья→вино для
   цитат — поле легко вернуть, сигнал есть в исходных данных, просто не был запрошен в контракте.
5. **Свободный текст vs структурные Filters для `pick`/`pairing`.** См. «Ключевая находка» выше:
   `search()` по чистому тексту (без `Filters`) — заведомо более слабый режим для запросов вида
   «вино из региона X, сорт Y», чем с извлечёнными `Filters`. Стоит явно закрепить в контракте (или
   в брифе B) ожидание, что `/chat` извлекает `Filters` из реплики перед вызовом `search()` там, где
   это возможно — это не новая работа, а формализация того, что и так подразумевает сцена 2 плана.
