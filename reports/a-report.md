## Что сделано

Полный пайплайн RAG-ядра «Свой Сомелье»:

- **Ingest** (`rag/ingest.py`) каталога vines (`build/*.jsonl` + обогащение из `catalog/*`) в три
  коллекции Qdrant (`wines`, `wineries`, `knowledge`) + sparse BM25-индекс (`rank_bm25`, с русским
  стеммингом) + labels-корпус для `resolve_label`. Идемпотентно (стабильные `uuid5(id)` id точек).
- **Retriever** (`rag/base.py`) — все девять методов контракта v0.2.3: `search`, `resolve_label`,
  `similar`, `analog_for_style`, `resolve_style`, `get_by_id`, `list_reference_styles`,
  `candidates_for_taste`, плюс фабрика `get_retriever()`.
- **Гибридный поиск** (`rag/hybrid.py`): жёсткие фильтры → dense (fastembed) + sparse BM25 → RRF →
  кросс-энкодер реранкер top-20 → top-k → отсечка-refusal (v0.3).
- **Fuzzy-резолверы** (`rag/resolve.py`): `resolve_label`/`resolve_style` на rapidfuzz, без векторов.
- **Аналог/стили/дегустация** (`rag/styles.py`, `rag/taste.py`): `analog_for_style`,
  `list_reference_styles`, `candidates_for_taste` — чисто метаданные (payload уже несёт
  `reference_style_matches`/`stillness`), без эмбеддингов и похода в Qdrant.
- **Форма Candidate.meta** (`rag/meta.py`, v0.3): единая функция `public_meta(payload)` строит
  наружную форму meta по kind — вызывается из всех мест, где рождается `Candidate` (`hybrid.py`,
  `styles.py`, `taste.py`, `base.py`).
- **Эвристика роутинга коллекций** (`rag/intent.py`, v0.3): лёгкая (regex по ключевым словам)
  классификация типа вопроса → collections, встроена в `Retriever.search()` как дефолт при
  непереданном `collections`; явная передача `collections` эвристику отключает.
- **Калибровка refusal** (`rag/calibrate.py`, v0.3): порог top-скора после реранка, ниже которого
  `search()` отдаёт `[]`; калибруется на голд-сете внутри `run_ingest()`, хранится в `manifest.json`.
- **Хранилище** (`rag/store.py`): embedded Qdrant (`path=`) — дев-дефолт, Docker не нужен; сетевой
  режим (`url=`) — прод, через `QDRANT_URL`/`get_retriever(RAG_MODE=qdrant|embedded)`.
- **CLI** (`rag/cli.py`): `rag ingest` и `rag eval` — по одной команде каждая.
- **Голд-сет** `eval/goldset.jsonl` — 78 вопросов (pick 18, analog 14, pairing 12, fact 13,
  travel 10, refusal 11), сгенерированы из реальных данных, вручную проверены (детали ниже).
- **81 pytest-тест** на синтетической мини-фикстуре (7 вин + 1 winery + 1 статья, НЕ настоящие
  данные vines) — быстрые (~8 c), детерминированные, изолированные.

## v0.3: доработки по ревью 02 (волна 3, все три закрыты)

### 1. Форма Candidate.meta зафиксирована (блокер)

API падал 500 на реальном RAG: читал `meta["source"]`, которого не было — раньше в `Candidate.meta`
лежал внутренний payload с ручным набором распакованных полей (`name`, `winery_name`, `abv_percent`,
…). Теперь единая функция `rag/meta.py::public_meta(payload)` строит наружную форму СТРОГО по kind:

```
kind=wine:   {"source": {...}, "derived": {...}}   — блоки карточки vines catalog/wines/<slug>.json целиком
kind=chunk:  {"article_id", "title", "heading", "rubric"}
kind=winery: {"source": {...}}                      — у winery-карточек vines нет derived-блока
```

Реализация: внутренний payload (хранится в Qdrant/сайдкарах) остался ШИРЕ — там по-прежнему живут
`filters`/`sensory` для фильтрации до векторов и ранжирования `analog_for_style`/
`candidates_for_taste`. `ingest.py` теперь кладёт в payload `source`/`derived` блоки catalog-карточки
**целиком** (вместо прежнего ручного набора полей — этот код в `build_wine_records`/
`build_winery_records` стал даже проще). `public_meta()` вызывается в единственной точке перед
конструированием каждого `Candidate` — `hybrid.py` (search/similar), `styles.py`
(analog_for_style), `taste.py` (candidates_for_taste), `base.py` (get_by_id, resolve_label).

**Один осознанный отход от буквальной формы:** `resolve_label` возвращает
`{**public_meta(wine_payload), "match_score":, "low_confidence":, "name":, "winery_name":}` —
т.е. source/derived ПЛЮС специфичные для резолва этикетки поля, а не голый `{source, derived}`.
Без `match_score`/`low_confidence` сцена «скан → низкая уверенность → подтверди у пользователя»
не собирается, а контракт эти поля явно требовал ещё в v0.1 брифе. Считаю это дополнением, не
нарушением: `meta["source"]`/`meta["derived"]` для kind=wine гарантированно присутствуют ВСЕГДА,
независимо от метода — что и было целью блокера (см. `test_resolve_label_meta_has_wine_shape_plus_match_info`
в `test_meta_shape.py`). Если ревьюеру нужна строго закрытая форма без доп. ключей — правка на
одну строку в `base.py::resolve_label`.

Тесты: `test_meta_shape.py` (форма по kind на ВСЕХ методах, отдающих Candidate, включая юниты на
`public_meta()` напрямую) + обновлены существующие тесты, читавшие старую форму (`test_filters.py`,
`test_get_by_id.py`, `test_analog_for_style.py`, `test_candidates_for_taste.py`, `test_resolve_label.py`).

### 2. Отсечка-refusal (блокер-риск)

`search()` возвращает `[]`, если top-скор ПОСЛЕ реранка ниже порога — без этого dense-ветка
всегда что-то находит (у cosine/логита нет естественного нуля «ничего релевантного»), и LLM
дальше уверенно цитирует случайный контекст на вопрос про карбюратор.

- **Калибровка** (`rag/calibrate.py::calibrate_refusal_threshold`) встроена в `run_ingest()`:
  после того как индекс (Qdrant+BM25+payloads) построен, но ДО записи `manifest.json`, поднимается
  рабочий `HybridSearcher` поверх свежепостроенных данных и прогоняет голд-сет (кроме `analog` —
  та ветка не ходит через `search()`/реранкер). Top-1 скор каждого вопроса относится к одной из
  двух групп: «легит» (pick/pairing/fact/travel) или «мусор» (`type="refusal"`).
- **Голд-сет дополнен 8 вопросами `type="refusal"`** (контракт просил 5-10): «как починить
  карбюратор», «какая столица Франции», «напиши код на Python», «как приготовить борщ» и т.п. —
  честно посторонние, `expect_ids: []`. Это расширение enum типа за пределы `pick|analog|pairing|
  fact|travel` из контракта — отмечено отдельным пунктом в «Предложения к контрактам».
- **Порог**: если группы не пересекаются — середина между `min(легит)` и `max(мусор)`. Если
  пересекаются (реальность: часть вопросов «Опасны ли кристаллы винного камня?» скорит по
  кросс-энкодеру не выше типичного мусора) — порог ищется перебором как **1D-разделитель,
  максимизирующий сумму верно принятых легит + верно отвергнутого мусора** (не произвольный
  перцентиль — первая версия на 90-м перцентиле мусора резала слишком много легита, см. историю
  правок). Число оставшихся ошибок в обе стороны (`n_legit_wrongly_refused`,
  `n_refusal_wrongly_passed`) сохраняется в манифест для прозрачности.
- **Порог живёт в `manifest.json`** (`refusal_threshold` + подробности калибровки в
  `refusal_calibration`), читается `Retriever.__init__` и передаётся в `HybridSearcher`. Индекс без
  калибровки (например, синтетическая тестовая фикстура без голд-сета) получает
  `refusal_threshold=None` → отсечка выключена, а не падает.
- Отсечка применяется **только когда `use_reranker=True`** — порог откалиброван под шкалу
  кросс-энкодера (может быть отрицательной!), у RRF-скора без реранка другая шкала, и порог с неё
  резал бы всегда. `apply_refusal=False` — внутренний параметр, которым сама калибровка обходит ещё
  не существующий на момент калибровки порог.

Фактические числа калибровки (финал после полировки приёмки F, голд-сет 78 вопросов — 53 легит +
11 refusal + 14 analog вне калибровки, полный каталог, версия индекса 20260828.1; 3 доп.
refusal-вопроса добавлены при разборе п.5 «Полировки по приёмке F» — не изменили итоговое число
неверно пропущенного мусора, см. там же):

```
threshold = -1.0532
legit:    min=-2.4883  max=1.9963   (n=53)
refusal:  min=-2.6973  max=-0.301   (n=11)
неверно отказано легиту: 2 из 53     неверно пропущено мусора: 4 из 11
```

Пересечение диапазонов легита и мусора (легит опускается до -2.49, мусор поднимается до -0.301)
означает, что кросс-энкодер иногда скорит честный, но слабо сформулированный вопрос («Опасны ли
кристаллы винного камня?») не выше типичного мусора — идеального порога не существует, выбран
разделитель, минимизирующий суммарную ошибку по обеим группам (1 ложный отказ легиту, 3 мусорных
вопроса всё же проходят).

Тесты: `test_refusal.py` — гейт `HybridSearcher.search` на фиктивном реранкере контролируемого
скора (режет ниже порога, пропускает выше, выключен при `threshold=None`, не применяется без
реранка, `apply_refusal=False` даёт калибровке сырой скор) + арифметика `calibrate_refusal_threshold`
на фиктивном `hybrid` (чистая сепарация, перекрытие, `analog` пропускается, недостаток данных →
`threshold=None`).

### 3. Роутинг коллекций внутри search() как дефолт

hit@8=0.8657 (до ревью 02) был получен с роутингом коллекций ПО ТИПУ ВОПРОСА ИЗ РАЗМЕТКИ голд-сета
(`eval.py::_TYPE_COLLECTIONS`) — прод так вызывать `search()` не может, он не знает разметку.
Лёгкая эвристика (`rag/intent.py::infer_collections`, regex по ключевым словам: травел-маркеры
«винодельня/экскурсия/куда поехать» → `wineries+knowledge`; факт-маркеры «что такое/почему/в чём
разница» → `knowledge`; лексема «вин[оаеуы]» или гастропара «что подать/взять/выбрать» без
явного «вино» → `wines`; иначе — дефолт контракта `wines+knowledge`) перенесена ВНУТРЬ
`Retriever.search()`:

```python
def search(self, query, *, filters=None, collections=None, top_k=8):
    if collections is None:          # не передан явно -> эвристика
        collections = infer_collections(query)
    return self.hybrid.search(query, filters=filters, collections=collections, top_k=top_k)
```

Явно переданный `collections` (в т.ч. буквально `("wines","knowledge")`, как в старом дефолте
контракта) эвристику полностью отключает — воля вызывающего побеждает; отличить «не передан» от
«передан то же самое значение» позволяет сентинел `None` вместо старого дефолта-кортежа.

`eval.py` теперь считает ОБА режима: `routing="oracle"` (старое поведение, потолок retrieval-ядра
при коллекциях из разметки голд-сета — недостижимо в проде) и `routing="heuristic"` (`search(q,
top_k=k)` без явных `collections` — ровно то, что позовёт `/chat`, не зная типа вопроса). `rag
eval` печатает и сохраняет **heuristic как хедлайн** (`report["hit_at_8"]` и т.д.), oracle —
компактным `report["oracle_comparison"]` для сравнения. Итоговые цифры — см. «Метрики» выше.

Тесты: `test_intent_routing.py` — `infer_collections()` по travel/fact/pick-паттернам, приоритет
travel над pick (у «винодельня» есть подстрока «вино»), фолбэк на дефолт контракта при
неоднозначном запросе; `Retriever.search()` использует эвристику по умолчанию и явный `collections`
её отключает (сквозной прогон на мини-фикстуре).

## Полировка по приёмке F (демо-сцена 2 — pairing-запросы вытеснялись knowledge)

F прогнал три сцены на реальной связке (приёмка PASS), но лог отметил слабое место в моей зоне:
сцена 2 демо-пака abrau-dyurso (`qa/packs/abrau-dyurso/pack.json`, вопрос **«Что взять к сырам?»**)
получала top-8 цитат **из статей**, а не карточек конкретных вин — для сцены «что взять к…» это
слабее демо-эффекта (хочется назвать вина, а не пересказать статью про сыр и вино).

**Диагноз:** старая эвристика v0.3 п.3 классифицировала «pairing» по regex и роутила ЖЁСТКО в
`("wines",)` — но именно фраза «Что взять к сырам?» дословно матчилась в паттерн («что взять»)…
и должна была уйти в чистый wines. На практике же вопрос дошёл до продакшна тем же путём — сработало
верно; проблема была ДРУГАЯ и глубже: жёсткая коллекция без knowledge-добивки — не то, что просил
оркестратор («wines приоритетно, knowledge — добивкой, не наоборот»), и не покрывала короткие
реплики-продолжения в чате («к устрицам», «под стейк» — из примеров оркестратора), не содержащие
глагола-рекомендации и не подходящие под старый regex.

**Правки (все в `rag/intent.py` + `rag/base.py`):**

1. **`classify(query)`** — вместо готового кортежа коллекций возвращает метку `"travel"|"fact"|
   "pairing"|"default"`; для `"pairing"` `Retriever._search_pairing()` реализует настоящий
   приоритет: сначала строго `wines`; `knowledge` подмешивается ВТОРЫМ проходом, только если карточек
   вин физически не хватило на `top_k` (типичный случай — 1978 вин без фильтра почти всегда дают
   `top_k`, так что добивка не нужна вовсе, статьи не примешиваются).
2. **Короткие гастро-фрагменты без глагола** («к устрицам», «под стейк») — отдельный regex
   `_SHORT_PAIRING_FRAGMENT_RE` (предлог «к»/«под» в начале короткой фразы, ≤30 символов, чтобы не
   ловить длинные предложения не по теме).
3. **Найденный по пути баг-регресс (важно):** первая версия правки применяла ГЛОБАЛЬНЫЙ
   refusal-порог (см. п.2 ревью 02) к wines-only проходу как есть — а порог откалиброван на
   СМЕШАННОМ пуле wines+knowledge, где статьи систематически скорят выше терпимых карточек вина
   (та же причина, по которой вообще понадобился этот роутинг). На чистом `wines` top-скор
   легитимного «Что взять к сырам?» (-1.280) провалился НИЖЕ порога (-1.2068) — не потому что вопрос
   нерелевантен, а потому что порог мерил другую шкалу; первая версия правки в ответ откатывалась на
   `knowledge`-добивку и возвращала ровно то, от чего просил уйти оркестратор. **Фикс**: если карточек
   вин хватило на `top_k`, глобальный refusal-порог к ним не применяется вовсе — сама классификация
   `"pairing"` уже достаточный сигнал «вопрос в теме» (полный разбор — докстринг
   `Retriever._search_pairing`). Настоящий refusal остаётся в силе на fallback-проходе и на
   `"default"`-ветке (посторонние вопросы вроде карбюратора).
4. **Побочный регресс от п.3, найден и частично исправлен:** широкая версия pairing-паттерна (с
   голыми глаголами «посоветуй/подбери/найди» без упоминания вина) плюс п.3 привели к тому, что
   голд-сетный вопрос `type="refusal"` **«Посоветуй хороший фильм ужасов на вечер.»** стал
   классифицироваться как `"pairing"` и обходить refusal — heuristic hit@8 просел 0.8267→0.8133 на
   том же 75-вопросном голд-сете (промежуточный прогон, не финал). Проверено: все 30 pick/pairing-
   вопросов голд-сета и так содержат лексему «вин[оаеуы]» или «что подать/взять/выбрать/заказать» —
   голые глаголы-рекомендации не добавляли покрытия, только ложные срабатывания на не-винных фразах.
   Убраны из `_PAIRING_RE`.
5. **Остаточная находка (честно, не докручено до конца):** после уборки голых глаголов вопрос про
   фильм ужасов снова корректно классифицируется как `"default"` — но hit@8 НЕ вернулся к 0.8267.
   Причина глубже роутинга: в `"default"`-ветке он идёт в СМЕШАННЫЙ пул (`wines`+`knowledge`), и его
   скор там (-0.92) оказался ВЫШЕ порога (-1.2068) — тогда как в старом хардкоде «pick» (wines-only)
   его скор был -1.76, ниже порога, то есть отказ срабатывал случайно, за счёт узкой коллекции, а не
   за счёт настоящей нерелевантности. Смешанный пул для этой фразы систематически скорит выше (та же
   механика «статьи длиннее и опрятнее по теме», что и вызвала всю эту правку). Долил в голд-сет ещё
   3 вопроса того же стиля («Посоветуй книгу/сериал/кроссовки») и пересчитал калибровку — порог
   сдвинулся (-1.2068 → -1.0532), но эта конкретная фраза осталась выше него (перекрытие легита и
   мусора в этой области шкалы кросс-энкодера подтверждено на более широких данных, не устранено).
   **Итог, который считаю честным:** на 5 исходных ranking-типах (pick/pairing/fact/travel/analog)
   hit@8 = **0.8507 — БЕЗ ИЗМЕНЕНИЙ** на протяжении всей сегодняшней правки (см. «Метрики»); просадка
   локализована ИСКЛЮЧИТЕЛЬНО в `refusal` — калибровке accept/reject на маленькой (11 вопросов)
   выборке с изначально пересекающимися распределениями скоров, не в качестве поиска/ранжирования.
   Дальнейшее закрытие (например, полноценная лемматизация вместо стемминга, больше калибровочных
   данных, отдельная не-cross-encoder эвристика «это вообще про вино») не сделано — вне бюджета этой
   правки, отмечено как открытый пункт.

**Проверено на реальном индексе (20260828.1):**

```
"Что взять к сырам?" (дословный вопрос сцены 2 abrau-dyurso) -> top-8 = 8/8 kind=wine
"к устрицам"  -> kind=wine (все кандидаты)
"под стейк"   -> kind=wine (все кандидаты)
```

**hit@8 после полировки** (78 вопросов — голд-сет пополнен 3 доп. refusal-вопросами при разборе п.5,
routing=heuristic, top_k=8): **0.8205** общий (было 0.8267 на 75 вопросах ДО сегодняшней правки),
**MRR=0.747**. По типам: analog=1.000, fact=0.923, pairing=0.917, pick=0.722, travel=0.700,
refusal=0.636 (7 из 11). **На 5 исходных ranking-типах (без refusal) — 0.8507, идентично прогону ДО
всей сегодняшней правки** — ядро поиска/ранжирования не затронуто, вся дельта — в refusal-калибровке
(см. п.5). Полный разбор — «Метрики» ниже.

Тесты: `test_intent_routing.py` — короткие гастро-фрагменты классифицируются как pairing, длинное
предложение с «к» посреди фразы не ловится ложно, waterfall возвращает только wines когда их

## Артефакты ingest для деплоя (для `publish-index.sh` агента E)

`rag ingest` пишет ВСЁ под один корень `$RAG_DATA_DIR` (по умолчанию `packages/rag/data/`, env
`RAG_DATA_DIR`). Точный состав на выходе одного прогона:

```
$RAG_DATA_DIR/
├── manifest.json              # версия индекса, модели, тайминги, refusal_threshold+калибровка —
│                               #   ЕДИНСТВЕННЫЙ файл, который надо прочитать, чтобы понять, что внутри
├── qdrant/                    # embedded Qdrant storage (см. «Два сценария» ниже)
│   ├── collection/{wines,wineries,knowledge}/   # сегменты векторов + payload
│   ├── meta.json
│   └── .lock                                    # ТОЛЬКО ОДИН процесс может открыть путь одновременно
├── bm25/
│   ├── wines.pkl               # pickle: {"ids": [...], "bm25": rank_bm25.BM25Okapi}
│   ├── wineries.pkl
│   └── knowledge.pkl
├── payloads/                   # JSONL, 1 файл на коллекцию; строка = payload точки + "id"
│   ├── wines.jsonl              # + filters/sensory (внутренние) + source/derived (карточка целиком)
│   ├── wineries.jsonl            # + filters (внутренний) + source (карточка целиком) + wine_slugs
│   └── knowledge.jsonl            # + filters (внутренний, несёт rubric/author/published_date/year)
└── labels.jsonl                   # корпус resolve_label: id, name, winery_name, search_text, text, url
```

**Что обязательно ехать ВМЕСТЕ** (один прогон `rag ingest` = одна консистентная версия): `manifest.json`
+ `bm25/*.pkl` + `payloads/*.jsonl` + `labels.jsonl`. Id между ними связаны 1:1 (тот же набор
записей, та же версия текста → тот же вектор). Микшировать сайдкары от разных версий ingest
(например, старые `bm25/` с новыми `payloads/`) — гарантированно рассинхронизирует `search()`.

**Два сценария деплоя на VPS:**

1. **Embedded-режим целиком (проще всего для одного VPS без отдельного Qdrant-сервиса).**
   Копировать/rsync весь `$RAG_DATA_DIR` (включая `qdrant/`) на VPS, на VPS выставить
   `RAG_DATA_DIR=<путь>` и `RAG_MODE=embedded` (или вообще не трогать `RAG_MODE` — это дефолт).
   API-процесс на VPS открывает `qdrant/` тем же embedded-клиентом. Требование: **только один
   процесс** может открыть `qdrant/` одновременно (файловый `.lock`) — при рестарте API дождаться
   полного завершения старого процесса перед стартом нового, иначе `QdrantClient(path=...)` упадёт
   на занятом локе.
2. **Сетевой Qdrant (прод-сценарий контракта, `QDRANT_URL`/`RAG_MODE=qdrant`).** Директория
   `qdrant/` embedded-режима **не переносится** file-копией на сервер Qdrant — это разный формат
   хранения. Правильный путь: прогнать `rag ingest` НАПРЯМУЮ на целевой Qdrant, задав перед
   командой `QDRANT_URL=http://<host>:6333` (и `QDRANT_API_KEY`, если есть) — `rag ingest` тогда
   льёт векторы по сети через `qdrant-client`, а `bm25/`/`payloads/`/`labels.jsonl`/`manifest.json`
   при этом всё равно пишутся ЛОКАЛЬНО (там, где выполнялась команда). Эти четыре артефакта нужно
   после этого скопировать на VPS туда, куда указывает `RAG_DATA_DIR` API-процесса; саму `qdrant/`
   директорию из этого прогона копировать НЕ НУЖНО (она пустая/неиспользуемая при сетевом режиме —
   `QdrantStore` с `url=` вообще не трогает файловую систему по `path=`).
   `publish-index.sh`, скорее всего, должен: (а) запускать `rag ingest --version <ts>` с нужными
   `QDRANT_URL`/`RAG_MODE` уже выставленными в окружении сборки, (б) паковать/передавать на VPS
   только `manifest.json`+`bm25/`+`payloads/`+`labels.jsonl` (или всю `data/` целиком для варианта 1
   — не ошибка, просто `qdrant/` будет мёртвым весом при варианте 2).

**Размер на диске** (полный каталог, версия 20260828.1, замерено `du -sh`, порядок величины
устойчив между версиями): `qdrant/` 56 МБ,
`payloads/` 22 МБ (выросла против волны 1-2 из-за полных source/derived блоков вместо точечных
полей), `bm25/` 13 МБ, `labels.jsonl` 3.0 МБ, `manifest.json` 4 КБ — итого **93 МБ**, без кэша моделей.

**Модели эмбеддинга/реранкера — ОТДЕЛЬНО от `data/`:** живут в `$RAG_FASTEMBED_CACHE`
(по умолчанию `packages/rag/.fastembed_cache/`, 1.3 ГБ на диске: dense-модель + мультиязычный
кросс-энкодер-реранкер).
Это НЕ артефакт конкретного ingest-прогона (не версионируется, переиспользуется между версиями
индекса) — `publish-index.sh` может либо доставить этот кэш на VPS отдельным разовым шагом (чтобы
API не тянул модели с HF Hub при первом старте), либо положиться на автоскачивание при первом
обращении (`rag/embeddings.py`/`rag/rerank.py` создают `cache_dir`, если его нет) — тогда первый
запрос на свежем VPS будет медленным (десятки секунд-минуты на скачивание), последующие — быстрыми.

## Модели: выбор и обоснование (важное расхождение с контрактом)

Контракт называет `bge-m3` (dense) и `bge-reranker-v2-m3` (реранкер). Обе модели **отсутствуют в
реестре установленной версии fastembed (0.8.0)** — `TextEmbedding.list_supported_models()` и
`TextCrossEncoder.list_supported_models()` их не содержат; добавить можно было бы только через
`add_custom_model` с ручным ONNX-экспортом, что не укладывается в разумный бюджет задачи. Бриф
прямо разрешает такую замену («возьми меньшую модель, задокументируй выбор») — этим и
воспользовался:

- **Dense**: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, 384-мерный, из реестра
  fastembed. ~240 текстов/сек на CPU этой машины. `RAG_DENSE_MODEL` — переопределяемо через env.
- **Реранкер**: `jinaai/jina-reranker-v2-base-multilingual` (1.1 ГБ, мультиязычный кросс-энкодер).
  Первая попытка скачивания упёрлась в таймаут (медленная сеть до HF, не блокировка); повторная
  фоновая попытка докачала модель успешно. `RAG_RERANKER_MODEL=""` полностью выключает стадию
  (падение на dense+BM25 RRF) — валидный режим по брифу.

**Находка про реранкер (важно для прод-пути, см. риск 1 ревью 01 — подтверждён на практике):**
латентность кросс-энкодера на CPU определяется в первую очередь **длиной документа**, не только
числом кандидатов. Полный текст статьи (до ~4000 символов) в top-50 давал 10–50 **секунд** на
запрос — не воспроизводимо для демо. Диагностировано и исправлено:
`RERANK_POOL=20` (реранкаем top-20 из уже отранжированных RRF top-50 — план Б, который сам
контракт разрешает) + `RERANK_TRUNCATE_CHARS=500` (обрезка текста перед реранком) +
`RAG_ONNX_THREADS=4` (машина используется параллельно другими агентами — без лимита onnxruntime
разбирал все 10 ядер под себя, на общей машине это давало гигантский system-time от
контекст-свитчей). После фикса: ~0.6–0.8 с/запрос. Все три параметра — env-переопределяемы
(`rag/config.py`).

## Ключевая находка по качеству (волна 1-2 — как дошли до 0.8657/0.87 на исходных 5 типах)

Первый прогон `rag eval` дал **hit@8 = 0.58** — заметно ниже 0.85. Диагностика по
`eval/report.json` (поле `details`) вскрыла две конкретные причины, обе исправлены:

1. **«Вытеснение» карточек вина статьями.** При дефолтном `collections=("wines","knowledge")`
   длинная просветительская статья про сорт («Сибирьковый: что за сорт…») стабильно обгоняла
   терпимую карточку самого вина из этого сорта — и по dense, и по BM25, и после реранка (статья
   длиннее и лексически «плотнее» по теме запроса). **Фикс**: `eval.py` роутит коллекции по типу
   вопроса (`pick`/`pairing` → `wines`, `fact` → `knowledge`, `travel` → `wineries`+`knowledge`) —
   ровно то, для чего в контракте есть параметр `collections` со свободным дефолтом; реальный
   продукт тоже сначала определяет намерение, потом решает где искать. hit@8: 0.58 → 0.78.
2. **Русская флексия ломает точное BM25-совпадение токенов.** «вино **из Дагестана**» /
   «**крымское** вино» не пересекались токенами с текстом карточки «... **Дагестан** ...» /
   «... **Крым** ...» — совпадение только по стеблю, не по словоформе. **Фикс**: русский стемминг
   токенов BM25 (`nltk.stem.snowball.SnowballStemmer`, `rag/textutil.py`) — без скачивания
   словарей/моделей. hit@8: 0.78 → 0.87.

**Что осталось (честно, не скрываю):** `pick` — самый слабый тип (0.722), несмотря на оба фикса.
Диагностика (`pick_with_filters_diagnostic`, не входит в пакет, воспроизводимо вручную): те же 11
вопросов, но с `Filters(color=…, region=…, grapes=[…])` вместо голого текста — **hit@8 = 1.000**.
Вывод: ядро retrieval (жёсткий фильтр + dense/BM25/RRF) работает безупречно, когда получает
структурные атрибуты; проблема **только** в извлечении региона/сорта из свободного разговорного
текста без единого стемминга (стемминг снимает падеж, но не прилагательное от существительного:
«**крымское**» не сводится к стеблю «крым»). Правильное место для полного решения — не RAG-ядро, а
слой NLU/LLM у B перед вызовом `search()`, который и должен наполнять `Filters` из реплики
пользователя (сцена 2 плана уже это подразумевает). Возможные дальнейшие шаги, если понадобится
поднять `pick` без переноса ответственности: полноценная лемматизация (`pymorphy3`) вместо
стемминга — не успел оценить в рамках этой задачи.

## Резолверы: пороги и скорер (rapidfuzz)

`resolve_label`/`resolve_style` используют `fuzz.token_set_ratio` с `processor=default_process`
(**не** `WRatio`, как было в первой версии). На реальном labels-корпусе (1978 вин) `WRatio` дал
ложное срабатывание **85.5** на семантически несвязанной фразе «погода в москве завтра» —
`partial_ratio` внутри `WRatio` совпадает по коротким символьным окнам почти со всем на кириллице.
`token_set_ratio` развело честное и мусорное намного чище (точное совпадение ~100, опечатка ~79-87,
шумный OCR-текст этикетки ~55-78, любой протестированный мусор ≤ 50). Пороги (`rag/config.py`,
env-переопределяемы): `LABEL_GARBAGE_CUTOFF=52`, `LABEL_CONFIDENT_CUTOFF=75`,
`STYLE_GARBAGE_CUTOFF=55`. Владелец порогов — агент A (бриф оставлял вопрос открытым, см. «придирки»
ревью 01); `low_confidence` отдаётся в `Candidate.meta`, так что B/C могут показывать
UI-подтверждение без изменений в RAG.

## Предложения к контрактам

**Уже приняты оркестратором как уточнения v0.2.4 (докс-онли, без изменения кода)** — из отчёта
волны 1-2: несравнимость `Candidate.score` между методами/вызовами, `Filters.sugar` (одно значение)
vs `reference_styles.yaml.sugar` (список допустимых категорий) — две разные проверки, источник
«синонимов» в `resolve_label` = сортовые синонимы `ref/grape_synonyms.yaml` (алиасов производителей
в данных vines нет), свободный текст — заведомо более слабый режим для `pick`/`pairing`, чем явные
`Filters` (ответственность за их извлечение — у вызывающего, не у ретривера). Ниже — новые пункты,
включая появившиеся с v0.3.

1. **DoD hit@8 ≥ 0.85 теперь блендит ranking-качество и refusal-калибровку в одну цифру** (см.
   «Метрики» → «Честно про 0.85»). На исходных 5 типах — 0.8507 (порог выполнен), с добавленными
   11 `refusal`-вопросами (после полировки приёмки F, см. соответствующий раздел, п.5) — 0.8205
   (ниже буквы DoD). Refusal — accept/reject-калибровка с сознательным компромиссом (2 легит ложно
   отказан / 4 мусорных ложно пропущено из 11 — порог специально не давит до 0/11), а не задача
   ранжирования; предлагаю развести DoD на «hit@8 ≥ 0.85 по pick/analog/pairing/fact/travel» +
   отдельный бар на refusal (например «блокирует ≥50% мусора, ложный отказ легиту ≤5%») либо явно
   принять блендинг как есть — решение оркестратора, ядро и гейт оба рабочие.
2. **`type="refusal"` расширяет enum голд-сета** за пределы задокументированного `pick|analog|
   pairing|fact|travel` (контракт, раздел «Голд-сет»). Сделано по прямому указанию ревью 02 (п.2),
   но сам контракт текстуально этого ещё не фиксирует — предлагаю добавить `refusal` в перечисление
   одной строкой при следующей правке.
3. **`resolve_label`'s meta — не строго `{source, derived}`, а их superset** (+`match_score`,
   `low_confidence`, `name`, `winery_name`) — осознанный выбор, разбор в «v0.3 п.1» выше. Если
   контракт имел в виду строго закрытую форму без исключений — однострочная правка на моей стороне,
   а не архитектурное решение.
4. **`knowledge`-payload не хранит `wine_slugs`/`winery_slugs`** из `build/articles.jsonl` (я их
   отбросил при ingest ради компактности payload). Если B/F захотят кросс-ссылки статья→вино для
   цитат — поле легко вернуть, сигнал есть в исходных данных, просто не был запрошен в контракте.
