# Исследование CPU-пути: сколько точности можно получить без GPU и уложиться в 10 с (оркестратор, 21.09)

Вопрос Вячеслава: как улучшить распознавание и работать только на дешёвых CPU (ориентир — 16 vCPU,
памяти сколько нужно), уложившись в performance-тесты (лимит скрипта 10 с на фото).
Выборка — 62 живых фото организаторов с вином из каталога (1 фото = 1.6 п.п., разброс ±3 п.п.).
Индекс — base-384 после чистки эталонов (D1). Железо для таймингов — ams3: 4 vCPU «Common KVM»,
только AVX2, 7.3 ГБ (слабее целевого). Скрипты — `qa/real_photos_cpu_path.py`,
`qa/real_photos_rapidocr.py`, `qa/vlm/read_labels_openai.py`, `qa/cpu-lab/*`.

## 1. Точность: чем читать этикетку (слияние CV + текст, W=0.3)

| Источник текста | top-1 (2 кропа CV) | top-1 (8 кропов CV) |
|---|---|---|
| PaddleOCR, детектор + 320 px (боевой путь сейчас) | 77–81% | 79–81% |
| PaddleOCR, центральный кроп 640 px | 88.7% | 90.3% |
| RapidOCR 640 px | 82–84% | 85–87% |
| RapidOCR 960 px | 88.7% | 90.3% |
| **RapidOCR 640 + 960 px (объединение текстов)** | **90.3%** | **93.5%** |
| Qwen3-VL-2B, кроп 448 / 640 / 768 px | 72.6 / 87.1 / 87.1% | 74 / 89 / 87% |
| Qwen3-VL-4B, кроп 448 / 640 / 1024 px | 75.8 / 87.1 / 95.2% | 77 / 89 / 95% |
| Qwen 27B (GPU-сервер), 1024 px | 95.2% | 95.2% |
| RapidOCR 640+960 + 2B или 4B при 640 px | 91.9% | 93.5% |
| RapidOCR 640+960 + 4B при 1024 px | 96.8% | 96.8% |

Строки OCR — с поправками матчинга (греческие и i→и двойники, текст ×0.5 без подтверждённой
винодельни); строки моделей — без гейта (моделям он вреден: 95.2 → 93.5%).

Выводы: (1) модели нужен кроп ~1024 px, чтобы обогнать OCR; на 448–640 px и 2B, и 4B читают хуже
двухмасштабного OCR; (2) маленькая модель поверх OCR прибавки не даёт; (3) объединение двух
масштабов OCR — главный рычаг CPU-пути: мелкие слова читаются на 960, крупные стилизованные — на 640.

## 2. Время на слабом CPU (ams3, 4 vCPU)

| Компонент | Время |
|---|---|
| SigLIP2 base-384, один эмбеддинг (torch, 3 потока) | 0.93 с |
| PaddleOCR 320 px / 640 px (серверный детектор, oneDNN выключен из-за бага paddle 3.3.1) | 1.3 с / 4.0 с |
| **RapidOCR (ONNX Runtime), 640 px: детектор mobile / server** | **0.34 с** / 2.0 с |
| Qwen3-VL-2B Q4 (llama.cpp, модель в памяти): 448 px все поля / 448 px 2 поля / 640 px 2 поля | 5.9 / 4.7 / 8.4 с |
| …из них картинка+промпт / генерация (640 px) | 7.3 с / 1.1 с (25 ток/с) |
| Qwen3-VL-4B Q4 | не помещается рядом со стендом (7.3 ГБ RAM), оценка ×2 к 2B |

RapidOCR быстрее PaddleOCR в 12 раз на том же входе и не зависит от рантайма paddle (баг oneDNN).

## 3. Что это значит для 16 vCPU

Вычислительные фазы (эмбеддинги, OCR, разбор картинки моделью) масштабируются почти линейно,
генерация токенов — слабо (упирается в память). Оценка для 16 vCPU того же класса:

| Конфигурация | top-1 | время на фото |
|---|---|---|
| CV 2 кропа + RapidOCR 640+960 | ~90% | ~1 с (на 4 vCPU — ~3 с) |
| CV 8 кропов + RapidOCR 640+960 | ~93% | ~2.5–3 с (на 4 vCPU — ~8.5 с, впритык) |
| + Qwen3-VL-2B при 640 px | ~93% (прибавки нет) | +3 с |
| Qwen3-VL-4B при 1024 px на CPU | ~95% | 15–25 с — вне лимита 10 с |

**Рекомендация: CPU-путь = CV base-384 + двухмасштабный RapidOCR + поправки матчинга, без VLM.**
~90–93% при 1–3 с на 16 vCPU против 95–97% с моделью на GPU/Apple Silicon. Дальнейший резерв CPU —
ускорение эмбеддингов (ONNX/int8, батч из 8 кропов), а не модель.

## 4. Попутные находки

- Сборка llama.cpp с OpenVINO на ams3 падает (Illegal instruction: нет нужных инструкций CPU).
- `llama-mtmd-cli` грузит модель на каждый запуск (23–40 с на фото) — мерить только через `llama-server`.
- Серия 4B выдавила память стенда в swap (стенд выжил, VPN не задет) — тяжёлые опыты на ams3 только
  с запасом по RAM.
- Для «полной» конфигурации (Mac/GPU): текст OCR стоит объединять с текстом модели, а не держать
  только фолбэком — 96.8% против 95.2% офлайн.
