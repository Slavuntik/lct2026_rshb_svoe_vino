# H1 · CPU-путь слияния: центральный OCR-кроп, греческие двойники, гейт винодельни

Три накопительные поправки CPU-пути (`CV_FUSION_TEXT_SOURCE=ocr`, без сети — только
PaddleOCR), поднятые в офлайн-эксперименте оркестратора с 75.8% до 88.7% top-1
(agents/H1-cpu-path.md, "Основание"):

1. **`packages/cv/cv/verify.py`** — `LabelVerifier` читает текст запроса с ЦЕНТРАЛЬНОГО
   кропа полного кадра (`CENTER_CROP=(0.15,0.05,0.85,0.98)` — те же доли, что видит VLM
   `apps/api/app/cv/vision_llm.py::CENTER_CROP` и офлайн-эксперимент
   `qa/real_photos_features.py::CWIDE`), БЕЗ классического детектора этикетки
   (`normalize.detect_label_region`). Новый метод `read_query_text_center()`, новый
   параметр `read_text(image_arr, *, size=None)`. Переключатели: `CV_OCR_QUERY_MODE`
   (`detector` — дефолт, бит-в-бит старое поведение; `center` — новый путь),
   `CV_OCR_CENTER_SIZE` (дефолт 640). `verify()`'s собственный fallback-путь (когда
   `ocr_text` не передан) НЕ тронут — по-прежнему всегда `normalize_query()`, независимо
   от режима (брифа п.1: "верификатор получает тот же текст — как сейчас").
2. **`packages/cv/cv/text_fusion.py`** (+ синхронно `qa/text_v2.py`) — греческие
   заглавные двойники пяти кириллических букв без латинского аналога: Λ→Л, Γ→Г, Π→П,
   Δ→Д, Φ→Ф (`_GREEK`). «OΛEΓ» → «ОЛЕГ» (O/E — уже латинские двойники, Λ/Γ —
   греческие). Работает БЕЗУСЛОВНО (не за флагом) — та же дисциплина, что латинские
   двойники `_UP`/`_DIG`; только подтверждённые измерением 5 пар, без домысливания
   остального греческого алфавита.
3. **`packages/cv/cv/text_fusion.py::fuse()`** + **`apps/api`** — вес текста для
   кандидата с НЕподтверждённой винодельней: новый параметр `fuse(winery_index=,
   unconfirmed_winery_w=, winery_recall_floor=0.5)`. Подтверждение — recall ОТДЕЛЬНОГО
   `TextIndexV2(fields=("winery",))` (не общей массы `text_index`) ≥ 0.5; при отказе
   `rel` кандидата умножается на `unconfirmed_winery_w` ДО `final = cv + w*rel`
   (инвариант держится, урезание сидит внутри `rel`). `app/config.py`:
   `CV_FUSION_UNCONFIRMED_WINERY_W` (дефолт 1.0 — вес для vlm/vlm_local/vlm_both, "как
   сейчас", гейт там вреден по офлайн-замеру) и `CV_FUSION_OCR_UNCONFIRMED_W` (дефолт
   0.5, применяется когда РАЗРЕШЁННЫЙ `text_source` запроса — `"ocr"`, включая случай
   `CV_FUSION_TEXT_SOURCE=vlm*`, но VLM не ответила и слияние фактически идёт на OCR).

## Приёмка — живой API (Mac, порты 8767/8768, вне боевого стенда/индекса)

Индекс `packages/cv/data-d1` (`case-20260921-d1-b384`, `google/siglip2-base-patch16-384`),
`CV_FUSION=1 CV_FUSION_W=0.3 CV_FUSION_TEXT_SOURCE=ocr`, 100 размеченных живых фото (62 в
каталоге). `qa/real_photos_serve.py` → `qa/real_photos_eval.py --served`.

| Конфигурация | top-1 (flat) | top-5 (rich) | p50 / p95, мс (сервер `timing_ms`) |
|---|---:|---:|---:|
| ДО (детектор+320, `CV_FUSION_OCR_UNCONFIRMED_W=1.0`, без гейта) | 77.4% (48/62) | 91.9% | 812 / 1142 |
| ПОСЛЕ (центр-кроп 640 + греч. двойники + гейт 0.5) | **85.5%** (53/62) | **96.8%** | 1296 / 2243 |

Цель брифа — ≥87% top-1 (офлайн 88.7%) — **не дотянута на 1.5 п.п.** (85.5%, 53/62;
разница — ~1 фото на 62). Разбор 7 улучшений/2 регрессий (flat_slug): net +5 фото —
корректно объясняет дельту 77.4%→85.5%. Один регресс — прямое попадание в собственный
пример из докстрингов («oleg»/«Олег»): OCR читает название верно, но винодельню
(«Табия») не читает НИКОГДА — гейт п.3 урезает текст и уступает CV-соседу; это ЦЕНА
уже принятого в брифе компромисса (offline тоже принесла отдельные такие регрессы при
чистом выигрыше +1.6пп 87.1→88.7%), не дефект переноса. Остальные "not_in_catalog" на
верном top-1 (12 фото) — это `CV_FUSION_GAP_FLOOR`/`CV_FUSION_CV_FLOOR` (гейт
уверенности, вне зоны этой задачи) — в **flat**-режиме (тот, что считает метрику) они
не теряются, `best_guess_slug` всегда лучший угад.

**p95 хуже цели (2243 мс против "нынешних 1.3 с") — с оговоркой по шумной машине.**
Изолированный микробенч `read_query_text()` вне HTTP на 12 фото: detector p50=737,
center p50=1143 (центр МЕДЛЕННЕЕ, не быстрее) — на реальных портретных фото 4032×3024
центр-кроп 640×… после сохранения пропорций несёт БОЛЬШЕ пикселей, чем квадрат 320×320
детектора (мой докстринг ошибочно повторил брифовую формулировку "меньше пикселей" — по
факту экономия НЕ в пикселях, а в отсутствии детектора/развёртки цилиндра). При этом
кэш `case-data/real-photos-labels/features/{ocr_crop320,ocr_cwide640}.jsonl`
(тот же Mac, раньше сегодня) показывает РОВНО обратное — p50 1662/1046 мс, совпадает с
брифом (1.7с/1.0с). В ЭТОЙ же сессии `test_verify_p95_latency_budget`
(`packages/cv/tests/test_verify.py`) без единого моего изменения кода давал 700мс→2390мс
→11555мс→1961мс на разных прогонах подряд (см. коммит-переписку теста — не трогала),
и на машине сейчас работают посторонние процессы (`mlx_vlm.server`, `VisualAlisa/server.py`
— чужие проекты, не мои). Прецедент: reports/g7-text-fusion.md уже фиксировал ту же
ненадёжность латентности "на загруженном Mac". Рекомендация (не мой мандат — контракт
не трогаю): перепроверить p95 на спокойной машине ПЕРЕД переключением дефолта
`CV_OCR_QUERY_MODE` на `center` — точность выигрывает уверенно, бюджет — под вопросом
именно сегодняшних измерений, не факт архитектуры.

## Регрессия `vlm_both` (офлайн, только гомоглифы могли её задеть — п.1/п.3 гейтированы источником `ocr`)

`CV_FUSION_UNCONFIRMED_WINERY_W`/`CV_FUSION_OCR_UNCONFIRMED_W` структурно не влияют на
vlm/vlm_local/vlm_both (вес 1.0 = no-op по построению, коммитная арифметика проверена
юнитами). `CV_OCR_QUERY_MODE` не меняет ТЕКСТ vlm-путей (OCR остаётся фолбэком, не
источником, пока VLM отвечает). Единственный кандидат на regressию — греческие
двойники в `query_tokens()`, применяются к ЛЮБОМУ тексту. Прямая проверка: токенизация
`query_tokens()` ДО/ПОСЛЕ правки на 500 реальных VLM-текстах (`features/{ocr_gwf1024,
ocr_gwf768,ocr_gw27b,ocr_vlm,ocr_gemma3_4b}.jsonl`, 100 фото × 5 кэшей) —
**0 различий**. Брифа файл `ocr_gwf1024.jsonl` — 0 греческих символов вовсе (полное
доказательство неизменности на нём). **Регрессии нет** (да/нет: нет; цифра: 0/500).

## Предложения к оркестратору (не блокеры)

1. **Зона записи брифа** не перечисляла `packages/cv/cv/verify.py`, хотя задача 1
   явно требует править `LabelVerifier` — без него задачу 1 не выполнить. Правила
   этой сессии (только нужные для задачи методы/параметры, тесты рядом в
   `packages/cv/tests/`) — стоит добавить файл в зону явно на будущее.
2. Перед переключением дефолта `CV_OCR_QUERY_MODE=center` — перепроверить p95 на
   свободной машине (см. раздел приёмки); на сегодняшнем прогоне бюджет 1.3с не выдержан,
   но замер ненадёжен (машина делит CPU с посторонними процессами).
3. 85.5% top-1 (живой API, эта же D1-индекс/конфигурация) — ниже офлайн 88.7% на
   1.5 п.п.; вероятная причина — снимок `sims384_*.npy` офлайн-эксперимента ЗАМЕТНО
   старше индекса D1 (`index_vectors_base384_d1.npy` пересобран ПОСЛЕ файлов sims384,
   по времени файлов в `case-data/real-photos-labels/features/`), т.е. офлайн-число
   считано не на том же самом снимке индекса. Не проверяла сама (вне зоны/времени) —
   ретранслирую наблюдение.

## Как запустить

```bash
# CV-юниты
cd packages/cv && .venv/bin/python -m pytest -q
# apps/api
cd apps/api && .venv/bin/python -m pytest -q
# приёмка (живой API, отдельный порт, НЕ боевой индекс/стенд)
cd apps/api
IMAGE_PROVIDER=real VERIFIER_PROVIDER=real \
CV_DATA_DIR=$(pwd)/../../packages/cv/data-d1 \
CV_MODEL=google/siglip2-base-patch16-384 \
CV_FUSION=1 CV_FUSION_W=0.3 CV_FUSION_TEXT_SOURCE=ocr \
CV_OCR_QUERY_MODE=center CV_OCR_CENTER_SIZE=640 \
./.venv/bin/uvicorn app.main:app --port 8767 &
cd .. && apps/api/.venv/bin/python qa/real_photos_serve.py --api http://127.0.0.1:8767 --out /tmp/served.jsonl
cd packages/cv && .venv/bin/python ../../qa/real_photos_eval.py --served /tmp/served.jsonl --only __none__
```
