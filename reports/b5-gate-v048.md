## 1. Кандидаты верификатора: близость скоров вместо семьи

`apps/api/app/cv/service.py::run_photo_scan()` — весь блок отбора (`if top.gap
is None / elif top.gap < threshold / else`, введённый мной же в предыдущей
волне B4) заменён на одну формулу:

```python
candidate_slugs = _dedupe_preserve_order(
    m.slug for m in matches[:top_k] if (top.score - m.score) <= settings.cv_verify_proximity
)[:5]
```

`top.gap` (family-based, G4) с этой волны читается ТОЛЬКО в `confident = ...`
(маржа not_in_catalog) — к отбору кандидатов отношения больше не имеет,
буквально по контракту §1/2 v0.4.8. `CV_NEAR_DUP_GAP_THRESHOLD` (мой же порог
из B4/более ранних волн) стал неиспользуемым — поле в `config.py` оставлено
не удалённым (обратная совместимость на случай внешнего env), но закомментировано
как заменённое; ни одна ветка кода его больше не читает.

Новый порог `cv_verify_proximity` (`CV_VERIFY_PROXIMITY`, дефолт `0.03` =
`CV_GROUP_EPSILON` пакета `packages/cv`) — по букве задания оркестратора, не
подбирал сам.

## 2. Диагноз q2 (Мускатель Массандра) — три независимые причины, разобраны раздельно

E2E-прогон обязателен по заданию — выполнен: `apps/api`, порт 8121,
`IMAGE_PROVIDER=real VERIFIER_PROVIDER=real RAG_PROVIDER=mock`, индекс
`case-20260917`, `CV_VERIFY_DEBUG=1`, фото
`case-data/eval/queries/02eef911.webp` через живой `/v1/scan/photo`.

**Живой топ-5** (score):
```
massandra-portveyn-belyy-gurzuf-...           0.83899   <- top1 (ANN)
massandra-muskat-belyy-yuzhnoberezhnyy-...    0.82711
massandra-muskatel-chernyy-...                0.81943
vinodelnya-myshako-marselan-...               0.80621
massandra-muskatel-belyy-...                  0.80612   <- ЦЕЛЬ (правильный ответ)
```
Разрыв top1 → цель: `0.83899 − 0.80612 = 0.03287`.

**Результат**: `ocr_verified: false`, `not_in_catalog: true`, `slug: null`.
Ожидание брифа ("верификатор вызван с ~5 кандидатами, выбирает
муската/мускателя белого") НЕ подтвердилось буквально — но, как и просил
бриф на случай воздержания, привожу честную трассировку и раскладываю её на
три отдельные, независимо проверенные причины:

### Причина 1 — цель НЕ попала в кандидаты (порог чуть тесноват)

`CV_VERIFY_DEBUG` показывает: верификатор вызван, но с **3** кандидатами
(top1/top2/top3), НЕ 5 — `vinodelnya-myshako-marselan` (ранг 4) и, что
критично, **сама цель `massandra-muskatel-belyy...` (ранг 5) в кандидаты не
попали**. Причина ровно числовая: `0.03287 > CV_VERIFY_PROXIMITY (0.03)` —
цель промахнулась мимо дефолтного порога на **0,0029**. Отбор кандидатов
работает ПРАВИЛЬНО по своей логике (близость к top1, не семья — юнит-тесты
п.5 это подтверждают отдельно, на чистых стабах) — но на этой конкретной
фотографии контрактный дефолт (= `CV_GROUP_EPSILON`) оказался на волосок
теснее, чем нужно для полного топ-5. **Не менял** `CV_VERIFY_PROXIMITY`
самостоятельно (это тоже, по духу задания, калибруемая величина) — фиксирую
число как есть для решения оркестратора.

### Причина 2 — OCR прочитал текст ВЕРНО

Трассировка: `ocr_text = "25.09.25 1894 МУСКАТЕЛЬ MYC MACCAHAPA KPA БЕЛЫЙ
ГОДУРОЖАЯ 2023"`, токены `wine_types=["мускатель"], colors=["белый"],
years=[2023]` — PaddleOCR + новые измерения G4 (`_WINE_TYPE_KEYWORDS`/
`_COLOR_KEYWORDS`, `packages/cv/cv/verify.py`) читают этикетку правильно.
Это не мой код (packages/cv, зона G4) — не трогал, только прочитал для
диагностики.

### Причина 3 — RAG_PROVIDER=mock не даёт кириллических названий (артефакт ЭТОГО прогона, не продовый баг)

Все 3 попавших в кандидаты слага получили `score: 0.0, matched_on: []` —
потому что `RAG_PROVIDER=mock` в этом прогоне не знает настоящий каталог, и
`_verify_candidates()` (`apps/api/app/cv/service.py`, не менялась) честно
деградирует до `name=slug` (латиница/транслит: `"massandra-muskat-belyy-..."`),
а `_WINE_TYPE_KEYWORDS`/`_COLOR_KEYWORDS` — кириллические словари с границей
слова. Латинский slug никогда не совпадёт с кириллическим "мускат"/"белый" —
это ожидаемое ограничение мок-RAG (та же категория артефакта, что B3 уже
документировала для `index_version` на `/healthz`), не дефект отбора
кандидатов и не дефект верификатора.

**Изолированная проверка** (`match_candidates()`, чистая функция без OCR,
`packages/cv`, только чтение) — тот же OCR-текст, но с РЕАЛИСТИЧНЫМИ
кириллическими именами (как их дал бы настоящий каталог) и ВСЕМИ 5
кандидатами, включая цель:
```
match_candidates(ocr_text, [все 5, кириллица]) -> 'massandra-muskatel-belyy-...'  ВЕРНО
match_candidates(ocr_text, [только те 3, что реально попали в live-прогон]) -> None
```
Это доказывает раздельно: (а) сама логика сопоставления (G4, wine_type+color
как независимые измерения) корректно выбирает верный слаг, ЕСЛИ он в списке
кандидатов и данные каталога кириллические; (б) `None` в живом прогоне —
следствие ИМЕННО отсечения кандидата порогом (причина 1) плюс мок-RAG
(причина 3), а не поломки где-либо ещё.

**Вывод**: механизм v0.4.8 (отбор по близости, независимость от gap) работает
по конструкции верно — юнит-тесты (п.5) и изолированная проверка
сопоставления это подтверждают. На КОНКРЕТНОМ q2 итог "воздержался" вместо
"выбрал верно" — из-за (1) минимального недобора порога `CV_VERIFY_PROXIMITY`
и (2) экспериментального ограничения `RAG_PROVIDER=mock`, а не из-за дефекта
в моей правке. Оба уже зафиксированы числом/трассировкой для решения
оркестратора; не корректировал `CV_VERIFY_PROXIMITY` сам.

## 3. Пороги v0.4.9 (свип оркестратора) — применены как дефолты

`apps/api/app/config.py`:
- `cv_abs_floor`: `0.9` → **`0.82`**.
- `cv_margin_floor`: `0.25` → **`0.02`** (family-gap шкала).

Источник — свип оркестратора (1982 синт-позитива с живым family-gap + 45
импосторов + 7 полевых полок), НЕ моя калибровка; число получено отдельным
сообщением, применено как есть, источник прописан в комментариях `config.py`
и здесь. Оговорка оркестратора: старый набор импосторов мог быть загрязнён
винами каталога (pass 8,9% при 0.02) — ретранслирую, не перепроверял сам.

Тесты на новые значения: `test_default_settings_pin_v049_threshold_starting_points`
(пин 0.82/0.02 напрямую), плюс два "boundary" теста
(`test_v049_abs_floor_actually_lowered_not_just_documented`,
`test_v049_margin_floor_actually_lowered_not_just_documented`) со
score/gap МЕЖДУ старым и новым порогом — падали бы под старыми дефолтами,
проходят под новыми: подтверждают, что пороги реально ПРИМЕНЯЮТСЯ, не только
задокументированы.

## 4. Приёмка на тех же 150 фото (seed 314159, из B4) — итоговый match-rate

Тот же индекс (`case-20260917`), тот же набор из 150 свежих синтетических
фото, что и в `reports/b4-gate-v047.md` (seed 314159, не перегенерировал) —
теперь с кодом v0.4.8 (отбор по близости) + порогами v0.4.9 (0.82/0.02).

| | B4 (v0.4.7, до пересчёта порогов) | B5 (v0.4.8+v0.4.9) |
|---|---:|---:|
| match-rate (гейт) | 0,0% (0/150) | **15,3% (23/150)** |
| raw top-1 (без гейта) | 44,0% | 44,0% (не менялось — ANN-ранжирование не трогал) |
| f1_top1 | 0,000 | 0,153 |
| f1_top5 | 0,573 | 0,573 (не менялось) |
| p50/p95 | 33/35 мс | 325/387 мс (верификатор теперь реально зовётся на большинстве запросов — см. ниже) |
| not_in_catalog | 150/150 | 125/150 |
| … из них по полу (score<0.82) | — | 2 |
| … из них по марже (gap<0.02) | — | **123** |
| … null-gap-заблокировано (нарушение контракта, если >0) | 0 | **0** |

**Латентность выросла на порядок (33→325 мс p50)** — ожидаемо и объяснимо:
proximity-based отбор на этом плотном каталоге теперь находит 2+ кандидата
почти на КАЖДОМ запросе (в отличие от family-based отбора, который редко
находил формальную семью) — верификатор реально вызывается на большинстве
из 150 запросов, а не почти никогда, как в B4. Всё равно на два порядка
внутри бюджета SLA (≤3с, case.md).

**Margin (123/125 = 98,4% оставшегося not_in_catalog) остаётся доминирующей
причиной даже при новом, сильно сниженном пороге 0.02** — это означает, что
у большинства оставшихся отказов gap ДЕЙСТВИТЕЛЬНО меньше 0,02 (не артефакт
плохой калибровки, а свойство каталога: много визуально похожих товарных
фото с почти неразличимым по score вторым/третьим кандидатом).

**Верификатор не спас НИ ОДНОГО из 23 совпадений** (`gated hits где raw
top-1 был неверен, а итоговый слаг верен` = 0 — все 23 confident-ответа это
случаи, где ANN top-1 УЖЕ был верен и просто прошёл более мягкий гейт).
Это прямое следствие находки §2 (RAG_PROVIDER=mock не даёт кириллических
имён — верификатор технически вызывается, но не может содержательно
сработать в ЭТОМ экспериментальном окружении). **Оговорка методологии**:
эта приёмка систематически ЗАНИЖАЕТ реальный вклад v0.4.8 — с
`RAG_PROVIDER=real` (настоящие кириллические названия) верификатор способен
дополнительно поднимать near-dup-случаи (см. §2, изолированная проверка
`match_candidates()` на кириллице сработала верно) — эту приёмку не
переделывал на `RAG_PROVIDER=real` (не было в задании этой волны, и живой
каталог RAG у меня не поднят), фиксирую ограничение явно.
