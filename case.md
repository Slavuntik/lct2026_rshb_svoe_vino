# Кейс ЛЦТ 2026 · «Сканер российских вин с описанием на платформе „Своё Вино"» (РСХБ.Цифра)

Выжимка технического задания. Первоисточник — ТЗ кейсодержателя, сохранено 15.09.2026.

## Задача

Сервис: фото этикетки (реальные условия — у полки, под углом, блики, плохой свет) →
**одна** карточка вина из каталога «Своё Вино», без экрана вариантов (референс — сканер Vivino).

Три бизнес-задачи:
1. Мгновенное достоверное распознавание по фото → сразу одна карточка.
2. Карточка в мобильном интерфейсе в стилистике портала — модуль «живёт» в каталоге платформы.
3. Удержание после поиска: доп-функция с реальной пользой (примеры из ТЗ: «Цифровой
   сомелье» с наводящими вопросами; подбор аналогов из других виноделен).

## Функциональность

1. Загрузка фото (галерея/камера) в **веб-интерфейсе**.
2. Поиск по изображению: **CV-компонент обязателен**; OCR — опциональный усилитель
   (даёт достоверность, стоит времени — на усмотрение команды).
3. Ответ карточкой в JSON + **метрика уверенности (F1) для топ-1 и топ-5** — виден отрыв
   лидера от конкурентов (в API, в UI не обязательно).
4. Страница карточки: mobile-first, открывается в мобильном браузере; нативные приложения не нужны.
5. Вина нет в каталоге → показать похожие/аналоги из других виноделен (**оценивается особенно
   высоко**) либо честно «не найдено».
6. Совместимость со скриптом оценки: bash шлёт фото по одному; на каждое — плоский JSON
   `{"slug":"wine-slug"}`; скрипт сам меряет время; сравнение с закрытой таблицей slug'ов.

## Важные вводные

- Каталог 1500–2000 позиций, **по одной эталонной фотографии на позицию**.
- **Near-duplicates — главный источник ошибок**: одна серия, разные год/сезон/категория
  при одинаковой этикетке; именно на них проверяют достоверность.
- Два набора «полевых» фото: публичный (командам) и приватный (у кейсодержателя;
  контрольный прогон — на онлайн-звонке, скрипт запускается на сервисе команды).
- Подсказка кейсодержателя: **нормализация фотографии заметно улучшает F1**.
- Каталог растёт ~50 позиций/день (в РФ ~5000 вин); скорость переиндексации не в фокусе.
- Нейросети не обязательны; для сомелье/LLM-функций — любые модели.

## Рамки

- **Точность на контрольной выборке: 90–100% совпадений — фундамент оценки.**
- F1: не обязательно 95%, но отрыв 1-го от 2-го ощутимый и стабильный — чтобы убрать
  экран вариантов.
- SLA ответа ≤ 3 с (скорость — плюс, не база).
- Деплой не требуется: демо локально, на компьютере команды.
- GPU желателен; нет GPU — оценивают на CPU. Ресурсы не предоставляются.

## Рекомендуемый стек (ориентир на целевую платформу, не требование)

Backend: Nuxt · БД: PostgreSQL + pgvector · CV: **SigLIP 2** (за основу или дообучить) ·
Каталог: Strapi CMS · Docker. Требований к лицензиям моделей и реестру ПО нет.

## Ресурсы кейса (пакет)

1. Дамп БД каталога (JSON), 1500–2000 позиций + CSV эталонных фото.
2. Публичный датасет полевых фото этикеток.
3. Стилистика портала — можно забрать и переиспользовать.
4. Скрипт оценки — предоставляется кейсодержателем.

## Сдача

Промежуточный этап: открытый репозиторий; end-to-end пайплайн (фото → поиск → JSON-карточка);
мобильный интерфейс карточки в стилистике портала; результаты на публичном датасете
(F1, время, доля совпадений 90–100%); видео-демо ≤ 7 мин без склеек; живое демо с замером
скорости и F1 топ-1/топ-5; контрольный прогон скрипта на приватном датасете на звонке.
Интерфейс на этом этапе не обязателен, но плюс.

Финал (топ-10): фиксированная версия; воспроизводимый сетап (Docker/README/ARCHITECTURE.md);
новая функция после поиска.

Документация: `README.md` (сетап, запуск, env, ограничения) и `ARCHITECTURE.md`
(границы слоёв: нормализация фото → извлечение признаков → поиск по каталогу →
выдача карточки → доп-функционал).

Питч ≤ 7 минут: концепция → архитектура пайплайна → живое демо без монтажа →
метрики F1 топ-1/топ-5 → доп-функция → выводы.
