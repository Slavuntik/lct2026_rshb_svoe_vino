## Задача 1 — слияние OCR с текстом модели в vlm/vlm_local/vlm_both (не фолбэк)

**Основание.** `apps/api/app/cv/service.py::_fusion_text_and_vectors()` (строка ~483-497):
OCR (`verifier.read_query_text`) читается ВСЕГДА, параллельно с моделью, но при ответе
хотя бы одной модели попадает в финальный текст слияния ТОЛЬКО текст модели(ей)
(`" ".join(got[k] for k in ("vlm","vlm_local") if k in got)`) — OCR используется лишь как
фолбэк, если НИ ОДНА модель не ответила. Замер (`qa/real_photos_cpu_path.py --ocr
gwf1024,vlm --union "vlm+rapidS_640+rapidS_960+lab_rapidS_1280"`, W=0.3, гейт винодельни
выключен для vlm — α=1.0, как сейчас в проде для не-ocr источников):

| Текст в слиянии | top-1 (62 фото) |
|---|---|
| только модель "vlm" (как сейчас в vlm-режиме) | 59/62 = 95.2% |
| только модель "gwf1024" (27B, как сейчас) | 59/62 = 95.2% |
| "vlm" + классический OCR (RapidOCR, объединено, НЕ фолбэк) | **60/62 = 96.8%** |
| "vlm" + "gwf1024" (обе модели, без OCR — как в vlm_both сейчас) | 60/62 = 96.8% |
| "vlm" + "gwf1024" + OCR (всё вместе) | 60/62 = 96.8% (потолок, дальше не растёт) |

Тот же +1.6 п.п. воспроизведён и на кэшах ДО чувствительного детектора (`rapid_640+rapid_960+
lab_rapid_1280`), и через независимый скрипт `qa/real_photos_two_readers.py --a vlm --b gwf1024`
(схема `union` = 96.8% против 95.2% у одиночных моделей) — не артефакт одного кэша.
Попутный вывод: ОДНА модель + бесплатный OCR даёт тот же потолок 96.8%, что и ДВЕ модели
вместе (`vlm_both`) — год ниже стоимости при том же результате, если понадобится решение
architect/devops по бюджету GPU-шлюза; в эту задачу НЕ входит, просто наблюдение.

**Важный подводный камень (проверено):** если у смешанного OCR+модель текста ОСТАЁТСЯ
включён гейт «не подтверждена винодельня» (`CV_FUSION_OCR_UNCONFIRMED_W`, применяется
сейчас только при `text_source=="ocr"`, см. `service.py` строка ~556-557), результат
падает обратно 96.8%→95.2%. Смешанный текст — это НЕ источник `"ocr"` (source остаётся
`"vlm"/"vlm_local"/"vlm_both"` по тому, какая модель ответила), поэтому веткой
`unconfirmed_winery_w = ... if text_source == "ocr" else ...` он и так не должен задеть
гейт — это тест на регрессию в приёмке (п. ниже), не новая ветка кода.

**Что сделать:**
1. В `_fusion_text_and_vectors()` изменить финальную строку так, чтобы при ответе модели(ей)
   `ocr_text` ВСЕГДА добавлялся к тексту слияния (не только при `not got`), под флагом
   `CV_FUSION_MERGE_MODEL_TEXT` (дефолт `false` до приёмки, как остальные флаги слияния).
   `source`/лейбл в ответе — как сейчас (по тому, какая модель ответила); `label_text`,
   который видит `verify()`, не менять (это отдельное поле `ocr_text`, уже так и есть).
2. Тесты: пусто-модель-текст → как фолбэк (не меняется); модель ответила + флаг выключен →
   как сейчас (текст = только модель); модель ответила + флаг включён → текст = модель + OCR
   через пробел; `text_source` не зависит от флага.
3. Не трогать `CV_FUSION_TEXT_SOURCE=ocr` ветку — она уже мержит правильно (просто не через
   этот код путь).

## Задача 2 — алиас винодельни в гейте подтверждения (только Голубицкое, только гейт)

**Основание.** Промах 93.97 (`golubitskoe-estate-chardonnay`, CPU-путь и все источники текста
одинаково): в каталоге ОДИН производитель, ДВА написания поля «Винодельня» — «Поместье
Голубицкое» (2 SKU, включая истину) и «Golubitskoe Estate» (28 SKU, включая ложный top1
`pomeste-golubitskoe-shardone-rezerv-...`). Текстовая масса УЖЕ отдаёт истине победу
(15.36 против 9.89 — имя истины само по себе «Golubitskoe Estate Chardonnay»), CV — почти
ничья (0.8678 против 0.8676). Решает ИСКЛЮЧИТЕЛЬНО гейт `winery_index`
(`cv/text_fusion.py::fuse(winery_index=...)`, ставится в `apps/api/service.py::
_fusion_winery_index()`): recall поля winery для истины = 0.40 (< 0.5 floor) — «Golubitskoe»
совпал, «Поместье»/«pomeste» нет; для ложного кандидата recall = 1.0 («Golubitskoe»+«Estate»
совпали оба). Без гейта истина побеждает с запасом +0.15; с гейтом проигрывает −0.04.
Подтверждено по ВСЕМ источникам текста (OCR-объединение, 27B, vlm, человек-читатель) —
не артефакт одного OCR-прочтения.

**Правило выведено из структуры каталога, НЕ подогнано под фото:** общий редкий токен поля
«Винодельня» — «golubitskoe» встречается ровно в 2 из 135 уникальных строк «Винодельня»
всего каталога (2103 позиции), это и есть сигнал «одна и та же винодельня, два написания».
**Важно — это НЕ безопасно как чисто статистическое правило.** Полный разбор всех токенов с
той же частотой (df 2-4 из 135 строк) показал: одинаково редкие токены — это ЧАСТО родовые
слова международного винного брендинга, а не имена собственные: «estate» (df=2: Golubitskoe
Estate И Mantra Estate — РАЗНЫЕ производители), «vineyards» (df=2: Litavshchuk И AYA Organic
— РАЗНЫЕ), «chateau» (df=4: 4 РАЗНЫЕ), «семейная»/semeynaya (df=2: винодельня Михаила
Колесникова И «ЛОРИО» Логуновых — РАЗНЫЕ; ровно то служебное слово, которое тимлид просил
проверить), «alma» (df=2: Alma Valley И Villa di Alma — общее ГЕОГРАФИЧЕСКОЕ имя). Полный
список и код разбора — `qa/real_photos_winery_alias.py` (запусти сам, воспроизводится
детерминированно). Поэтому: НЕ реализуй автоматическую рантайм-кластеризацию по df/idf —
она либо ловит только Голубицкое (тогда зачем автоматика), либо цепляет мусорные пары.

**Что сделать:**
1. Создать `case-data/winery_aliases.json` (вне git, рядом с `families.json`, тот же по духу
   формат — список групп): один проверенный вручную алиас на старте:
   ```json
   {"groups": [{"strings": ["Поместье Голубицкое", "Golubitskoe Estate"],
                "anchor_token": "golubitskoe",
                "note": "один производитель, 2 vs 28 SKU в каталоге, см. reports/ml-lead-plan.md"}]}
   ```
2. `cv/text_fusion.py` (или `load_catalog_index`/новая функция рядом): при построении
   `winery_index` (вызывается из `_fusion_winery_index()` в `service.py`, СТРОГО с
   `fields=("winery",)`) — для строки «Винодельня» слага, которая входит в группу алиасов,
   доктокены = ОБЪЕДИНЕНИЕ токенов ВСЕХ строк группы (а не только своей строки). Загрузка —
   как `cv/families.py::load_family_by_slug()`: путь `CV_WINERY_ALIASES_JSON`, дефолт
   `$CASE_DATA_DIR/winery_aliases.json`, файл отсутствует/пуст → текущее поведение 1:1, ничего
   не ломая. Основной индекс слияния (`FUSION_FIELDS`, name+winery+grape+category+sugar) НЕ
   трогать — алиас только в `winery_index`, ровно как просил тимлид.
3. Тесты: пара группы алиасов confirm друг друга (recall по объединённым токенам ≥ floor
   в синтетическом примере); винодельня вне любой группы — поведение не меняется (регрессия);
   файл алиасов отсутствует — старое поведение.
4. Не добавляй «nikolaev» (df=2, `А. Гордиенко & М. Николаев` / `Николаев и сыновья`) в
   `winery_aliases.json` — совпадающая фамилия НЕ подтверждена как один производитель
   (нет фото, нет способа проверить в этом спринте); оставь на усмотрение pm/product, если
   понадобится чистка каталога.
