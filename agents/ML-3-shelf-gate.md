## Основание (ml-lead, 22.09, офлайн; полный разбор — `reports/ml-lead-shelf-gate-v2.md`)

Живая приёмка ML-2 (`reports/ml-eng-ml2.md`): гейт v1 (`cv.shelf_crop.segment_boxes` —
колонок ≥ 2 И боксов текста в ряду ≥ 30) ложно сработал на одиночной бутылке
`87.88_28-08-2026_16-56-20.webp` — 2 "колонки" родились из 2 OCR-разрывов ВНУТРИ этикетки
ОДНОЙ бутылки (не между бутылками), кроп срезал ~38% кадра слева, живая регрессия
95.2%→93.5% (59/62→58/62). Блокер ml-engineer: "нужен доп. сигнал (площадь/пропорции
центральной колонки к кадру)".

Офлайн проверил 4 сигнала-кандидата тимлида на ВСЕХ 100 фото организаторов
(`case-data/real-photos`, 62 в каталоге + 38 NONE) + 32 полевых (`Field/`) + 25 «настоящих
полок» (qa-manual confidence sure/likely минус 1 побайтный дубль) — только один даёт 0/100:

| сигнал | 100 орг. (цель 0) | 32 полевых | 25 полок |
|---|---|---|---|
| только v1 | 4 | 17 | 15 |
| **text_aspect ≥ 1.2** | **0** | **12** | **10** |

`text_aspect` = (охват ВСЕХ текстовых боксов уже выбранного ряда по X, `max(x1)-min(x0)` —
считается из `rx0`/`rx1`, которые уже есть в `segment_boxes()`, новых боксов искать не нужно)
/ (высота ряда, `ry1-ry0`). Настоящая полка — широкий ряд (много бутылок в ширину), одиночная
бутылка — этикетка почти квадратная или выше, чем шире. Порог 1.2 — запас 0.09 над МАКСИМУМОМ
среди всех 4 ложных срабатываний v1 на 100 фото (1.106), НЕ подогнан под сам регрессионный
кейс (у него 1.06). На 8 целевых полевых (`part3-field.csv`, sure/likely, вино в каталоге)
теряет только F04 (живьём был чистый минус, ранг 3→нет) и F08 (живьём нейтрален, both=1) —
остаются F02/F10/F16/F17/F21/F30 = 6/8. Другие 3 кандидата (доля ширины центр. колонки, число
"сопоставимых" колонок, повторяемость высоты боксов) поодиночке 0/100 не дали — таблица и
разбор всех вариантов в отчёте. Прототип для сверки — `qa/real_photos_shelf_gate_v2.py`
(`--diagnose` затем `--sweep --target8`, детерминировано, ~36 с).

## Что сделать

1. `packages/cv/cv/shelf_crop.py::segment_boxes()` — сразу после строки
   `rx0, rx1 = x0[row_mask], x1[row_mask]` посчитать `row_height = ry1 - ry0` и
   `text_aspect = (rx1.max() - rx0.min()) / row_height if n_row_boxes and row_height > 0
   else 0.0` (деление на 0 при вырожденном ряде/пустом ряде → 0.0, не исключение — та же
   дисциплина, что остальной модуль). Новая константа `DEFAULT_MIN_TEXT_ASPECT = 1.2`
   (докстринг-комментарий — откуда порог, как у `DEFAULT_MIN_BOXES`), новый параметр
   `min_text_aspect: float = DEFAULT_MIN_TEXT_ASPECT` в `segment_boxes()` и `segment_shelf()`.
   Расширить условие: `is_shelf = len(cols) >= 2 and n_row_boxes >= min_boxes and
   text_aspect >= min_text_aspect`. Добавь `text_aspect` полем в `ShelfSegmentation`
   (диагностика, как `n_row_boxes`/`col_method`) — не обязательно, но полезно для будущей
   отладки на живом.
2. `apps/api/app/config.py` — `cv_shelf_min_text_aspect: float` из `CV_SHELF_MIN_TEXT_ASPECT`
   (дефолт `"1.2"`), по образцу `cv_shelf_min_boxes` (см. соседние строки ~320-327, тот же
   `field(default_factory=lambda: float(os.environ.get(...)))`, с комментарием-докстрингом
   про происхождение порога). `apps/api/app/cv/service.py::_apply_shelf_crop` — передать
   `min_text_aspect=settings.cv_shelf_min_text_aspect` в вызов `segment_shelf()`.
3. Тесты `packages/cv/tests/test_shelf_crop.py`:
   а) РЕГРЕССИОННЫЙ синтетический паттерн, воспроизводящий форму "87.88" — один ряд, ≥30
      боксов, 2 X-кластера (колонки), но узкий охват по X относительно высоты ряда (аспект
      < 1.2) → `is_shelf=False` с дефолтным порогом; отдельно проверь, что с
      `min_text_aspect=0` (эквивалент старого поведения) тот же паттерн даёт `is_shelf=True`
      — то есть тест доказывает, что именно НОВЫЙ сигнал ловит старую регрессию, а не
      случайное совпадение с чем-то другим.
   б) существующий "проход" паттерн (широкий ряд, 3+ колонки, широкий охват текста) —
      `is_shelf` не должен измениться относительно теста до этой правки.
   в) паттерн на границе порога (аспект ≈ 1.2 ± небольшой шаг) — задокументируй поведение
      в самом тесте (какая сторона границы что даёт).
   `apps/api/tests`: если правишь — флаг `cv_shelf_crop` по умолчанию выключен, поведение не
   меняется (регрессия невозможна by construction); при включённом флаге — фикстура-регрессия
   ML-2 (или синтетическая аналогичная) больше не режется.
4. `CV_SHELF_CROP` остаётся выключенным по умолчанию — включение флага в проде решает
   тимлид отдельным шагом после живой приёмки, это не часть этого брифа.

## Критерии приёмки (живой API — `qa/real_photos_serve.py --flat-only` →
`qa/real_photos_eval.py --served`, `CV_SHELF_CROP=1 CV_SHELF_MIN_TEXT_ASPECT=1.2`; полевой
аналог по образцу `reports/qa-auto-field-photos.md`, глоб `*.jpeg` вместо `*.webp`)

- 62 фото каталога: **0 регрессий** относительно свежего живого бейзлайна флага-выключен
  (сверь заново в день прогона — офлайн/живое расхождение в проекте случалось уже 3 раза,
  `ORCHESTRATION.md`). Проверь именно `87.88_28-08-2026_16-56-20.webp` поимённо — top-1 на
  ней не должен ухудшиться относительно бейзлайна без гейта (это и есть регрессия ML-2).
- 22 полевых NONE (`part3-field.csv`, true_slug=NONE): **0 новых ложно-уверенных**
  (`rich.not_in_catalog`) относительно бейзлайна флага-выключен — ML-2 живьём получил 1/22
  (F09) при v1, с v2 не должно остаться ни одного.
- 8 целевых полевых (sure/likely, вино в каталоге, `part3-field.csv`): top-1 **≥ 2/8**. Мой
  офлайн потолок — кроп срабатывает (гейт проходит) на 6/8, но живой top-1 требует ЕЩЁ и
  правильно распознать по кропу — ML-2 живьём получил 0 чистых побед top-1 на этих же 8 при
  `TEXT_SOURCE=ocr`, поэтому бар именно ≥2/8 (критерий тимлида), не 6/8.
- Тайминг: p95 в пределах бюджета 10 с (детектор ~0.3-0.6 с/фото на Mac, доп. сигнал —
  арифметика над уже посчитанными боксами, нулевая доп. стоимость; перепроверь на стенде).
- Полные тесты `packages/cv`/`apps/api` зелёные. Коммиты с pathspec.

эта задача только про НОВЫЙ сигнал поверх них. Не трогать `_split_oversized_segments`/
`geometric_columns` (риск №1 ml-lead из ML-2 — плотные ряды ОДИНАКОВЫХ бутылок без текста
между ними — вне бюджета). Не подгонять `1.2` под живые 62/8 фото задним числом: если живая
приёмка хуже офлайн-ожидания — блокер тимлиду с числами (тот же принцип, что ML-1/ML-2:
правило должно быть объяснимо на структуре данных, не подогнано под конкретную выборку). Не
включать `CV_SHELF_CROP` по умолчанию и не трогать боевой индекс/стенд ams3 — не твоя зона.
