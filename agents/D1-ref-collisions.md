(`packages/cv/data-d1/`), отчёт `reports/d1-ref-collisions.md`. Боевой индекс
`packages/cv/data/` НЕ трогать — подмену делает оркестратор после проверки.

## Находка оркестратора (21.09)

Сопоставление «вино → фото» шло по нормализованному имени файла. Имена вроде
`Screenshot_7.webp`, `Screenshot_17.webp` в CSV использовали РАЗНЫЕ винодельни, и в uploads
лежат несколько разных файлов с одним стемом. Пример `roze-2` (Табия Розе): кандидаты
`Screenshot_17_6d600742f0` — чистое фото бутылки ТАБИЯ Розе (правильный!),
`Screenshot_17_949d72d743` — люди с лошадью на винограднике, `Screenshot_17_f963c072a9` —
афиша Château Pinot. Выбрана афиша → класс `person_with_wine` → `usable=false` → вино выпало
из индекса. На реальных фото организаторов Табия Розе встречается 3 раза из 100.

Вторая половина проблемы: `cv/cli.py::_refs_from_slug_refs` кладёт в индекс ВСЕ кандидаты
(`[chosen] + candidates` → ракурсы `real-2..real-8`, ~100 векторов). Для коллизий это чужие
бутылки и афиши под чужим слагом — реальное фото чужого вина может «найтись» как этот слаг.

## Задача

1. Перечень: все слаги `slug_refs.json` с `len(candidates) > 1` (66 шт., список
   `multi_candidate_slugs` в шапке файла) + все с `usable=false` и заданным
   `ref_quality_class` (10 шт.: pobeda, rozovoe-zoloto, roze-2 и др.).
2. На каждый слаг — контакт-лист всех кандидатов (PIL, подписи с номером и хэшем), смотри
   глазами (Read). Каталожные данные: `case-data/case_catalog.json` (name, winery_name,
   color, grapes), превью соседних вин той же винодельни — `case-data/thumbs/`.
3. Решение на слаг: какой кандидат — ЭТО вино (винодельня/название на этикетке, цвет,
   форма бутылки); какие кандидаты — тоже это вино (другие фото той же бутылки — можно
   оставить доп. ракурсами); какие — чужие вина/шум (исключить). Нет ни одного подходящего —
   слаг остаётся без эталона (usable=false), это честно.
4. Внести решения штатно: `qa/manual_photo_matches.yaml` (slug → файл) — посмотри, как
   census применяет оверрайды (`load_manual_matches`, ~стр. 328) и как считается `usable`
   для оверрайда; если нужны доп. ракурсы «тоже это вино» — предложи минимальное расширение
   схемы (список файлов) и обнови census + `cv/cli.py::_refs_from_slug_refs` согласованно, с
   тестами. Комментарий в YAML — метод и доказательство по каждому слагу коротко.
5. Перегенерировать `slug_refs.json` штатным census (сначала сделай копию текущего файла
   `slug_refs.before-d1.json`), собрать индекс в `packages/cv/data-d1/` версией
   `case-20260921-d1` (кэш синтетических ракурсов переиспользуется — пересчитываются только
   эмбеддинги; см. `cv build-index --views-cache`; длинная сборка — в фоне, правило из
   ORCHESTRATION.md про фоновые процессы).
6. Проверка: `qa/real_photos_features.py` умеет считать близости реальных фото
   (`CV_DATA_DIR=packages/cv/data-d1`, вывод — в отдельную папку: добавь аргумент
   `--out-dir`, по умолчанию прежний путь) и `qa/real_photos_eval.py` — top-1 на размеченных
   реальных фото (`case-data/real-photos-labels/part*.csv`) ДО/ПОСЛЕ. Плюс self-check
   `cv selfcheck` на новом индексе.

## Отчёт (reports/d1-ref-collisions.md, ≤ 60 строк)

Сколько слагов проверено; сколько исправлено (выбран другой файл), сколько доп. ракурсов
удалено как чужие, сколько слагов вернулось в индекс, сколько осталось без эталона; 5
показательных примеров; метрики ДО/ПОСЛЕ на реальных фото и self-check.

## Не делать

Не трогать боевой индекс и стенд; не коммитить данные кейса (фото, json кейса); коммиты —
только с pathspec. Не угадывать: сомнение → исключить кандидата и пометить в отчёте.
