# Основной сканер: эксплуатация и диагностика

Актуализация: 28.09.2026. Дополнение к [устройству сканера](label-recognition.md). Проверенный профиль — `IMAGE_PROVIDER=real`, `CV_FUSION=1`. Для витрины и отдельного адаптера WineScan действуют собственные инструкции: [native-схема](../infra/native/README.md), [полки](product/shelf-sommelier.md), [запуск всего проекта](local-full-stack.md).

## Где выполняются вычисления

На проверенных native-серверах API, SigLIP2, визуальный поиск и OCR выполняются локально на CPU; VLM вызывается через настроенный LiteLLM/OpenAI-совместимый шлюз. Приложению нужен HTTP API модели, SSH к GPU для каждого распознавания не нужен. Каталог, векторный индекс и веса локальных моделей устанавливаются отдельно: LiteLLM их не поставляет.

Для работы требуются совместимые каталог/slug, визуальный индекс, веса CV/OCR и окружение Python. Работающий шлюз сам по себе не исправляет отсутствующий или несовместимый индекс. Режим без VLM (`CV_FUSION_TEXT_SOURCE=ocr`) возможен, но его качество нельзя объявлять равным опубликованным результатам совместной ветки.

Значение `CV_MODEL` должно соответствовать подготовленному индексу; сменить только имя модели недостаточно. Индекс: `case-20260921-d1-b384`, 2058 позиций, 14394 вектора размерности 768. Каталог содержит 2103 позиции, 44 без выбранного эталона; эти числа описывают разные сущности и не должны искусственно уравниваться.

`VISION_LLM_URL`, `VISION_LLM_KEY`, `VISION_LLM_MODEL` задают шлюз. В аудите использован alias `qwen3.8-27b`; официальная ревизия модели за этим алиасом не подтверждена. Храните ключ в локальном окружении/секретах сервера, не в примерах команд или отчётах. Дедлайн VLM считается от начала обработки распознавания, но не является жёстким пределом всей HTTP-задержки: CV, обработка файла, очередь, прокси и нагрузка тоже требуют времени.

## Запуск

Для Docker следуйте [полному quick-start](DOCKER_QUICKSTART.md): базовая демонстрационная сборка и full-профиль с реальными индексами — разные режимы. В full-профиле каталог и модели монтируются из подготовленной копии данных, кэш — в постоянном томе. Не запускайте два embedded Qdrant на одном рабочем каталоге: индекс имеет блокировку. Для оценки используйте отдельную копию.

Для native-серверов см. [infra/native/README.md](../infra/native/README.md) и [инструкцию ams3](../infra/ams3/README.md). Рабочие файлы:

| Путь | Назначение |
|---|---|
| `/opt/somelye/app` | Активное дерево приложения |
| `/opt/somelye/web` | Опубликованная сборка фронтенда |
| `/opt/somelye/somelye.env` | Окружение сервиса, включая секреты |
| `/opt/somelye/venv` | Python-окружение API |
| `/opt/somelye/releases` | Подготовленные релизы и предыдущие деревья |
| `/opt/somelye/deployed-commit` | Отметка успешно опубликованной ревизии |

Эти пути не означают, что все данные находятся внутри `app`: каталог, модели, индексы и изменяемое состояние должны иметь собственные постоянные пути.

## Кэш и причина устранённого падения

Раньше UI-only активация заменяла дерево `app`, хотя работающий API не перезапускался. Вложенный `.embed_cache` исчезал по живому пути. Старый энкодер создавал каталог только в конструкторе, поэтому последующая запись в кэш вызывала исключение. `healthz` продолжал показывать прогрев; rich-скан падал с HTTP 500, flat скрывал сбой пустым slug.

Теперь UI-only не перемещает `app`; кэш по умолчанию вынесен в `$XDG_CACHE_HOME/vinchik/embeddings` или `~/.cache/vinchik/embeddings`. Явный `CV_EMBED_CACHE_DIR` имеет приоритет и тоже должен находиться вне дерева релиза. В Docker full используется `/cache/cv` в `api_cache`.

Запись создаёт каталог при необходимости, использует временный файл и атомарную замену. Ошибка записи не отменяет вычисленный вектор. Повреждённый JSON или ошибка чтения приводит к пересчёту. Ключ учитывает байты, форму и dtype входа, схему обработки, версию Transformers и имя модели. Это не полная проверка произвольного семантически неверного вектора в корректном JSON и не замена проверке целостности индекса.

Смена схемы ключа означает холодные первые обращения. Пересобирать индекс из-за этого исправления не требуется. Не удаляйте пользовательские данные или индексы для проверки кэша: воспроизведение выполняется в отдельном стенде с сохранением прежнего каталога.

## Логи и архив

| Наблюдение | Значение |
|---|---|
| `cv_fusion_sources: models=...` | Источник вернул текст, пустой ответ либо ошибку/дедлайн; это не подробный HTTP trace |
| `cv_fusion: local=... model=... chosen=...` | Предположения веток и выбранная сторона |
| `source=ocr` | Текст выбранной ветки; не доказательство недоступности VLM |
| `cv_identity: ... applied=False` | Конфликт обнаружен только для диагностики, ответ не отклонён |
| `Embedding cache write failed` | Вектор вычислен, сохранение не удалось; проверить права и диск |

При `SCAN_ARCHIVE_DIR` сохраняются только rich-запросы. Flat и `/v1/eval/predict` в этот архив намеренно не попадают. На диске создаются JPEG и JSON sidecar, распределённые по `confident`, `unsure`, `failed`, а также `index.jsonl`.

В архив попадает изображение **после обработки HTTP-обработчиком**, затем оно перекодируется в JPEG без EXIF. Это не гарантированная копия оригинальной фотографии полного разрешения. Для точного повторного прогона сохраняйте исходный файл и SHA256 отдельно.

Sidecar содержит выбранный slug, кандидатов, score, время, источник/текст, структурированные VLM-поля, предположения двух веток, `identity_rejection`, версию индекса. `verified_slug` изначально не задан: уверенная корзина не является ручной разметкой. Поле `reason` корзины описывает общий гейт и не заменяет отдельное `identity_rejection`; в эксперименте конфликт может попасть в `unsure` с общей причиной `margin`. Автоматическая очистка архива в модуле не реализована — объём и срок хранения задаются эксплуатацией.

## Диагностика по симптомам

| Симптом | Проверка и действие |
|---|---|
| `warm=true`, но скан не работает | Отправить известную этикетку через `flat=0`; проверить JSON и ожидаемый slug, затем журнал API |
| HTTP 200, пустой flat-slug | Повторить rich; различить отказ модели и техническое исключение |
| `not_in_catalog=true` на известном вине | Проверить наличие slug/эталона, позицию в `matches`, floor/gap, текст OCR/VLM и версию этикетки |
| Карточка соседней линейки | Сопоставить название, серию, год и семейство; высокий семейный gap не доказывает точный SKU |
| Модельный источник пуст/ошибка | Проверить URL, имя модели, права ключа, дедлайн и breaker; не печатать ключ в журнал |
| HTTP 429 | Установить, какой слой ограничивает запросы; не запускать массовые повторы параллельно |
| HTTP 502 или HTML вместо JSON | Проверить nginx/upstream, состояние API и таймауты; это не валидный ответ распознавания |
| Долгое первое фото | Проверить прогрев моделей, холодный кэш и нагрузку CPU; сравнивать новые фото отдельно от повторов |
| Ошибка Qdrant lock | Проверить второй процесс на том же каталоге; подготовить изолированную копию для аудита |

На сервере, с правами чтения журнала:

```bash
systemctl is-active somelye-api
curl --fail-with-body -sS http://127.0.0.1:8000/v1/healthz
journalctl -u somelye-api --since '15 minutes ago' --no-pager
cat /opt/somelye/deployed-commit
curl --fail-with-body -sS http://127.0.0.1/release.json
```

Читать полный env для обычной диагностики не требуется. Сопоставляйте время запроса, код HTTP и сообщения веток; старые сохранённые метрики `/v1/metrics/scan` сами по себе не подтверждают новый прогон.

## Выкладка через Git и откат

1. Проверить рабочее дерево, получить свежий `origin/main`, интегрировать изменения без потери чужих коммитов. Зафиксировать код и отправить обычным push без force.
2. Выбрать конкретный `DEPLOY_REF`. Скрипт собирает фронтенд из `git archive`, затем переносит приложение и сборку. Незакоммиченные файлы в релиз не попадают.
3. Обычная активация заменяет приложение, синхронизирует зависимости и перезапускает API. Новая веб-сборка публикуется после прогрева и проверок.
4. Проверяются health/OpenAPI, эталон Nature Vert с точным slug, белый кадр без карточки и готовность настроенной витрины. Нужен установленный эталон; его отсутствие блокирует релиз реального провайдера.
5. Сверить `deployed-commit`, `release.json` и реальный скан. GitHub Actions и ручной запуск скрипта — разные способы запуска одного механизма; не объявлять CI успешным без проверки его результата.

Пример из корня репозитория, с собственными существующими ключом и known_hosts:

```bash
DEPLOY_REF='<проверенный SHA>' \
SSH_KNOWN_HOSTS="$HOME/.ssh/known_hosts" \
bash infra/ams3/push-release.sh 89.110.72.101 "$HOME/.ssh/ci_do_ams3"
```

Для второго хоста применяется тот же скрипт с соответствующими доступами. `PUSH_ONLY=1` подготавливает релиз без активации. `SKIP_API_RESTART=1` допустим только при неизменных runtime-деревьях, проверяемых `runtime-unchanged.py` (`apps/api`, сервер витрины, `packages`, `pipeline`). Не используйте его для изменений модели/распознавания. В этом режиме API и его каталог сохраняются; проверки инференса всё равно выполняются.

При неудачной активации скрипт возвращает перемещённые деревья и пытается запустить прежний API. Отметка коммита обновляется после успешной публикации веба. Это откат файлов приложения, не резервная копия базы, моделей и всего состояния машины. Изменения зависимостей и внешних данных требуют отдельной проверки.

Для управляемого возврата на предыдущую версию заново выложите известный исправный Git SHA обычным полным релизом и выполните те же проверки. Если автоматический откат сообщил ошибку, сохраните журнал, проверьте systemd и данные; не маскируйте неудачу ручной заменой `deployed-commit`.
