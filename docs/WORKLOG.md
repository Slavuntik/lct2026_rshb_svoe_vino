### Проверки и что нашлось

- **Qwen3-VL-4B на 3 публичных фото читает этикетки хорошо:** «ТАБИЯ Пино Нуар 2025»,

  белый» выше розового (+1,87 против +1,32). Для вин вне каталога винодельня не совпадает ни с
  одним кандидатом.
- **Не получилось:**
  - задержка VLM 16–40 с на фото вместо ожидаемой ~1 с; мерили на GPU 3 рядом с двумя
    процессами кэша и при высокой загрузке CPU — нужно перемерить на свободной карте;
  - у фото Массандры JSON обрезался на 160 токенах (исправлено: 256 токенов, компактный JSON,
    разбор обрезанного ответа, тест на реальном случае);
  - модель выдумала сладость «сухое» у сладкого вина — промпт требует поля «только если
    написаны».
- **Аналоги на реальном каталоге.** Первая версия подбирала к «Мускателю белому» бюджетные
  купажи одного производителя: поле «Белые сорта винограда» считалось сортом, дубли карточек
  занимали выдачу. Исправлено: обобщённые сорта не учитываются, один аналог от винодельни,
  тихое и игристое не смешиваются. Тест тоже переписан: он закреплял спорное поведение.
- **Сомелье на реальном каталоге.** К рыбе сначала выходили только брюты, объяснения были с
  ошибкой в числе («подают красное сухое вина»), порядок при равных очках был случайным.
  Исправлены веса, множественное число и порядок.
- **Выбор рамки на публичных фото** (без подбора правила): Массандра остаётся верной, у Табии

### Мультиракурсная галерея эталонов (PLAN 3.3)

**Гипотеза.** На `synth_v2` даже с настоящей рамкой top-1 0,743: этикетка на полке повёрнута,
а эталон фронтальный. Если добавить в индекс повёрнутые виды эталона (как в работе Huang et
al. 2024 про этикетки вин, только без обучения), поиск станет устойчивее к ракурсу.

**Как сделано.**

- `build_index --yaws=-30,-15,0,15,30`: высокие упаковки (h/w ≥ 1,8) поворачиваются
  `rotate_cylinder`, у коробок остаётся один вид.
- Вино представлено несколькими векторами, скор вина — максимум по ним.
- 10 483 вектора на 2103 вина, 47 МБ на индекс.
- Сборка на GPU 3: full — 12 мин (подготовка 264 с, эмбеддинги 458 с), label — 9 мин
  (213 с и 348 с).
- Точный поиск по 10 тыс. векторов — по-прежнему миллисекунды.
- Оценка — офлайн по тем же кэшам: эмбеддинги запросов не зависят от галереи
  (`offline index-compare`, `QueryCache.load(indexes=...)`).

**Результат** (fold 1, top-1 / top-5):

| Галерея full + label | v1 первая рамка | v1 настоящая | v2 первая рамка | v2 настоящая |
|---|---|---|---|---|
| фронтальные | 0,812 / 0,913 | 0,896 / 0,990 | 0,618 / 0,763 | 0,743 / 0,905 |
| full с поворотами | 0,824 / 0,916 | 0,912 / 0,995 | 0,635 / 0,769 | 0,755 / 0,913 |
| label с поворотами | 0,822 / 0,915 | 0,902 / 0,993 | 0,624 / 0,770 | 0,755 / 0,914 |
| **обе с поворотами** | **0,826 / 0,917** | 0,911 / 0,998 | **0,642 / 0,775** | **0,768 / 0,920** |

- Выбор рамки, переобученный на скорах новой галереи (`configs/box_ranker_v2.joblib`):
  v1 0,843 / 0,940, v2 0,661 / 0,801.
- Против прежней связки (фронтальная галерея + `box_ranker_v1`: 0,833 / 0,934 и
  0,638 / 0,790) это +1,0 и +2,3 п.п. top-1. **Принято.**

**Оговорка.** Повёрнутые запросы `synth_v2` и повёрнутые эталоны делает одна и та же функция
`rotate_cylinder`, так что на v2 выигрыш может быть завышен: модель поворота «угадывает» сама
себя. Частично успокаивает, что на `synth_v1` поворотов нет, а прирост есть (+1,4 п.п.): видимо,
повёрнутые виды просто дают более плотное покрытие эталона. Проверять на реальных фото.

### Утечка в негативах leave-one-out — все прежние цифры отказа по логиту были завышены

**Как нашлось.** Разбирал странность:

- на реальных фото вина вне каталога получали логит −0,18 и +0,32, выше порога;
- на синтетике порог −1,0 отклонял 60% «вин вне каталога» при 0,9% ложных отказов;
- у визуального top-1 логит не опускается ниже −1,06, а 5,6% кадров лежат скоплением
  −1,00…−0,96 (кандидаты без совпадений SIFT).

**Причина.** Негатив «вина нет в каталоге» строился из тех же кандидатов без верного вина, но
признак `gap` (отставание от лучшего визуального скора) оставался посчитанным вместе с верным
вином. Если верное вино было визуальным top-1, у лучшего оставшегося gap < 0. У настоящего вина
вне каталога gap = 0. Вес `gap` в модели самый большой, и модель по сути узнавала «убранное»
вино. Проверка: `gap == visual − max(visual)` в каждом запросе таблицы — да.

**Исправление.** `train_fusion.without_true_wine` пересчитывает gap относительно лучшего из
оставшихся, добавлен тест. Веса модели и осторожный порог не меняются: они считаются по
позитивам.

**Исправленные цифры:**

| Модель | AUROC отказа | Отклонено вин вне каталога при осторожном пороге |
|---|---|---|
| `fusion_synth_v1` (v1, фронтальная галерея) | 0,953 → **0,867** | 51,6% → **8,8%** |
| `fusion_v2` (v1+v2, повороты, выбор рамки) | 0,950 → **0,815** | 60,5% → **2,8%** |

Для сравнения визуальный скор (там утечки не было: негатив берётся прямо из скоров):

| Сплит | AUROC фронтальная → повороты | Порог 0,74: ложные отказы | Отклонено вин вне каталога |
|---|---|---|---|
| `synth_v1` | 0,776 → 0,791 | 1,9% | 6,9% |
| `synth_v2` | 0,744 → 0,756 | 6,6% | 12,7% |

**Выводы.**

- Отказ «вина нет в каталоге» на синтетике не решён ни одним сигналом. Почти каждое «вино вне
  каталога» здесь — соседнее вино той же серии, и оно выглядит как ответ.

### 2.2. Локальные признаки ALIKED + LightGlue

**Зачем.** SIFT видит только градиенты яркости: на реальном фото Массандры у верного вина
63 согласованных точки, у розового двойника той же серии — 87. ALIKED (обучаемый детектор
точек) и LightGlue (обучаемый сопоставитель) должны давать более чистые совпадения.

**Ловушка окружения: `Illegal instruction`.** `pip install kornia` встал, но `import kornia`
падал с SIGILL. Разбор:

- Первая проверка обманула: `python -c "import kornia_rs" | tail` показал код возврата `tail`,
  а не Python. Та же ошибка с конвейером, что и с `pytest | tail` раньше. Правильный ответ дал
  `python -X faulthandler`: падение внутри `kornia_rs/__init__.py`.
- Процессор сервера — Xeon E5-2670 v2 (2013), без AVX2 и FMA. Свежие сборки `kornia_rs`
  (расширение на Rust) требуют этих инструкций.
- Решение: `kornia-rs==0.1.7`. После этого импортируются и `kornia`, и отдельный пакет
  LightGlue (он тянет kornia). В README добавлено объяснение.
- Взят официальный LightGlue от ETH (Apache-2.0) с ALIKED (BSD-3), а не реализация kornia:
  API проще и стабильнее.

**Встраивание.** `search/deep_match.py` повторяет интерфейс `local_match`: `extract` и
`match` → тот же `MatchResult`. Порог MAGSAC вынесен в общий `homography_result`, чтобы
признаки проверки у обоих сопоставителей считались одинаково; `verify` принимает сопоставитель
параметром; у `candidates` появился ключ `--features sift|aliked` (ALIKED считается на GPU в
один поток, ~2,6 с на запрос против ~0,13 с у SIFT на 16 процессах).

**Первые замеры** (30 кадров `synth_v2`, признаки на тех же рамках и кандидатах):

| Сопоставитель | Согласованных точек у верного / у неверных | Отношение | Покрытие | NCC | Цвет |
|---|---|---|---|---|---|
| SIFT | 54 / 11 | 4,8 | 0,25 / 0,09 | 0,53 / 0,16 | 0,10 / 0,37 |
| ALIKED + LightGlue | 145 / 46 | 3,2 | 0,40 / 0,20 | 0,59 / 0,24 | 0,06 / 0,26 |

- ALIKED даёт втрое больше точек, но по их числу разделяет хуже: верные кандидаты упираются в
  насыщение бонуса (150 точек).
- Поэтому сравнение идёт с подбором веса и насыщения отдельно для каждого сопоставителя
  (иначе ALIKED наказан чужими константами) и с обучением слияния на его собственных признаках.

**Замер на 300 кадрах** (подбор на половине, проверка на другой):

| Сопоставитель | Лучшие вес и насыщение | Проверочная половина | Половина подбора | Все 300 | Слияние на своих признаках |
|---|---|---|---|---|---|
| SIFT | 0,15 / 150 | 0,720 | 0,787 | 0,753 | 0,713 |
| ALIKED + LightGlue | 0,8 / 400 | 0,747 | 0,747 | 0,747 | 0,727 |

- Преимущество ALIKED на проверочной половине не подтверждается: на половине подбора картина
  обратная, а **парный тест** по расходящимся ответам даёт 9:11 (p = 0,82). Разницы нет.
- Задержка в режиме сервиса (признаки эталонов считаются офлайн): ALIKED — 32 мс на точки
  запроса и 257 мс на 5 сопоставлений, всего 289 мс; SIFT — 142 и 30 мс, всего 171 мс. То есть
  ALIKED дороже на 118 мс при равном качестве.
**Решающий замер на всех 2103 запросах `synth_v2`** (подбор на половине, проверка на другой):

| Сопоставитель | Лучшие вес / насыщение | Половина подбора | Проверочная половина | Слияние на своих признаках |
|---|---|---|---|---|
| SIFT | 0,3 / 150 | 0,818 | **0,732** | 0,698 |
| ALIKED + LightGlue | 0,8 / 400 | 0,827 | **0,722** | 0,693 |

Парный тест при лучших константах каждого (ALIKED 0,8/400 против нынешних SIFT 0,15/150):

| Часть выборки | ALIKED | SIFT | Расхождения | p |
|---|---|---|---|---|
| половина подбора | 0,827 | 0,811 | 37:20 | 0,033 |
| **проверочная половина** | 0,722 | 0,723 | 21:22 | 1,0 |
| все 2103 | 0,775 | 0,767 | 58:42 | 0,13 |

**Вывод: ALIKED + LightGlue в сервис не берём.** Преимущество видно только на той половине, где
подбирались его константы, — это отбор, а не качество. На отложенной половине разницы нет
вовсе, при этом ALIKED дороже на 118 мс на запрос, требует GPU в онлайне и отдельного
хранилища признаков эталонов (около 1 ГБ на 2103 вина против 322 МБ у SIFT).

Модуль `search/deep_match.py` и ключ `candidates --features aliked` остаются: проверку стоит
повторить на реальных фото, где у SIFT всего 5–87 совпадений и обучаемый сопоставитель может
себя показать.

**Побочная находка: вес SIFT.** На полной синтетике оптимальный вес — 0,3 (проверочная половина
0,732 против 0,723 при нынешних 0,15). Прежде вес выше ~0,24 ломал единственное реальное фото
серии (ARCHITECTURE.md, D10), поэтому проверил публичные фото заново:

| Вес | Фото Массандры | Порядок первых кандидатов | Отрыв от двойника |
|---|---|---|---|
| 0,15 (сейчас) | найдено верно | «Мускатель белый», затем «Мускатель розовый» | 0,0168 |
| 0,3 | найдено верно | тот же | 0,0089 |

- В нынешнем гибриде вес 0,3 реальное фото **не ломает**: верное вино остаётся первым, оба вина
  вне каталога по-прежнему отклонены.
- Но запас над двойником по серии сокращается вдвое. То есть +0,9 п.п. на синтетике покупаются
  уменьшением устойчивости на том единственном реальном примере, ради которого вес и занижали.
**Сквозной прогон с весом 0,3** (те же 533 отложенных запроса `synth_v2`, что у нынешних
умолчаний):

| Вес SIFT | top-1 | на сериях | верный ответ | отказ | p50 |
|---|---|---|---|---|---|
| 0,15 (умолчание) | 0,702 | 0,703 | 0,685 | 0,096 | — |
| 0,3 | 0,711 | 0,712 | 0,692 | 0,084 | 1228 мс |

Парный тест по расходящимся ответам: **8:3, p = 0,23** — незначимо.

**Решение: оставляю 0,15.** Выигрыш устойчив по направлению в трёх независимых замерах
(офлайн-подбор +0,9 п.п., сквозной +0,9 п.п., на сериях +0,9 п.п.), но ни в одном не значим,
а плата — вдвое меньший запас над двойником по серии на единственном реальном фото. На
синтетике мы уже один раз обожглись, перенеся на реальность порог отказа (раздел про утечку),
и повторять это ради недостоверных +1 п.п. не стоит. Вернуться к вопросу — когда появятся
реальные размеченные фото.

Заодно этот прогон дал **чистый замер задержки** нынешних умолчаний на свободной карте:
p50 1228 мс, p95 1714 мс (прежние 3919 и 7466 мс были сняты при трёх одновременных прогонах).

### Где на самом деле остался резерв: выбор рамки

Измерил потолок на отложенной половине `synth_v2` (галерея с поворотами, 1050 запросов):

| Вариант | top-1 |
|---|---|
| первая рамка по весу | 0,643 |
| обучаемый выбор (сейчас) | 0,663 |
| **идеальный выбор среди тех же рамок** | **0,775** |
| настоящая рамка из разметки | 0,770 |
| верное вино в top-5 хотя бы по одной рамке | 0,914 |

**Главное:** идеальный выбор среди уже имеющихся рамок даёт больше, чем настоящая рамка. Значит,
рамки у нас есть, и дообучать детектор или брать больше рамок-кандидатов незачем — весь резерв
(11 п.п.) в том, **как** выбирать среди трёх. Это сэкономило час GPU: я собирался строить кэш с
пятью рамками и отказался от этого после замера.

Что попробовал на готовом кэше (офлайн, секунды на итерацию):

1. **Сменить цель обучения.** Сейчас выбор учится предсказывать «рамка совпала с настоящей»
   (IoU ≥ 0,5), а метрика — «по этой рамке поиск даёт верное вино». Переобучение на правильной
   цели: 0,669 против 0,662, парный тест **30:23, p = 0,41** — незначимо. Цель оставляю
   прежней: она даёт более плотную разметку (37% рамок против 31%) и не зависит от галереи,
   то есть модель не придётся переобучать при каждой смене индексов.
2. **Отказаться от выбора вовсе** — объединить кандидатов по всем рамкам, скор вина = максимум
   по рамкам: top-1 **0,402** против 0,661, top-5 0,817 против 0,801. Максимум по рамкам
   выигрывают соседние бутылки: они тоже вина из каталога и на своей рамке дают высокий скор.
   Вариант с лёгким предпочтением «главной» рамки — 0,450, тоже мимо.

3. **Выбирать рамку по проверке совпадений.** Для каждой рамки посчитал `verify` её лучшего
   кандидата — 2844 рамки на 1050 запросах отложенной половины:

   | Правило выбора рамки | top-1 | против нынешнего выбора |
   |---|---|---|
   | нынешний выбор (геометрия и поиск) | 0,661 | — |
   | по числу совпадений SIFT | 0,419 | 43:297, p < 0,001 |
   | по доле совпадений | 0,391 | 41:324, p < 0,001 |
   | по покрытию этикетки | 0,436 | 51:287, p < 0,001 |
   | по NCC после выравнивания | 0,394 | 46:326, p < 0,001 |
   | скор поиска + бонус SIFT (0,15 и 0,5) | 0,403 и 0,419 | ≈40:300, p < 0,001 |
   | обучаемое правило со всеми признаками проверки | 0,667 против 0,678 у нынешнего | 24:30, p = 0,50 |
   | потолок (идеальный выбор) | 0,775 | — |

   **Причина провала.** Проверка сравнивает рамку с эталоном **её собственного** лучшего
   кандидата. Соседняя бутылка, целиком попавшая в кадр, совпадает со своим эталоном лучше,
   чем целевая — со своим: целевая обрезана краем кадра, повёрнута, перекрыта. То есть это
   признак «рамка чистая», а не «рамка та самая».

**Итог по резерву выбора рамки.** Одиннадцать процентных пунктов между нынешним выбором (0,661)
и потолком (0,775) недостижимы ни геометрией, ни уверенностью поиска, ни проверкой совпадений:
потолок — это оракул, который уже знает ответ. Все три попытки дали отрицательный результат, и
это, по-моему, главный содержательный вывод дня.

Чтобы брать этот резерв, нужен признак «эта бутылка — та, на которую наведён кадр», которого в
самом кадре нет. Практические пути:

- **Прицел в интерфейсе** — пользователь сам указывает бутылку, и мы берём кроп по его рамке.
  Важно не обмануться: рамка на экране сканера сейчас **декоративная** — снимок делает системный
  диалог камеры, а накладка рисуется поверх предпросмотра и с координатами изображения не
  связана. Значит, это не «передать уже готовую рамку», а отдельная работа: редактор кропа
  поверх сделанного снимка и передача рамки в `/v1/scan`. Зато в живом сценарии это убирает
  проблему соседних бутылок целиком, а не на проценты.
- Модель «центрального объекта внимания» вместо эвристики веса рамки — дороже и требует
  разметки, которой у нас нет.

Дообучение детектора (пункт 1.2 плана) при этом теряет смысл: нужная бутылка отсутствует во
всех рамках лишь у 1% кадров, а идеальный выбор среди имеющихся рамок обгоняет даже настоящую
рамку из разметки.

### Из чего состоят ошибки при идеальной рамке

Чтобы выбрать последний непроверенный пункт маршрута Б, разобрал ошибки на отложенной половине
`synth_v2` с рамкой из разметки: 1052 запроса, top-1 0,768, 244 ошибки.

| Чем оказался неверный ответ | Доля ошибок |
|---|---|
| вино той же серии (pHash ≤ 4) | 22% |
| та же винодельня, другая серия | 39% |
| чужая винодельня | 39% |

- У **66%** ошибок верное вино всё равно попадает в пятёрку: это ошибки порядка, а не полноты.
- **61%** ошибок — путаница внутри одной винодельни. Это ровно те трудные негативы, против
  которых в плане стоит дообучение эмбеддинга (3.4).
- Оставшиеся 39% — чужие винодельни: там либо этикетка действительно похожа, либо мешает
  синтетика (соседи, блики).

**Что из этого следует.** Полное дообучение SigLIP — часы GPU на общей машине, где длинные
задачи гасит нехватка памяти, плюс риск подгонки под генератор синтетики. Поэтому сначала
проверяю дешёвый вариант той же идеи: обучаемое линейное преобразование поверх **замороженных**
эмбеддингов. Все нужные векторы уже есть (эталоны — в индексах, запросы — в кэше), картинки не
нужны, счёт — минуты. Проверка честная: вина делятся пополам, преобразование учится на одной
половине **вин**, а измеряется на другой, поиск при этом идёт по всему каталогу.

### 3.4 (дешёвый вариант). Линейное преобразование поверх замороженных эмбеддингов — первый крупный выигрыш

**Идея.** Полное дообучение SigLIP — часы GPU и риск подгонки под генератор синтетики. Но 61%
ошибок — путаница внутри винодельни: похоже, дело не в нехватке признаков, а в геометрии
пространства. Тогда должно хватить линейного отображения, обученного поверх уже посчитанных
эмбеддингов: запросы берём из кэша (рамка из разметки), эталоны — из индексов, картинки не
нужны, обучение — минуты.

**Как обучается.** Один слой без смещения (1152 → 512), общий для запроса и эталона, поверх
нормированных векторов; функция потерь — перекрёстная энтропия по каталогу с температурой 0,05
(по сути ArcFace без полей). Оба вида (вся упаковка и этикетка) проходят через одно и то же
преобразование и складываются с весами 0,5 / 0,5, как в сервисе.

**Честность проверки.** Вина делятся пополам: преобразование учится на запросах одной половины
**вин**, метрики считаются на запросах другой половины, а искать можно любое вино каталога.
То есть проверяется перенос на вина, которых модель не видела.

| Проверка (только отложенные вина) | top-1 без → с преобразованием | top-5 | p |
|---|---|---|---|
| `synth_v2`, фронтальная галерея, рамка из разметки | 0,746 → 0,879 | 0,911 → 0,979 | < 0,001 |
| `synth_v2`, фронтальная галерея, рамка детектора | 0,624 → 0,723 | 0,770 → 0,822 | < 0,001 |
| `synth_v2`, **галерея с поворотами, рамка детектора** (режим сервиса) | **0,650 → 0,753** | 0,789 → 0,830 | < 0,001 |
| `synth_v2`, галерея с поворотами, рамка из разметки | 0,780 → 0,908 | 0,928 → 0,986 | < 0,001 |
| `synth_v1` (другой генератор), рамка из разметки | 0,912 → 0,947 | 0,994 → 1,000 | < 0,001 |
| `synth_v1`, рамка детектора | 0,823 → 0,864 | 0,912 → 0,925 | < 0,001 |

**Обратная проверка.** Обучение на `synth_v1` и замер на `synth_v2` дают ту же картину
(0,746 → 0,862 на рамке из разметки, 0,621 → 0,711 на рамке детектора). Перенос симметричен,
значит выучено выравнивание «кроп запроса → эталон», а не особенности одного генератора.

**Реальные фото** (три публичных, преобразование обучено только на синтетике):

| Фото | Без преобразования | С преобразованием |
|---|---|---|
| Массандра (есть в каталоге) | верное вино 0,784, соперник 0,767 | верное вино 0,425, соперник 0,353 |
| Табия (нет в каталоге) | 0,660 | 0,330 |
| Абрау-Дюрсо (нет в каталоге) | 0,697 | 0,315 |

- Верное вино осталось первым, а относительный отрыв от ближайшего соперника вырос с 2% до 20%.
- Все скоры сжались: **порог отказа 0,74 в новом пространстве бессмыслен** и требует пересчёта.
  Разрыв «вино из каталога против вина вне каталога» сохранился примерно прежним (0,42 против
  0,31–0,33).

**Устойчивость к размерности** (режим сервиса: галерея с поворотами, рамка детектора, отложенные
вина; без преобразования 0,650):

| Размерность | top-1 | top-5 | расхождения |
|---|---|---|---|
| 128 | 0,739 | 0,820 | 109:15 |
| 256 | 0,742 | 0,823 | 111:14 |
| 512 | 0,741 | 0,824 | 114:18 |
| 1152 (полный ранг) | 0,745 | 0,831 | 116:16 |

Выигрыш не зависит от выбора размерности — это довод против «повезло с настройкой». Разброс
между запусками около 1 п.п. (в первом прогоне при 512 вышло 0,753). Для сервиса беру **512**:
именно эта версия уже проверена на реальных фото, на галерее с поворотами и в обратном переносе.

**И вот главное: преобразование запоминает синтетический рендер конкретного вина.** Обучил
итоговую версию на **всех** винах (как и надо для сервиса) и проверил на реальном фото:

| Преобразование | Массандра, фронтальная галерея | Массандра, галерея с поворотами |
|---|---|---|
| нет | место 1 (0,784) | место 1 (0,787) |
| обучено на половине вин (Массандры среди них не было) | место 1 (0,425) | место 1 (0,425) |
| обучено на всех винах (Массандра внутри) | **место 16** | **место 36** |

Галерея ни при чём — разница только в том, было ли вино в обучении. Объяснение: для вина из
обучения преобразование подгоняет отображение под его **синтетический** кроп, а реальное фото
от этого кропа далеко, и выученное направление тянет ответ в сторону. Для вина, которого
преобразование не видело, остаётся только общая часть — выравнивание «кроп → эталон», она и
давала +10 п.п.

**Следствие, которое обесценивает замер.** В сервисе каждое вино каталога — «виденное». Значит,
измеренные +10 п.п. относятся к режиму, которого в продакшене не существует. Честная оценка
пользы преобразования — это поведение на винах из обучения, а оно на единственном реальном фото
отрицательное.

**Что настораживало ещё до этого.** На обучающей половине вин top-1 доходит до 0,97 против 0,74
без преобразования — подгонка была видна сразу, я просто списывал её на нормальную разницу
«обучение против проверки».

**Попытка спасти низким рангом.** Матрица малого ранга физически не может запомнить 2103 вина —
может, останется только общая часть? Для каждого ранга две проверки: обучение на половине вин с
замером на отложенных (синтетика, режим сервиса) и обучение на всех винах с проверкой реального
фото Массандры.

| Ранг | Синтетика (обучено на половине) | Реальное фото: обучено на всех | Обучено на половине |
|---|---|---|---|
| без преобразования | 0,650 | место 1 | место 1 |
| 8 | 0,410 | место 120 | место 420 |
| 16 | 0,630 | место 9 | место 12 |
| 32 | 0,690 | место 70 | место 37 |
| 64 | 0,730 | место 9 | место 1 |
| 128 | 0,738 | место 2 | место 1 |
| 512 | 0,744 | место 10 | место 1 |

Ни один ранг не держит одновременно выигрыш на синтетике и верный ответ на реальном фото при
обучении на всех винах. Лучший случай (ранг 128) — второе место вместо первого, то есть всё
равно ухудшение. А разброс по рангам (120, 9, 70, 9, 2, 10) показывает, что на реальных фото
поведение преобразования непредсказуемо: оно определяется случайностями обучения, а не смыслом.

**Итог линии 3.4: отклоняю.** Это самый поучительный результат дня. Замер «+10 п.п. на
отложенных винах» был методически чистым — и при этом бесполезным, потому что в сервисе
отложенных вин не бывает. Код остаётся в репозитории (`search/metric.py`, поддержка в
`MultiIndexSearcher`), но **выключен**, и в его описании прямо сказано, почему включать нельзя.

**Что это меняет в подходе.** Дообучение любого вида на синтетике, где каждое вино представлено
одним рендером своего же эталона, будет запоминать эти рендеры. Чтобы такой путь заработал,
нужны несколько разных изображений одного вина — то есть снова реальные фото (этап 0.1 плана). Поэтому дальше — проверка устойчивости к размерности, а перед
встраиванием придётся заново подобрать порог отказа и переобучить выбор рамки и слияние:
их признаки (скор, отрыв) живут в другом масштабе.

### Рамка пользователя: единственный способ взять оставшиеся 11 п.п.

Замеры показали, что выбор бутылки в кадре — самый большой оставшийся разрыв (0,663 против
потолка 0,775), и что из самого кадра он не берётся. Значит, признак «та самая бутылка» должен
прийти от пользователя.

**Сервис.** `POST /v1/scan` принимает необязательное поле `box` — «x1,y1,x2,y2» в долях кадра
(0…1). Доли, а не пиксели: фото уменьшается и в браузере, и в сервисе, и абсолютные координаты
разъехались бы. Если рамка задана, детектор не запускается вовсе.

Сквозная проверка на реальном фото Массандры через живой сервис:

| Запрос | Ответ | Скор | Детекция |
|---|---|---|---|
| без рамки | найдено, верное вино | 0,9967 | 437 мс |
| рамка по бутылке `0.25,0.10,0.75,0.98` | найдено, верное вино | 1,0067 | пропущена |
| рамка мимо `0.0,0.0,0.3,0.4` | «не найдено» | 0,8099 | пропущена |
| вырожденная рамка `0.5,0.5,0.505,0.9` | ошибка 400 «рамка слишком мала» | — | — |

Рамка мимо бутылки честно приводит к отказу, а не к случайному ответу — это правильное
поведение: мусор на входе не должен превращаться в уверенный ответ.

**Интерфейс.** После выбора фото открывается экран наведения: фотография показывается **целиком**
(`object-fit: contain`, иначе доли рамки не совпали бы с долями кадра), поверх неё — рамка с
угловыми ручками, которую можно двигать и растягивать пальцем. Кнопки: «Распознать по рамке» и
«Распознать всё фото». Прежний путь остался, просто перестал быть единственным.

Ожидаемая польза в живом сценарии больше, чем на синтетике: у полки соседние бутылки — главная
причина ошибок, а рамка убирает их из кадра целиком.

### Ошибки и уроки прогонов в этом блоке

Здесь собрано то, на что я потратил время впустую, — чтобы не повторять.

1. **Расчёт молча ушёл на процессор.** Первая полная таблица ALIKED считалась на CPU: в момент
   старта `torch.cuda.is_available()` вернул False (GPU 3 делит чужая задача), а `DeepMatcher`
   в таком случае просто выбирал `cpu`. Внешне это видно только по 834% загрузки процессора и
   отсутствию дескрипторов `/dev/nvidia*` у процесса. На CPU проход был бы в разы дольше.
   **Лечение:** ключ `--device cuda` (при недоступной карте — падение с ошибкой, а не тихая
   подмена) и строка в логе с выбранным устройством.
2. **Вывод фоновых задач был не виден.** Команды писались как `... | grep -v warning`, а `grep`
   при выводе в файл копит данные блоками. Переменная `PYTHONUNBUFFERED=1` тут не помогает:
   буферизует не Python, а `grep`. Из-за этого я дважды перезапускал прогон вслепую.
   **Лечение:** для долгих задач писать вывод напрямую в файл и фильтровать при чтении.
3. **Проверка кода возврата через конвейер обманывает.** `python -c "import kornia_rs" | tail;
   echo $?` показывает код `tail`, а не Python, — и я решил, что модуль импортируется, хотя он
   падал. Та же ошибка, что с `pytest | tail && git commit` в прошлом блоке. **Лечение:**
   `set -o pipefail` или проверка без конвейера; для падения по сигналу — `python -X faulthandler`.
4. **Убийство одного сплита не останавливает цикл.** Прогон был запущен как
   `for split in synth_v2 synth_v1; do ...; done`; я убил процесс первого сплита, и оболочка
   тут же запустила второй, который ещё полчаса жёг процессор незамеченным. **Лечение:**
   останавливать всю группу процессов, а не один python.
5. **Внешние остановки.** Два прогона получили SIGTERM (код 143) сразу после выхода на GPU;
   причину установить не удалось. **Лечение:** долгие расчёты запускаются отдельной сессией
   (`nohup setsid`), а за их завершением следит сторож, который сообщает и об успехе, и о том,
   что процесс умер, — молчание не принимается за успех.
6. **Лишняя работа в подмене галереи.** `QueryCache.load(indexes=...)` загружал исходные
   индексы целиком только ради сверки модели и вида. Теперь читается их `meta.json`.

### 2.7. Текстовый канал кандидатов — отрицательный результат на синтетике

**Гипотеза плана.** Поиск по тексту этикетки (триграммы, BM25) найдёт вина, которых нет в
визуальном top-10, и объединение через RRF поднимет полноту.

**Как проверял.** Офлайн, без GPU, на готовом прогоне `synth_v1` с OCR (2103 кадра, текст
сохранён в `predictions.csv`). Символьные триграммы и четырёхграммы TF-IDF по карточкам
(название, винодельня, регион, сорта, год), запрос — строка OCR.

| Список кандидатов | top-1 | верное вино в top-10 |
|---|---|---|
| визуальный (база) | 0,819 | 0,919 |
| только текстовый | 0,178 | 0,383 |
| RRF визуальный + текстовый | 0,642 | 0,916 |
| текст в хвост без перестановки | 0,819 | 0,919 (top-20 — 0,925) |
| RRF только при визуальном скоре < 0,74 (4,5% запросов) | 0,818 | 0,917 |
| RRF только при визуальном скоре < 0,82 (16% запросов) | 0,807 | 0,917 |

- Из 170 кадров, где верного вина нет в визуальном top-10, текст находит его у 12.
- Полный RRF рушит top-1 на 18 п.п., щадящие варианты в лучшем случае ничего не меняют.
- **Причина** — качество OCR на синтетике: в среднем 28 символов, у 6–7% кадров пусто.
  Примеры «спасённых» запросов показывают обрывки вроде `€ 4 #4` и `KATHARON`.

**Вывод.** Как генератор кандидатов текст не работает; он остаётся тем, чем был, — слабым
сигналом переранжирования внутри top-10 (вес 0,02). Проверку стоит повторить на реальных фото:
там OCR читает вдвое длиннее (65 символов против 28 на публичных снимках). Замена OCR на
PP-OCRv5 из плана пока не пробовалась.

### 2.3. Маски отличий внутри серий — первый замер

**Идея плана.** Вина одной серии различаются мелочью: словом на этикетке, годом, оттенком.
Если офлайн выровнять эталоны серии друг с другом и построить маску различающихся областей,
то запрос можно сравнивать с кандидатами **только внутри этой маски**.

**Построение масок.** Серии — группы эталонов с расстоянием pHash ≤ 4 (та же граница, что в
каталоге: 844 вина, 262 группы, 1227 пар). Выравнивание пары — SIFT и гомография, маска —
разница в Lab больше 25 с морфологической чисткой.

- Из 40 случайных пар выровнялось 39.
- Медианная площадь маски — 16% силуэта этикетки; у 5 пар меньше 1% (отличий почти нет),
  у 8 больше половины (этикетки разошлись сильно).

**Проверка на трудных случаях.** 250 запросов `synth_v2`, где верное вино и его двойник по
серии оба попали в визуальный top-5 — то есть именно те, где система и путается:

| Признак | Верное вино выбрано |
|---|---|
| визуальный скор | 0,872 |
| визуальный + SIFT 0,15 (текущее слияние) | **0,924** |
| NCC глобальный | 0,692 |
| NCC внутри маски | 0,740 |
| цвет глобальный | 0,764 |
| цвет внутри маски | 0,784 |
| маска: NCC минус цвет | 0,756 |

- Маска улучшает свои же признаки: NCC +4,8 п.п., цвет +2,0 п.п. Значит, идея работает.
- Но по отдельности все они слабее уже работающей связки «визуальный скор + SIFT» (0,924).
- Ещё 210 пар пришлось пропустить: эталоны не выровнялись или маска вышла вырожденной.

**Ответ на главный вопрос: не добавляет.** Повторный прогон сохранил все признаки по 308 парам
(медианная площадь маски — 13% этикетки):

| Правило выбора | Верное вино выбрано |
|---|---|
| визуальный скор | 0,880 |
| визуальный + SIFT 0,15 (сейчас) | **0,925** |
| NCC внутри маски | 0,753 |
| цвет внутри маски | 0,789 |
| текущее правило + цвет в маске как решающий голос при близких скорах | 0,906 |
| обученное правило **без** маски (перекрёстная проверка) | **0,909 ± 0,049** |
| обученное правило **с** маской | 0,885 ± 0,040 |

- Цвет в маске **чинит 16** ошибок текущего правила и **ломает 58** верных ответов (p < 0,001).
- Обученное правило с масочными признаками стабильно хуже, чем без них: признаки шумные, и
  модель на них переобучается.
- Почему так: маска строится по чужому эталону и переносится на запрос **двумя** гомографиями
  подряд, поэтому её край размывается; внутри узкой области сравнивать почти нечего (у пар с
  маской меньше 1% площади сравнение вырождается, их пришлось выбрасывать).

**Вывод.** Пункт 2.3 закрыт как отрицательный. Цена — офлайн-выравнивание всех пар серии и два
лишних сопоставления на запрос — не окупается. Вернуться к идее имеет смысл только на реальных

### Этап 5: страница метрик

- `GET /v1/metrics` отдаёт этот файл. Сервис **не импортирует** пакет измерений — по границам

- Страница `/metrics` в интерфейсе показывает сквозные прогоны карточками (включая долю отказов

- Проверено: типы чистые, сборка проходит, страница отвечает 200 и отдаёт разделы, прокси
  `/api/v1/metrics` возвращает сводку.
