# Быстрый старт

Как поднять «Свой Сомелье» на своей машине одной командой. Два режима: **быстрый**
(интерфейс и поиск сомелье, минуты) и **полный** (настоящее распознавание фото, дольше
и с оговорками — читайте раздел «Полный режим» перед запуском).

## Что понадобится

| Инструмент | Версия | Проверка | Установка |
|---|---|---|---|
| bash | любой современный | входит в macOS и Linux | — |
| git | любой | `git --version` | — |
| [uv](https://docs.astral.sh/uv/) | любая свежая | `uv --version` | `curl -LsSf https://astral.sh/uv/install.sh \| sh` |
| Python | 3.12 | ставится через uv | uv скачает сам при первом запуске, если не найдёт |
| Node.js | ≥ 22 | `node --version` | https://nodejs.org/en/download или `nvm install 22` |

Скрипт сам проверяет версии и подскажет, чего не хватает — устанавливать всё заранее
не обязательно, uv умеет докачать подходящий Python сам.

## Быстрый режим — интерфейс и поиск сомелье за минуты

```bash
git clone <адрес вашего репозитория> svoy-somelye
cd svoy-somelye
scripts/quickstart.sh
```

(или `make quickstart` из корня репозитория — то же самое).

Через несколько минут скрипт напечатает адреса:

- веб-интерфейс — `http://127.0.0.1:5173/`;
- Swagger (документация и проверка API руками) — `http://127.0.0.1:8000/v1/docs`;
- метрики распознавания — `http://127.0.0.1:8000/v1/metrics/scan`.

В этом режиме:

- **поиск сомелье (чат, каталог, гастропары) — настоящий**: индекс из 2103 вин уже лежит
  в репозитории, скачивать ничего не нужно. При самом первом обращении к поиску скрипт
  ещё скачает небольшую (~250 МБ) модель эмбеддинга текста — один раз, дальше она берётся
  из локального кэша;
- **распознавание фото по этикетке — заглушка**: любое загруженное фото получает
  предсказуемый ответ-пример, чтобы можно было увидеть карточку вина и весь путь
  интерфейса, не скачивая тяжёлые модели. Настоящее распознавание — см. «Полный режим»;
- **чат с сомелье отвечает по-настоящему найденным вином**, но сам текст ответа — простой
  шаблон, а не генерация языковой модели: ключей от нашей языковой модели в репозитории
  нет и не будет (это приватный доступ команды). Если у вас есть свой OpenAI-совместимый
  или GigaChat-ключ, его можно подключить — переменные `LLM_PROVIDER`/`LLM_BASE_URL`/
  `LLM_API_KEY`/`LLM_MODEL` описаны в `docs/architecture/operations.md`, раздел 4.

Остановить: `scripts/quickstart.sh stop` (или `make quickstart-stop`).
Посмотреть, что сейчас поднято: `scripts/quickstart.sh status`.

## Полный режим — настоящее распознавание фото

Здесь сканер работает по-настоящему: та же модель (SigLIP2) и тот же алгоритм, что и на
нашем демо-стенде. За это придётся заплатить временем и местом на диске — скрипт прямо
об этом предупредит и попросит подтверждения, ничего не скачивается втихую.

### 1. Подготовьте свои данные кейса

У вас должен быть свой экземпляр материалов кейса (дамп каталога вин и фотографии),
полученный от организаторов, — мы его не публикуем и не пересылаем. Укажите путь к нему
переменной `CASE_DATA_DIR`.

**Формат каталога.** Скрипт понимает три варианта (проверяются по порядку, можно указать
явно переменной, если автоопределение не сработало):

1. Файл `slug_refs.json` (слаг → фото) рядом с папкой
   `prod-svoe-vino-strapi/prod-svoe-vino/strapi/uploads/` внутри `CASE_DATA_DIR` — так
   устроены наши собственные обработанные данные. Другое расположение папки с фото —
   переменная `CASE_UPLOADS_DIR`.
2. CSV-файл с колонками `slug` и `image_path` (пути — относительно самого CSV или
   абсолютные) — путь к нему через `CASE_REFS_CSV`.
3. Простая папка с фото, где имя файла без расширения — это слаг вина
   (`kokur-suhoe-2025.jpg` и т. п.) — путь к ней через `CASE_REFS_DIR`.

Если ни один вариант не подошёл, скрипт честно скажет, что не нашёл, и не будет
гадать или падать невнятной ошибкой.

### 2. Запустите

```bash
CASE_DATA_DIR=/путь/к/своим/данным scripts/quickstart.sh full
```

Скрипт сначала печатает план (что именно будет скачано и сколько это займёт) и просит
подтверждения — добавьте `--yes` (или `-y`), если хотите пропустить вопрос.

**Честно о времени и месте.** Оценка ниже — не «пара минут»:

- Python-зависимости для распознавания (torch, transformers, PaddleOCR, RapidOCR) —
  на нашей машине это ~1.8 ГБ на диске, качается один раз;
- веса модели изображений SigLIP2 — ~1.4 ГБ с Hugging Face;
- модели OCR — ещё около 100 МБ;
- **сборка индекса по вашему каталогу — самый долгий шаг.** На нашей машине
  (Apple Silicon, с ускорителем) сборка индекса на ~2050 позиций каталога заняла
  ~29 минут. На процессоре без ускорителя (как наш продовый сервер, 4 ядра) — около
  45 минут на тот же объём. Время растёт примерно линейно с числом вин в каталоге.

В сумме — реалистично от 40 минут до полутора часов от команды до готового API, в
основном в зависимости от скорости интернета и вашего процессора. Прогресс сборки
индекса скрипт печатает по ходу дела, а не молчит всё это время.

Если ваш каталог заметно больше нашего (по умолчанию мы используем те же ~24
синтетических ракурса на вино, что и в бою, — это не единственное, что влияет на
качество распознавания, но и не самый быстрый путь) и вы хотите сначала быстро
проверить, что всё работает, — соберите индекс на части каталога, ограничив выборку
на стороне своих данных, и запустите заново на полном каталоге, когда убедитесь, что
всё в порядке.

**Что не переносится из полного каталога автоматически.** У нас есть дополнительный
этап ручной проверки фотографий (какие ракурсы можно доверять, дубликаты и т. п.),
который заметно поднимает точность и не входит в этот скрипт как автоматический шаг
— на своём каталоге без него точность может быть ниже наших опубликованных цифр в
`README.md`. Скрипт всё равно строит рабочий индекс и честно предупреждает об этом.

### 3. Дальше — как в быстром режиме

Адреса, `status`, `stop` — те же, что в быстром режиме. `/v1/metrics/scan` останется
пустым, пока вы не прогоните проверку ниже: правильные ответы известны только
организаторам, мы их не храним и не подделываем.

## Проверка официальным скриптом организаторов

Когда API поднят (быстрым или полным режимом), можно прогнать `participant_test.sh`
— тот же скрипт, которым будет пользоваться жюри, без единой правки — против своего
локального адреса:

```bash
scripts/quickstart.sh verify \
  --images-dir /путь/к/своим/фото \
  --manifest /путь/к/manifest.tsv
```

Без аргументов команда попробует использовать образец из `eval/queries` — если фото
там нет (мы не публикуем чужие фотографии), скрипт скажет об этом и попросит указать
свою папку. Результат — файл `predictions.jsonl`; посчитать по нему точность может
только тот, у кого есть правильные ответы (в контексте кейса — организаторы), см.
`eval/README.md`.

## Порты и переменные окружения

- `API_PORT` (по умолчанию 8000) и `WEB_PORT` (по умолчанию 5173) — если заняты,
  скрипт скажет, что и как, и подскажет, как передать другой порт;
- `--no-web` — поднять только API, без веб-клиента;
- полный список переменных боевого окружения (для тех, кто хочет заглянуть глубже) —
  `docs/architecture/operations.md`, раздел «Справочник env».

## Частые проблемы

- **«порт NNNN уже занят»** — освободите порт или запустите с другим:
  `API_PORT=8001 WEB_PORT=5174 scripts/quickstart.sh`.
- **«не найден Node.js» / «нужен Node.js >= 22»** — поставьте актуальный Node.js
  (https://nodejs.org/en/download) или через `nvm install 22`.
- **«uv не найден»** — `curl -LsSf https://astral.sh/uv/install.sh | sh`, затем
  откройте новый терминал.
- **API не поднимается (fast)** — посмотрите `.local/quickstart/logs/api.log`.
- **API поднимается очень долго (full)** — это ожидаемо на первом запуске (скачивание
  моделей + сборка индекса), см. «Честно о времени» выше; следите за
  `.local/quickstart/logs/api.log`.
- **`/v1/metrics/scan` пустой** — так и должно быть, пока вы не прогнали `verify` и
  не посчитали точность на своей стороне (у нас нет правильных ответов организаторов).
- **Чат отвечает шаблонной фразой** — ожидаемо: ключей нашей языковой модели в
  репозитории нет, см. «Быстрый режим» выше про `LLM_PROVIDER`.
