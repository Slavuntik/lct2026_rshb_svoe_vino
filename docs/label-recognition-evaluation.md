# Основной сканер: оценка качества и приёмка изменений

Актуализация: 28.09.2026. [Устройство и контракт](label-recognition.md), [эксплуатация](label-recognition-operations.md). Документ описывает выполненные измерения и способ их повторить. Он не заменяет официальную скрытую оценку организаторов.

## Что именно проверено

Объект — одна фотография и одно решение основного сканера `IMAGE_PROVIDER=real`, `CV_FUSION=1`. Витрина, локальный браузерный поиск и адаптер `winescan` не являются этим экспериментом. Полки, попавшие в диагностический архив как отрицательные фотографии, не превращают его в оценку обнаружения всех бутылок.

Использованы 119 фотографий: 72 известных вина, 46 отрицательных случаев, один кадр без надёжной истины. Последний участвует в измерении технических ошибок и времени, но исключён из качества. Источник разметки — прежнее ручное ревью, с дополнительно проверенными исправлениями; модельное предсказание само по себе не считается истиной. Подробное происхождение описано в [исходном аудите](../reports/label-recognition-audit-2026-09-28.md).

Это диагностический архив с повторными съёмками и примерами, уже использованными при настройке. Он не является слепым holdout и не даёт независимую оценку на каждом SKU каталога. Два близких варианта C56/C58 оценены строго как отрицательные; чувствительность к их исключению показана отдельно, без изменения основной разметки.

Найдены также 100 контрольных фото, но исходные `real-photos-labels/part1.csv` и `part2.csv` в доступных данных отсутствовали. Поэтому исторические 60/62 и 61/62 не объявлены независимо воспроизведёнными. В `eval.zip` три изображения без доступной публичной истины — официальный score из них вычислить нельзя.

## Метрики и знаменатели

| Метрика | Расчёт | Что она не доказывает |
|---|---|---|
| Candidate top-1 | Правильный первый кандидат / 72 известных | Что карточка была показана пользователю |
| Candidate top-5 | Правильный slug среди первых пяти / 72 | Что система выбрала его окончательно |
| Recall принятых карточек | Правильно показанные известные вина / 72 | Отсутствие ложных совпадений |
| Precision принятых карточек | Правильные / все показанные карточки на размеченных кадрах | Полноту распознавания известных вин |
| False accepts | Показанная карточка на отрицательных / 46 | Верность распознавания положительных |
| Конечная accuracy | Верные карточки + верные отказы / 118 | Официальный результат на неизвестном тесте |
| HTTP/protocol errors | Ошибки транспорта, статуса или формата / 119 | Корректный отказ модели |
| p50/p95/max | Полное HTTP-время успешных запросов | SLA при иной нагрузке или ином кэше |

При верном отказе на отрицательном фото требуется успешный rich-ответ с `not_in_catalog=true`. HTTP 500 не считается верным отказом. Время неуспешных запросов и число ошибок нужно сохранять отдельно: низкая задержка оставшихся успешных запросов не компенсирует падения.

Сырые `matches[].score` не калиброваны и могут превышать 1. `confidence.top1_score` — визуальная составляющая. Исторические имена `f1_top1/f1_top5` не превращают top-k accuracy в F1. Для новых отчётов используйте явные определения выше.

Рабочий вариант сохранил все 119 решений `slug/not_in_catalog` относительно baseline. Top-1 — 97,2%, top-5 — 98,6%, recall карточек — 84,7%, precision — 91,0%, конечная accuracy — 85,6%. Исправлена доступность сервиса и сохранение деталей пользовательской рамки; **измеренного роста точности на этом наборе нет**.

Эксперимент потерял C32: географический текст «Самара» принят за название. OCR подтвердил текст, но не его семантическую роль. Ни одно ложное совпадение не устранено, поэтому проверка выключена по умолчанию.

| Условия задержки | p50 | p95 | max |
|---|---:|---:|---:|

Стенд общий; часть времени параллельно выполнялись сборки и серверные smoke-запросы. Разница между строками не является доказательством ускорения алгоритма. В тёплом повторе 6/119 запросов всё ещё превысили 10 секунд. Отдельная проверка потери кэша вернула правильную карточку за 14,09 с после пересчёта.

На production выполнены только smoke C01/C02/C32: 3/3 на каждом хосте. p50/max: ams3 6,27/8,46 с, YC 5,07/5,43 с. По трём фотографиям нельзя оценить точность всего каталога или гарантировать время для любого снимка.

## Воспроизведение полного прогона

1. Зафиксировать Git SHA, версию Python/зависимостей, имя модели и индекс. Скопировать индекс в отдельное рабочее хранилище; не делить embedded Qdrant с production.
2. Подготовить исходные фото и переносимую разметку [`label-archive-20260928.manifest.json`](../qa/audits/label-archive-20260928.manifest.json). Каждый путь разрешается относительно `--images-root`; инструмент проверяет SHA256 файла до запроса.
3. Явно выставить профиль: CV/OCR/VLM, пороги, выбор ветки, флаг проверки имени. Сохранить только безопасные значения конфигурации, без ключей и заголовков Authorization.
4. Прогреть модели и проверить известную этикетку/пустое изображение. Отдельно указать, был ли кэш эмбеддингов пустым. Прогретая модель и тёплый кэш фотографий — разные условия.
5. Запустить один последовательный прогон. Не добавлять автоматические повторы, скрывающие первичные ошибки, и не запускать другие аудиты на том же API.

```bash
# Из корня Vinchik. API уже запущен в отдельном окружении.
python3 qa/label_audit.py \
  --manifest qa/audits/label-archive-20260928.manifest.json \
  --images-root '/path/to/label-audit-20260928' \
  --out /tmp/label-run-new.jsonl \
  --api http://127.0.0.1:19871 \
  --timeout 45
```

Порт 19871 использовался только изолированным стендом аудита; это не порт приложения по умолчанию. Выберите адрес своего стенда. Скрипт намеренно отказывается дописывать существующий output: используйте новое имя для каждой конфигурации.

Создаются JSONL с полными ответами, `.metadata.json` с адресом/временем/хешем манифеста и `.metrics.json` для rich-режима. Эти файлы сначала хранятся вне Git; публикуйте только необходимые обезличенные поля. Нельзя передавать обрезанные опубликованные predictions вместо полного runner-JSONL в функции, ожидающие вложенное поле `response`.

`--mode flat` обращается к `/v1/eval/predict`. Он полезен для отдельной проверки контракта, но не даёт оценки rich-отказов. Для оценки качества принятия карточки используйте стандартный rich-режим.

## Постобработка и сравнение

`qa/audits/analyze_label_audit.py` — специализированный анализ **исходного** аудита. Он ожидает имена `archive-isolated-vlm.jsonl`, `isolated-api.log`, `catalog-audit.json`, ровно 119 строк и ровно один соответствующий лог выбора ветки на каждый запрос. Логи предварительных smoke-запросов нарушат эту предпосылку. Скрипт также записывает `analysis.json` в указанный `--root`; запускайте на рабочей копии результатов.

```bash
python3 qa/audits/analyze_label_audit.py \
  --root /path/to/baseline-working-copy \
  --out /tmp/label-baseline-analysis
```

Для другого прогона первичные метрики уже вычисляет `qa/label_audit.py`. При парном сравнении связывайте записи по `qid` и SHA256, а не только по номеру строки. Отдельно сравнивайте кандидатов, принятый slug, отказ, ошибки и время. В опубликованном [`paired.json`](../reports/data/label-improved-20260928/paired.json) проверены одинаковые входы и неизменность принятых решений; это не утверждение о побитовом равенстве каждого численного score.

Сравнение локальной/модельной веток внутри одного запроса не является независимым OCR-only экспериментом: обе используют общую вселенную кандидатов. Таблицы изменения floor/gap поверх сохранённых ответов — контрфактический post-filter, не новый инференс с изменёнными настройками.

```bash

cd apps/api
uv sync --frozen --all-extras --dev

  ../../packages/cv/tests/test_identity.py \

uv run python ../../qa/audits/label_cache_proof.py

```

Проверяются восстановление кэша, повреждённый JSON, запрет записи, разные shape/dtype, cache hit, порядок crop/resize, обработка неверной рамки, сохранение VLM-полей, rich/flat-семантика проверки имени, откат релиза и положительный/отрицательный inference-gate.

В выполненной проверке: API 641 passed/14 skipped; энкодер 8 passed; text fusion + identity 84 passed; выкладка 11 passed; аудит + выкладка 16 passed. Группы пересекаются — их нельзя складывать в количество уникальных тестов. Отдельный контейнерный запуск дал 806 passed/12 skipped и одну ошибку окружения из-за отсутствующего `git`; этот тест отдельно прошёл после установки `git`. Первый запуск API из неправильного cwd также ошибался на путях данных; корректный запуск прошёл. Эти обстоятельства сохранены для прозрачности, а не скрыты за общей цифрой.

Unit-тесты не измеряют качество настоящих моделей. Прогон 119 фото не заменяет HTTP/контрактные тесты. Реальная проверка потери кэша выполнялась дополнительно: каталог переименован с сохранением файлов, процесс API не перезапускался, после нового запроса каталог и векторы появились снова.

## Что остаётся улучшить и как принимать изменения

- **Покрытие эталонов.** Разобрать 44 позиции без выбранного изображения, добавить разрешённые варианты этикеток. Не добавлять контрольное фото в индекс, а затем объявлять улучшение на том же фото независимым результатом.
- **Винодельни и варианты написания.** Проверить алиасы на разных винах производителя, включая отрицательные примеры. F11 с иной этикеткой «Мерло Литавщуков» не попал в top-5; одна настройка порога этот случай не исправит.
- **Точное название и линейка.** Ложные C36/C43/U05 показывают риск совпадения по общей винодельне/стилю при отсутствующем названии. Требуется проверять роль текста, а не просто его присутствие.
- **Гейт принятия.** В девяти из одиннадцати пропусков baseline правильное вино уже top-1. Настраивать отказ нужно с учётом отрицательных примеров: снижение порога может увеличить ложные карточки, повышение — потерять верные.
- **Детали рамки.** Сохранение 800×600 вместо 205×153 доказано тестом, но прирост качества требует отдельного набора реальных фото с пользовательскими рамками.
- **Калибровка и скорость.** Нужны отдельный отложенный набор, честная вероятность/уверенность и замеры новых снимков при известной конкуренции запросов. На тёплом повторе нельзя обещать время нового кадра.

До нового эксперимента зафиксируйте критерии: допустимое число ложных карточек, минимальный recall, предел технических ошибок и целевой p95 с описанием оборудования/нагрузки. Сохраняйте baseline, меняйте один фактор за раз, разбирайте все новые ошибки и отдельно проверяйте неизвестные вина. Только после этого включайте эксперимент в production. Текущий результат — устранение подтверждённых эксплуатационных дефектов без регрессии на архиве; задача роста точности остаётся открытой.
