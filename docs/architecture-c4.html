Архитектура сканера вина

Сервис «фото → карточка вина» на массиве платформы. Три уровня C4: контекст, контейнеры, компоненты сопоставления. Сквозной принцип: сопоставление важнее распознавания — снимок в магазине всегда несовершенен, точность добирается каталогом, синонимами и калиброванным порогом уверенности.

наш сервис внешнее / офлайн-контур данных

C1 — контекст

Один пользователь, один сервис, один источник данных. Персональных данных нет по построению: ни аккаунтов, ни хранения фото.

C2 — контейнеры

Онлайн-путь из трёх контейнеров и офлайн-контур данных. Состояния у сервиса нет: всё знание живёт в версионируемом индексе.

C3 — компоненты сопоставления

Сердце сервиса. Быстрая точная ступень закрывает типовые случаи, гибридная — трудные снимки; калиброванный порог даёт три честных исхода вместо ложной уверенности.

  • Почему две ступени: точное нечёткое совпадение дёшево и объяснимо — оно первым; тяжёлый гибрид с реранкером включается только когда нужен.
  • Почему порог в манифесте: порог зависит от версии индекса; храня его рядом с данными, нельзя случайно применить старый порог к новому индексу.
  • Почему «не найдено» — фича: ложная уверенность в точке продажи хуже отказа; проверочный набор содержит и посторонние снимки/запросы с ожиданием отказа.

C4: контекст → контейнеры → компоненты. Сервис по кейсу «Своё Вино» (ЛЦТ); карточки ссылаются на первоисточник.
