# Сценарий видео ≤7 минут — демо на живом стенде

Требование кейса: питч ≤7 минут, порядок — концепция → архитектура пайплайна → живое демо без
монтажа → метрики F1 топ-1/топ-5 → доп-функция → выводы (`case.md` строки 76–77); демо — без
склеек, эксперты сами меряют скорость. Заменяет/обновляет черновик `docs/video-demo-scenario.md`
(тот писался 17.09 под `localhost:5173` и синтетику 1982 позиций до прихода живых фото
организаторов) — демо теперь на публичном стенде **http://89.110.72.101** (жив на 22.09,
`/v1/healthz` → `warm:true`, `cv_index_version=case-20260921-d1-b384` — проверено вживую при
подготовке этого сценария).

Реквизит: 2–3 бутылки, из них минимум одна — из линейки, где есть «близнец» (тот же дизайн
этикетки, другой год/сахар/категория, например семья «Табия» — `reports/h1-cpu-path.md`,
`reports/d1-ref-collisions.md`), одна заведомо не из каталога (импорт); стенд прогрет заранее;
браузер на вкладке стенда + вкладка `http://89.110.72.101/v1/metrics/scan`; таймер в кадре.

## Хронометраж (7:00)

**0:00–0:30 — Концепция.** «Покупатель фотографирует этикетку у полки — сервис должен вернуть
ОДНУ карточку вина из каталога „Своё Вино", без экрана вариантов (как в Vivino, `case.md`
строка 8). Каталог — 2103 позиции. Организаторы сами оценивают текущий сервис примерно в
**60%** точности и просят довести до **90–95%** — это и есть наша планка (цитата организаторов
на сессии вопросов: «Правильное вино на первом месте. Сейчас около 60%, ориентир — 95%», файл
`ChatExport_Задача №10 _ РСХБ _ ЛЦТ 26/messages.html`, сообщение «РСХБ / ЛЦТ — вопросы и ответы
по сканеру вина», пункт «Что важнее всего? (08:20; 46:22)»; см. также исходный анонс кейса в том
же файле — «точность совпадения составляет около 60%, задача участников — повысить её до 90%»).
Главная трудность — не «узнать бутылку», а разлепить близнецов: одна серия, разный год или сахар
при одинаковой этикетке (`case.md` строка 33, «near-duplicates — главный источник ошибок»)».

**0:30–1:15 — Архитектура (1 слайд, `ARCHITECTURE.md`/слайд 8 презентации).** Фото →
нормализация (кроп, развёртка цилиндра) → эмбеддинг SigLIP2 → ANN по мульти-ракурсному индексу →
схлопывание в позиции → слияние CV-скора с текстом этикетки, сверенным со ВСЕМ каталогом (не
только с похожими) → калиброванное решение (`contracts/image-scan.md` v0.4.13). Один пайплайн
отдаёт и `{"slug":...}` для скрипта оценки, и полную карточку для интерфейса.

**1:15–4:00 — Живое демо на стенде, без монтажа.**
1. *(1:15–2:15)* Сканируем бутылку из каталога, у которой есть визуальный «близнец» другого
   года/сахара → одна карточка. Проговорить: «текст на этикетке сверился со всем каталогом,
   не только с похожими на вид — это и отличает близнецов» (`contracts/image-scan.md` v0.4.13
   §2). Показать карточку целиком: фото, винодельня, описание, ссылка «Открыть на «Своё Вино»»
   (`reports/c3-candidates-ui.md`).
2. *(2:15–3:00)* Сканируем вино НЕ из каталога (импорт) → честное «нет в каталоге» +
   блок **«Возможно, это одно из:»** (кандидаты — ближайшие вина каталога с фото и винодельней,
   `contracts/image-scan.md` v0.4.11, `reports/b8-candidates-card.md`, `reports/c3-candidates-ui.md`)
   + ниже — **«Аналоги из других виноделен»** (аналоги по стилю среди российских вин — то, что
   кейс «оценивает особенно высоко», `case.md` строка 24). Если под рукой окажется импортный
   рислинг/шардоне — показать текстовый разбор «иностранное → российский аналог»
   (`reports/b7-foreign-analogs.md`).
3. *(3:00–4:00)* С любой карточки — кнопка **«Спросить сомелье»**: один содержательный вопрос
   (например, про сочетание с блюдом или про вкус) → ответ с цитатой-ссылкой на первоисточник
   (`ARCHITECTURE.md` шаг 5, гибридный RAG). Ответ теперь от Qwen3.8-27b через свой GPU-шлюз, не
   заглушка (`LLM_PROVIDER=openai`, живой дым-тест дал содержательную рекомендацию с
   обоснованием, `reports/backend-llm-openai.md`, hack-v13) — статус шлюза проверить заранее по
   чек-листу ниже (`docs/product/post-scan.md`).

**4:00–5:00 — Метрики (вкладка `/v1/metrics/scan`, требование «F1 в API», `case.md` строка 22).**
Прочитать с экрана живые цифры: топ-1 **96.8%**, топ-5 **98.4%** на 100 живых фото организаторов
(62 вина есть в каталоге) — CPU-путь + модель 27B через свой GPU-шлюз, p50/p95/max
**4.4/5.2/6.9 с** при лимите скрипта 10 с (`qa/scan-eval-runs/real-photos-stand/README.md`,
hack-v15). Честно: «без модели, на голом CPU — 95.2%; модель даёт ещё 1.6 процентных пункта»
(`reports/devops-hack-v15.md`). Проговорить: «от 60% организаторов мы подняли систему до 95–97%
в зависимости от железа — выше их же ориентира 95% в обеих конфигурациях, с моделью и без»
(источник цифры 60%/95% — цитата выше; наши цифры — эта же вкладка).

**5:00–5:20 — «Выключаем GPU — сканер продолжает работать» (аргумент TCO; вставка снята ЗАРАНЕЕ
на своей проверочной машине, НЕ на живом публичном стенде).** На Mac-сервере проверки командой
временно переключаем адрес GPU-шлюза на недоступный и повторяем тот же скан — сервис не падает и
не виснет: дедлайн ответа модели `VISION_LLM_TIMEOUT_S=6.0 с`, после 3 сбоев подряд —
предохранитель на 60 с, скан сразу уходит на локальный CPU-путь и отдаёт тот же валидный
`{"slug":...}` (механизм проверен живьём 60/60 на четырёх видах отказа шлюза,
`reports/qa-auto-scan-budget.md`). Произнести честно: «без модели — 95.2%, с моделью — 96.8%;
GPU добавляет 1.6 процентных пункта точности, а не делает сканер зависимым от своей доступности —
это и есть наш ответ на вопрос про TCO» (`reports/devops-hack-v15.md`, `docs/strategy/tco.md`).
Снято заранее и вставлено монтажно именно потому, что живая правка адреса шлюза на публичном
стенде — риск для демо; сама сцена показывает реальный, а не постановочный отказ.

**5:20–5:50 — Скрипт кейсодержателя вживую, без монтажа.** В терминале, поверх стенда: запуск
`case-data/eval/participant_test.sh --endpoint http://89.110.72.101/v1/eval/predict` (или
локальный порт 8080 — см. `README.md`) на заранее подготовленной пачке фото → дождаться
`predictions.jsonl` → показать итоговую долю совпадений и `latency_ms` прямо в файле. Это тот же
плоский несгораемый эндпоинт, которым будут проверять нас на приватном датасете
(`contracts/image-scan.md` v0.4.6) — самое сильное доказательство для жюри, что цифры со
слайда — не рисунок, а действительно то, что отдаёт сервис на их собственном скрипте.

**5:50–6:40 — Доп-функция (ретеншн, вес критерия 20/100, `case.md` строка 84).** Сомелье-чат с
цитатами (теперь Qwen 27B через свой GPU-шлюз, не заглушка), аналоги российских вин иностранным,
вкусовой профиль по свайпам (7 осей вкуса, `contracts/openapi.yaml` `/taste/profile`) — коротко
показать один экран паспорта вкуса, если успеваем по хронометражу; если нет — оставить на словах
со ссылкой «работает, показано в приложении к репозиторию» (подробный статус —
`docs/product/post-scan.md`).

**6:40–7:00 — Выводы, честно (20 секунд — сжато, чтобы уместить сцену GPU и скрипт).**
- «Потолок — не 100%, а потолок каталога: у 2054–2058 из 2103 позиций вообще есть пригодное
  эталонное фото (**97.7–97.9%**, `reports/f4-data-hygiene.md`, `reports/d1-ref-collisions.md`) —
  и близнецы одной линейки остаются главным источником оставшихся ошибок
  (`reports/label-crop-study.md`)».
- «Всё воспроизводимо: репозиторий, README и ARCHITECTURE.md, метрики и скрипт — только что
  видели вживую, не на слайде» (`README.md`, `ARCHITECTURE.md`).

## Решение тимлида (22.09) по хронометражу

Раньше здесь стоял вопрос — возвращать ли в ролик терминал со скриптом кейсодержателя. Тимлид
подтвердил: да, вернуть короткий (~30 с) сегмент с живым запуском `participant_test.sh` против
стенда и итоговой цифрой — «самое сильное доказательство для жюри»; сомелье и кандидаты остаются
без сокращений. Место найдено сжатием «Выводов» с 60 до 30 секунд (см. хронометраж выше) — сумма
по-прежнему 7:00.
