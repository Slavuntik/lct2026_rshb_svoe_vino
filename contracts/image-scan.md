## ImageIndex (packages/cv)

```python
@dataclass
class Match:
    slug: str
    score: float          # сравним только внутри одного ответа (как Candidate.score)
    gap: float | None     # отрыв от следующего НЕ-той-же-группы кандидата
    view: str             # какой ракурс эталона сматчился (реальный | synth-N)

class ImageIndex:
    def embed(self, image: bytes) -> list[float]: ...
    def search(self, image: bytes, top_k: int = 5) -> list[Match]:
        """Запрос проходит нормализацию ДО эмбеддинга: детект этикетки → кроп →
        выпрямление цилиндра → фотометрия. Без нормализации — только явным флагом."""
    def build(self, refs: dict[str, list[str]], version: str) -> None:
        """slug → список файлов (эталон + синтетические ракурсы). Версия в манифест."""
    def add(self, slug: str, images: list[bytes]) -> None:  # +50 позиций/день без ребилда
```

- Бэкенд: env `IMAGE_INDEX_MODE=qdrant_embedded | pgvector`. Дев-дефолт — qdrant_embedded
  (на машине нет Docker); pgvector — прод-профиль в compose (ориентир платформы кейса).
  Интерфейс один, переезд — строчка env.
- Энкодер: SigLIP 2 (env `CV_MODEL`, размер по замеру на MPS/CPU); эмбеддинги кэшируются.
- Индекс мульти-ракурсный: на позицию — эталон + N синтетических видов (цилиндр, наклоны,
  блики, смаз). Поиск возвращает лучший ракурс позиции, дубли позиции схлопываются.

### Уточнения v0.4.2 (по отчёту G)

- **Конвенция build/add:** в `refs[slug]` первый файл — эталон (view="real"), остальные —
  synth-1..N в данном порядке; `add(slug, images)` дозаписывает ракурсы той же конвенцией.
- **Единый домен нормализации:** каждый ракурс индекса проходит ТУ ЖЕ `normalize_query()`,
  что и запрос. Рассинхрон доменов стоил 10+ п.п. self-match (находка G: 83% → 93.9%).
  Менять нормализацию = пересобирать индекс; версия нормализации пишется в манифест.
- **Группировка near-dup:** `gap` считается через порог `CV_GROUP_EPSILON`, откалиброванный
  пока на дев-фикстурах; обязательная перекалибровка на реальных near-dup парах датасета
  кейса. Фотометрия намеренно мягкая — тоже перепроверяется на реальных «полевых» фото.

## OCR-верификатор (v0.4.4 — реальная спецификация; владелец: packages/cv, агент G)

До сих пор был моком — а кейс проверяет достоверность именно на near-dup (ревью 04, блокер 1).

```python
class VerifyCandidate(TypedDict):
    slug: str
    name: str            # из каталога: несёт год/категорию текстом
    vintage: int | None

class LabelVerifier:
    def verify(self, image: bytes, candidates: list[VerifyCandidate]) -> str | None:
        """Различение near-dup семьи по мелкому тексту этикетки: OCR нормализованного
        запроса (регион этикетки), извлечение токенов года (19xx/20xx), объёма и
        категории, сопоставление с name/vintage кандидатов. None = воздержался —
        API оставляет ANN-топ (честная деградация, не ошибка). Бюджет ≤ 700 мс p95
        (цель обычного окружения; измеренное на стенде — в примечании под блоком).
        Движок: PaddleOCR (кириллица + латиница), офлайн после первой загрузки."""
```

**Бюджет `verify()` ≤ 700 мс p95 — цель, а не наблюдаемое на стенде** (уточнено v0.4.19, 26.09).
700 мс мерялись на машине разработки (Mac): p50 456 мс, `reports/ml-eng-verify-latency-test.md`. На
боевом стенде ams3 (4 vCPU) разовый прогон при выкате hack-v18 (`RUN_CV_BENCHMARKS=1`, n=30) дал
**p50 1993 / p95 2118 / max 2240 мс** — втрое выше цели (`reports/devops-hack-v18.md` §«Разовый
бенчмарк verify()»). Причина известна и не является регрессией: на этом боксе обязателен обход бага
oneDNN у paddlepaddle 3.3.1 (`ENABLE_MKLDNN_BYDEFAULT=0 FLAGS_use_mkldnn=0`), без него движок молча
возвращает пустой результат — `infra/ams3/README.md`. **Сквозной бюджет скана при этом соблюдается**:
тот же выкат — `flat_ms` p50/p95/max **4650/6416/6537 мс** при жёстком лимите кейса 10 с. Цифру 700
мс не меняю: она остаётся целью для окружения без этого обхода и порогом бенчмарка
`packages/cv/tests/test_verify.py::test_verify_p95_latency_budget` (с hack-v18 скипается по
умолчанию, включается `RUN_CV_BENCHMARKS=1`). Пересмотр порога — отдельным решением после сдачи.

B передаёт метаданные кандидатов из каталога (get_by_id); Protocol в apps/api приводится
к этой сигнатуре. Приём фото (v0.4.4, ревью 04): decode обязан применять EXIF Orientation
и открывать HEIC; лимит размера 25 МБ; flat-режим ловит ЛЮБОЕ исключение (не только
ValueError), принимает первое файловое поле multipart независимо от имени; env-флаг
SCAN_FLAT_DEFAULT=1 делает flat режимом по умолчанию (страховка под неизвестный скрипт
кейсодержателя). ImageIndex отдаёт index_version из манифеста — /metrics/scan обязан
показывать её, не env-плейсхолдер.

## Пайплайн /scan/photo

фото → нормализация → embed → ANN top-K по ракурсам → схлопывание в позиции →
если топ-позиции из одной near-dup-группы (одна этикетка, разные год/категория) →
OCR-верификатор (год, категория, объём с этикетки) → калиброванное решение.

Исходы (это НЕ прежние «три исхода» текст-сканера — семантика кейса):
- **confident** → одна карточка. Никакого экрана вариантов.
- **not_in_catalog** → похожие вина и аналоги из других виноделен (ветка «нет в каталоге»,
  по ТЗ оценивается особенно высоко) либо честное «не найдено».

v0.4.5 (калибровка F2 на impostor-холдауте): решение not_in_catalog — **относительное,
по марже**, не по абсолютному скору. Доказано: глобальный порог скора не разделяет
(0.55 → FPR 100%; 0.9 → FNR 66.7%; equal-error 0.85 → 8.9%/26.7% — всё неприемлемо).
Правило: not_in_catalog когда top1_score < CV_ABS_FLOOR (грубый пол) ИЛИ маржа
(top1 − top2_чужой_семьи, т.е. gap) < CV_MARGIN_FLOOR. Оба env-параметра калибруются
на реальном dev-сплите + impostor-холдауте в день датасета (qa/calibrate_not_in_catalog_threshold.py
уже умеет свип); синтетические значения — только стартовые точки.

### v0.4.7 — семантика gap и null-gap (блокер TODO-0 ревью 05; baseline F3 b4f9608)

Измерено на 1982 позитивных запросах: raw top-1 69.4%, но гейт v0.4.5 пропускал 6.8% —
`gap` почти всегда `null` на плотном каталоге и трактовался как провал маржи. Исправление:

1. **Конкурент для gap** — первый кандидат top-K, НЕ принадлежащий near-dup СЕМЬЕ
   top-1 по переписи (`case-data/families.json`, загружается ImageIndex опционально);
   эпсилон-группировка (CV_GROUP_EPSILON) — только фолбэк, когда переписи нет.
2. **gap = null означает доминирование** (в top-K нет чужой семьи), НЕ неуверенность:
   маржинальная проверка при null СЧИТАЕТСЯ ПРОЙДЕННОЙ. not_in_catalog при null-gap
   возможен только по абсолютному полу (top1_score < CV_ABS_FLOOR).
3. Если top-K содержит НЕСКОЛЬКО членов одной семьи — верификатор вызывается как
   раньше (различение внутри семьи), независимо от исхода маржинальной проверки.
4. flat-режим не меняется (несгораемость и «всегда лучший slug» не зависят от гейта).
5. Прогрев на старте обязан греть И верификатор (первый verify тянул PaddleOCR
   лениво: +2 c первому запросу — репетиция B3, c03edd0).
6. /healthz разводит версии по пространствам имён: `rag_index_version` +
   `cv_index_version` (поле `index_version` — deprecated-алиас rag, до v0.5).
   Синхронная правка openapi.yaml — оркестратором.

CV_ABS_FLOOR=0.9 при среднем скоре верного top-1 0.87 — вопрос КАЛИБРОВКИ: не трогать
до полевого dev-сплита (ревью 05, TODO-8).

### v0.4.10 — архив сканов для контрольной выборки (решение Вячеслава, 21.09)

- env `SCAN_ARCHIVE_DIR`; не задан — ничего не сохраняется (дефолт dev/тестов).
- Архивируются ТОЛЬКО rich-сканы `POST /v1/scan/photo` (интерфейс). flat-режим и
  `/v1/eval/predict` не архивируются НИКОГДА: через них идёт приватная контрольная выборка
  кейсодержателя, копить её у себя недопустимо.
- Раскладка по исходу гейта: `confident/` (карточка показана), `unsure/` (скор ≥ CV_ABS_FLOOR,
  маржа не пройдена — близнецы и т.п.), `failed/` (ниже пола или нет совпадений); внутри —
  подкаталог по дате. На скан: `<id>.jpg` — перекодирован в JPEG БЕЗ метаданных (EXIF телефона
  несёт GPS), `<id>.json` — предсказание, top-5, скор, gap, ocr_verified, index_version,
  `verified_slug: null`; общий `index.jsonl`. Не декодируется — только сайдкар, байты не пишутся.
- Корзины — уверенность системы, не истина: контрольная выборка собирается только после
  ручной сверки (`verified_slug`) и из всех корзин, иначе метрика оценивает систему её же ответами.
- Запись — фоновой задачей после отправки ответа; сбой архива на ответ не влияет.
- Режим ВРЕМЕННЫЙ — только на стенде, на время сбора выборки; в прод-конфигурациях
  SCAN_ARCHIVE_DIR не задаётся, архив выключен. Интерфейс о сборе не сообщает (решение
  Вячеслава), поэтому и заявлений «фото не сохраняется» в подписи сканера нет. Перед тем
  как ссылку на стенд получат люди вне команды, режим выключается (строка в somelye.env).

### v0.4.13 — слияние CV + текст этикетки по всему каталогу (G7, оркестратор; живые фото, 21.09)

Основание — 100 живых фото организаторов, размеченных вручную (62 вина из каталога, 38 вне):
на них прежний путь (ANN + верификатор) даёт top-1 51.6%; переранжирование v0.4.12 не меняет

фото («ориентир — выданные живые примеры»), поэтому решения по пайплайну — только по ним.

1. `CV_FUSION=1` полностью заменяет путь ANN/near-dup/`CV_TEXT_RERANK` (включены оба — действует

   маркер сахара. Кандидаты = CV top-50 ∪ текст top-30 (CV-скор текстовых — точным запросом).
   Итог `final = cv + CV_FUSION_W·rel`; слагу без эталона в индексе — CV-заглушка `cv_top1 − 0.03`.
3. Источник текста `CV_FUSION_TEXT_SOURCE`: `ocr` (PaddleOCR), `vlm` (модель на GPU-сервере

5. Ответ: flat — итоговый top-1; rich — `matches`/`candidates` = итоговый top-5 (score = final),
   `confidence.top1_score` = CV-скор top-1, `gap` = итоговый отрыв по семье (до verify).

   `vlm_both` 95.2% (5.3 с) top-1; прежний путь 51.6%.

## Режимы ответа API

`POST /v1/scan/photo` (multipart: image; необязательный `?flat=1`)

- **flat (режим скрипта оценки):** ровно `{"slug": "wine-slug"}`, одной строкой JSON.
  ВАЖНО: flat ВСЕГДА отдаёт лучший доступный slug, даже при низкой уверенности —
  скрипт сверяет с закрытой таблицей, пустой ответ гарантированно мимо, лучший кандидат
  имеет шанс. Честность про уверенность живёт в rich-режиме и UI, не в flat.
- **rich (UI):** `{slug, card, confidence: {top1_score, gap, f1_top1, f1_top5},
  ocr_verified: bool, timing_ms, not_in_catalog: bool, similar: [...], analogs: [...]}`.
  v0.4.1 (пробел нашёл C): `card` — ровно тело ответа `GET /wines/{id}`
  (`{wine_id, source, derived, source_url, similar}`); отдельной формы у карточки скана нет,
  клиент рендерит её тем же компонентом, что и прямой переход на вино. С v0.4.17
  (`openapi.yaml` 0.3.6) тело несёт ещё `similar_wines` (объекты вместо голых слагов
  `similar` — тот же баг класса «слаг вместо названия», найден жюри) — `card` получает поле
  автоматически, отдельной правки этого пункта контракта по сути не требуется, изменение
  документируется здесь для трассируемости.
  v0.4.3 (пробел нашёл F): rich дополнительно несёт `matches: [{slug, score}]` — top-5
  схлопнутых позиций в порядке убывания. UI это поле НЕ рендерит (одна карточка — закон);
  оно для eval-раннера: без top-5 в ответе F1-top5 через живой API вырождается в top-1,
  а ТЗ требует обе метрики. flat-режим не меняется — ровно {"slug": "..."}.
  F1-цифры — с последнего eval-прогона (версия индекса в манифесте), это требование ТЗ
  «показать метрику в API».

`GET /v1/metrics/scan` → {index_version, f1_top1, f1_top5, match_rate, eval_set, measured_at}.

v0.4.6 (по скрипту кейсодержателя, получен 16.09): `POST /v1/eval/predict` — фиксированный
алиас flat-режима (общий обработчик, та же несгораемость, без auth, HTTP 200). Дефолтный
эндпоинт их participant_test.sh: `http://127.0.0.1:8080/v1/eval/predict`, поле multipart
`image`, валидный ответ — `{"slug":"..."}` либо `[{"slug":"..."}]`, HTTP 200/201,
curl max-time 10 c. Запуск под скрипт: uvicorn на :8080 (README).

### v0.4.10 — рамка пользователя в `/v1/scan/photo` (необязательное поле `box`)

Второй движок (`packages/winescan`, `IMAGE_PROVIDER=winescan`) принёс замер, который
касается обоих: **выбор нужной бутылки, а не качество поиска, — главный резерв точности на
кадре «у полки»**. При идеальном выборе среди рамок детектора top-1 достигает 0,775, при
автоматическом — 0,663; попытки вытащить признак «та самая бутылка» из кадра (другая цель
обучения, объединение кандидатов, проверка совпадений) дали 0,669 / 0,402 / 0,667 — то есть
ничего. Единственный способ забрать эти 11 п.п. — спросить пользователя.

Поле: `box` в той же multipart-форме, `"x1,y1,x2,y2"` в **долях** кадра (0…1, слева сверху).
Доли, а не пиксели: клиент показывает фотографию вписанной и не знает итогового разрешения
после сжатия камерой.

Семантика:

1. Рамка применяется **до** движка — кадр вырезается в `app/cv/user_box.py`, `ImageIndex`
   получает готовые байты. Контракт движка не меняется, фича работает у обоих провайдеров.
2. rich-режим: негодная рамка (не четыре числа, вне 0…1, стороны меньше 2% кадра) —
   `400 validation_error`, как и любой другой негодный ввод.
3. flat-режим: рамка разбирается внутри той же несгораемой обёртки. Негодная рамка не
   ломает ответ — она просто игнорируется, и скан идёт по всему кадру: у скрипта оценки
   поля `box` нет вовсе, и появиться оно там может только по ошибке.
4. Поле необязательное; без него поведение прежнее, ни один существующий вызов не меняется.
