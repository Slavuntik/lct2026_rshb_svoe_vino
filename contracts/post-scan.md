## 1. Гастропары к распознанному вину — `GET /v1/wines/{wine_id}/pairings`

Резолвит `wine_id` **тем же путём**, что `GET /wines/{wine_id}` (переиспользовать
`apps/api/app/rag/cards.py::build_wine_card`, не дублировать резолюцию наш-каталог/каталог-кейса).
404 `not_found`, если `wine_id` не резолвится ни там, ни там — как у `GET /wines/{id}`.

### Схема ответа 200

```
{
  "wine_id": "...",
  "basis": "catalog" | "sensory" | "heuristic" | "unavailable",
  "pairings": [
    { "tag": "Сыры", "score": 0.83, "triggered_rules": [{"id": "fat_needs_acidity", "explain": "..."}] }
  ],
  "message": null | "человекочитаемый текст — непусто ⟺ pairings=[]"
}
```

`pairings` — не более `output_contract.top_n=3` (`food_pairing_rules.yaml`, число не меняем).
`score`/`triggered_rules` — `null`/`[]` при `basis=catalog` (см. Уровень 1 — это чужой, не
скорингованный текст). Важно: `output_contract` в yaml описан для направления «блюдо → вино»
(`must_include: wine_slug, source_url` — там это ссылка на карточку рекомендованного вина).
Наше направление обратное (вино уже известно, ищем блюдо) — из `output_contract` берём ТОЛЬКО
`top_n=3`; `wine_slug`/`source_url` в ответе не нужны (wine_id уже в корне объекта), а
`never_include` (никаких заявлений о пользе алкоголя) соблюдается автоматически: `explain`
всегда дословно из `rules[].explain` в yaml, никакая LLM текст не генерирует.

### Три уровня данных (проверять по порядку, первый пригодный — используется)

**Уровень 1 — `basis="catalog"`.** `source.food_pairings` (`WineSource`, `apps/web/src/lib/
apiTypes.ts:133`) непуст → каждый элемент как есть, `{tag, score: null, triggered_rules: []}`.
Это наш каталог (1978 позиций); поле уже рендерится карточкой напрямую
(`WineCardContent.tsx:93-104`) — новый эндпоинт не подменяет этот рендер, а даёt тот же контент
вторым путём ради единообразия фронта (один код-путь на обеих карточках, см. бриф frontend).
Каталог **кейса** этого поля не несёт НИКОГДА (`build_wine_card`, `cards.py:44-53`) — сразу
уровень 2/3. Словарь тегов уровня 1 — сырой текст портала, шире и НЕ обязан совпадать с 9 тегами
уровня 2/3 ниже (`food_pairings: partial — видно 6 из N`, `pipeline/ref/taxonomy.yaml:12`) — это
ожидаемо, не баг рассинхрона.

**Уровень 2 — `basis="sensory"`.** `derived.sensory` присутствует (`WineDerived`,
`apiTypes.ts:147-151` — наш каталог, когда `food_pairings` пуст) → это и есть `wine.*` в правилах
`food_pairing_rules.yaml` без каких-либо преобразований: имена осей совпадают буквально
(sweetness/acidity/tannin/body/oak/aromatic_intensity/bubbles). Одно исключение — `wine.abv_percent`
(используется в `spice_needs_sugar`): это НЕ ось `derived.sensory`, брать из `source.abv_percent`;
если `null`/нет поля — см. дефолт в конце уровня 3.

**Уровень 3 — `basis="heuristic"`.** Ни уровня 1, ни уровня 2 (каталог кейса — это ПОЧТИ ВСЕГДА
именно этот случай при сканировании) → `wine.*` строится эвристикой из `color`/ключевых слов
`name`+`description`. Если даже `color` пуст (в дампе кейса это редкие строки без колонки
«Категория») → `basis="unavailable"`, `pairings=[]`, `message` заполнен.

### Правила скоринга (сама логика — `food_pairing_rules.yaml`, не меняем; ниже — как читать
мини-DSL для РЕАЛИЗАЦИИ, коротко, т.к. в файле это не расписано программно)

Кандидаты — 9 тегов `portal_tag_defaults`. Отсутствующая в теге ось `dish.*` = 0.0. Формат
условий (`when`/`require`/`penalize`/`hard_blocks[].condition`) — словарь из 1+ ключей,
несколько ключей = **И** (все должны выполниться); ключи `hard_blocks[].condition` МОГУТ
смешивать `dish.*` и `wine.*` в одном словаре (остальные секции — только свой namespace) —
нужен один общий `eval_condition(dict, dish, wine)`, не два разных. Операторы, реально
встречающиеся в файле: `>=X`, `<=X`, `~=dish.Y ± Z` (допуск), `>=dish.Y` (сверка с ДРУГИМ полем
блюда, не константой), `matches wine.region` (строковое совпадение; структурно недостижимо —
у тега блюда нет `cuisine_region`, `regional_affinity` ожидаемо не сработает НИКОГДА — это не баг).

1. Хард-блоки: если `condition` истинно — тег исключён из кандидатов целиком, до скоринга.
2. Для тега: `applicable = Σ weight` правил, чей `when` истинен. Для каждого такого правила:
   `require` выполнен → `+weight`; `penalize` выполнен → `−weight` (У `umami_needs_maturity`
   ОБА поля сразу — независимые вклады, могут погасить друг друга); ни require, ни penalize
   (бонус-правило вроде `regional_affinity`) → `+weight` безусловно при истинном `when`.
3. `score = clamp(raw / applicable, 0, 1)`, если `applicable>0`, иначе 0. Тег входит в
   `pairings`, только если `score > 0` (не показываем тег без единого сработавшего правила —
   не выдумываем уверенность из шума).
4. Топ-3 по `score` убыв.; равенство — по алфавиту тега (детерминированность тестов).
5. Если 0 тегов прошли `score>0` → `pairings=[]`, `basis` остаётся тем, что было (sensory/
   heuristic — вектор БЫЛ, просто ни одно правило не выстрелило), `message` заполнен.

**Примечание (22.09, ml-lead, `b6872e5`, `reports/ml-lead-dish-pairing-poultry-fix.md`):**
`portal_tag_defaults["Блюда из птицы"].protein_heavy` исправлен 0.6→0.55 — при 0.6 тег ровно
попадал под порог `protein_needs_tannin` («мясо просит танинное красное»), из-за чего
скоринг систематически предпочитал танинные красные птице вопреки реальному распределению
цвета каталога у этого тега (портал сам маркирует им 54.8% белых вин, 27.2% красных). Это
калибровка данных (тот же механизм скоринга, не логика), затрагивает ОБА направления —
§1 (вино→блюдо, тег «Блюда из птицы» в выдаче) и §4.3 ниже (блюдо→вино, ярус `rules` для
категории «Блюда из птицы»); текст контракта не меняет ни в одном из двух направлений.

## 2. «Похоже по вкусу» — без новых сущностей

`/v1/analogs` и `/v1/taste/*` не меняются НИ НА ПОЛЕ. Вся реализация — frontend (оркестрация
существующих вызовов), см. бриф.

### 2.1 Похожие по стилю — карточка → `POST /v1/analogs`

Запрос строится из уже полученной карточки (`WineCardResponse.source`), без нового API:

1. `query = source.grapes.join(", ")`, если `grapes` непуст;
2. иначе `query = source.name`;
3. если (1) вернул 404 `not_found` и `grapes.length > 1` — один повторный запрос с
   `query = source.grapes[0]` (один сорт часто матчится лучше, чем весь купаж целиком —
   `resolve_style` это rapidfuzz `token_set_ratio` против `name`/`slug` 146 стилей,
   `RAG_STYLE_GARBAGE_CUTOFF=55`, `packages/rag/rag/config.py:109`; многие стили названы
   буквально по сорту — «Совиньон Блан Марлборо», «Пино Гриджо», «Зинфандель Калифорния»,
   `pipeline/ref/reference_styles.yaml`);
4. если все попытки 404 — блок показывает `message` ИЗ ОТВЕТА `/analogs` (он уже содержит топ-5
   популярных стилей, `apps/api/app/routers/analogs.py:32-37`) — не изобретать новый текст,
   не показывать как ошибку/тост.

### 2.2 Личный вкусовой профиль (опционально, НЕ критерий приёмки)

Для авторизованных не-гостей — если `style.slug` из 2.1 входит в `top_styles` из
`GET /v1/taste/profile`, можно показать короткую пометку «в вашем вкусе». Гостю эндпоинт отдаёт
403 `consent_required` (scope profiling) — ожидаемо, не ошибка; просто не показывать пометку.

### 2.3 Переход к вкусовому паспорту (CTA, тоже без нового API)

Кнопка «Пройти вкусовой паспорт» → переход на существующий экран свайп-дегустации
(`GET /v1/taste/candidates`, уже реализован и покрыт тестами — `docs/product/post-scan.md:15`:
«это фронтенд-связка экранов, не новый API»). Гостю — переход на апгрейд токена
(`POST /auth/register` с гостевым Bearer, `openapi.yaml` `/auth/register`: «апгрейд ТОЙ ЖЕ
строки users»), не на дохлую 403.

## 4. Что подать к блюду по фото — `POST /v1/pairing/dish-photo`, `POST /v1/pairing/dish`

Основание: задача тимлида 22.09 (решение Вячеслава) — обратное направление «блюдо → вино»,
до сих пор специфицированное (`food_pairing_rules.yaml`), но нигде не подключённое
(`docs/product/post-scan.md` строка 17: «движок правил есть… но НЕ импортируется ни в
packages/rag, ни в apps/api»). Обе ручки отдают **одну и ту же форму ответа**
(`DishPairingResponse`, `openapi.yaml`); различаются только тем, как резолвится `category`.

### 4.0 Общее для обеих ручек

- Кандидаты на вино — **только наш каталог** (`packages/rag`, тот же источник, что
  `/analogs` и уровни 1/2 §1 выше), каталог кейса НЕ используется: у него структурно нет
  `food_pairings` (§1 «Находка»), а эта ручка — рекомендация «что купить/выбрать», не карточка
  сканирования, где фолбэк на каталог кейса оправдан требованием ТЗ показывать то, что
  реально стоит на полке.
- `category` — строго один из 9 тегов `portal_tag_defaults` (`pipeline/ref/
  food_pairing_rules.yaml`): Устрицы, Сыры, Блюда из рыбы, Блюда из птицы, Салаты, Брускетты,
  BBQ, Азиатская кухня, Выпечка и десерты. Значение вне этого списка нигде не возникает как
  легальное — ни от модели (промпт задаёт их перечислением, не свободной генерацией), ни от
  пользователя (400 `validation_error`, см. 4.2).
- Схема 200 (обе ручки; типы сверены с реализацией backend 22.09,
  `apps/api/app/schemas.py::DishInfo/DishPairingWineItem/DishPairingResponse`):
  ```
  {"status": "food"|"not_food"|"bottle"|"unsure",
   "dish": {"name": str, "category": str|null, "alternatives": [str],
            "ingredients": [str], "source": "vlm"|"vlm_local"|"zero_shot"|"user"|"none"},
   "wines": [{"wine_id", "name", "winery": str|null, "color": str|null, "sugar": str|null,
              "image_url": str|null, "reason", "basis": "catalog"|"rules"}],
   "message": str|null, "timing_ms": int}
  ```
  `dish.name` — **не `null`**, пустая строка `""`, когда нечего показать (не противоречит
  «str|null» из брифа тимлида буквально, но проще для клиента — один тип на поле, без
  дополнительной ветки `null`-проверки). `wines[].winery/color/sugar` — `null`, если у
  конкретного вина нет соответствующего поля в `source` (не пустая строка — отличать
  «данных нет» от «пустое значение»).
- `wines` — max 6, **не более 2 на одну винодельню** (группировка по слагу `source.winery`,
  фолбэк — `winery_name`, затем `wine_id`, если нет ни того ни другого — у отображаемого
  `winery_name` возможны варианты написания, группировать по нему ненадёжно). Подбор —
  §4.3. Список пуст ⟺ `message` заполнен (тот же принцип, что §1 п.5 — честно, не тишина).
- Намеренно **нет `source_url`** в схеме вина этой ручки (в отличие от `ScanCandidateItem`/
  `analogs`, где поле историческое) — переход только на внутреннюю карточку
  `/app/wine/:wineId`, внешняя ссылка — из карточки, см. §5 «Правило ссылок» ниже.
- Фото блюда **не пишутся в архив сканов** (`SCAN_ARCHIVE_DIR`/`archive_scan()`, v0.4.10
  `image-scan.md`) — другая категория данных, вне цели и согласия того архива (контрольная
  выборка организаторов о винных бутылках, не о еде).

### 4.1 `POST /v1/pairing/dish-photo` — классификация фото блюда

Multipart, поле `image`. Лимиты и приём файла — **как у `/v1/scan/photo`**: до 25 МБ
(`SCAN_MAX_UPLOAD_BYTES`), EXIF-ориентация, декодирует HEIC. Авторизация — **как у
`/v1/scan/photo`**: опциональный принципал (`get_current_principal_optional`,
`apps/api/app/routers/scan.py` — НЕ обязательный Bearer, в отличие от текста `openapi.yaml`
для rich-режима скана, который на практике тоже опционален; гость и вошедший пользователь
получают одинаковый ответ, авторизация только атрибутирует запись, если она где-то будет
использована). Как у rich-режима скана: некорректный запрос (нет поля `image`, битый
multipart) — обычная валидация FastAPI (4xx); сбой ВНУТРИ классификации (шлюз недоступен,
модель вернула мусор, оба таймаута, фото не декодируется) — **никогда 500**, деградация по
цепочке ниже до `status="unsure"`.

Классификация (реализация backend 22.09, `apps/api/app/dish_recognition.py`, сверено
architect построчно — ниже описывает КОД, не первоначальный черновик брифа):

1. **`vlm` / `vlm_local`** — шлюз (`VISION_LLM_URL/KEY`, тот же шлюз и та же модель, что
   чтение этикетки, `image-scan.md` v0.4.13 п.3) и локальная модель на Mac
   (`VISION_LLM_LOCAL_URL`, Qwen3-VL-4B через MLX, служба `local-vlm`, тот же процесс/порт
   8093, что скан) запрашиваются **параллельно** (обе, если настроены и предохранитель
   разрешает — тот же пул `_FUSION_MODEL_POOL`, что у скана), один общий дедлайн
   `VISION_LLM_TIMEOUT_S` (дефолт **6.0 с**) от начала запроса на каждую. Результат шлюза
   побеждает, если успел; иначе — локальный (**не склейка текстов**, в отличие от слияния
   сканера — здесь простой приоритет). `dish.source` — какой из двух реально ответил.
   Промпт — строгий JSON: `is_food`, `is_wine_bottle` (независимый признак — может быть
   `true` даже при `is_food=false`), `dish` (название), `ingredients` (до 5), `category`
   (один тег из 9 — **весь список передаётся в промпт перечислением**, пустая строка, если
   модель не уверена — не выдумывает), `alternatives` (до 2 других уместных тегов).
   `category`/`alternatives` от модели проходят через ту же нормализацию, что и ручной ввод
   (см. 4.2: точное совпадение → синонимы → нечёткое rapidfuzz) — модель не обязана попасть
   в написание тега буквально.
2. **`zero_shot`** — ни `vlm`, ни `vlm_local` не ответили (не настроены/предохранитель
   открыт/оба не уложились в дедлайн): CLIP-подобная классификация текстовой башней ТОГО ЖЕ
   SigLIP2-энкодера, что индекс сканера (`image_index.encoder`, без правок `packages/cv`) —
   эмбеддинг фото сравнивается с эмбеддингами якорей (9 тегов + «бутылка вина» + «не еда»,
   каждый как `"фото: <якорь>"`). Побеждает ближайший якорь, **только если** отрыв
   top1/top2 ≥ `DISH_ZERO_SHOT_MARGIN` (env, дефолт **0.03**) — иначе воздержание (шаг 3).
   `ingredients`/`alternatives` всегда `[]`, `dish.name=""` — эмбеддинг не читает состав
   блюда и его название, только образ. Энкодер без текстовой башни (тестовые моки) →
   воздержание, тот же путь, что недостаточный отрыв.
3. Ни одна ступень не дала ответа (или фото не декодируется вовсе) — `status="unsure"`,
   `dish.source="none"`, `dish.alternatives` = **все 9 тегов** (не пустой массив — см. 4.0
   и ниже), `message` честный («не удалось точно распознать блюдо — выберите категорию
   вручную»).

**`alternatives` при неуверенности — отдаёт API, не додумывает фронт.** Когда модель
вернула `category` вне словаря 9 тегов (не спасли ни синонимы, ни нечёткое совпадение) —
`status="unsure"`, `alternatives` = все 9 тегов (тот же список, что и в п.3 выше). Когда
модель уверена в `category`, но сомневается между вариантами — `alternatives` — её
собственные 0–2 тега (п.1). Разница инкапсулирована в ответе, фронт не хранит копию списка
9 тегов только ради этого случая (расхождение с более ранним черновиком контракта, где
пустой `alternatives` предполагал фронт-фолбэк — реализация проще: сервер всегда знает,
какой список показать).

**Предохранитель — тот же, что у скана, не независимый.** Один физический шлюз — одна
история сбоев: `VISION_LLM_BREAKER_FAILS` (3) сбоев/таймаутов подряд на модель → открыт
`VISION_LLM_BREAKER_COOLDOWN_S` (60 с), сразу локальный/zero_shot ответ без ожидания
дедлайна. Реализация буквально делит состояние — те же объекты, не копия:
`app/dish_recognition.py` импортирует `_MODEL_BREAKERS`/`_FUSION_MODEL_POOL` из
`app/cv/service.py` (тот же файл, что использует скан), без правок `cv/service.py`.

### 4.2 `POST /v1/pairing/dish` — ручной выбор/исправление категории

JSON `{"category": "<до 100 симв.>", "dish": "<до 200 симв., опционально>"}`. Нет фото —
нет VLM, нет предохранителя, нет дедлайна 6 с (только подбор вин, §4.3). Auth —
**обязательный** Bearer (`get_current_principal`, НЕ опциональный, в отличие от 4.1) —
сюда не бьёт приватная проверка кейсодержателя (той нужно только фото), поэтому действует
общее правило `app/security.py` («scan/chat/wines/analogs требуют принципала»), без
исключения, которое есть у `/scan/photo` и `/pairing/dish-photo`.

- `category` — точное совпадение тега (без учёта регистра) → словарь частых синонимов
  («стейк»/«гриль»/«барбекю»→BBQ, «сыр»→Сыры и т.п., неисчерпывающий) → нечёткое совпадение
  (`rapidfuzz.fuzz.token_set_ratio`, порог **80**) → ничего не подошло → `400
  validation_error`. **Порог исправлен с 60 на 80 тимлидом 22.09** (эмпирика — `reports/
  backend-dish-photo.md`, «Расхождения с контрактом»): при 60 общее слово «кухня»
  переоценивалось `token_set_ratio`, и «итальянская кухня»/«марсианская кухня» ложно
  резолвились в «Азиатская кухня»; 80 больше не даёт этих ложных срабатываний, но
  по-прежнему ловит опечатки («Азиятская кухня» → 93%). Один и тот же резолвер
  (`resolve_category()`) обслуживает и эту ручку, и `category`/`alternatives` модели в 4.1 —
  не два независимых парсера.
- `status` всегда `"food"` — пользователь явным действием утверждает, что это блюдо.
- `dish.source="user"`, `dish.name` = переданный `dish` (обрезка пробелов) либо `""`,
  `dish.category` = **резолвленный** тег (после синонима/нечёткого совпадения, не
  обязательно байт-в-байт то, что прислал клиент), `alternatives=[]`, `ingredients=[]`
  (свободный текст `dish` не разбирается на ингредиенты — v1, тот же принцип ограничения
  объёма, что §1 не использует `grapes` в эвристике).
- Путь для UI: чип из `alternatives` (уже содержит нужный список — 4.1) → тап → этот
  эндпоинт с выбранным `category`.

### 4.3 Подбор вин (общий для обеих ручек, когда `category` резолвлен и `status="food"`)

**v2 (22.09, вернул тимлид как дефект backend'у, исправлено `451c481`).** Первая версия
подбирала кандидатов пулом `Retriever.search(query, top_k=30)` — тимлид отклонил: «колода
свайп-дегустации — разнообразие без учёта блюда, к стейку предложат лучшее из колоды, а не
из каталога». Ниже — исправленная версия, реализация сверена architect построчно
(`apps/api/app/dish_pairing.py`).

**Кандидаты — весь каталог, не выборка.** Все слаги `case_catalog.json` (2103 на снимке
22.09), карточка каждого — через `build_wine_card()` (тот же RAG-первым/case-catalog-фолбэк
источник, что `GET /wines/{id}`), `wine`-вектор считается один раз при построении карточки.
Список карточек+векторов **кэшируется на весь процесс** (не на запрос) — построение занимает
измеримое время (12.0 с холодный кэш на 2103 карточки, `reports/backend-dish-photo.md`),
поэтому прогревается в фоновом потоке при старте (`warm_up_catalog_cache()`, вызывается из
`app/main.py`, НЕ блокирует готовность процесса — сбой прогрева не роняет старт, кэш тогда
соберётся лениво на первом запросе). На тёплом кэше сам подбор — **20–69 мс** (среднее ≈50
мс) по всем 9 тегам, измерено на реальном каталоге.

1. **Ярус `basis="catalog"`**: **все** вина, у которых `category` буквально есть в
   `source.food_pairings` (тот же список, что §1 «Уровень 1») — включение СТРОГО по тегу, не
   по score («портал уже сказал, что сочетается» — score движка правил тег не отменяет).
   Сортировка ВНУТРИ яруса — по `score_wine_for_dish(dish, wine, rules_data)` (тот же
   скоринг, что ярус 2, но здесь только для порядка, не для фильтрации): убыв., `wine_id`
   возр. (tie-break); вина без посчитанного score (нет usable-вектора — ни надёжной
   sensory, ни пригодного `color`) — в конец яруса, тоже по `wine_id`.
2. **Ярус `basis="rules"`**: остаток каталога (вина, где `category` НЕ встретился в
   `food_pairings`, либо `food_pairings` вовсе пуст — обычный случай для карточки-фолбэка
   каталога кейса, см. 4.0). Для каждого — `wine`-вектор: `derived.sensory`, если он надёжен
   (`_is_usable_sensory` — тот же гейт «все 7 осей числом», что уровень 2 §1), иначе
   `color`+ключевые слова (`build_heuristic_wine_vector`) — **те же функции
   `app/food_pairing.py`, что уровни 2/3 §1**, переиспользованы буквально, не продублированы.
   `dish`-вектор фиксирован = `portal_tag_defaults[category]`. Скоринг —
   `score_wine_for_dish(dish, wine, rules_data)`, зеркало `score_pairings` (§1 «Правила
   скоринга»: тот же `eval_condition`, те же `hard_blocks`, та же формула
   `score=clamp(raw/applicable,0,1)`), но один `dish` фиксирован, перебор идёт по `wine`.
   **Здесь**, в отличие от яруса `catalog`, `score<=0` или сработавший hard-block →
   вино НЕ участвует вовсе (score — единственное основание попасть в выдачу, не только
   порядок). Сортировка: `score` убыв., `wine_id` возр. (tie-break).
3. **Объединение ярусов**: сначала весь ярус `catalog` по порядку, затем весь ярус `rules`
   по порядку, с ограничением ≤2 вин на винодельню (4.0) и ≤6 вин суммарно; вино не может
   попасть в оба яруса одновременно (проверка тега в п.2 явно это исключает).
4. **`reason`** (одна строка на вино, детерминированно, БЕЗ LLM):
   - `basis="catalog"` — фиксированный шаблон «Портал рекомендует это вино к категории
     «{category}»» (реализация, можно менять текст без изменения контракта — смысл
     важнее буквы);
   - `basis="rules"` — `explain` **самого весомого** сработавшего require/бонус-правила
     (не обязательно первого по порядку в yaml, как в §1 — реализация берёт максимум по
     `weight` среди положительных вкладов), дословно из `rules[].explain`; фолбэк-текст
     «Хорошо сочетается по вкусовому профилю блюда», если `explain` почему-то пуст.
5. Поля вина — из `source.*` кандидата: `winery` = `source.winery_name`, фолбэк
   `source.winery` (слаг), иначе `null`; `sugar` = `source.sugar_category` или `null`
   (пустая строка трактуется как отсутствие — `null`, не `""`); `color`/`image_url` = поле
   `source` или `null`; `name` = `source.name`, фолбэк `wine_id`. Группировка ≤2/винодельня
   (п.3) — по `source.winery` (слаг), фолбэк `winery_name`, затем `wine_id`.

Санити-проверка тимлида на реальном каталоге (все 9 тегов, топ-6) подтверждена: BBQ 6/6
красное, Блюда из рыбы 6/6 белое, Выпечка и десерты 5 сладких+1 полусладкое. По ходу этой
проверки нашлась и отдельно исправлена калибровка тега «Блюда из птицы» — см. §1 примечание
и `HLD.md` «Что пробовали и почему отвергли» (не меняет текст этого пункта, только данные
`food_pairing_rules.yaml`, ml-lead зона).

### 4.4 Статусы

- **`food`** — `category` резолвлен (моделью либо пользователем); `wines` — по §4.3.
- **`not_food`** — уверенно не еда и не бутылка (случайный предмет, меню, пустой стол);
  `category=null`, `wines=[]`, честный `message`.
- **`bottle`** — это вино, не блюдо; `message` предлагает сканер (`/app/scan`), `wines=[]`,

  словаря 9 без спасения синонимом/нечётким совпадением (или вход не обработан вовсе);
  `category=null`, честный `message`, `alternatives` = **все 9 тегов** (API отдаёт готовый
  список чипов сам, см. 4.1 «`alternatives` при неуверенности»).

## 5. Правило ссылок на вино в выдаче

Ратифицировано 22.09 (задача тимлида): в любом списке вин в ответах API — цитаты-вина чата
(`/chat`, событие `citation` с `wine_id`), аналоги (`/analogs`, `similar`/`analogs` в
rich-скане), кандидаты скана (`candidates`, `image-scan.md` v0.4.11), вина подбора к блюду
(§4 выше) — клиент обязан вести **сначала на внутреннюю карточку `/app/wine/:wineId`**;
внешняя ссылка на портал (`source_url`) показывается **только внутри самой карточки**
(`GET /wines/{wine_id}`, `WineCardContent.tsx`), не как прямая ссылка из списка/цитаты.
Полный текст правила — `contracts/openapi.yaml`, шапка файла («Ссылки на вино в выдаче»).
Найденное при ратификации отклонение (цитаты чата вели по внешней ссылке напрямую) исправлено
frontend тем же днём (`5d7772a`, `reports/frontend-dish-photo-links.md`) — на 22.09 все
четыре места (цитаты чата, аналоги, кандидаты скана, вина подбора к блюду) правилу
соответствуют.
Это правило, а не отдельное поле, поэтому у схемы §4 намеренно нет `source_url` (4.0).
