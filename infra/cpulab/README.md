# Второй хак-стенд «Свой Сомелье» — cpulab

Второй, ПАРАЛЛЕЛЬНЫЙ стенд кейса ЛЦТ (задание Вячеслава 27.09). `infra/ams3/` — боевой,
**не трогать**, остаётся источником истины, пока этот стенд не проверен и Вячеслав не
решил переключиться. Сервер: `ssh -i ~/.ssh/cpu_lab somelye@46.243.211.32`.

## Железо и чем отличается от ams3

| | ams3 (боевой) | cpulab (этот) |
|---|---|---|
| CPU | 4 vCPU, «Common KVM», только AVX2 | **8 vCPU**, Intel Xeon Icelake, AVX-512/VNNI |
| RAM | 7.3 ГБ | **15 ГБ** |
| Диск свободно | — | 27 ГБ |
| ОС | Ubuntu 26.04 | Ubuntu 22.04.5 |
| Сосед на боксе | боевой VPN-выход (Reality/hysteria2/WireGuard) | **никого** |
| GPU | нет | нет (шлюз VLM — тот же общий GPU-сервер команды, по сети) |
| node/nginx/uv | было поставлено раньше | ставились этим bootstrap (node НЕ нужен — веб едет готовой сборкой с Mac) |
| Python | системный 3.10 не трогаем, отдельно 3.12 через uv | то же |
| Фаервол | НЕЛЬЗЯ трогать (`ufw`/`iptables`/`nftables` запрещены — боевой VPN) | можно и нужно — см. ниже |

Пользователь `somelye` на этом сервере — **обычный логин-аккаунт с passwordless sudo**,
уже созданный при выдаче доступа (не системный сервисный аккаунт без судо, как на ams3).
Поэтому `bootstrap.sh` здесь не создаёт пользователя и не пишет `/etc/sudoers.d/*` — только
пакеты/каталоги/сервис/nginx/ufw через уже имеющийся sudo. `$HOME` пользователя —
`/home/somelye` (не `/opt/somelye/`, как на ams3) — на это завязана всего одна деталь,
путь к `uv` (`deploy.sh` использует `"$HOME/.local/bin/uv"`, портативно для обоих стендов).

## Фаервол (задание 27.09: «не VPN-бокс, но настрой аккуратно и опиши, что открыл»)

До bootstrap слушали только `22` (ssh) и `53` (systemd-resolved, **только** `127.0.0.53` —
не наружу, не трогали). `bootstrap.sh` включает `ufw` (был `inactive`) с политикой
`deny incoming` / `allow outgoing` и ровно двумя разрешениями:

```
22/tcp   ALLOW IN   Anywhere      # ssh
80/tcp   ALLOW IN   Anywhere      # nginx: статика веба + прокси /v1
```
(и те же два правила для v6 — ufw по умолчанию зеркалит). Порт `8000` (uvicorn) слушает
только `127.0.0.1` (`somelye-api.service`, `--host 127.0.0.1`) — снаружи недостижим, отдельное
правило не требуется. `443` не открывали — нет домена и TLS-сертификата (тот же расклад,
что на ams3, но по другой причине: там порт занят VPN, здесь его просто некому обслуживать).
Правило `22/tcp` ставится **до** `ufw enable`, а после включения фаервола проверено новое
SSH-подключение (не через уже открытую sessию) — самоблокировки не было.

## Состав каталога

| Файл | Что делает |
|---|---|
| `bootstrap.sh` | Разово: пакеты (nginx/rsync/libgl1/libgomp1/...), каталоги `/opt/somelye/*`, uv + Python 3.12, `somelye.env` из шаблона, systemd-юнит, nginx-сайт, ufw (22+80) |
| `somelye-api.service` | uvicorn под systemd — БЕЗ троттлинга ams3 (там `CPUWeight=40`/`Nice=5` ради соседа-VPN); здесь весь CPU процессу, память с запасом (`MemoryHigh=8000M`/`MemoryMax=10000M` против замеренного пика ams3 3.2-3.9 ГБ) |
| `nginx-somelye.conf` | `:80` → статика SPA + прокси `/v1` (тело до 26 МБ, `/v1/chat` — SSE без буферизации, 300с). Проброс витрины Потапа НЕ перенесён (на ams3 тоже выключен, не в задании) |
| `somelye.env.example` | Шаблон окружения — алгоритмические переменные **идентичны** боевому `/opt/somelye/somelye.env` на ams3 (перенесены, не переизобретены); отличаются только инфраструктурные (пути к тем же по содержимому индексам, число потоков, oneDNN — см. ниже) |
| `target.env` | Единственное место с адресом/ключом по умолчанию (`CPULAB_HOST`/`CPULAB_KEY`) — источник для `push-release.sh`/`sync-data.sh`/`pull-scans.sh`, чтобы IP не был продублирован в трёх файлах (см. «Как не хардкодить адрес» ниже) |
| `push-release.sh` | Код (`git archive`) + сборка веба → сервер, затем `deploy.sh` |
| `deploy.sh` | На сервере: `uv sync --frozen --extra integration`, предзагрузка RapidOCR, рестарт, ждать `healthz warm:true` |
| `sync-data.sh` | Индексы и модели с Mac (~3.9 ГБ) — дефолты сразу на `cv-d1`/`rag-20260922` (то, что реально стоит на ams3 сегодня, не историческую `cv`/`rag` заготовку) |
| `pull-scans.sh` | Забрать архив сканов интерфейса (`SCAN_ARCHIVE_DIR`, перенесён из ams3.env) |

## Секреты (перенос с ams3, задание 27.09: «значения не печатать нигде»)

`JWT_SECRET`, `VISION_LLM_URL`/`VISION_LLM_KEY` (адрес и ключ GPU-шлюза), `LLM_BASE_URL`/
`LLM_API_KEY` — перенесены с БОЕВОГО `/opt/somelye/somelye.env` на ams3 (не из
`somelye.env.example` в git, который секретов не несёт) напрямую по конвейеру SSH→SSH,
**без** промежуточного файла и без печати значений в терминал:

```bash
ssh -i ~/.ssh/ci_do_ams3 -o ControlPath=/tmp/somelye-%r@%h somelye@89.110.72.101 \
  'grep -E "^(VISION_LLM_URL|VISION_LLM_KEY|JWT_SECRET|LLM_API_KEY|LLM_BASE_URL)=" /opt/somelye/somelye.env' \
| ssh -i ~/.ssh/cpu_lab somelye@46.243.211.32 'cat >> /opt/somelye/somelye.env'
```

Приём: обе стороны — `ssh`, между ними голый канал (никакого `cat`/`tee` с печатью в
консоль), правый `ssh` пишет ТОЛЬКО в файл на сервере (`cat >>`, стандартный вывод
самого `cat` пуст) — значения ни разу не появляются в выводе команды. `LLM_PROVIDER=openai`
и `LLM_MODEL=qwen3.8-27b` — НЕ секрет (см. `infra/ams3/README.md`, «Секреты GitHub»), взяты
с ams3 напрямую и вписаны в `somelye.env.example` открытым текстом. Перед переносом секретов
на новом сервере `sed -i '/^JWT_SECRET=/d'` и т.п. — на случай, если в файле уже есть
одноимённая строка (systemd `EnvironmentFile` берёт последнюю, но чище без дублей).

Ротация ключа ПОСЛЕ переноса — тем же приёмом, что в `infra/ams3/README.md` («Подключение
LLM через шлюз»), только на порт/хост cpulab, либо через `VISION_LLM_URL`/`VISION_LLM_KEY`/
`GIGACHAT_AUTH_KEY` в `push-release.sh` (переменные окружения, как у ams3-скрипта).

## oneDNN на Icelake: проверка обхода (задание 27.09, ГЛАВНЫЙ вопрос производительности)

**Контекст, которого не было в задании: обход бага НЕ на горячем пути дефолтной
конфигурации.** `PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT`/`FLAGS_use_mkldnn` управляют ТОЛЬКО
`PaddleOCR`, а `PaddleOCR` в проде грузится и вызывается лишь в двух случаях (оба —
`packages/cv/cv/verify.py`, докстринг «Движок текста запроса»): (а) `CV_FUSION_VERIFY=1`
(на ams3 и здесь — ВЫКЛЮЧЕНО, дефолт) и (б) СОБСТВЕННЫЙ внутренний фолбэк
`read_query_text()`, когда быстрый `CV_OCR_ENGINE=rapid` не вернул текст — этот фолбэк
срабатывает независимо от `CV_OCR_ENGINE` (см. `apps/api/app/cv/factory.py`, докстринг
`warm_up_label_verifier`), но только на ДОЛЕ фото, где RapidOCR не читает этикетку.
Поэтому даже честный ответ «обход не нужен» на этой машине не даёт «заметного ускорения»
на p50 всей выборки — он может подтянуть только хвост (p95/max), и только если этот
фолбэк вообще сработал на каких-то фото 100-прогона.

**Метод:** `packages/cv/tests/test_verify.py` (реальный `LabelVerifier`, реальный
`PaddleOCR`, синтетические этикетки с читаемым годом — не фото кейса, воспроизводимо без
`case-data`) — `test_verify_distinguishes_near_dup_pair_by_year_on_readable_view`
(корректность: читает ли Paddle текст вообще, если движок молча возвращает пустоту — тест
красный) и `test_verify_p95_latency_budget` (`RUN_CV_BENCHMARKS=1`, n=30, тот же бенчмарк,
которым ams3 мерялся в `reports/devops-hack-v18.md`). Прогнано дважды: с
`PADDLE_PDX_ENABLE_MKLDNN_BYDEFAULT=0 FLAGS_use_mkldnn=0` (обход, как на ams3) и без них
(oneDNN включён, дефолт Paddle). `pytest` ставился во `/opt/somelye/venv` временно (`uv pip
install`, `--no-dev` его не тянет) и удалён сразу после — тем же приёмом, что
`reports/devops-hack-v18.md` на ams3; живой `somelye-api` не запускался на момент теста
(деплой ещё не выполнялся), сравнение никак не задевало прод-процесс.

**Результат: баг ВОСПРОИЗВОДИТСЯ и на Icelake — обход остаётся ОБЯЗАТЕЛЬНЫМ, «заметного
ускорения» от этого флага нет** (он не даёт лишний, но численно доказано, ПОЧЕМУ):

| | С обходом (`...MKLDNN_BYDEFAULT=0 FLAGS_use_mkldnn=0`) | БЕЗ обхода (oneDNN включён) |
|---|---|---|
| `test_verify_distinguishes_near_dup_pair_by_year_on_readable_view` (2 параметра) | **PASSED** — верно отличает 2024/2025 | **FAILED** — `verify()` вернул `None` вместо `aligote-barrel-2024`/`-2025` на ОБОИХ |
| `verify()`, n=30, синтетическая читаемая этикетка | p50 **1287** / p95 **1319** / max **1358** мс | p50 **25.6** / p95 **26.9** / max **28.4** мс |

Цифры без обхода — не ускорение, а СИМПТОМ: `PaddleOCR` внутри `verify()` при включённом
oneDNN на этом Paddle 3.3.1 молча возвращает пустой текст почти мгновенно (25 мс — заведомо
недостаточно для реального прохода детектор+распознаватель), поэтому `verify()` для ЛЮБОЙ
этикетки, включая читаемую, ничего не находит и воздерживается (`None`) — ровно баг,
описанный в `infra/ams3/README.md` («движок не бросает ошибку наружу, а возвращает ПУСТОЙ
текст»), не CPU-специфичный (AVX2 у ams3 vs AVX-512 у Icelake роли не сыграло — баг в связке
PIR+oneDNN самого Paddle 3.3.1). **Решение: обход остаётся включённым**,
`somelye.env.example` этого стенда несёт те же две строки, что и ams3. Метод и число тестов
воспроизводимы: `packages/cv/tests/test_verify.py -k "p95_latency or readable_view"`,
`RUN_CV_BENCHMARKS=1`, `pytest` временно ставился/удалялся во `/opt/somelye/venv` (как в
`reports/devops-hack-v18.md` на ams3), живой `somelye-api` не запускался/не задет.

Отдельно, ПОБОЧНОЕ наблюдение (не то, о чём спрашивало задание, но полезно для контекста
скорости): даже С обходом `verify()` на этом Icelake ЗАМЕТНО быстрее, чем на ams3 — p50
1287 мс против 1993 мс на ams3 (`reports/devops-hack-v18.md`, тот же тест, тот же n=30) —
на **35%** быстрее ОДНОГО вызова, видимо, из-за более сильного одного ядра (Icelake vs
«Common KVM» AVX2), не из-за 8 vCPU против 4 (сам `verify()` — не то место, что качает
параллелизм по потокам). Но эта функция не на горячем пути дефолтной конфигурации (см. выше)
— к измеренному ниже ускорению 100-фото прогона это отношения не имеет, реальный источник
там — CPU/RAM с запасом и отсутствие соседа-VPN на ВСЕХ этапах конвейера (эмбеддинг, RapidOCR,
сетевой вызов VLM), не эта конкретная переменная.

## Как не хардкодить адрес (задание 27.09, п.7)

Сделано сейчас: `target.env` — единственное место с IP/ключом по умолчанию для локальных
запусков (`push-release.sh`/`sync-data.sh`/`pull-scans.sh` подключают его строкой `.
"$(dirname "$0")/target.env"`, дефолт — `CPULAB_HOST=46.243.211.32`/`CPULAB_KEY=~/.ssh/cpu_lab`);
переопределяется без правки файла — переменными окружения `CPULAB_HOST`/`CPULAB_KEY` или
позиционным аргументом скрипта. Для CI — `.github/workflows/deploy-hack-cpulab.yml` (копия
`deploy-hack-ams3.yml`, секреты `CPULAB_HOST`/`CPULAB_SSH_KEY`/`CPULAB_KNOWN_HOSTS`, свой тег
`hack-cpulab-v*` — НЕ `hack-v*`, тот занят ams3, иначе один тег катил бы оба стенда сразу).

**Что стоит поменять дальше, если появится третий стенд или сменится IP этого:** сам
`46.243.211.32` в `target.env` — единственное место правки для локального использования;
в GitHub — секрет `CPULAB_HOST`, а не текст workflow. `infra/ams3/*.sh` таким файлом пока не
обзавелись (там хост — обязательный позиционный аргумент без дефолта вообще, что тоже
валидно, просто многословнее в каждом вызове); для симметрии стоило бы завести и туда
`infra/ams3/target.env` — технически тоже моя зона (`infra/`), но НЕ делаю это сейчас
сознательно: правка файла, который `push-release.sh`/`sync-data.sh` уже читают на БОЕВОМ
стенде, — риск не в этом задании, без нужды трогать не стал. Если девопс когда-нибудь
унифицирует оба стенда одним параметризуемым скриптом (`infra/deploy.sh --stand
ams3|cpulab`) — `target.env` двух каталогов ровно то, что нужно передать параметром.
