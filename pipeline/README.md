### Поля карточки вина

Название, винодельня, регион, сорта винограда (список), цвет, категория по
сахару, цвет в бокале (текстом), температура подачи, крепость, гастросочетания
(список категорий), описание, фото бутылки, народный рейтинг, рейтинг
Роскачества, блок «похожие вина».

Метатег `title` карточки — самый плотный источник структуры, шаблон:
`Вино <цвет> <категория> <название> <винодельня> из винограда сорта <сорт> региона <регион>`

## Структура папок

```
vines/
├── schema/          модели данных (Pydantic v2) + JSON Schema
├── crawler/         пайплайн выкачки и парсинга
├── ref/             справочники: таксономия, синонимы сортов,
│                    правила гастропар, эталонные импортные стили
├── raw/             сырые HTML-снапшоты (провенанс, не в git)
├── catalog/         нормализованные JSON: wines/, wineries/, articles/
└── build/           индексы: index.jsonl (вина), wineries.jsonl,
                     articles.jsonl (чанки по разделам, потолок 2000 знаков)
```

`crawler/dom.py` — общие примитивы разбора: обход дерева в порядке документа,
привязка значения к текстовой метке, чтение JSON-LD и метатегов. Все три
парсера ходят через него.

## Порядок работы

```bash
make install                    # .venv на Python 3.12 + зависимости
make wines                      # discover -> fetch -> parse -> normalize -> index -> report
make wineries
make articles
make reparse                    # пересборка из raw/ без единого сетевого запроса
```

Или поштучно:

```bash
cd vines/crawler
../.venv/bin/python run.py discover --entity wines
../.venv/bin/python run.py fetch --entity wines --concurrency 4 --delay 0.7
../.venv/bin/python run.py parse --entity wines
../.venv/bin/python run.py normalize      # справочники, сенсорика, связи
../.venv/bin/python run.py build-index    # catalog/ -> build/*.jsonl
../.venv/bin/python run.py report         # покрытие полей по всем сущностям + связность
```

Каждый шаг идемпотентен: `fetch` не перекачивает то, что уже в `raw/`;
`parse` перезаписывает `catalog/`. Порядок важен: `parse` затирает блок
`derived`, поэтому после него всегда нужен `normalize`.

## Правила ведения каталога

1. **Провенанс обязателен.** У каждой сущности `source_url`, `fetched_at`,
   `content_hash`. У каждого производного поля — `derived_from`.
2. **Разделять факт и вывод.** Всё, что пришло с портала, лежит в блоке
   `source`. Всё, что посчитали мы (сенсорный вектор, стиль, теги) — в
   `derived`. Ассистент цитирует только `source`.
3. **Ничего не досочинять.** Отсутствующее поле = `null`, не пустая строка и
   не догадка. Полнота полей меряется отчётом `report`.
4. **Сырьё не трогаем.** `raw/` — только на запись, парсер читает оттуда.
   Перепарсить можно всегда, перекачать — не всегда.
5. **Правовой режим.** Кэш используется как база для поиска и цитирования со
   ссылкой на первоисточник. Редакционные тексты не переиспользуются как
   собственный контент, ответы ассистента ведут на страницу портала.
   Материалы 18+, обязателен дисклеймер об умеренном потреблении.

## Грабли источника

Проверено на боевой выкачке — если что-то из этого «починить обратно»,
данные молча испортятся:

| Что | Почему важно |
|---|---|
| Slug'и бывают с подчёркиванием (`/wineries/jd_winery`) | регулярка `[a-z0-9\-]+` обрезает такой slug и получается 404. Стоило 12 виноделен и 122 связи «вино → винодельня» |
| `css("div, p")` в selectolax отдаёт совпадения **сгруппированными по селектору**, не в порядке документа | привязка «метка → следующий блок» на таком порядке работает только когда метка и значение в одинаковых тегах. См. `dom.text_blocks` |
| `text(strip=True)` склеивает узлы без пробела | `<p>Крепость<br>вина</p>` даёт «Крепостьвина», метка не совпадает, поле пустеет |
| Портал изредка роняет HTTP/2 (GOAWAY) | без ретраев `discover` обрывался на 7-й странице и молча писал 96 slug'ов вместо 1983 |
| Новости размечены как `NewsArticle`, лонгриды — как `Article` | если искать только `Article`, 301 новость теряет текст, дату и автора |
| Года урожая на портале нет отдельным полем | `vintage` берётся только из названия — 111 вин из 1978, это потолок источника, а не баг |

## Грабли модели

| Что | Почему важно |
|---|---|
| Танин и тело задаются винификацией, а не сортом | сортовой профиль протаскивал в розе из Каберне Совиньона танин 0.75. Потолки `TANNIN_CAP`/`BODY_CAP` в `normalize.py` это режут; без них покрытие розовых эталонными стилями падало с 90% до 48% |
| Порог матчинга стилей должен лежать ВНУТРИ диапазона метрики | прежние 0.55 были ниже её пола (минимум по каталогу 0.64) — матч получали все вина без исключения, и поле не значило ничего. Менять `STYLE_MATCH_THRESHOLD` только вместе с замером распределения |
| Категорию нельзя чинить близостью вектора | без жёстких фильтров по игристости и сахару 223 тихих вина попадали в пет-нат и Moscato d'Asti. Фильтры в `match_reference_styles` первичны, вектор — вторичен |
| «Вин без матча стиля: 0» — не достижение | одной доли мало, она была 100% и при сломанном матчере. `report` теперь показывает ещё и сколько разных стилей задействовано и у скольких стилей нашёлся аналог |
| `load_ref` обязан быть закеширован | матчер зовётся на каждое вино; без `lru_cache` `normalize` перечитывал YAML 1978 раз и прогон не укладывался в 10 минут вместо секунды |
