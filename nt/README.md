# nt — нагрузочное тестирование сканера «фото → JSON»

Гоняет картинки из `dataset/` на API (`apps/api`, эндпоинт «фото на вход, JSON на выход»)
в несколько потоков заданное время и показывает **среднее, медианное, максимальное и
минимальное время ответа** — плюс перцентили, пропускную способность и разбор ошибок.

Зависимостей нет: только стандартная библиотека Python 3.11+ (как `qa/scan_eval.py`),
венв и `pip install` не нужны.

```
nt/
  loadtest.py      сам раннер (CLI)
  make_dataset.py  генератор картинок-заглушек для dataset/ (нужен Pillow)
  dataset/         папка для картинок, которыми бьём по API (в git не хранятся — положите свои)
```

## Быстрый старт

```bash
cd nt
./loadtest.py --url http://127.0.0.1:8080 --threads 8 --duration 60s
```

Всё, что нужно задать — три параметра из постановки:

| параметр | что задаёт | пример |
|---|---|---|
| `--url` | адрес API | `http://127.0.0.1:8080`, `https://host:18443/v1/scan/photo?flat=1` |
| `--threads`, `-t` | число потоков (параллельных клиентов) | `--threads 16` |
| `--duration`, `-d` | продолжительность замера | `60s`, `5m`, `1h`, `1m30s`, `90` |

Адрес разбирается терпимо: можно дать только хост (`127.0.0.1:8080`) или базу с версией
(`https://host:18443/v1/`) — путь допишется до `/v1/eval/predict` (плоский режим кейса:
multipart-поле `image`, ответ `{"slug": "..."}`). Полный URL с query берётся как есть —
так гоняется и `/v1/scan/photo?flat=1`, и любой другой эндпоинт «картинка → JSON».

## Все параметры

```
--url URL                адрес API (обязательный)
--threads, -t N          число потоков                                  (4)
--duration, -d T         продолжительность замера: 30s / 5m / 1h        (60s)
--dataset DIR            каталог с картинками, читается рекурсивно      (./dataset)
--warmup T               прогрев: эти запросы не попадают в метрики     (0)
--field NAME             имя multipart-поля с файлом                    (image)
--timeout SEC            таймаут запроса                                (30)
--rps N                  ограничить общий темп, запросов/с              (без лимита)
--no-keepalive           новое соединение на каждый запрос
--header, -H 'K: v'      дополнительный заголовок (можно повторять)
--insecure, -k           не проверять TLS-сертификат
--sla-ms MS              порог для доли уложившихся ответов             (3000, case.md)
--json PATH              записать отчёт в JSON
--quiet, -q              без строки прогресса
--fail-over-p95-ms MS    выйти с кодом 1, если p95 выше порога          (для CI)
--fail-under-rps N       выйти с кодом 1, если rps ниже порога
--fail-over-errors 0..1  выйти с кодом 1, если доля ошибок выше порога
```

Коды возврата: `0` — прогон состоялся, `1` — нарушен заданный порог `--fail-*`,
`2` — ошибка использования (нет картинок, кривой адрес) или ни одного успешного ответа
(сервис недоступен, не тот путь, все запросы упали по таймауту).

## Примеры

```bash
# длинный прогон с прогревом, отчёт в файл
./loadtest.py --url http://127.0.0.1:8080 -t 16 -d 10m --warmup 30s --json runs/16x10m.json

# плоский режим сканера и свои фото
./loadtest.py --url http://127.0.0.1:8080/v1/scan/photo?flat=1 -t 8 -d 5m --dataset ~/photos

# ровный фон 20 запросов/с (проверка стабильности, а не потолка)
./loadtest.py --url http://api:8080 -t 8 -d 30m --rps 20

# гейт для CI: падаем, если p95 хуже 3 с или больше 1 % ошибок
./loadtest.py --url http://api:8080 -t 8 -d 2m --quiet \
              --fail-over-p95-ms 3000 --fail-over-errors 0.01

# сервис за TLS с самоподписанным сертификатом и авторизацией
./loadtest.py --url https://host:18443/v1/ -k -H 'Authorization: Bearer …' -t 4 -d 1m
```

Ctrl+C останавливает прогон досрочно и печатает отчёт по уже собранным замерам.

## Как считается время ответа

- **latency** — полное время запроса в потоке: отправка тела, ожидание сервиса, чтение
  ответа целиком. Считается `time.perf_counter()`.
- **Соединения переиспользуются** (keep-alive), чтобы в метрику не попадал TCP/TLS-хендшейк
  на каждый запрос — так ведёт себя настоящий клиент. `--no-keepalive` включает обратное.
- **Тела multipart собираются один раз на старте**, картинки держатся в памяти: в замер не
  попадают чтение с диска и сборка запроса.
- **Статистика — только по успешным ответам** (HTTP 200 + валидный JSON). Ошибки не
  размывают среднее, а выносятся отдельным разделом с разбивкой по причинам
  (`HTTP 503`, `timeout`, `ConnectionRefusedError…`).
- **Потоки делят картинки чересполосно** (поток i шлёт i-ю, i+N-ю, i+2N-ю…) — чтобы одну и
  ту же картинку не слали все потоки подряд и замер не мерил кэш сервиса вместо работы.
- Если сервис отвечает медленнее дедлайна, прогон занимает чуть больше `--duration`:
  запрос, начатый до дедлайна, дочитывается после. Окно замера в отчёте — фактическое,
  по нему же считается rps; при заметном расхождении раннер это проговаривает.

## Картинки

`dataset/` — папка, куда нужно положить картинки для прогона. Сами картинки в git не хранятся
(см. `.gitignore`), в репозитории лежит только `dataset/README.md`, поэтому перед первым
запуском наполните папку сами — подробности в [dataset/README.md](dataset/README.md).
Подойдут `.jpg/.jpeg/.png/.webp/.bmp/.heic`, вложенные папки тоже читаются. Другой каталог
можно указать через `--dataset`.

Если настоящих фото нет, можно сгенерировать заглушки (нужен Pillow). Они годятся только для
**замера производительности, а не точности**:

```bash
python3 make_dataset.py --count 40 --size 2000x2600     # тяжелее фото — выше цена декодирования
```
