## A01 — ошибка структуры LiteLLM уничтожает результат локальных моделей

**Код:** `server/src/shelf_api/vlm.py:119–123,192–199`; API-преобразование ошибки:
`server/src/shelf_api/app.py:310–312` (пути относительно `apps/shelf-finder`).

**Предусловие:** профиль litellm, есть хотя бы одна спорная бутылка; шлюз возвращает
HTTP 200 с `{"choices":[null]}`. Тест моделирует уже подтверждённую локальную бутылку
и одну спорную; реальные `LiteLLMClient.choose`, `LiteLLMEngine.refine` и HTTP route
исполняются без подмены их логики.

**Ожидание:** отказ дополнительной проверки, HTTP 200 с локальными matches и
предупреждением, как обещано в инструкции. **Факт:** `choice.get` вызывает
`AttributeError`, которого нет в обработчике fallback; весь запрос HTTP 500, matches
отсутствуют. Вывод: `ATTACK malformed_choice: HTTP 500; pre-existing native match lost`.

**Последствие:** частичная неисправность внешнего провайдера ломает основной локальный
результат. **Направление улучшения:** проверять envelope до доступа к полям и изолировать
ошибки дополнительного этапа, сохраняя диагностируемость причины. Не реализовано.

## A02 — повреждённый reference PNG ломает весь скан

**Код:** `server/src/shelf_api/vlm.py:86–94,192–199`.

**Предусловие:** настроены необязательные reference images; файл кандидата существует,
но содержит `not-a-png`. Файл создаётся только во временном каталоге pytest.

**Ожидание:** пропуск повреждённого эталона или fallback на уже готовые CV matches.
**Факт:** `PIL.UnidentifiedImageError` / `OSError` не перехватывается; HTTP 500 вместо
готового локального результата. Вывод:
`ATTACK corrupt_reference: HTTP 500; pre-existing native match lost`.

**Последствие:** один дефект при переносе дополнительных эталонов способен ломать
распознавание соответствующих фотографий; наличие core model manifest этого не ловит.
**Направление:** отдельная проверка эталонов и граница обработки ошибок необязательного
этапа. Это дефект устойчивости, а не доказанная возможность удалённой записи файлов.

## A03 — вторая отмена освобождает слот до завершения native scan

**Код:** `server/src/shelf_api/app.py:302–308,318–324`.

**Предусловие:** ASGI request task получает две отмены, пока `to_thread(scan)` ещё
работает. Это воспроизводит lifecycle/cancellation race, а не утверждает, что обычное
нажатие «Отмена» в браузере отправляет две `Task.cancel()` серверу.

**Ожидание:** один активный scan до реального выхода первого native thread, в том числе
при повторной отмене. **Факт:** первая отмена ловится, но `await task` уже не shielded;
вторая отменяет оболочку `to_thread`, не её поток. `finally` снимает busy, закрывает
изображение и очищает inference. Второй запрос запускает второй поток раньше выхода
первого. Вывод: `busy=False while first native thread active; concurrent scan threads=2`.

**Последствие:** нарушается обещание сериализации; возможны гонки состояния движка,
рост памяти/GPU-нагрузки и доступ к уже закрытому изображению. Последние последствия
не симулировались настоящими моделями и не считаются отдельно доказанными сбоями.
**Направление:** привязать освобождение ресурсов/слота к фактическому завершению worker,
а не жизненному циклу запроса, устойчиво обрабатывать повторную отмену.

## A04 — malformed multipart → HTTP 500

**Код:** `server/src/shelf_api/app.py:292–293`.

**Предусловие:** POST с `Content-Type: multipart/form-data; boundary=x` и телом
`garbage`. Нет больших загрузок, нагрузки или сторонних запросов.

**Ожидание:** контролируемая 400/415, человекочитаемая ошибка входных данных.
**Факт:** исключение низкоуровневого multipart parser не преобразуется; ответ
`HTTP 500, body='Internal Server Error'`. Слот busy освобождается — постоянной блокировки
этим тестом не найдено.

**Последствие:** ошибочный клиентский ввод регистрируется как внутренняя авария сервера,
ухудшая диагностику и обработку ошибок в UI. **Направление:** явное преобразование
ошибок парсинга в 4xx. Не заявляется компрометация или DoS сервера.

## A05 — auto на переносимом сервере выбирает несуществующую GPU 2

**Код:** `tools/run_local.py:93–95`.

**Предусловие:** новый локальный shelf service, `SHELF_DEVICE=auto`, переменная SHELF_GPU
не задана. На принимающей машине есть только GPU с физическим индексом 0.

**Ожидание:** auto обнаруживает доступную CUDA либо сохраняет явный внешний выбор
`CUDA_VISIBLE_DEVICES`. **Факт теста:** реальный launcher при mock process spawn всегда
передаёт `CUDA_VISIBLE_DEVICES='2'`. Вывод:
`fresh auto launcher: forces CUDA_VISIBLE_DEVICES=2`.

**Граница доказательства:** env дочернего процесса проверен исполнением настоящего
launcher; физический single-GPU-хост не использовался. Недоступность GPU 0 следует из
явной маски видимости, а не из нового аппаратного benchmark.

**Последствие:** на обычном single-GPU-сервере auto уходит на CPU; explicit cuda при
такой маске не инициализируется. Потенциальная потеря скорости значительна, но её величина
здесь не измерялась. **Направление:** переносимый выбор GPU по умолчанию и сохранение
внешней маски; индекс общей рабочей машины задавать её конфигурацией.

## A06 — explicit cuda не проверяется при переиспользовании CPU

**Код:** `tools/run_local.py:84–91`.

**Предусловие:** работающий ready baseline Shelf API сообщает `device=cpu`, пользователь
запускает launcher с `SHELF_DEVICE=cuda`.

**Ожидание:** сообщение о несовпадении конфигурации, аналогично обратному переходу.
**Факт:** проверяется только wanted_device==cpu; launcher пишет `Reusing ready shelf
API`, запускает frontend, CPU-сервис продолжает использоваться. Mock-тест проверяет,
что единственный создаваемый процесс — web. Вывод:
`explicit SHELF_DEVICE=cuda: existing ready CPU service reused without mismatch error`.

**Последствие:** явная настройка производительности не вступает в силу без предупреждения.
**Направление:** симметрично проверять требуемое и фактическое устройство, отдельно
учитывая осмысленное поведение auto.

## A07 — временный 503 кешируется до закрытия вкладки

**Код:** `apps/web/src/lib/shelfAvailability.ts:52–59,71–81`.

**Предусловие:** первая проверка попала на прогрев сервиса и получила 503; затем тот же
backend стал ready. Это штатный переход состояния Shelf API.

**Ожидание:** возможность повторной проверки/восстановления раздела без перезагрузки
всего приложения. **Факт:** повторный `checkShelfAvailability()` возвращает старый
unavailable без fetch; контрольный прямой `probeShelfHealth()` уже видит available.
Vitest: первый тест `frontend-health.test.ts` проходит, проверяя это различие.

**Последствие:** работоспособная витрина остаётся скрытой в текущей вкладке после
временной ошибки/прогрева. Код явно описывает вечное кеширование: это воспроизведённый
недостаток принятого UX-решения, а не скрытый дефект самого Promise.
**Направление:** TTL для отрицательного результата, retry/backoff или явное повторное
подключение; не выполнять бесконтрольный polling.

## A08 — произвольный JSON с HTTP 200 принимается за готовность

**Код:** `apps/web/src/lib/shelfAvailability.ts:37–41`.

**Предусловие:** неправильно направленный proxy или несовместимый health endpoint
возвращает 200 application/json с `{"ready":false,"state":"failed"}` либо вообще
посторонний JSON. Штатный Shelf API при failed возвращает 503; тест не утверждает обратное.

**Ожидание:** подтверждение хотя бы `ready===true` и структуры health.
**Факт:** оба случая классифицируются available; тело вообще не читается.
Vitest: два параметризованных случая `frontend-health.test.ts` проходят.

**Последствие:** UI показывает неработающий раздел, контроль корректности remote
routing слабее заявленной проверки готовности. **Направление:** проверять контракт
health и совместимость. Низкая важность: основной server client проверяет ready отдельно.

## D01 — «Qwen проверил» даже при нуле валидных ответов

**Код:** `server/src/shelf_api/vlm.py:127–152,208–219`.

**Предусловие:** корректный JSON `{"bottles":[]}`, или ни одного принятого результата.
В тесте mock client возвращает `{}`, точный результат валидатора для такого JSON.

**Ожидание:** различать отправленные, отвеченные, отказанные и подтверждённые области.
**Факт:** requested=1, proposed=0, confirmed=0, но warning: `Qwen проверил 1 спорных
бутылок`. Тест подтверждает счётчики и строку. Это неточность диагностики, не ошибочная
зелёная рамка: дополнительный match не появляется.

**Направление:** явно отделять число запросов от числа валидных решений/воздержаний;
не использовать текущую строку как свидетельство завершённой OCR-проверки.

## R01 — медленный поток LiteLLM удерживает слот дольше timeout

**Код:** `server/src/shelf_api/vlm.py:111–116`; сериализация:
`server/src/shelf_api/app.py:254–259,302–308`.

**Предусловие:** provider периодически присылает небольшие куски тела ответа, не
превышая read timeout между ними. Loopback fixture отправляет 10 байт каждые 0,2 с,
клиент настроен допустимым timeout=1 с.

**Факт:** запрос успешно заканчивается через ~1,45 с без TimeoutException. Тест
проверяет превышение полного времени, а не рассчитывает на загрузку внешнего шлюза.
Увеличением длины медленного потока можно увеличивать время удержания единственного
слота; бесконечный поток намеренно не запускался.

**Классификация:** это уже честно описано в portable-litellm инструкции как сетевой,
не общий deadline. Поэтому не объявляется ошибкой документации или SLA. Это значимый
операционный риск для shared single-slot API: клиент может перестать ждать, остальные
сканы получают busy, пока native работа не закончена.

**Направление:** общий бюджет дополнительной проверки и изоляция её исполнения,
ограничение объёма ответа; при повторяющейся недоступности — circuit breaker.
Отсутствие breaker само по себе отдельным воспроизведённым багом не заявляется.

## Что этот аудит не доказывает

- Не измерялась точность распознавания на независимой полной разметке. Из документа
  `portable-litellm-2026-09-27.md` нельзя делать вывод о приросте качества: там прямо
  указаны один снимок, четыре совпадения в обоих режимах и отсутствие новых
  подтверждений Qwen. Это корректно обозначенное ограничение исходного замера.
- CPU-only wheels, полный accuracy profile на CPU, физический iPhone и внешний
  production nginx заново не проверялись; прежняя инструкция также не утверждает это.
- Внутренний TorchScript graph API требует совместимости версий; новый доказанный
  сбой runtime loader в этом аудите не найден. Не заменяем проверку реальных моделей
  успешным импортом Python.
- Отдельный тест HTTP на неизвестные формы JSON не доказывает, что реальный LiteLLM
  сейчас возвращает такой payload. Он доказывает отсутствие обещанной изоляции отказов.
- Уменьшение latency или рост accuracy не получены: рекомендации выше не реализованы.
