# Распознавание вин на телефоне: результаты изучения подходов

Дата: 24 сентября 2026. Цель — автоматическая подсветка бутылок из полного каталога в браузере телефона, без ручных исправлений результатов.

## Главный вывод

Задача относится к поиску конкретного товара по эталону, а не к классификации общих объектов. Увеличение обычной модели ImageNet и снижение порога сходства не решают различение почти одинаковых этикеток. Рабочая гипотеза: компактный поиск кандидатов → выделение этикетки/товара → обученное сопоставление локальных деталей → отказ при неоднозначности.

## Что стоит использовать

1. **Специализированный компактный поиск товаров.** PP-ShiTuV2 объединяет детектор, обученный для retrieval экстрактор признаков и поиск по галерее. У версии из PaddleClas экстрактор занимает около 19 МБ; есть Android-демонстрация и экспорт ONNX. Это более обоснованный следующий кандидат, чем ImageNet MobileNet без обучения для retrieval. Android-приложение не доказывает скорость в мобильном браузере. [Документация разработчиков](https://github.com/PaddlePaddle/PaddleClas/blob/release/2.6/docs/en/PPShiTu/PPShiTuV2_introduction.md).

2. **Двухступенчатый поиск и learned matching.** PRISM (2025) использует SigLIP для top-35, сегментацию YOLO-E и ALIKED + LightGlue с RANSAC для окончательного выбора. Это прямо соответствует нашей проблеме с похожими винами. В статье top-1 вырос с 38,58% до 42,79%, время — 725 мс на запрос на A100: результат нельзя переносить на телефон или считать почти безошибочным. [Статья](https://arxiv.org/html/2509.14985v1).

3. **Дешёвая проверка деталей.** XFeat создан для быстрых локальных признаков, использует 64-мерные дескрипторы; у разработчиков есть облегчённый LighterGlue. Скорость из их CPU-демонстраций относится к ноутбуку, не к Safari. Начальный эксперимент: XFeat + взаимные ближайшие соседи + геометрия; более сложный matcher включать только если он улучшает проверку. [Код авторов](https://github.com/verlab/accelerated_features).

4. **Перенос уже существующей сильной проверки.** В основном WineScan уже есть `src/winescan/search/deep_match.py` с ALIKED + LightGlue. В отдельном браузерном модуле её не было. У LightGlue-ONNX есть браузерная WebGPU-демонстрация, поэтому начинать с проверки совместимости готового экспорта разумнее самостоятельной реализации нейросетевого matcher. [LightGlue](https://github.com/cvg/LightGlue), [ONNX и WebGPU demo](https://github.com/fabio-sim/LightGlue-ONNX).

5. **Сохранение мелких деталей.** SAHI обрабатывает перекрывающиеся фрагменты исходного изображения и объединяет detections. У нас уже есть упрощённый dense-режим; нужно измерять пропуски и дубликаты отдельно от качества названий. Для сравнения этикетки брать исходный crop, а не уменьшенное изображение всего стеллажа. [Официальное описание](https://obss.github.io/sahi/guides/sliced-inference/).

6. **Мобильное исполнение.** Признаки эталонов вычислять заранее, загружать подробные признаки только для кандидатов, ограничивать кэш. Для камеры выбирать резкий кадр и отслеживать найденное между распознаваниями. WebGPU использовать при доступности, WASM — с отдельным измерением времени и памяти; многопоточность требует cross-origin isolation. Это предложенная архитектура, ещё не подтверждённая измерениями на физических телефонах. [ONNX Runtime](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html).

## Что показали наши эксперименты

- Исходные MobileNet + YOLO в настоящем Chromium: 0 принятых совпадений на трёх примерах, примерно 7 секунд на фото на данном сервере.
- SigLIP2 Base FP16 возвращает выбранный при визуальной сверке ID первым в 19 из 32 положительных областей. Это диагностическая проверка ID на неполной разметке, не точность по всем бутылкам и не проверка точного SKU.
- На том же наборе DINOv2 Small: 1/32; MobileNet, дообученная только на эталонах: 3/32. Их нельзя объявлять улучшением.
- В одном численном тесте готовый SigLIP2 int8 имел cosine 0,618 к исходному FP16-вектору; q4 — 0,961. Нужно проверять совместимость признаков и пересчитывать галерею под фактическую модель, а не считать любой ONNX-экспорт эквивалентным.
- OCR читает лишь часть мелких этикеток. Он полезен как дополнительное свидетельство, но сейчас не обеспечивает самостоятельную идентификацию.

## Проверка идеи learned matching на наших фото

После изучения источников выполнен локальный прогон существующего ALIKED + LightGlue с 512 точками для top-10 кандидатов сильного SigLIP2 на трёх примерах. Победитель по числу геометрически согласованных точек совпал с ранее выбранным ID у всех 15 положительных областей: 4/4 Шато Тамань, 8/8 AGORA, 3/3 Nature Vert / Высокий берег. Выбор кандидатов выполнялся моделями без ручных подстановок.

Это **не 100% точность**: проверены ранее положительные области, точные SKU/винтажи не установлены; на остальных областях модель тоже возвращает кандидатов, среди них есть неподтверждённые. Автоматический порог отказа ещё не валидирован. Вычисления выполнены в Python на GPU, не на телефоне. Выход: `artifacts/browser-upgrade/learned-matching-probe.json`.

## Следующие проверяемые шаги

Сначала сравнить PP-ShiTuV2 с SigLIP2 на одинаковых crops и полном каталоге. Затем отдельно измерить пользу ALIKED/LightGlue или XFeat для top-k. Только после этого переносить победившую схему в браузер. Сохранять чистый тестовый набор: не обучаться на витринах, по которым измеряется результат, и не переносить ручные исправления в предсказания. Измерять принятые ошибочные названия, пропуски, неоднозначные варианты, задержку, загрузку и память отдельно. Проверка Chromium на сервере не заменяет физические Android и iPhone.
