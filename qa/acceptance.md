**Важные находки живой проверки (не гипотетические — пойманы конкретными прогонами против
настоящего `apps/api`, не только против своего мока):**
- **Пустой/null slug — валидный ответ, не ошибка транспорта.** Контракт прямо требует: "flat
  ВСЕГДА отдаёт лучший доступный slug" — при нуле кандидатов лучший доступный пуст
  (`{"slug": ""}` в flat, `slug: null` + `not_in_catalog: true` в rich). Первая версия
  `FlatApiPredictor`/`RichApiPredictor` ошибочно считала это ошибкой транспорта и тихо
  исключала такие ответы из знаменателя match-rate/F1 — систематически завышая метрику.
  Найдено прогоном против живого `apps/api` (сценарий `MOCKPHOTO:weak:...`), исправлено,
  закрыто регрессионными тестами (`test_flat_api_predictor_empty_slug_is_a_valid_miss_not_an_
  error`, rich-аналог).
- **`similar`/`analogs` используют поле `wine_id`, не `slug`** (`apps/api/app/schemas.py::
  AnalogsWineItem`) — собственный `qa/mock_scan_server.py` был написан с полем `slug` по
  предположению, не по чтению настоящей схемы; из-за этого `RichApiPredictor` против ЖИВОГО
  API тихо не собирал бы топ-5 из `similar` вовсе (деградация к топ-1 маскировала бы
  фактическую причину). Исправлено на обеих сторонах (`scan_eval.py` читает `wine_id`,
  `mock_scan_server.py` теперь зеркалит настоящую форму).
- **`/v1/healthz.index_version` — версия RAG-индекса, не CV-индекса.** `GET /v1/metrics/scan`
  корректно резолвит именно версию image-индекса (даже до первого eval-прогона) — раннер
  переключён на него для `--write-eval-report`.
- **`rich`-режим сегодня НЕ отдаёт ранжированный топ-5 даже для near-dup сценария** (`similar`

  но ограничивает то, что `rich`-режим раннера может измерить как F1@5 против живого API
  сегодня — задокументировано как предложение к контракту (явное поле
  `confidence.candidates: [{slug, score}]`), не молчаливое ограничение.
