# EVAL.md — обвязка приёмки

## 1. Как прогнать наш eval

Инструмент: `../qa/scan_eval.py` (не переписывать/не дублировать — параметризуемый
CLI, уже умеет всё нужное). Режимы (`--mode`):

- **`flat`** — `POST /v1/scan/photo?flat=1` — РОВНО то, что делает скрипт
  кейсодержателя (`case.md` п.6): один slug на фото, ничего больше. **Основной режим
  для match-rate/SLA** — критерий "90–100% совпадений" (50/100 баллов кейса) и SLA
  ≤3с кейсодержатель меряет именно так.
- **`rich`** — полный ответ (`confidence`, `matches[]`) — нужен для F1 топ-1/топ-5:
  топ-5 берётся из `matches: [{slug, score}]` (`contracts/image-scan.md` v0.4.3), а
  НЕ из `similar` (фолбэк только при API < v0.4.3, раннер честно помечает
  деградацию, не молчит).
- **`mock`** — без сети (`MockPredictor` в процессе) — для unit-прогонов/CI.

Пример (актуальный порт — см. §4, ГОТОВЯЩИЙ стенд, НЕ трогать чужой):

```bash
cd svoy-somelye/apps/api
IMAGE_PROVIDER=real VERIFIER_PROVIDER=real RAG_PROVIDER=mock \
  ./.venv/bin/uvicorn app.main:app --port <свободный_порт>
# в другом терминале, синхронно (ORCHESTRATION.md — poll готовности /healthz в том
# же вызове, не отвязанный фон):
python qa/scan_eval.py --photos-dir <публичный набор>/dev --mode rich \
  --api-url http://localhost:<свободный_порт> --split dev
```

Когда `apps/api` поднимать не нужно (чистое CV, без API-обвязки) — адаптер вида
`qa/run_cv_index_baseline.py` (см. `../qa/acceptance.md` §9(в)).

## 2. Какие цифры сдавать

| Метрика | Откуда | Зачем |
|---|---|---|
| **raw top-1 / top-5** | `matches[0]`/`matches[:5]` без гейта confident/not_in_catalog | Потолок ranking'а — то, что эта fine-tune задача обязана двигать |
| **match-rate top-1 / top-5** | С гейтом (основной путь `/v1/scan/photo`, `flat`-режим для top-1) | То, что реально увидит кейсодержатель — итоговый критерий ТЗ |
| **F1 top-1 / top-5 (macro)** | `scan_eval.py::_macro_f1` — класс = только slug'и, реально встретившиеся как `true_slug` в eval-сете | ТЗ формулу F1 не даёт, только цель "виден отрыв лидера" — это НАША интерпретация (докстринг `_macro_f1`); при получении реального скрипта оценки — сверить и задокументировать расхождение, если есть |
| **Срезы near-dup / НЕ near-dup** | по `families.json` | `case.md`: near-dup — "главный источник ошибок", обязательный срез |
| **Срезы clean / fallback-детектор** | по `cv.audit.label_detector_outcomes` | Уже показал 14 п.п. разницы в raw top-1 (BASELINES.md) — устойчивый сигнал качества эталона/фото |
| **p50 / p95, отдельно MPS и CPU** | `cv bench --devices mps,cpu` или полный путь через `scan_eval.py` | SLA ≤3с (case.md); "GPU желателен, нет GPU — на CPU" |

## 3. Eval-gate — принцип "новая модель не публикуется, если метрики просели"

Тот же принцип, что версии индекса в этом проекте (`index_version` в манифесте,
`/v1/healthz`, `/v1/metrics/scan`) — распространить на модель/чекпойнт:

1. Прогнать НОВЫЙ чекпойнт/адаптер на **ТОМ ЖЕ eval-сете** (тот же `--split`,
   `--seed`, `--holdout-frac` — DATA.md §7) — apples-to-apples, тот же принцип, что
   уже применялся при сравнении гейтов (`../reports/b5-gate-v048.md`: "тот же индекс,
   тот же набор из 150 фото... что и в b4-gate-v047.md").
2. Сравнить с зафиксированным baseline (`BASELINES.md`).
3. Публиковать/переключать `CV_MODEL`/индекс только при неухудшении match-rate/F1 (с
   учётом SLA) — либо явное обоснованное компромиссное решение (например: небольшая
   просадка raw top-1, но существенный выигрыш в задержке).
4. Версия новой модели — В МАНИФЕСТ индекса (`cv build-index --version <имя-с-датой-
   и-моделью>`), не перезаписывать существующую боевую версию (`case-20260917` и
   предыдущие — оставить как есть, для отката).

Подробный порядок команд — `scripts/eval_new_encoder.md`.

## 4. Подводные камни (из отчётов, не в мануале SigLIP2/FastAPI)

- **`/v1/healthz.index_version` — это версия RAG (текстового) индекса, НЕ CV!**
  Deprecated-алиас `rag_index_version`, оставлен для обратной совместимости
  (`contracts/image-scan.md` v0.4.7 п.6). Для CV — `cv_index_version` в том же
  `/healthz`, ИЛИ `GET /v1/metrics/scan.index_version` (последний работает даже ДО
  первого eval-прогона). Путаница уже ловила ревьюера вживую: `../reports/
  b3-eval-route.md` — "ложная тревога... поле RAG-ретривера, решающая улика — лог
  qdrant «49650 points», невозможный на моке".
- **`RAG_PROVIDER=mock` не даёт кириллических названий верификатору** — систематически
  ЗАНИЖАЕТ вклад OCR-переустановки near-dup в любой приёмке на моке. Источник:
  `../reports/b5-gate-v048.md` §4 ("верификатор не спас НИ ОДНОГО из 23 совпадений...
  прямое следствие того, что RAG_PROVIDER=mock не даёт кириллических имён"). Для
  честной оценки вклада fine-tune на near-dup — нужен `RAG_PROVIDER=real`.
- **Холодный первый запрос — не только модель, но и Qdrant-стор.** Прогрев обязан
  включать реальный `image_index.search()` (не только `.embed()`) — иначе первый
  боевой поиск на коллекции >20k точек стоит ~2с САМ ПО СЕБЕ, независимо от
  OCR-верификатора (диагностическая находка `../reports/b4-gate-v047.md` §3: "warm
  embed() — 5 мс... ПЕРВЫЙ store.search() напрямую — 2037 мс"). При замере latency
  новой модели — прогреть так же, иначе первое число будет артефактом холодного
  старта, не свойством модели.
- **Синтетика — верхняя граница, не прогноз полевого F1.** Явно зафиксировано
  создателем самих чисел: `../reports/f3-synthetic-baseline.md` §6: "Числа — верхняя
  граница self-match-качества, НЕ прогноз реального F1 на приезжающем публичном
  датасете". См. RECIPE.md §4 про конкретное доказательство (полочный стресс-тест).
- **Офлайн-флаги обязательны** для воспроизводимости без сетевых обращений:
  `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1` — иначе `AutoProcessor.from_pretrained`
  ходит в сеть за метаданными (etag) даже когда чекпойнт уже полностью в кэше
  (`../qa/acceptance.md` строка 282).
- **Два разных порта, две разные цели**: `:8080` — фиксированный эндпоинт скрипта
  кейсодержателя (`POST /v1/eval/predict`, `../README.md` "Прогон скрипта
  кейсодержателя"); любой другой свободный порт — для `scan_eval.py`-прогонов этого
  пакета. **Порт :8000 на момент сборки этого пакета — живой стенд, не трогать**
  (agents/M1-ml-handoff.md).

## 5. Как собрать индекс новой моделью

```bash
cd packages/cv && source .venv/bin/activate
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
export CV_MODEL=<новый чекпойнт или свой fine-tuned>

python3 -m cv.cli build-index \
  --refs-json <CASE_DATA_DIR>/slug_refs.json \
  --uploads-dir <CASE_DATA_DIR>/prod-svoe-vino-strapi/prod-svoe-vino/strapi/uploads \
  --version <новая-версия-с-датой-и-именем-модели> --views 24 \
  --out data/build_summary_<версия>.json
```

`--version` ОБЯЗАН отражаться в `index_version` (манифест → `/v1/healthz.
cv_index_version` → `/v1/metrics/scan`) — контракт ТЗ "метрика уверенности в API"
(`case.md` п.3) требует, чтобы это была видимая, не заглушечная строка. Полный
пошаговый runbook (сравнение до/после, откат) — `scripts/eval_new_encoder.md`.
